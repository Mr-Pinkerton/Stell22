## 3. Target model — `ProductionOperationMutation`

Append-only immutable history of consequential `ProductionOperation` mutations.

Current runtime still mutates the live `ProductionOperation` / lines in place. The **target** is: live row may show the net current state, **and** an immutable mutation record holds reconstructable before/after snapshots.

`ChangeLog` remains **secondary** audit/display. It is **not** the reconstruction source (`08.02` §9.1).

### 3.1 Conceptual fields (not Prisma)

| Field | Role |
| --- | --- |
| `id` | Immutable mutation identity |
| `operationId` | Posted `ProductionOperation.id` (original fact retained) |
| `mutationType` | `CORRECTION` now; `CANCELLATION` **reserved**, not in v1 |
| `adminUserId` | Authenticated admin `User.id` from `requireAdmin()` — real user, not hardcoded |
| `reason` | Mandatory free-text business reason |
| `recordedAt` | Server recording time of the mutation |
| `requestId` / idempotency identity | Distinct from terminal `ProductionOperation.clientRequestId`. Retry of the same admin apply must not double-apply stock/payroll |
| `revisionBefore` | `ProductionOperation.revision` observed after lock/reread |
| `revisionAfter` | `revisionBefore + 1` (conceptual) |
| `beforeSnapshot` | Immutable reconstructable business fact **before** this correction |
| `afterSnapshot` | Immutable reconstructable business fact **after** this correction |
| `effectSummary` | Physical / payroll delta summary (stock, lot, payroll, affected batch/lot) |

Exact types, nullability, JSON shape, and uniqueness constraints are **implementation later**.

### 3.2 Conceptual field on `ProductionOperation`

| Field | Role |
| --- | --- |
| `revision` | Monotonic compare-and-set token. Apply fails closed if `revision != expectedRevision`. |

Existing rows have **no** `revision` today. Introducing it is a **future schema** change, not this cycle.

Posted `ProductionOperation` is **not physically destroyed** by a v1 correction.

## 4. Snapshot contract

`beforeSnapshot` / `afterSnapshot` must reconstruct the **business fact** as it existed before/after the correction — not only header fields.

When relevant for the operation type, the snapshot **must** include:

- operation header (`id`, type, employeeId, workDate, createdAt, isPaid/paidAt if present)
- `batchId`, `railLotId`, `railsTaken`
- `hours`
- `productId` / `productQty`
- rate snapshots used for payroll (`rateSnapshotVersion` and the stored piece/hourly snapshot values)
- **all** `OperationDetailLine` values (ids, detail identity, quantity, sort, monetary/rate snapshot fields present on the line)
- **all** `OperationNomenclatureLine` values when present
- submit-time provenance fields that affect business meaning (allocation/source identity as stored on the posted op/lines at that revision)
- exact `Decimal` values **without JS float corruption** (serialize decimals as strings or equivalent exact text)

Snapshot is **immutable history**. Later BOM/stock/nomenclature edits must not rewrite stored snapshots.

`ChangeLog` JSON diffs (`field` / `oldValue` / `newValue`) are **not sufficient** as the only reconstruction source.

---

## 5. Correction transaction invariant

Future **apply** flow, all in **one** DB transaction:

1. `requireAdmin()` → real `User` (`id`, `name`)
2. Validate mandatory `reason`
3. Lock `ProductionOperation`
4. Reread current operation + lines + relevant stock/lot/batch
5. Paid / frozen / inventory / downstream guards
6. Compare `revision == expectedRevision` (fail stale if not)
7. Recompute the correction plan **inside** the transaction (do **not** trust preview)
8. Capture immutable **BEFORE** snapshot
9. Apply stock / payroll-affecting current-state mutation
10. Capture **AFTER** snapshot
11. Insert `ProductionOperationMutation`
12. Write `ChangeLog` with `userId` and mutation identity
13. Increment `ProductionOperation.revision`
14. **COMMIT**

If any step fails: **ROLLBACK everything**.

Consequential stock/payroll effects + immutable history + audit are atomic. Mutation must not commit without history.

---

## 6. Preview invariant

Preview is **advisory, not authorization**.

Server-side preview (read-only; **no** “begin TX then rollback”) returns:

- current `revision`
- before (current fact)
- proposed after
- stock delta
- payroll delta
- affected batch / lot
- blockers
- warnings

**Apply MUST NOT trust the preview.**

At apply: lock → reread → compare revision → recompute plan → fail stale if revision changed.

## 7. Correction Center v1 — supported / blocked

Existing reverse/reapply **physical guards** for supported qty/rails paths are preserved. v1 does not invent new stock math.

**Invariant:** once history-preserving correction is enabled for an operation type, **destructive delete of that posted operation type MUST be blocked**. This is containment, **not** cancellation. Cancellation remains **DEFERRED / NOT IMPLEMENTED**.

### SUPPORTED

| ID | What | Constraints |
| --- | --- | --- |
| **A. HOURS** | Change `hours` | No stock effect. Payroll from **existing** rate snapshot × new hours. Paid blocked. **Implementation of Correction Center v1 MUST also block destructive delete of posted HOURS** (minimal containment; no compensating reversal/cancel workflow). |
| **B. TORCOVKA `railsTaken`** | **Decrease only** | Existing physical guards: restore `RailLot` remaining by delta; paid/frozen/length (`producedM ≤ newTakenM`)/inventory boundary preserved. Mandatory reason (already required in current runtime). Generic TORCOVKA delete already blocked; existing INC-001 containment remains. |
| **C. TORCOVKA detail-line quantity** | Increase/decrease | Paid reject. Cannot exceed already taken rail length. Decrease fails if blanks already consumed downstream. Inventory boundary preserved. Existing TORCOVKA delete containment remains. **Apply MUST reject a frozen batch** — explicit hardening to match `railsTaken` finality. Current runtime `updateProductionLineQuantity` does **not** check frozen batch; v1 must not preserve that gap. |

### NOT IN V1

- PRISADKA quantity correction
- UPAKOVKA quantity correction
- employee replacement
- workDate replacement
- batch replacement
- railLot replacement
- detail / product identity replacement
- paid operation correction
- arbitrary backdating
- cancellation
- PRISADKA / UPAKOVKA destructive-delete changes (those types are **not** in v1; existing hard delete remains current-runtime debt / PSR-P5)
- `InventoryMovement`
- `production_cost_flow` activation

**Reason:** current PRISADKA qty edit **repicks from current stock**; current UPAKOVKA qty edit **reapplies current BOM**. Those are **not** accepted correction semantics for original physical provenance. Identity replacement is a new domain model, not a qty delta.

Do **not** read “hard-delete behavior changes” as “HOURS may still be physically deleted after v1.” Corrected (or correctable-under-v1) HOURS **must not** be physically deleted.
