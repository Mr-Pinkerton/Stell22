## 1. Two states that must not be collapsed

| State | Meaning |
| --- | --- |
| A. `SHADOW GATE ACTIVATED` | `inventory_movement_shadow_write` is `{version:1, active:true}` |
| B. `PSR-P2 DUAL-WRITE STARTED` | Later real physical production activity wrote at least one valid SHADOW `InventoryMovement` while the gate was ACTIVE, shown by read-only evidence |

This package can only prepare A. Running the control workflow is not B. The control policy and the post-activation verifier always report `PSR_P2_DUAL_WRITE_STARTED=NO`. A SHADOW row count above zero is reported separately as `SHADOW_ROW_EVIDENCE=PRESENT` and is still not a dual-write-start declaration. This package does not create a synthetic production mutation to manufacture that evidence.

## 2. Activation workflow

File: `.github/workflows/shadow-activation-control.yml`

- Manual `workflow_dispatch` only. No push, pull request, or schedule trigger.
- Actions are exactly `activate` and `deactivate`.
- Job `control` uses GitHub `environment: production`. The pin job does not.
- The supplied `expected_application_sha` must equal the pinned production application SHA `2d2cbcbdc01ee83cb9103ad8fdaa43ebf8488dcf`.
- The workflow checkout SHA is printed and is not that pin. GitHub `main` is not the production application SHA.
- Before any mutation, a read-only snapshot is taken on the server from the live `git rev-parse HEAD`.
- The runner evaluates that snapshot with `scripts/shadow-activation-policy.ts`. Refusal exits before apply.
- Apply pipes `scripts/shadow-activation-apply-deployed-cli.sh` to the server. That script re-checks the live SHA, the clean setter tree, and the image/host hash of `scripts/set-inventory-movement-shadow-write.ts`, re-reads the SHADOW setting in `BEGIN TRANSACTION READ ONLY`, then runs the deployed CLI:

`./node_modules/.bin/tsx scripts/set-inventory-movement-shadow-write.ts --state=on|off --confirm=INVENTORY_MOVEMENT_SHADOW_WRITE_CONTROL`

- The production image does not contain `src/`. The one-off container mounts the pinned checkout `src/` read-only so the already deployed CLI can load `setInventoryMovementShadowWriteGate`. The entrypoint is `tsx`, so the image entrypoint does not run migrations.
- The deployed setter remains the only Setting mutation. It upserts `{version:1, active}` under the existing EXCLUSIVE advisory transaction lock `(8322,1)`. Writers keep SHARED `(8322,1)`.
- There is no raw SQL Setting mutation, no reset, no backfill, and no `production_cost_flow` write.

The deployed setter does not itself branch on the previous Setting value. The control plane refuses the wrong prior state in the read-only precheck and again in a read-only read immediately before the CLI. Those checks are not inside the setter transaction. Overlapping control runs are serialized by the workflow concurrency group `inventory-movement-shadow-gate-control`. The setter transaction still holds EXCLUSIVE `(8322,1)` for the upsert.

### ACTIVATE

Transition: `ABSENT | INACTIVE → {version:1, active:true}`.

Already `ACTIVE` or `MALFORMED` fails closed. `CLI_STATE=on`.

### DEACTIVATE

Transition: `ACTIVE → {version:1, active:false}`.

`ABSENT`, `INACTIVE`, and `MALFORMED` fail closed. `CLI_STATE=off`.

Deactivation does not delete SHADOW rows, invoke reset, alter AUTHORITATIVE rows, alter epoch data, or alter `production_cost_flow`. Post-check requires SHADOW count, AUTHORITATIVE count, non-null epoch counts, cost-flow state, and the application SHA to be unchanged, and the Setting to be `INACTIVE`.

## 3. Pre-activation checks

ACTIVATE refuses unless all of the following hold:

- live production application SHA equals the supplied SHA and the pin `2d2cbcbdc01ee83cb9103ad8fdaa43ebf8488dcf`;
- setter sources are clean and the deployed CLI file hash matches the checkout;
- `inventory_movement_shadow_write` is `ABSENT` or `INACTIVE`;
- `production_cost_flow` is `ABSENT` or `INACTIVE`;
- `AUTHORITATIVE` InventoryMovement count = 0;
- AUTHORITATIVE rows with non-null `epochId` = 0;
- any-row non-null `epochId` count = 0;
- SHADOW count + AUTHORITATIVE count = total InventoryMovement count;
- these migrations are applied and not rolled back:
  - `20260917150000_psr_p1_inventory_movement_shadow`
  - `20260917180000_psr_p2_inventory_movement_recorded_at_timestamptz`
  - `20260917200000_psr_p2_r04_supply_stock_accounting_cycle`
  - `20260918120000_psr_p2_r05_production_operation_correction`
  - `20260918130000_psr_p2_r06_inventory_line_identity`
  - `20260920120000_psr_p2_raw_identity_prerequisite`
  - `20260920180000_psr_p2_production_quantity_edit_identity`
- `InventoryMovement.recordedAt` is `timestamptz`;
- `InventoryMovement_authority_epoch` exists;
- Supply.`stockAccountingGeneration` exists;
- `ProductionOperationCorrection` exists;
- `InventoryLine_inventoryId_refType_refId_key` exists;
- `BatchCreationCommand`, `BatchRemainderWriteOff`, and `SimplePurchaseCreationCommand` exist;
- `ProductionOperationQuantityEdit` exists, has zero foreign keys, and `requestId` is unique.

`InventoryMovement` total count = 0 is **not** an activation invariant. A later OFF→ON with retained SHADOW rows (`epochId` null) is allowed. Any non-null `epochId` fails closed for this pre-epoch start.

## 4. Post-activation verifier

File: `.github/workflows/shadow-post-activation-verify.yml`

Read-only. Manual dispatch. `environment: production` on the verify job only. It uses the same snapshot script and `verify-active`. It does not call the apply script or the gate CLI.

It passes only when:

- production application SHA matches the pin;
- SHADOW Setting = `ACTIVE`;
- SHADOW count is a separate integer `>= 0` (zero is valid);
- AUTHORITATIVE count is separate and = 0;
- non-null `epochId` count is separate and = 0;
- `production_cost_flow` is `ABSENT` or `INACTIVE`;
- writer schema prerequisites in the snapshot are still present.

Success token: `SHADOW_POST_ACTIVATION_VERIFY_OK`.

It also prints `SHADOW_GATE_ACTIVATED=YES` and `PSR_P2_DUAL_WRITE_STARTED=NO`. This workflow was not run in production by this package.

## 5. What this package does not do

- production SHADOW activation or deactivation;
- production Setting mutation;
- schema migration;
- SHADOW reset or row deletion;
- `production_cost_flow` activation or mutation;
- epoch creation, OPENING_BALANCE, backfill, or an authoritative ledger;
- PSR-P3;
- writer semantic changes;
- Correction Center, INC-001 data correction, AUDIT 2, ARCH-P1-001 closure.

Deploy does not call the gate CLI. CI runs `security:shadow-activation-control`, which fails if deploy or the application entrypoint references activation.
