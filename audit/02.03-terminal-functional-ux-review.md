## 0.1 EXECUTIVE VERDICT

Владелец описывает два симптома. Оба воспроизводятся, но это **разные слои**.

1. «Ввод деталей выкидывает на терминал, непонятно, сохранилось ли» — это **не logout и не потеря сессии при количестве**. Финальный «Подтвердить» **намеренно** вызывает `onDone` → `setScreen("home")`. Операция при этом пишется. Тост успеха есть в коде; на живом проходе он надёжно пойман только у HOURS. Журнал обновляет агрегаты, строка дня свёрнута. Работник легко путает это с «меня выкинуло».
2. «Можно ввести детали без пакета» — на TORCOVKA **нельзя** открыть заготовки без выбранного лота. Можно ввести количества **после выбора плитки пакета, отменив диалог «сколько реек»** (`railsTaken = 0`). Главный Confirm скрыт/disabled. Сервер пакет и `railsTaken` требует.

Общий паттерн всех четырёх операций: после успешной записи экран **сразу** «Терминал производства». Это ожидаемое текущее поведение кода, и это же главный UX-разрыв владельца.

## 1. OWNER ISSUE 1 — DETAIL ENTRY → UNEXPECTED TERMINAL NAVIGATION

**Reproduced: YES** (финальный submit). Quantity-only: **NO** (остаёмся на операции).

### 1.1 Точный экран

Воспроизведено с свежего PIN-входа на **TORCOVKA** (заготовки). Тот же механизм `handleOperationDone` стоит на **PRISADKA, UPAKOVKA, HOURS** — live подтверждено на всех четырёх.

Владелец говорит «детали». В текущем UI:

- TORCOVKA секция 3 = «ЗАГОТОВКИ» (длины, не именованные детали каталога)
- PRISADKA = именованные детали без партии/пакета

Оба потока после финального Confirm ведут на home. Не гадать, какой из них имел в виду владелец: механизм один.

### 1.2 Последовательность (свежий PIN, TORCOVKA, NORMAL)

1. PIN → home «Терминал производства», сессия есть, тост «Здравствуйте, …»
2. Плитка «Торцовка»
3. Партия «Волочек 2419» (`batch-1`)
4. Пакет `PKG-0004` (`lot-5`)
5. Диалог реек → 1 → «Подтвердить»
6. Заготовка 0,6 м / 1 сорт → 4 шт → «Подтвердить» (диалог количества)
7. Нижняя кнопка **«Подтвердить»** (финальный submit, не quantity)
8. Результирующий экран: **home «Терминал производства»**, сотрудник всё ещё в шапке, кнопка «Выйти»

Это **B. final operation submit**, не quantity/edit.

Quantity-only (шаг 6 без шага 7): экран остаётся «Торцовка», тоста нет, БД не пишется, черновик есть.

### 1.6 Причина (клиент → сервер)

```text

         → await getTerminalData()

```

Тот же `onDone` у PRISADKA / UPAKOVKA / HOURS.

URL не меняется. «Терминал» в языке владельца = home title «Терминал производства».

## 2. OWNER ISSUE 2 — DETAIL ENTRY WITHOUT PACKAGE

**Reproduced: YES (частично).** Workflow: **TORCOVKA**.

PRISADKA не имеет пакета вообще — это не этот баг, это модель (см. §4).

### 2.1 Матрица A–E (TORCOVKA)

| Вопрос | Ответ |
| --- | --- |
| A. Открыть ввод количества **без** выбранного лота | **NO**. Секция «3. ЗАГОТОВКИ» только при `lot`. T03: партия есть, пакетов список есть, заготовок нет |
| B. Выставить количества без лота | **NO**. С лотом, но **без** `railsTaken` (Отмена в диалоге реек): **YES** — диалог длины открывается, `max` не ставится |
| C. Главный Confirm enabled | Без `railsTaken`: полоса Confirm **не рендерится**. С рейками и 0 заготовок: видна, **disabled** |
| D. Запрос доходит до сервера | С UI — нет (ранний `return` без `lotId` / `railsTaken` / picks) |
| E. Сервер создаёт TORCOVKA без пакета | **NO.** `railLotId` обязателен; нет лота → «Пакет реек не найден»; `railsTaken <= 0` → «Укажите количество взятых реек» |

### 2.2 Фактическая связь

```text
batchId  →  railLotId (пакет / поштучно)  →  railsTaken  →  picks[] (длина+сорт+кол-во)
```

Пакет **фактом операции нужен**: списание `RailLot.remainingQuantity`, длина рейки, отход, себестоимость партии. Заготовки в терминале — длины, не `Detail.id`; деталь появляется на присадке.

### 2.3 Live

1. Партия выбрана.
2. Тап `PKG-0004` → диалог «Сколько реек вы взяли в работу?».
3. **Отмена** (реек = 0).
4. Секция заготовок **уже на экране**. Тап 0,6 м → клавиатура без лимита длины. 4 шт принимаются.
5. Confirm bar нет. Черновик: `lotId=lot-5`, `railsTaken=0`, `picks=[{0.6, SORT1, 4}]`.

Когда `railsTaken > 0`, лимит включается: ввод 9 при max≈4 → Confirm диалога disabled, текст «Длина заготовок превышает длину взятых реек».

### 2.4 Классификация

**UI PREREQUISITE BUG** (не SERVER INVARIANT BUG).

Сервер пакет требует. UI требует лот для показа заготовок, но **не** требует факт «взял рейки», прежде чем вводить длины.

Самый ранний уместный UI-guard (не делать в этом этапе): не показывать секцию 3 и не открывать `QuantityDialog` длины, пока `railsTaken > 0`. Альтернатива: после Отмены в диалоге реек сбрасывать `lotId`.

Если владелец имел в виду PRISADKA («детали без пакета») — это **EXPECTED DESIGN**, не баг.

## 4. PRISADKA

### 4.1 Фактические предпосылки (не копия TORCOVKA)

Присадка **не привязана** к партии/пакету. Заготовки уже обезличены в `BlankStock` по спецификации (материал × длина × тип × сорт). Работник выбирает, **какой деталью** станет заготовка.

Нужно до submit: хотя бы один pick `{detailId, kind, quantity>0}`. Партия/лот **не** в payload (`submitPrisadka`).

Сервер: сессия, непустые picks, атомарное списание blank/partial (`Недостаточно заготовок/остатка деталей для присадки`).

### 4.2 Live

- Экран «Требуют присадки»: плитки только с `pending > 0`. Confirm disabled пока 0 шт.
- Нет селектора пакета — **EXPECTED DESIGN**.
- Quantity: «Полка 600 — торцевая», hint «Ожидает присадки: 94 шт», max=94.
- Quantity Confirm → остаёмся на Присадке, 1 шт на плитке, «Сбросить», главный Confirm enabled.
- Финальный Confirm → **home**. Журнал 313→314 присадк. Op `PRISADKA` `f59735ab-…`, 1 line. Draft cleared.
- Success toast в коде `Присадка внесена: 1 шт`; в snapshot home не пойман (как TORCOVKA).

| Журнал | +N «дет» (не «заг.»), день свёрнут | +N «присадк.» | +N «шт» | +N «ч» |

## 10. FINDINGS

### F-01 — После успешного submit всегда home, запись неочевидна

- **Class:** UX BUG  
- **Severity:** P2  
- **Где:** все операции, `handleOperationDone`  
- **Суть:** операция пишется, работника сразу возвращает на «Терминал производства». Тост короткий и легко пропустить (кроме HOURS, где его видели). Журнал не раскрывает новую строку. Owner issue 1.

### F-02 — Quantity и операция подписаны одинаково «Подтвердить»

- **Class:** UX BUG  
- **Severity:** P3 (рядом с P2, если работник думает, что quantity = запись)  
- **Где:** `QuantityDialog` default `confirmLabel`, `TerminalConfirmBar`  
- **Суть:** после количества нет тоста. Назад → home, журнал не изменился → «сохранилось ли?»

### F-03 — TORCOVKA: ввод заготовок без `railsTaken`

- **Class:** UX BUG / UI PREREQUISITE  
- **Severity:** P2  
- **Где:** `TorcovkaScreen` секция 3 при `lot &&`; `QuantityDialog` max только если `railsTaken > 0`  
- **Суть:** Owner issue 2. Сервер не примет. Работник тратит время / думает, что пакет не нужен. Без лимита можно набрать невозможную длину.

### F-04 — Смена пакета/партии молча стирает количества

- **Class:** FUNCTIONAL / UX  
- **Severity:** P2  
- **Где:** `selectLot` / `selectBatch` → `resetLot`  
- **Суть:** нет «сбросить ввод?». Live T09: 4 шт исчезли после тапа другого пакета.

### F-05 — F5 сбрасывает UI на PIN, хотя черновик жив

- **Class:** FUNCTIONAL / UX  
- **Severity:** P2  
- **Где:** `TerminalApp` — нет restore сессии при mount; cookie httpOnly  
- **Суть:** refresh киоска = «выход». Resume только после повторного PIN. Не путать с idle-logout.

### F-06 — Sticky Confirm bar перекрывает нижние плитки заготовок

- **Class:** UX BUG (touch)  
- **Severity:** P2  
- **Где:** `TerminalConfirmBar` sticky + сетка длин  
- **Суть:** после ввода реек нижние длины плохо нажимаются. Live: 0,6 м не открылась, 0,44 м открылась.

### F-07 — Недоступная упаковка без причины

- **Class:** UX BUG  
- **Severity:** P3  
- **Где:** `UpakovkaScreen` `disabled={max===0 && qty===0}`  
- **Суть:** тап ничего не делает. Не видно, чего не хватает (деталь / крепёж / коробка).

### F-08 — TORCOVKA журнал говорит «дет», хотя это заготовки

- **Class:** UX  
- **Severity:** P3  
- **Где:** `entries-journal.tsx` `TYPE_UNIT.TORCOVKA = "дет"`  
- **Суть:** после торцовки +4 «дет» при том, что деталь ещё не выбрана.

### F-09 — SORT2 скрывает количества SORT1

- **Class:** UX  
- **Severity:** P3  
- **Где:** сетка длин по `activeSort`  
- **Суть:** после T08/resume на SORT2 плитки 0, хотя бейдж «1 сорт 4». Кажется, что ввод пропал.

### F-10 — Нельзя обнулить одну длину в диалоге

- **Class:** UX  
- **Severity:** P3  
- **Где:** `QuantityDialog` `numeric > 0`  
- **Суть:** только «Сбросить» на весь сорт. T07.

### F-11 — Неверный approval-код не очищает поле

- **Class:** UX  
- **Severity:** P3  
- **Где:** `retryWithApprovalCode` catch  
- **Суть:** `0000` остаётся, тост есть. Случайный повторный Confirm = ещё попытка (лимит на сервере).

### F-12 — Confirm bar при 0 заготовках показывает 100% отход

- **Class:** UX  
- **Severity:** P3  
- **Где:** T04 с railsTaken>0, picks=0  
- **Суть:** Confirm disabled (правильно), цифра 100% пугает и не про операцию.

### F-13 — Двойной тап до `setSubmitting`

- **Class:** INVARIANT WEAKNESS (UI)  
- **Severity:** P3 при живом серверном unique  
- **Где:** confirm handlers  
- **Суть:** сервер идемпотентен. Клиент может дважды показать success. Не P1.

### F-14 — Hours без ставки всё ещё отправляются (код)

- **Суть:** подпись «ставка не задана», submit не блокируется. На тестовом сотруднике ставка была.

### F-15 — Дробные часы нельзя ввести

- **Class:** EXPECTED DESIGN / NEEDS OWNER DECISION  
- **Severity:** —  
- **Суть:** keypad integer. Исторические 7.5 ч в сиде с UI не набрать.

### F-16 — Approval-код виден открытым текстом на экране терминала
