## 2. Explicit READ COMMITTED

`audit/08.11` blocked this writer until READ COMMITTED is a declared correctness dependency.

The physical R-05 transaction now sets:

```ts
isolationLevel: Prisma.TransactionIsolationLevel.ReadCommitted
```

It does **not** rely on PostgreSQL's default isolation.

The TX performs: requestId lookup → wait for `ProductionOperation FOR UPDATE` → second requestId lookup. The second lookup must observe a correction committed while this transaction was waiting. Replay/CAS semantics are unchanged.

PostgreSQL proof: holder locks the operation; waiter passes first requestId lookup and blocks; a non-conforming writer inserts and COMMITs a matching `ProductionOperationCorrection` for the same `requestId`; holder releases; waiter’s second lookup sees the row and returns replay; no RailLot/op mutation; no second correction; no P2002.

## 3. Gate-first transaction order

Authenticated admin + USER actor are captured **outside** the TX. Ordinary code does not read `inventory_movement_shadow_write`.

```text
requireAdmin() + userMovementActorFromAdmin(admin) outside TX

BEGIN READ COMMITTED
→ SHARED InventoryMovement advisory lock + SHADOW gate read
  (isInventoryMovementShadowWriteActiveForWriter(tx))
→ R-05 requestId advisory lock (8325)
→ lookup retained correction
→ replay if found (no InventoryMovement, including no backfill)
→ ProductionOperation FOR UPDATE
→ second requestId lookup
→ operation/type/paid/CAS validation
→ existing cost-flow decision
→ RailLot / Batch / existing physical locks
→ physical validation
→ insert ProductionOperationCorrection
→ apply physical correction
→ append SHADOW InventoryMovement if outer SHADOW gate was ACTIVE
→ ChangeLog / Batch reopen audit/status
→ COMMIT
```

No physical mutation before SHADOW gate validation. No direct Setting read.

Malformed SHADOW Setting fails closed in the gate helper before the R-05 request lock, retained insert, operation-lock-dependent physical mutation, RailLot/op change, ChangeLog, or InventoryMovement.

## 10. Replay / no backfill

If `ProductionOperationCorrection` already exists for the same `requestId` and payload matches: return the existing replay result. Do **not** append an InventoryMovement.

Includes:

- correction committed while SHADOW OFF → gate later ON → same requestId retried → **no movement backfill**
- correction committed while SHADOW ON → retry → **no second movement**

The movement is created only in the transaction that creates the retained correction and applies the physical effect.

## 11. Gateway-result invariant

When the outer SHADOW read was ACTIVE, a newly committed nonzero R-05 correction requires:

```text
result.gateActive === true
result.inserted === 1
```

Schema/command already guarantees `deltaReturned > 0`. Mismatch throws `R05_SHADOW_GATE_INVARIANT_VIOLATION` and rolls back. Replay does not call the gateway.

## 12. Writer placement

`correctTorcovkaRailsTaken` remains the `"use server"` action. The physical TX body lives in `src/server/internal/correct-torcovka-rails-taken-tx.ts`. The SHADOW append wrapper is `appendR05CorrectionShadowMovement` → `appendShadowInventoryMovements`.

For a new correction only: persist correction → apply physical effect → append SHADOW if outer gate ACTIVE → ChangeLog / Batch reopen → commit. Movement append failure rolls back the whole correction.
