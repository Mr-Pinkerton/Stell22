# 09.02 Cost scenarios A–V

**Base:** `506bfa0d687d61d4d3d02df57b978c31838f728f`  
**Contour under test:** live report and live writers with `production_cost_flow` inactive, unless a row says otherwise.

Verdicts:

- **PASS** — the live rule and the cited code/test agree.
- **FAIL** — the live rule's own conservation is broken on the cited path.
- **UNVERIFIED** — the code was read, but this phase did not execute the database path or production rows.

"Expected" is the **current** live rule (`src/lib/cost.ts`, cost-integrity, DI cards that are closed). The accepted target in `audit/03.02` is named only where the live path deliberately differs. That difference is not a new FAIL while the gate stays off. See `09.00`.

Unit tests re-run this phase: 167 passed. They cover the pure functions, not PostgreSQL rounding and not production.

## A. One batch, one sort

Expected: all `C` on that sort.  
Example: `C = 50 000`, produced sort 1 only → `costSort1 = 50 000`, `costSort2 = 0`.  
Path: `distributeBatchCost` (`cost.ts:83–133`).  
Test: `cost.test.ts` "один сорт".  
**PASS**

## B. One batch, two sorts

Expected: shares `P×V`, `costSort2 = C − costSort1`.  
Example: `C = 100 000`, `P1 = 30 000`, `P2 = 20 000`, lengths 1000 m and 500 m, area `0.0008` → volumes `0.8` and `0.4`, costs `75 000` and `25 000`, ₽/m³ `93 750` and `62 500`.  
Test: `cost.test.ts` first distribute case. A repeating fraction `1/3` still sums to `C` in `Decimal`.  
**PASS** for the pure function. Stored FINAL is scenario T / `BA-P01-002`.

## C. Two batches, one material, different purchase prices

Expected: each batch keeps its own `C` on its own produced metres. SKU wood is Σ cost / Σ metres of that material, not a simple average of the two prices.  
Example: batch A `10 000` on 100 m and batch B `20 000` on 100 m → `150 ₽/m`, not "the latest price".  
Path: `blendedCostPerMeterByMaterial` (`cost-report.ts:322–344`). Detail rows stay on one batch (`cost-report.test.ts`, "детали строго по партии").  
**PASS** for the blend. In-progress inflation (`COST-001`) still applies to each batch separately.

## D. Two materials

Expected: blends do not cross `materialId`.  
Test: `cost-report.test.ts` "blendedCostPerMeterByMaterial".  
**PASS**

## E. Extra delivery

Expected: `C = purchaseCost +` share of confirmed expense above Σ purchases. One batch receives the whole extra.  
Example: purchase `150 000`, confirmed expense `160 500` → extra `10 500`, `C = 160 500` (`deal-cost.test.ts`).  
Unconfirmed account: excluded (`sumConfirmedExpense`).  
Path: `syncBatchTotalCostInternal` (`finance-operations.ts:279–320`). Frozen batch is not updated.  
Two or three batches: the pure share sums to the extra (`deal-cost.test.ts`, three ways of `100`). The writer then `toFixed(2)` **each** batch.  
Example executed in Decimal.js `ROUND_HALF_UP` this phase: extra `100.00` split 3 ways → stored `33.33 × 3 = 99.99`. Extra `0.01` split 2 ways → stored `0.01 × 2 = 0.02`.  
**FAIL** at persistence (`BA-P01-001`). The single-batch example **PASS**.

## F. Both sort prices zero

Expected: volume fallback, sum still `C`.  
Example: `C = 60 000`, lengths 1000 and 500 → `40 000` and `20 000`, same ₽/m³.  
Test: `cost.test.ts` "нулевые цены". One zero price puts all `C` on the priced sort.  
**PASS**

## G. Partly consumed batch

Expected live rule: 100% of `C` is on metres already cut. Remaining rails hold quantity and none of `C`.  
Example: `C = 116 500` on `12.16 m` is the `03.01` illustration of `COST-001`. The formula is unchanged.  
Target BD-COST-06 (money stays on remaining rails) is not live.  
**PASS** against the live formula. Not a new defect. Production metres on this SHA were not remeasured.

## H. Fully consumed batch

Expected: `remainingQuantity = 0` → `archiveBatchIfDepleted` sets `closedAt`. FINAL only if unpaid TORCOVKA count is 0 (`canFreezeBatch`, `cost.ts:407–424` and `cost.ts` `canFreezeBatch`).  
**PASS** for the predicate (unit-tested). The database freeze path was not re-executed here.

## I. High waste percent

Expected: waste metres = taken − produced. Money has no waste line; ₽/m rises.  
Example: `C = 100 000`, produced `30 m` of `100 m` taken → waste `70%` of taken, wood `100 000 / 30` ₽/m. `batchWaste` does not price it.  
Tests: `waste.test.ts`.  
**PASS**

## J. Write off unused rails

Expected live rule: quantities go to 0 (`purchases.ts:741–748` inactive branch), batch can archive and maybe freeze. If nothing was cut, there is no snapshot and `C` never enters the wood blend. If something was cut, the whole `C` stays on those metres.  
Target BD-COST-07 would post an explicit loss. Not live.  
**PASS** against the live rule. Active write-off was not executed.

## K. Correct a TORCOVKA quantity

Expected: unpaid, not frozen, not cancelled. Stock `gte` check. Then recalc. Paid or frozen edit is rejected.  
Path: `production-quantity-edit-tx.ts` (enqueue only for TORCOVKA, line 383).  
**UNVERIFIED** as an executed transaction. The guards match the closed DI-019 shape. This phase did not re-run the integrity file.

## L. Cancel a production operation

Expected live rule: unpaid, not frozen, fingerprint matches. TORCOVKA cancel returns `railsTaken` and removes blanks, or blocks if blanks are gone (`cancel-production-operation-tx.ts:244–297`). PRISADKA and UPAKOVKA reverse their own buckets. `cancelledAt` drops the operation from `loadCostContext` and from `recalcBatchCosts`. Replay of the same `requestId` does not apply twice.  
Generic TORCOVKA **delete** is a different path and still does not restore rails (`INC-001`, open).  
**PASS** for the cancel function as read. **UNVERIFIED** on a database. `INC-001` is not closed.

## M. PRISADKA with several operations

Expected: each terminal pick is one kind. A line gets `prisadkaTorcevaya` xor `prisadkaPloskost` (`production-reversal.ts:157–158`). A second operation fills the other flag. Payroll `operationEarning` adds a rate per flag that is true.  
The SKU average uses `else if` (`payroll.ts:348–356`), so a line with **both** flags would drop the face rate. The live writer does not create that line.  
**PASS** for the writer. Both-flags average is an unreached branch, not a confirmed data defect.

## N. UPAKOVKA with several components

Expected: one product pick consumes every current BOM detail, fastener, and packaging unit, and stores those lines (`applyUpakovkaPrepared`). Reverse uses the stored lines. The cost report later prices the **current** catalog and BOM, not those lines (`COST-005`, `COST-006`).  
**PASS** for stock identity. SKU extras remain a price-list figure.

## O. Change the product specification

Expected: later packs use the new BOM. Old operation lines stay as packed. The cost report multiplies the new BOM by the all-time wood rate, so an old month's SKU row changes. `ProductCost` is not written.  
**PASS** for "the live report restates". It does **not** implement BD-COST-03. That decision waits on activation and `closeMonth`, which have no writer.

## P. Change an employee rate

Expected: new operations snapshot the new card. Old operations keep DI-015 snapshots. `actualProductionRates` reads snapshots (`cost.ts:196–200`).  
**PASS** (payroll snapshot tests). A database edit of a historical row was not performed.

## Q. Piece pay and hourly pay together

Expected live rule: payroll pays both. The SKU rate for that employee-day is piece rate plus `dayHoursPay / pieceUnits`.  
Example: 2 hours × `100` = `200`, 10 sort-1 pieces × `5` → unit rate `25` (`payroll.test.ts` "гибрид").  
Hours-only day: comment says the pay is not spread; the second loop skips `HOURS`. No test asserts the exclusion.  
Target BD-COST-01 puts hours into `CostPeriod`, not into the piece rate. That object has no writer.  
**PASS** for the tested hybrid. Hours-only exclusion: **UNVERIFIED** by a test, visible in code.

## R. Change overhead after the fact

Expected live rule: `getPeriodOverhead` reads current `isOverhead`, confirmed accounts, and cashflow dates in the period. Moving a date or a flag changes that month's overhead on the next report. There is no month lock.  
**PASS** for the live query. Historical immutability is not implemented (`COST-003`, `COST-008`).

## S. Inventory shortage

Expected live rule: quantity becomes the count. `deviationSum` is stored from the current unit snapshot (`inventory-conduct.ts:170–179`). `buildCostReport` does not read it.  
**PASS** for "shortage is not in the SKU report" (`COST-007`). The money on the inventory document is not a ledger entry. Active `CostEvent` shortage was not executed.

## T. A past period and FINAL snapshots

Expected: a frozen batch's wood in the report is the FINAL row, not a new distribute (`cost-report.ts:201–215`). Labor, BOM, nomenclature prices, and overhead for that month are still current. `CostPeriod.status` is never set to FINAL by a writer.  
FINAL columns are `Decimal(14,2)` (`schema.prisma:1089–1092`). The writer stores full-precision strings (`cost.ts:328–335`, `384–386`). Independent 2 dp rounding of `1.005` and `8.995` (which sum to `10`) becomes `1.01` and `9.00`.  
**FAIL** for stored FINAL conservation (`BA-P01-002`). **PASS** for "FINAL is preferred over live math" and for "the month itself is not frozen".

## U. Concurrent repeats

Expected: same `clientRequestId` does not create a second operation (`INV-014`). Purchase write-off and cancel use a request id and a second look inside the lock. Cost recalc coalesces in one process (`cost-queue.ts`).  
**UNVERIFIED** under two database sessions. This phase did not run the integrity suite. The code and existing tests are the evidence already accepted for DI-014 / DI-018 / DI-019; they were not re-executed here.

## V. Unconfirmed bank account

Expected: its expense does not increase `C` and does not enter overhead.  
Path: `sumConfirmedExpense` (`deal-cost.ts:19–26`); `getPeriodOverhead` requires `account.confirmed` (`cost.ts:150`).  
Test: `deal-cost.test.ts` "карантин".  
**PASS** in the pure function and the overhead query. Production quarantine rows were not read.
