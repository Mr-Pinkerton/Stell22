## 3. DI-007 — контракт retry для ТОРЦОВКИ

### 3.1 Текущий порядок (после DI-020)

`submitTorcovka` `terminal.ts:363-468`, ровно в этом порядке:

1. `:364` `lockRailLots(tx,[railLotId])` — `SELECT … FOR UPDATE`;
2. `:365-368` чтение лота и партии;
3. `:370-374` длина заготовки ≤ длине рейки;
4. `:376-379` INV-008 `producedM ≤ takenM`;
5. `:381-386` **DI-020** `decideTorcovkaSubmit` → при `ACK_REQUIRED` **ранний
   `return` из TX** (ни INSERT, ни decrement);
6. `:388-392` `railLot.updateMany where remainingQuantity >= railsTaken` →
   `dec.count === 0` → `throw new Error("Недостаточно реек в пакете")`;
7. `:394-416` `productionOperation.create` c `clientRequestId` → **только здесь
   срабатывает UNIQUE (P2002)**;
8. `:434-451` `blankStock.upsert`;
9. `:454-461` `writeChangeLog` (в TX);
10. `:463` `archiveBatchIfDepleted` (в TX);
11. `:465-468` `.catch(isDuplicateClientRequest)` → `{status:"CREATED"}`;
12. `:472` `enqueueRecalcBatchCosts` (после TX).

**DI-020 порядок decrement→create не менял.** Он добавил шаг 5 ПЕРЕД
decrement. Значит DI-007 не только сохранился, но получил второй канал
нарушения (§3.3).

### 3.2 Ответы на вопросы

- **Дубль обнаруживается до отказа по остатку?** **НЕТ.** Отказ по остатку —
  шаг 6, UNIQUE — шаг 7.
- **Тот же clientRequestId после закоммиченного success всегда даёт success?**
  **НЕТ.** Даёт success только пока `remainingQuantity >= railsTaken`.
- **Если остаток лота стал 0?** `throw "Недостаточно реек в пакете"`.
  Воспроизведено (S1a).
- **NORMAL / SUSPICIOUS / EXTREME?** Идентично. NORMAL идёт по шагам 6-7 сразу;
  SUSPICIOUS/EXTREME с валидным ack — по тем же шагам 6-7 (S1c: та же ошибка).
- **Меняет ли ack/причина идемпотентность?** ДА, добавляет второй канал: retry
  **без** ack после успешного submit **с** ack возвращает `ACK_REQUIRED`, а не
  success (S1d). Данные не портятся, но клиент получает «подтвердите отход»
  для уже записанной операции.
- **Двойной ChangeLog?** НЕТ. `writeChangeLog` внутри TX; при P2002 и при
  «Недостаточно реек» TX откатывается. Локально: `logs` = 1 в S1a/S1b/S1c/S1d.
- **Двойной enqueue себестоимости?** ДА, на идемпотентном пути (`:472`
  выполняется, т.к. `txResult.status==="CREATED"`). Безвреден: `cost-queue`
  коалесцирует по ключу партии (dirty-flag), FINAL не трогается. На пути
  «Недостаточно реек» enqueue не выполняется (throw до `:472`).
- **Дубли BlankStock / строк операции?** НЕТ. `ops`/`lines`/`blankQty`
  неизменны в S1a-S1d.
- **Двойное close/freeze партии?** НЕТ. `archiveBatchIfDepleted` внутри TX
  (откат) и сам идемпотентен: `internal/cost.ts:436` `if (preBatch.closedAt) return false`.

### 3.4 Классификация DI-007

**INVARIANT WEAKNESS, по-прежнему воспроизводимо (NOT FIXED, NOT STALE).**
DI-020 нарушение не устранил и добавил `ACK_REQUIRED`-канал.

конфигурация, при которой S1a срабатывает.

**C. Может ли старый/устаревший клиентский код его опустить?** **Практически

билду — после деплоя такой вызов не резолвится. Гипотетический канал, evidence
о его реализации нет.

**D. Могут ли скрипты/тесты/internal callers его опустить?** **ДА, и уже

## 9. Опции исправления

### 9.1 DI-007 (находка открыта → опции проектируются)

Цель инварианта: **повтор закоммиченного `clientRequestId` НИКОГДА не
возвращает ошибку остатка и НИКОГДА не требует повторного ack.**

- **A. Проверка ключа первым запросом в TX.** До `lockRailLots`:
  `findUnique({ where: { clientRequestId } })` → если найдено, вернуть
  `{status:"CREATED"}` без мутаций. Дёшево, закрывает и `Недостаточно реек`, и
  `ACK_REQUIRED`-канал (S1a/S1c/S1d). Под конкуренцией сам по себе не
  достаточен — UNIQUE (шаг 7) остаётся страховкой, S7 уже показывает, что она
  работает. Требует, чтобы ключ был непустым (пересекается с DI-008 A).
- **B. Переставить create перед decrement** (как в PRISADKA). Устраняет S1a/S1c,
  **не** устраняет S1d (`ACK_REQUIRED` — шаг 5, раньше обоих). Меняет порядок
  локов в горячем пути TORCOVKA — нужно сверить с DI-019/DI-020
  (`lockRailLots → …`), риск выше, чем у A.
- **C. Мягкая обработка `dec.count === 0`:** перед throw проверить наличие
  операции с этим ключом → success. Точечно, но оставляет `ACK_REQUIRED`-канал
  и добавляет ветку в самый чувствительный guard остатка (DI-020).
- **D. Ничего не делать** (принять как известный UX-дефект). Порчи данных нет;
  но именно эта путаница провоцирует повтор с новым id, а это уже реальная
  лишняя операция.

Ожидаемая рекомендация к обсуждению — **A** (наименьший риск для DI-019/DI-020
инвариантов, закрывает оба канала). Реализация в этом pass не делается.

### 9.2 DI-008 — узкое сравнение

| | Вариант | Что даёт | Цена / риск |
|---|---|---|---|
| **A** | Требовать `clientRequestId` только в приложении (guard в 4 действиях: непустая строка, иначе throw) | закрывает B и D; закрывает S3c-класс, если добавить дедуп picks; ноль миграций; обратимо | не защищает от прямого INSERT в БД; `prisma/seed.ts` и integrity-тесты придётся править (они ключ не передают) |
| **B** | Только DB `NOT NULL` | гарантия на уровне БД | без app-guard клиент получит сырую ошибку Prisma вместо доменного сообщения; та же правка seed/тестов; миграция |
| **C** | App required + DB `NOT NULL` | максимальная гарантия | сумма цен A и B; необратимо без обратной миграции |
| **D** | Оставить nullable намеренно | ноль работы | контракт «дубль попытки не создаёт две операции» остаётся необеспеченным для любого не-UI вызова |

**Проверка перед `NOT NULL` (сделана):** production
`COUNT(*) FILTER (WHERE "clientRequestId" IS NULL)` = **0**, всего строк
**0**. Backfill на production **не нужен**, миграция `SET NOT NULL`
выполнится за один проход без переписывания данных.

Если NULL-строки появятся до применения (штатный UI их не создаёт, но прямой
вызов может), безопасная стратегия — **не реализуется здесь, только проектируется**:
1. Preflight-гейт в `scripts/preflight-prod.sh`: `COUNT(*) WHERE
   "clientRequestId" IS NULL` > 0 → STOP, печать `id/type/employeeId/workDate/createdAt`.
2. Сначала выпустить app-guard (вариант A) — новые NULL перестают появляться.
3. `NOT NULL` — отдельной последующей миграцией, только после того как
   preflight показал 0.

Явно запрещено и не предлагается: случайный backfill ключей, удаление
исторических операций, массовая генерация id. Исторически осмысленного
значения для NULL-строки не существует (ключ — идентификатор попытки клиента,
восстановить его нельзя), поэтому единственная корректная стратегия — гейт, а
не backfill.

Все варианты требуют решения владельца по одному пункту (§10).
