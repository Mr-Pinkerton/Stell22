## 1. Result

Neither option satisfies safe offline P1 maintenance without an Owner decision that this task does not make.

Option A, full offline application shutdown with exclusive maintenance access, can be measured on a disposable cluster without a new architecture decision. That measurement does not close the startup hard stop in `audit/08.55` §7. The production entrypoint still runs `npx prisma migrate deploy` on every start.

Option B, a restricted application role with a separate migrator and app-only startup, is the only tree that omits `prisma migrate deploy` from an entrypoint. The production image does not use that entrypoint. The app-only gate refuses a superuser, and the current Compose login is `stell22`. Installing B is a role split. That split is **NOT AUTHORIZED**. `audit/08.55` §13 records that Design D and the role split were not requested again. This contract does not reopen them.

The recommended candidate for subsequent HEAD acceptance is a disposable shutdown measurement of Option A. It is not a production cutover and it is not a freeze pass.

## 4. Option A — full offline shutdown

Definition used here: the `stell22-app` process is stopped for the whole maintenance interval, and the only admitted writer is the one recorded operator action. The database container stays up. This is not a privilege freeze and not Design D.

### Required technical changes

No repository change makes A true today. A later disposable package would have to add a test harness only. It must not edit `Dockerfile`, `docker-compose.prod.yml`, `docker-entrypoint.sh`, `scripts/deploy.sh`, `scripts/backup-db.sh`, `scripts/restore-db.sh`, or a migration.

The production files would still need, before any production use, a control that keeps `stell22-app` stopped across process exit and across daemon restart, and a P1 command that is not an application start. Those controls are not in this tree. Adding them is **NOT AUTHORIZED**.

### Existing reusable implementation

`docker stop` and `docker start` are operator commands. Compose supplies `restart: unless-stopped` and does not supply a maintenance lock. `scripts/deploy.sh` is the opposite of a held stop: it builds and starts the app. The isolated one-shot in `audit/08.42` applies pinned P1 without starting the Next.js server. The later adapter (`audit/08.43` through `audit/08.45`) is not fully authenticated for production. Public apply stays unauthorized.

### Writer-exclusion mechanism

The mechanism is absence of the Node process. Server Actions, the cron route, notification sync, and the cost queue live in that process (`audit/08.55` §4). Caddy has nothing to proxy to while `app:3000` is down.

That absence is not exclusive maintenance access. `scripts/backup-db.sh` and `scripts/p1-writer-preflight.sh` open a database session as `stell22` through `docker compose exec`. `audit/08.54` showed, on a disposable daemon, that `docker exec` as root rewrote `pg_hba` and a bootstrap insert committed. The Owner's trusted-operator boundary (`audit/08.55` §6, `PROJECT.md`) accounts for one recorded operator. It does not ban a second SSH key, a second socket holder, or host root.

`UNAUTHORIZED_WRITERS_EXCLUDED` stays **NOT PROVEN**.

### In-flight transactions

`audit/08.56` proved, on a synthetic session, that a transaction opened before the declaration committed afterwards, and that 4 of 4 terminate races committed. `audit/08.53` proved that an insert already executed inside an open transaction became visible when the coordinator crashed after the privilege commit and before the drain. `audit/08.50` proved that `pg_terminate_backend` of historical-app backends rolled back an open transaction on a disposable cluster. None of those runs is `docker stop` of `stell22-app` during a Server Action.

This tree sets no `stop_grace_period` and installs no application drain. Whether an in-flight Server Action commits during the engine's stop timeout is **UNKNOWN IN PRODUCTION** and is not a disposable result.

### Direct SQL

Not excluded. The bootstrap login in Compose is `stell22`. A stopped app does not close `docker exec`, a sibling on the Docker network, or a port published outside git. The unpublished `5432` mapping is `PROVEN FROM CODE`. Running peers are **UNKNOWN IN PRODUCTION**.

### Background jobs

In-process cost follow-ups die with the process only after the process is actually dead. A job that commits before death is durable. Host crontab, `scripts/fetch-statements.ts`, and GitHub `workflow_dispatch` are outside the process. Their production presence is **UNKNOWN IN PRODUCTION**. A dispatch of `deploy-production.yml` would start the app and run the entrypoint. That dispatch is **NOT AUTHORIZED**.

### Automatic restart

| Event | Evidence | Class |
| --- | --- | --- |
| Compose policy | `restart: unless-stopped` on `app` | `PROVEN FROM CODE` |
| Explicit `docker stop` of an unless-stopped synthetic writer | Still exited after 3 seconds. No new row | `PROVEN DISPOSABLE` (`audit/08.56`). Not `stell22-app` |
| Process exit of that writer | `StartedAt` changed. Inserts resumed while the admission file stayed `open` | `PROVEN DISPOSABLE` |
| `docker kill` on Docker 29.2.1 | Stayed exited. `RestartCount` 0 | `PROVEN DISPOSABLE` on that daemon only |
| Docker daemon restart | Not run. Foreign containers included `stell22-db` | Not tested. **UNKNOWN** even on that daemon |
| Production `stell22-app` | Not stopped | **UNKNOWN IN PRODUCTION** |

A manual stop and a process crash are different engine events on the daemon A01 used. A contract that treats them as one restart rule is false.

### Migration-on-start prevention

While the app stays stopped, the entrypoint is not executed. That is avoidance, not removal. The script still contains `npx prisma migrate deploy`. The next ordinary start runs it. `audit/08.50` measured the historical image on a disposable cluster: when nothing was pending, the server came up and the Prisma log said nothing to apply. The migrate exit code was not captured. `audit/08.55` §7 requires that an ordinary start does not run `prisma migrate deploy`. Option A does not meet that sentence.

`scripts/deploy.sh` remains the wrong P1 tool. It checks out a SHA and starts the image whose entrypoint migrates.

### Failure and recovery

| Event | Required result |
| --- | --- |
| Stop command fails, or the app is still running | Stop the sequence. Do not apply P1. Do not call the stop a freeze |
| `StartedAt` changes after the stop record | STOP. Treat the new start as an uncontrolled migrate attempt |
| Process crash brings the app back | STOP. The admission file in A01 did not bind this entrypoint |
| Daemon restart not measured, or it starts the app | STOP. Do not simulate the daemon (`audit/08.56`) |
| In-flight result not shown | STOP. A quiet table is not the proof |
| Direct SQL session other than the one recorded operator action | STOP |
| P1 result uncertain | No second apply, no production restore, no unfreeze. Diagnosis only under a separate Owner decision (`audit/08.55` §8) |
| Operator wants the previous bytes | `scripts/restore-db.sh` stays a refusal |

### Operational downtime

The application is down for the whole held stop. Caddy can keep listening. The database container stays up. No production duration was measured. A later start is a separate downtime risk because the entrypoint migrates before the server listens.

### Owner authorization

The physical-isolation model and the trusted operator are already decided (`audit/08.55` §6). They are not `APPROVAL TO PREPARE`, `APPROVAL TO APPLY`, `APPROVAL TO DIAGNOSE`, or `APPROVAL TO UNFREEZE`. All four remain absent. A disposable measurement of stop behavior does not need those four. Production use of A does.

## 5. Option B — restricted role and app-only startup

Definition used here: the application logs in as a non-superuser that does not own the schema, migrations are applied by a different role before that process starts, and the process uses `docker-entrypoint-app-only.sh`. Design D in `audit/08.48` is this shape. It stays a candidate.

### Required technical changes

All of the following are absent from the production path:

1. A break-glass superuser that is not the application login, with custody outside the app container (`audit/08.48`).
2. `stell22_migrator` as the owner of the application objects. The adapter names that role. `PRODUCTION_ROLE_NAME` remains `stell22`. The credential file is not in the repository.
3. An application role that passes `evaluateAppOnlyStartup`. A superuser is `BOOTSTRAP_SUPERUSER`. Today's Compose URL uses `stell22`.
4. `DATABASE_URL` pointed at that application role. `audit/08.48` records that this recreates `stell22-app` and changes `StartedAt`. It is outside any protected interval.
5. Compose and the production `Dockerfile` selecting `docker-entrypoint-app-only.sh`. `readStartupFacts` currently sets `appOnlyIsProductionPath` false.
6. `scripts/deploy.sh` step `[3/5]` no longer treating entrypoint migrate as the migration step (`audit/08.52`).
7. A freeze that is not the startup gate. The gate does not read table DML grants.

Each item is **NOT AUTHORIZED**. Item 2 is an Owner role-split decision that has not been given.

| Piece | Reuse limit |
| --- | --- |
| `docker-entrypoint-app-only.sh` and `docker/app-only-startup/Dockerfile` | Candidate image only. `audit/08.52` disposable restart logs did not contain `migrate deploy` |
| `gate.ts` | Read-only schema and role gate. Passes with DML still granted. `audit/08.52` then revoked DML in the same disposable run; `SELECT` stayed, `INSERT` was denied, health stayed 200 |
| Package E coordinator | `APPLICATION_ROLE_ONLY` on `p1wc_<8 hex>`. Refuses the database name `stell22`. Not called by Compose, the entrypoint, or `scripts/deploy.sh` |
| `audit/08.49` | Bootstrap `ALTER ROLE stell22 NOSUPERUSER` failed and rolled back. The candidate does not demote `stell22` |
| `audit/08.50` | Historical app as a non-superuser on a disposable cluster, with no pending migration, stayed up. Not the production login |
| `audit/08.54` | Default-reject `pg_hba` blocked new logins. An existing session, the admitted superuser, and host root still wrote. Gate `PRIVILEGED_WRITER_BARRIER_BLOCKED` |
| Production adapter migrator probes | Disposable privilege tests exist. Production identity still requires the observed role `stell22` (`identity.ts`) |

### Writer-exclusion mechanism

After a committed revoke and a completed drain, a new login as the disposable application role receives SQLSTATE `42501` for business DML (`audit/08.53`). Coverage is `APPLICATION_ROLE_ONLY`. The bootstrap superuser, the break-glass superuser, and the owning migrator can still write. An open session of either superuser blocks `FROZEN_VERIFIED`.

`audit/08.56` showed a different hole on the same role family: `p1wc_app` inherited `p1wc_migrator` and updated the admission row. The app-only gate refuses membership. The coordinator freeze is not that gate. A role that still inherits the owner is not frozen.

App-only startup itself is not a writer exclusion. `audit/08.52` recorded `INSERT` succeeding before the separate revoke.

### In-flight transactions

The coordinator terminates application backends after the privilege commit. An open insert that had not committed was absent. An insert that had already executed became visible when the process died between commit and drain (`audit/08.53`). `audit/08.54` showed an existing backend commit after `pg_hba` reload, before terminate. The window is part of the mechanism. It is `PROVEN DISPOSABLE` and it is not closed.

### Direct SQL

A new session as the frozen application role cannot `INSERT` (`PROVEN DISPOSABLE`). A session as the bootstrap superuser can. Production Compose still authenticates as `stell22`. Whether that role is the bootstrap superuser on the live cluster was not read from `pg_authid`. `audit/08.48` leaves that catalog fact **UNKNOWN**. `pg_hba` on the disposable image did not stop an already authenticated superuser (`audit/08.54`).

### Background jobs

With the app still running as the frozen role, the next notification sync, cron import, or cost write fails at the database if it uses that role. `audit/08.52` measured the `INSERT` denial and health 200. It did not call `getNotifications` or `POST /api/cron/fetch-statements`. Production `CRON_SECRET` and `MAIL_*` are **UNKNOWN IN PRODUCTION**. Host cron is **UNKNOWN IN PRODUCTION**. A failed statement is not proof that a different login is closed.

### Automatic restart

The candidate entrypoint does not migrate. `audit/08.52` recorded a disposable restart whose logs did not contain `migrate deploy` or `Applying migration`. The production Compose file would still apply `restart: unless-stopped` to whichever image it runs. A failed app-only gate exits the script (`set -eu`). Compose would restart that container, change `StartedAt`, and leave the site down while the gate keeps failing. That restart loop was described in `audit/08.48` and was not measured as a production Compose service.

Switching the image is itself a start. It is not a held freeze.

### Migration-on-start prevention

`PROVEN FROM CODE` for the candidate script. `PROVEN DISPOSABLE` for the candidate image in `audit/08.52`. False for the path production runs: `startup-facts.ts` and `Dockerfile`. Citing the candidate does not satisfy `audit/08.55` §7 items 1–5.

The separate migrator is not wired as the production one-shot identity. `PRODUCTION_ROLE_NAME` is `stell22`. Using `stell22_migrator` in production is **NOT AUTHORIZED**.

### Failure and recovery

Use the coordinator rules already recorded in `audit/08.53`, without widening them:

- Privilege rollback stays at the pre-commit state.
- Crash after commit and before drain is `UNCERTAIN`. No automatic `GRANT`.
- A durable P1 intent without `P1_COMMITTED` is `MANUAL_RECOVERY_REQUIRED`. No second apply. No destructive restore.
- `rejectDestructiveRestore` returns `DESTRUCTIVE_RESTORE_FORBIDDEN`.
- A missing break-glass proof means the procedure does not start (`audit/08.48`).
- App-only gate failure must leave the new container down. It must not fall back to `docker-entrypoint.sh`.
- Unfreeze is a separate decision. A postcheck does not grant DML.

Those rules are implemented for the disposable coordinator. They are not installed on the production operator.

### Operational downtime

The URL switch recreates the app container. That is downtime, and it changes `StartedAt`, so it cannot sit inside a later protected interval (`audit/08.48`). After a successful restricted start, reads can succeed while writes fail. Notification sync is a write, so the admin UI errors. No production duration was measured. Returning ownership to the application role is not the unfreeze. Unfreeze is `GRANT` of DML from the break-glass role.

### Owner authorization

Required before B can leave the candidate state:

1. Permanent role split. Not a temporary maintenance mode. Not demotion of the bootstrap superuser. **NOT GIVEN**.
2. Break-glass custody outside the repository and outside the app container.
3. Acceptance that the admitted superuser and the Docker socket holder remain writers (`audit/08.54`).
4. A later, separate approval to change the production image. That approval is not `APPROVAL TO APPLY`.
5. The existing absent approvals: prepare, apply, diagnose, unfreeze.

`audit/08.55` §13 says the Owner is not asked by that draft to choose another architecture. This contract repeats the technical consequence and does not record a new choice.
