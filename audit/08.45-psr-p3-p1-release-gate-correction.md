## What changed

P1-1. The one-shot container is no longer started from the mutable tag `stell22-p1-oneshot:node22`. The operator asks the local Docker daemon for `{{.Id}}` of that tag, then inspects that id again. Both values must be `sha256:` plus 64 lowercase hex digits and must be equal. Production accepts only the id in `/var/lib/stell22/p1-oneshot-image-pin.json` (`kind` = `PRODUCTION_ONESHOT_IMAGE_PIN`). The repository does not contain that file. Test-owned scope cannot read it. A test must pass `testApprovedOneShotImageId`, and a production request that carries that field stops with `INJECTED_PRODUCTION_DEPENDENCY`.

The approved id is part of the dossier canonical JSON, so the existing `dossierSha256` binds it. The signed payload keys are unchanged: `attemptId`, `daemonId`, `decision`, `dossierSha256`, `kind`, `nonce`, `notAfter`, `notBefore`, `operation`, `recoverySha256`, `scope`. The spawn argument is the digest, with `--pull never`. The tag is rejected if it appears in the argument list. The same observation is repeated after the plan is built and immediately before `authorize()`. A missing, malformed, unpinned, unapproved, or changed id stops with `spawned=false`, does not write the ambiguous-completion marker, and does not create the authorization replay marker.

P1-2. The public CLI prints one machine-readable line:

```text
verdict= code= phase= attempt= imageGitSha= oneShotImageId= dossierSha256= recoverySha256= recoveryEvidence= signingInputs= spawned= retryAttempted= targetClass=
```

`recoveryEvidence` is `NONE` or `VERIFIED`. `signingInputs` is `COMPLETE` only when the verdict is not `STOP` or `BLOCKED`, `recoveryEvidence` is `VERIFIED`, and both digests are 64-hex SHA-256. Otherwise a recovery hash is printed as `UNAVAILABLE`. A preflight dossier is `INCOMPLETE`. An early stop is `NOT_SIGNABLE`. The line does not contain the database password, `DATABASE_URL`, or a PostgreSQL URL.

The reviewed build recipe is `docker/p1-oneshot/`. The operator does not build or retag the image. Building or installing that image on a production host is a separate authorization. This package does not perform it on production.

## R2 — image identity and dependency risk

HEAD review of R1 required another rework before merge. `attachReviewedImageToOperatorTag` treated `stell22-p1-oneshot:node22` as the reviewed build when `RootFS.Layers` matched. Two images can share those layers and still differ in entrypoint, command, environment, user, or labels. R2 does not use rootfs equality.

The operator tag is created only when it is absent. It is reused only when `docker image inspect` returns the same image id as the build just produced. An id this process published may be replaced by a later build from this same process, and the replacement is recorded as `replaced-owned`. Any other existing id is rejected and the tag is not moved or deleted. Runtime checks run `docker run` against that image id, not against the mutable tag. Each action is appended to the in-process record: `built`, `tagged`, `reused`, `replaced-owned`, `rejected`, or `removed-owned`.

A test-owned tag is removed only when this process created it and the current id is still the expected id. That applies to the random `p1pa-oneshot-*` tag and, at the end of a disposable file, to `stell22-p1-oneshot:node22` if this process published it. A failed build removes the random tag only if that name was absent before the build and present afterward. A foreign tag is left in place.

### deepmerge-ts

`npm audit --omit=dev` on `docker/p1-oneshot` exits 1. The only advisory is GitHub advisory `1145093`, `GHSA-ggr8-5vv4-36mx`, `CVE-2026-40345`, high. It is `deepmerge-ts` `< 8.0.0`. The lockfile pins `deepmerge-ts@7.1.5` (`sha512-HOJkrhaYsweh+W+e74Yn7YStZOilkoPb6fycpwNLKzSPtruFs48nYis0zy5yJz1+ktUhHxoRDJ27RQAWLIJVJw==`) through `@prisma/config@6.19.3`. npm also marks `prisma@6.19.3` and `@prisma/config@6.19.3` high because they depend on that package. There is no second advisory id in that audit.

`@prisma/config@6.19.3` passes `deepmerge` to `c12` only while loading `prisma.config.*`. The published defect is stack exhaustion when both inputs contain a cycle at the same key. Plain JSON does not trigger it. This one-shot runs `prisma migrate deploy` on the pinned schema mount and a `DATABASE_URL` file. The repository has no `prisma.config.*`. Those inputs are not objects passed to `deepmerge`. A remote caller cannot supply a cyclic config through this command. The realistic effect, if a cyclic config were introduced later, is a crashed migrator process, not code execution.

`deepmerge-ts@8.0.0` is the patched release and a new major. `@prisma/config@6.19.3` depends on `7.1.5` exactly. This correction does not add an override and does not upgrade Prisma. That override is a separate compatibility decision and is not accepted here.

## Not in this package

P1-3 write-freeze is not implemented. The other Opus findings are not implemented: host-wide lock scope, crash-time secret handling, fingerprint parentheses, `lock_timeout`, restore runbook, and host runbook. P1 SQL, the historical migration inventory, SHADOW, ledger authority, and the production application are unchanged.

After the pre-spawn recheck, `authorize()` runs and then the container is created. A tag move cannot select a different image, because the argument is the digest. Deleting that digest in the interval after authorization and before the daemon creates the container can still consume the signature. That window is not closed by starting the container before authorization.
