## 1. EXECUTIVE VERDICT

DI-016 **подтверждён и требует повышения severity** относительно текущей карточки в
`audit/01-data-integrity-findings.md` (там `P3 / Business impact: Низкий`).

Три установленных факта:

1. **CONFIRMED RACE.** `createInventoryDraft` выполняет `findFirst({status:"DRAFT"})` и
   `inventory.create(...)` двумя независимыми запросами **вне какой-либо транзакции**, без
   блокировок и без DB-ограничения. Два параллельных вызова создают два DRAFT.
   Воспроизведено локально **без принудительного барьера** — обычным `Promise.all` (§7, опыт A).

2. **DI-009 защищает остаток, но НЕ защищает работоспособность.** Второй DRAFT после
   проведения первого почти всегда упирается в `STALE_SNAPSHOT` (§7, опыт C). Порчи склада нет.
   Но второй DRAFT остаётся навсегда: `accountedQty` не обновляется ни одним writer'ом,
   `updateInventoryLineActual` меняет только `actualQty`, а delete/cancel/close DRAFT
   **в приложении не существует**.

3. **Итог — отказ функции инвентаризации (denial of function), а не порча данных.**
   Застрявший DRAFT заставляет `createInventoryDraft` навсегда бросать
   «Черновик инвентаризации уже существует». Инвентаризация становится недоступна до
   ручной операции в БД. Воспроизведено (§7, опыт E).

Дополнительно найдена узкая, но реальная дыра в защите остатка: если первый DRAFT проведён
**с нулевым отклонением**, `assertLiveEqualsAccounted` для второго DRAFT проходит, и второй
документ выполняет собственный абсолютный SET (§7, опыт D). Это не «идемпотентный повтор тех
же actualQty», как утверждает текущая карточка DI-016, а второе независимое присвоение.

**Минимальный рекомендуемый fix:** partial UNIQUE index в PostgreSQL + обработка `P2002`
(вариант **D** в §11). Осуществимость подтверждена эмпирически на PostgreSQL 17 (§7, опыты F, G).

Ответы на вопросы §3 задания:

- **Где читается существующий DRAFT:** шаг 2, `findFirst`, отдельным запросом.
- **Внутри/снаружи транзакции:** **снаружи**. Между шагом 2 и шагом 6 нет ни одной
  транзакционной границы, охватывающей их обоих.
- **Какая isolation:** PostgreSQL default `READ COMMITTED`. Но здесь это неважно:
  два statement'а находятся в **разных** транзакциях (каждый — автокоммит), поэтому
  никакой уровень изоляции не связывает чтение с записью.
- **Lock / advisory lock / table lock:** отсутствуют полностью. `lockInventoryForUpdate`
  (`inventory-integrity.ts:135`) существует и используется в `updateInventoryLineActual:315`
  и `conductInventory:347`, но в `createInventoryDraft` **не вызывается** — и не может быть
  вызван осмысленно: блокировать нечего, строки ещё нет.
- **DB uniqueness:** отсутствует (§3.1, подтверждено на проде §8).
- **Могут ли две TX обе увидеть «DRAFT отсутствует» и обе вставить:** **да.**

### 4.1 Конкретный interleaving

```
T1: requireAdmin()                                        OK
T2: requireAdmin()                                        OK
T1: SELECT ... FROM "Inventory" WHERE status='DRAFT' LIMIT 1   → 0 строк
T2: SELECT ... FROM "Inventory" WHERE status='DRAFT' LIMIT 1   → 0 строк
T1: getWarehouseStock()                                   snapshot S1
T2: getWarehouseStock()                                   snapshot S2
T1: BEGIN; INSERT INTO "Inventory" (status='DRAFT') ...; INSERT "InventoryLine" ×N; COMMIT
T2: BEGIN; INSERT INTO "Inventory" (status='DRAFT') ...; INSERT "InventoryLine" ×N; COMMIT
--------------------------------------------------------------------------------
Результат: COUNT(*) WHERE status='DRAFT' = 2. Обе TX success. Ошибок PostgreSQL нет.
```

Окно гонки — не микросекунды: между шагом 2 и шагом 6 выполняется `getWarehouseStock()`
плюс (в режиме `includeAllActive`) полный `detail.findMany`. Окно — **десятки–сотни мс**.
Именно поэтому опыт A воспроизвёл гонку без искусственного барьера.

| Вход | Вызов | Файл |

## 6. CONCURRENCY RECONSTRUCTION

### 6.1 Гонка создания

См. §4.1. Обе TX успешны, ошибок PostgreSQL нет, в БД два DRAFT.
`READ COMMITTED` здесь не помогает и `SERIALIZABLE` бы тоже не помог: между чтением и
записью нет общей транзакции, а `findFirst` на пустом множестве не создаёт predicate-конфликта,
который SSI мог бы обнаружить — вставляются две **разные** строки без общего уникального ключа.

### 6.2 Что происходит дальше — цепочка проведения

Ключевой факт: `assertLiveEqualsAccounted` (`inventory-integrity.ts:287-295`) сравнивает
`live` с `accountedQty` **по каждой строке**. Оба DRAFT созданы примерно одновременно, поэтому
их `accountedQty` **одинаковы** (движений между созданиями нет — производство остановлено).

| Случай | Проведение A | live после A | Проведение B | Итог |
| --- | --- | --- | --- | --- |
| **A с отклонением** (100 → 95) | OK, SET 95 | 95 ≠ `B.accountedQty`=100 | **`STALE_SNAPSHOT`, zero writes** | склад верен (95); **B застрял DRAFT навсегда** |
| **A без отклонения** (100 → 100) | OK, SET 100 | 100 = `B.accountedQty`=100 | **проходит**, SET `B.actualQty` | **два CONDUCTED на один физический факт**; второй абсолютный SET перезаписывает первый |

Оба случая воспроизведены (§7, опыты C и D).

Смешанный документ (часть строк с отклонением, часть без) → `STALE_SNAPSHOT` на первой же
разошедшейся строке аварийно завершает **всю** TX B (`01.7` тест 3, «one stale among many
aborts whole doc»). То есть достаточно **одного** отклонения в A, чтобы B умер целиком.

### 6.3 Почему это тупик, а не неудобство

`STALE_SNAPSHOT`-сообщение говорит администратору: «Инвентаризацию необходимо
**обновить/создать заново**». Ни то, ни другое приложением не поддержано:

- **«обновить»** — writer'а, который перезапишет `accountedQty`, не существует (§5.2).
  `updateInventoryLineActual` меняет только `actualQty`, а guard сравнивает `accountedQty`.
  Сколько бы админ ни правил факт, `STALE_SNAPSHOT` останется.
- **«создать заново»** — `createInventoryDraft` видит застрявший DRAFT и бросает
  «Черновик инвентаризации уже существует».
- **удалить застрявший** — server action отсутствует, кнопки нет.

Замкнутый цикл. Выход только через прямой SQL / Prisma Studio на production-БД
(и с учётом `onDelete: Restrict` на `InventoryLine` — сначала строки, потом header).

### 6.4 Что видит UI

`docs` отсортированы `date desc`; `date` двух DRAFT различаются на миллисекунды или совпадают
(при равенстве порядок в PostgreSQL без tie-break **не определён**).

1. До проведения: `find(status==="DRAFT")` вернёт **один произвольный** из двух. Второй
   невидим — история его отфильтровывает. Админ считает и правит факт в том, который показан;
   второй документ содержит `actualQty == accountedQty` (prefill) и никак не отображается.
2. После проведения A: A уходит в историю, DRAFT B **становится видимым**. Админ видит
   черновик, которого не создавал, с уже заполненными «фактическими» = учётным.
3. Нажатие «Провести» на B → toast `STALE_SNAPSHOT`.
4. Попытка создать новый черновик → toast «Черновик инвентаризации уже существует».

Т.е. «потерять draft из UI» **можно** (шаг 1), и это же скрытие делает шаг 3–4 внезапным.

| Вопрос | Ответ |

| Оба snapshot `accountedQty` могут отличаться? | Практически — нет (производство остановлено, создания рядом). Теоретически да, если движения идут; тогда оба обречены на `STALE_SNAPSHOT`. |
| Update actual в обоих документах? | Да, `updateInventoryLineActual` работает по `lineId`, документ не проверяется на «видимость». Но UI показывает только один. |
| Conduct первого | Успешен. |
| Conduct второго после первого | `STALE_SNAPSHOT`, если A изменил хоть один остаток; **успешен**, если A прошёл без отклонений. |
| DI-009 `STALE_SNAPSHOT` остановит второй? | **Не всегда.** Останавливает только при фактическом изменении остатка. |
| Может ли второй провести тот же физический факт? | Да — при нулевом отклонении A (опыт D). |
| Может ли второй стать валидным после изменения `actualQty`? | **Нет.** Guard смотрит `accountedQty`, а его изменить нельзя. |

### 11.1 Осуществимость в PostgreSQL — проверено эмпирически

Оба варианта индекса создаются без ошибок на PostgreSQL 17 (опыт F):

- `ON "Inventory" ((true)) WHERE status = 'DRAFT'` — константное выражение принимается;
- `ON "Inventory" (status) WHERE status = 'DRAFT'` — **предпочтительный**.

Второй лучше по двум причинам: (1) Prisma отдаёт `P2002` с `target = ['status']` —
стабильный дискриминатор, как в тестах DI-003/DI-010 «Prisma error exposes a stable
discriminator»; (2) `indexdef` читается однозначно при аудите. Функционально оба
эквивалентны: из-за `WHERE` в индексе может быть максимум одна строка.

### 11.2 Почему A и C отклонены

**A** не даёт корректности без `LOCK TABLE ... ACCESS EXCLUSIVE`, а держать такой lock
на протяжении `getWarehouseStock()` — это блокировка чтений таблицы на всё время сборки
черновика. Цена не соответствует задаче.

**C** корректен, но защита живёт в соглашении «все writer'ы берут lock». В проекте уже
есть канонический порядок блокировок для conduct (`lockInventoryStockRows`); добавление
ещё одного lock-объекта в другой code path — источник будущих deadlock-регрессий.
Ни одного advisory lock в проекте сейчас нет — вводить новый примитив ради одного случая
неоправданно.

| 2 | `createDraft ‖ updateActual` | `updateActual` работает по `lineId` существующего документа; новый create создаёт другие строки. Пересечения нет | **нет находки** |
| 3 | `createDraft` сразу после conduct | Корректно: индекс (после fix) освобождён, `findFirst` не видит DRAFT, snapshot берётся с уже скорректированного склада. Проверено (опыт F) | **EXPECTED** |
| 4 | ordering / `findFirst` ambiguity | `findFirst({where:{status:"DRAFT"}})` **без `orderBy`** (`:246`); UI `find` по `date desc` без tie-break. При двух DRAFT выбор не детерминирован | поглощается fix'ом DI-016 (двух DRAFT не будет) |
| 5 | orphan DRAFT после закрытия браузера | Черновик живёт бессрочно. На проде подтверждён 59-дневный открытый DRAFT (§8.5). Сам по себе безвреден: DI-009 не даст провести устаревший | **EXPECTED / INTENTIONAL** (нет TTL — намеренно) |
| 6 | **отсутствие cancel / delete DRAFT** | Writer'а нет (§5.2). В сочетании с (a) отказом `createInventoryDraft` при существующем DRAFT и (b) `STALE_SNAPSHOT` из DI-009 образует **тупик без выхода из UI** (§6.3, опыт E). **DB-unique из §12 этот тупик НЕ устраняет** — он лишь убирает один из способов в него попасть; путь из строки 1 остаётся | **CONFIRMED BUG — отдельная карточка, кандидат DI-022** |
| 7 | `CLOSED` без writer'а | Enum-значение недостижимо; присутствует в типах, UI-лейблах, моках | **зафиксировано, не чинится** |
| 8 | нет unique на `InventoryLine(inventoryId, refType, refId)` | Дубликат строки в одном документе схемой не запрещён. Внутри `createInventoryDraft` не достижим (источники не пересекаются), но `BlankStock`-aliasing уже описан в `01.6` §f-6 | **DESIGN RISK** — уже покрыто `01.6`, карточка не открывается |

Строки 1 и 6 — **один и тот же** дефект восстановления (нет способа выбросить/обновить
непроводимый DRAFT). Он **не входит** в DI-016 и требует отдельной карточки; DI-016
закрывает только уникальность.

Не рассматривалось (прямой запрет задания): warehouse ledger, inventory counted UX,
WIP/НЗП, CashFlow, marketplace, production cost, re-review DI-009.

## 15. OPEN OWNER DECISIONS

По самому инварианту решение **не требуется**: «максимум одна глобальная DRAFT» однозначно
следует из кода, UI и зафиксированных решений владельца (§2).

Требуется **одно** решение — об объёме:

> **Вопрос.** Partial UNIQUE закрывает гонку создания, но не устраняет тупик
> «непроводимый DRAFT нельзя ни обновить, ни удалить, ни заменить» — в него можно попасть
> и без гонки (§14, строка 1). Что делать?
>
> 1. **DI-016 = только partial UNIQUE + P2002** (§12). Тупик оформляется отдельной карточкой
>    (DI-022) и решается позже. *Последствие:* минимальный, полностью обратимый деплой;
>    но если тупик наступит до DI-022, восстановление — ручной SQL на проде.
> 2. **DI-016 = partial UNIQUE + admin-действие «Удалить черновик»** (delete DRAFT: удалить
>    строки, затем header, ChangeLog, только `requireAdmin`, только для `status='DRAFT'`).
>    *Последствие:* +1 server action, +1 UI-кнопка, +тесты; тупик закрывается сразу и
>    инвентаризация перестаёт быть блокируемой. Объём вырастает примерно вдвое.
> 3. **DI-016 = partial UNIQUE + «Обновить учётные остатки в черновике»** (перезапись
>    `accountedQty` из живого склада). *Последствие:* прямо отвечает тексту ошибки
>    `STALE_SNAPSHOT` («обновить/создать заново»), но это **новый writer, меняющий snapshot**,
>    т.е. касается семантики DI-009 — потребуется отдельная проверка инвариантов.

Рекомендация аудита: **вариант 2**. Он оставляет DI-009 нетронутым (в отличие от 3) и
делает результат DI-016 практически полезным (в отличие от 1). Но это решение владельца,
а не вывод из кода.
