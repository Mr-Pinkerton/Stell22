**Дата:** 2026-09-05
**Статус:** IMPLEMENTATION APPROVED. Review-правки ниже обязательны до кода.
**Базовый commit:** `1f411e5e0f8018069e9f91d69439ff306fdc2572` (DI-009 CLOSED / DEPLOYED).
**Аудит-основание:** `audit/01.8-inventory-draft-uniqueness-review.md`.
**DI-009 остаётся CLOSED и не перепроектируется.**

### Review corrections (перед кодом)

1. **`deleteDraft || createDraft`.** Дружелюбный `findFirst` в `createInventoryDraft` делает валидными **оба** исхода: (A) delete коммитится первым → create доходит до INSERT → новый DRAFT успешен; (B) precheck `create` видит ещё живой DRAFT → контролируемое «Черновик инвентаризации уже существует». Если INSERT доходит до БД, пока delete не закоммичен, partial UNIQUE может ждать xid удаления и затем успеть (delete commit) или дать `P2002` (delete rollback) → доменное сообщение. Тест 10 **не** требует, чтобы create всегда успевал. Инвариант: `COUNT(DRAFT) <= 1`, нет сырого `P2002`, нет orphan-состояния.
2. **Torn `getWarehouseStock` snapshot.** Не называть это «без конкурентности». Классификация: **DESIGN RISK / SEPARATE RACE**. Conduct (или иное изменение остатка) между несколькими чтениями внутри `getWarehouseStock` может дать неатомарный snapshot. **Вне DI-016.** `deleteDraft` снимает операционный тупик, но **не** делает snapshot атомарным. В этой реализации **не чинить**.

## Зафиксированные решения владельца

| ID | Решение |
| --- | --- |
| **BD-16.1** | Одновременно может существовать **максимум одна глобальная** `Inventory` со `status = DRAFT`. |
| **BD-16.2** | Инвариант обеспечивается **на уровне БД** через PostgreSQL partial UNIQUE. `findFirst` в приложении остаётся только дружелюбной предпроверкой. Проигравший в гонке получает **существующее доменное сообщение**, не сырой `P2002`. |
| **BD-16.3** | Администратор может **удалить** DRAFT-инвентаризацию. Удаление трогает только `Inventory` + её `InventoryLine`. **Не** мутирует `ProductStock` / `DetailStock` / `BlankStock` / `NomenclatureStock` / `RailLot`, **не** создаёт корректировку, **не** трогает production-операции и **не** трогает исторические CONDUCTED. |
| **BD-16.4** | CONDUCTED **immutable**: нельзя удалить, отменить, переоткрыть, обновить, превратить в DRAFT. |

## 1. DB INVARIANT

### 1.1 Фактическое SQL-представление enum

`prisma/migrations/20260629154204_init/migration.sql`:

```sql
-- :32
CREATE TYPE "InventoryStatus" AS ENUM ('DRAFT', 'CONDUCTED', 'CLOSED');
-- :266-273
CREATE TABLE "Inventory" (
    "id" TEXT NOT NULL,
    "date" TIMESTAMP(3) NOT NULL,
    "status" "InventoryStatus" NOT NULL DEFAULT 'DRAFT',
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "Inventory_pkey" PRIMARY KEY ("id")
);
```

`status` — **нативный PostgreSQL enum-тип** `"InventoryStatus"`, `NOT NULL`.
Литерал `'DRAFT'` приводится к enum неявно; приведение immutable, поэтому предикат
допустим в partial index. **[проверено]**

### 1.2 Целевой инвариант

```
COUNT(*) FROM "Inventory" WHERE status = 'DRAFT'  <=  1
```

Scope — **GLOBAL**. В модели `Inventory` нет ни одного scope-поля
(warehouse / location / site / organization / period) — `audit/01.8` §3.1, §3.4.
Новый scope не вводится.

### 1.3 Точное имя и форма индекса

**Имя: `Inventory_status_draft_key`.**
Соответствует принятому в проекте шаблону `<Table>_<column>_<condition>_key`:
`Product_skuOzon_active_key`, `Product_skuWb_active_key` (DI-010),
`BatchCost_batchId_final_key` (DI-005), `Account_accountNumber_key` (DI-003).

```sql
CREATE UNIQUE INDEX "Inventory_status_draft_key"
  ON "Inventory" ("status")
  WHERE "status" = 'DRAFT';
```

Как PostgreSQL сохраняет и отдаёт это в `pg_indexes.indexdef` **[проверено]**:

```
CREATE UNIQUE INDEX "Inventory_status_draft_key" ON public."Inventory"
  USING btree (status) WHERE (status = 'DRAFT'::"InventoryStatus")
```

Именно эту строку следует ожидать в post-deploy проверке (§11.3): PostgreSQL
нормализует предикат, добавляя явный каст к enum-типу. Совпадения байт-в-байт с текстом
миграции **не будет** — сравнивать нужно по `indexname` и по наличию `WHERE`.

Индекс частичный, поэтому:

- строк со `status = 'CONDUCTED'` может быть **сколько угодно** — 3 CONDUCTED одновременно
  созданы под индексом без ошибки **[проверено]**;
- `status = 'CLOSED'` не ограничен (значение всё равно недостижимо, `01.8` §3.3);
- переход `DRAFT → CONDUCTED` **освобождает** индекс: следующий черновик создаётся
  нормально **[проверено]**.

### 1.4 Почему НЕ `@@unique` в Prisma

Prisma-схема **не умеет** выражать частичное условие (`WHERE`). `@@unique([status])`
означал бы «уникальность по всем строкам», что запретило бы два CONDUCTED и сломало
всю историю инвентаризаций. Поэтому:

- **`@@unique` не добавляется.**
- Индекс живёт только в SQL-миграции.
- В `schema.prisma` над `model Inventory` добавляется **комментарий** — точно по образцу
  уже существующего `Account.accountNumber` (`schema.prisma:556-557`):

```prisma
model Inventory {
  id     String          @id @default(cuid())
  date   DateTime
  // BD-16.1: не более одной DRAFT одновременно. Обеспечено partial UNIQUE
  // Inventory_status_draft_key WHERE status = 'DRAFT' (Prisma не выражает
  // частичное условие). CONDUCTED/CLOSED не ограничены.
  status InventoryStatus @default(DRAFT)
  ...
}
```

Это **не** изменение модели: ни полей, ни атрибутов, ни типов. `prisma generate`
результат не меняет, drift не возникает.

### 1.5 Ожидаемое поведение Prisma при нарушении

**[проверено]** — точная форма ошибки при втором DRAFT:

| Свойство | Значение |
| --- | --- |
| Класс | `Prisma.PrismaClientKnownRequestError` |
| `code` | `"P2002"` |
| `meta` | `{"modelName":"Inventory","target":["status"]}` |
| `meta.target` | `["status"]` — **массив строк**, `Array.isArray === true` |

Идентичная форма получена и при вложенном `create` с `lines` (реальный вызов из
`createInventoryDraft`), и при плоском `create`. Для контраста — постороннее нарушение
(DI-010, `Product.skuOzon`) даёт `{"modelName":"Product","target":["skuOzon"]}`,
т.е. **различимо по обоим полям**. Это основание для матчера в §4.

Конкурентная вставка под индексом: один INSERT успешен, второй — `P2002`,
итог `COUNT(DRAFT) = 1` **[проверено, `01.8` §7 опыт G]**.

## 2. MIGRATION SAFETY

**Файл (создать на этапе реализации, не сейчас):**
`prisma/migrations/<timestamp>_di016_inventory_single_draft/migration.sql`

Стиль — ровно как `20260904170000_batchcost_final_unique` / `20260904151000_di010_active_sku_unique`:
один явный `BEGIN/COMMIT` (Prisma 6 classic PostgreSQL `migration.sql` **не** оборачивается
в транзакцию автоматически), `LOCK TABLE ... ACCESS EXCLUSIVE`, `DO $$ ... RAISE EXCEPTION`,
без `CONCURRENTLY`.

```sql
-- DI-016 / BD-16.1: partial UNIQUE — не более одной Inventory со status = 'DRAFT'.
-- LOCK + recheck + RAISE при >1 DRAFT. Без auto-delete / auto-conduct / выбора «победителя».
-- Одна явная транзакция PostgreSQL: Prisma 6 classic PostgreSQL migration.sql
-- не оборачивается в транзакцию автоматически.
-- Без CREATE INDEX CONCURRENTLY (несовместимо с транзакцией и с LOCK-моделью).

BEGIN;

LOCK TABLE "Inventory" IN ACCESS EXCLUSIVE MODE;

DO $$
DECLARE
  dup   text;
  n_dup integer;
BEGIN
  SELECT count(*) INTO n_dup FROM "Inventory" WHERE status = 'DRAFT';

  IF n_dup > 1 THEN
    SELECT string_agg(
             format(
               'id=%s status=%s createdAt=%s date=%s lines=%s',
               i.id,
               i.status,
               i."createdAt",
               i.date,
               (SELECT count(*) FROM "InventoryLine" l WHERE l."inventoryId" = i.id)
             ),
             '; ' ORDER BY i."createdAt", i.id
           )
    INTO dup
    FROM "Inventory" i
    WHERE i.status = 'DRAFT';

    RAISE EXCEPTION
      'DI-016: % DRAFT inventories exist, expected <= 1: %; resolve before migrate (no auto-delete/auto-conduct)',
      n_dup, dup;
  END IF;
END $$;

CREATE UNIQUE INDEX "Inventory_status_draft_key"
  ON "Inventory" ("status")
  WHERE "status" = 'DRAFT';

COMMIT;
```

### 2.1 Почему `LOCK TABLE ... ACCESS EXCLUSIVE` нужен

`CREATE UNIQUE INDEX` (без `CONCURRENTLY`) сам берёт `SHARE` на таблицу, что **не**
блокирует пишущих до момента взятия. Явный `ACCESS EXCLUSIVE` перед recheck закрывает
окно «проверили 1 DRAFT → кто-то вставил второй → индекс падает на середине».
Так же сделано в DI-003/DI-005/DI-010.

### 2.2 Что миграция НЕ делает

- **NO auto-delete** лишних DRAFT;
- **NO auto-conduct**;
- **NO auto-selection of winner** — не выбирает «правильный» черновик;
- **NO DML вообще** — только `LOCK`, `SELECT` внутри `DO`, `CREATE INDEX`;
- не трогает CONDUCTED, не переписывает `Inventory.date` (BD-9.6, `01.7` §3).

### 2.3 Rollback implications

Deploy **не откатывает миграции автоматически** (`scripts/deploy.sh`, `ci-prod-remote.sh`:
стадия `deploy` вызывает `migrate deploy` через entrypoint контейнера; стадии
автоматического DB-rollback нет). Последствия:

| Сценарий | Итог |
| --- | --- |
| Миграция упала на `RAISE` (>1 DRAFT) | Вся транзакция откачена, **индекс не создан**, БД в исходном состоянии. Deploy падает. Безопасно. |
| Миграция применилась, код откатили на предыдущий SHA | **Совместимо.** Старый `createInventoryDraft` намеренно не создаёт второй DRAFT (у него есть `findFirst`-guard). В недостижимом для него сценарии гонки он получит сырой `P2002` вместо доменного текста — это ухудшение текста ошибки, не поломка. Старый код `deleteInventoryDraft` не вызывает — функции просто нет в UI. |
| Нужен ручной откат индекса | `DROP INDEX IF EXISTS "Inventory_status_draft_key";` — без потери данных, без пересчётов. |

Миграция **аддитивна** (только `CREATE INDEX`), поэтому forward-only deploy-модель
проекта её принимает без специальных мер.

### 2.4 Фактический риск на сегодня

Production: **0 DRAFT** (`01.8` §8.1, read-only recheck 2026-09-05). Recheck внутри
миграции пройдёт, `RAISE` не сработает, индекс применится без вмешательства.

Место: после блока `DI-005: duplicate BatchCost FINAL`, до финального

```bash
# --- DI-016: more than one DRAFT inventory ---
draft_n="$(psql_q "$(
  cat <<'SQL'
SELECT count(*) FROM "Inventory" WHERE status = 'DRAFT';
SQL
)" | tr -d '[:space:]')"

if ! [[ "$draft_n" =~ ^[0-9]+$ ]]; then
  echo "PRECHECK FAILED" >&2

fi

  failed=1
  echo "DI-016: ${draft_n} DRAFT inventories (expected <= 1). STOP. Do not migrate/delete/conduct." >&2
  echo "id / status / createdAt / date / line count:" >&2
  psql_q "$(
    cat <<'SQL'
SELECT i.id || ' / ' || i.status || ' / ' || i."createdAt"::text || ' / ' || i.date::text || ' / ' ||
       (SELECT COUNT(*) FROM "InventoryLine" l WHERE l."inventoryId" = i.id)::text

WHERE i.status = 'DRAFT'
ORDER BY i."createdAt", i.id;
SQL
  )" >&2

```

| Условие | Итог |
| --- | --- |
| `0` DRAFT | **PASS** |
| `1` DRAFT | **PASS** (штатное состояние — открытый черновик) |
| `> 1` DRAFT | **STOP deployment**, печать `id / status / createdAt / date / InventoryLine count`, exit 1 через общий `PRECHECK FAILED` |

Preflight запускается **до checkout** и материализуется из `EXPECTED_SHA`

self-contained: использует только `psql_q`, `failed`, стандартные кавычки — совместим
с материализацией во временный каталог.

Дублирующий recheck внутри миграции (§2) обязателен: между preflight и `migrate deploy`
есть окно (checkout + сборка образа).

## 4. `createInventoryDraft`

Файл: `src/server/warehouse.ts:244-299`. Изменение **минимальное и локальное**.

### 4.1 Что остаётся без изменений

- `await requireAdmin()` первым исполняемым statement (`:245`);
- `findFirst({ where: { status: "DRAFT" } })` + throw (`:246-247`) — **остаётся**
  как дружелюбная предпроверка. Она закрывает 100 % последовательных случаев
  (обычный повторный клик, второй админ через секунду) и делает так, что путь
  `P2002` — редкое исключение, а не штатный;
- `getWarehouseStock()`, сборка строк, `writeChangeLog`, `revalidatePath`, возвращаемый
  `serializeDoc(...)`.

### 4.2 Что добавляется

Корректность после предпроверки обеспечивает **только DB-unique**. Поэтому единственный
`prisma.inventory.create(...)` (`:275-291`) оборачивается в `try/catch`:

```ts
let doc;
try {
  doc = await prisma.inventory.create({ /* ... без изменений ... */ });
} catch (err) {
  if (isDraftUniqueViolation(err)) throw new Error(DRAFT_ALREADY_EXISTS);
  throw err;
}
```

**Область `try` — ровно один statement.** Ни `getWarehouseStock()`, ни
`detail.findMany`, ни `writeChangeLog`, ни `revalidatePath` внутрь не попадают.
Это ключевое свойство: любое `P2002`, вылетевшее из этого блока, физически может
происходить только из вставки `Inventory`/`InventoryLine`.

### 4.3 Матчер

Основан на **[проверено]** форме `meta` (§1.5). Место — `src/server/internal/inventory-integrity.ts`,
рядом с уже живущими там доменными константами `STALE_SNAPSHOT`, `ALREADY_CONDUCTED`,
`INVENTORY_BOUNDARY`. Добавление **аддитивно**, поведение DI-009 не меняется.

```ts
export const DRAFT_ALREADY_EXISTS = "Черновик инвентаризации уже существует";

/**
 * BD-16.2: нарушение partial UNIQUE Inventory_status_draft_key.
 * Проверено на PostgreSQL 17 / Prisma 6: meta = { modelName: "Inventory", target: ["status"] }.
 */
export function isDraftUniqueViolation(err: unknown): boolean {
  if (!(err instanceof Prisma.PrismaClientKnownRequestError)) return false;
  if (err.code !== "P2002") return false;
  const meta = err.meta as { modelName?: unknown; target?: unknown } | undefined;
  if (meta?.modelName !== "Inventory") return false;
  return Array.isArray(meta.target) && meta.target.includes("status");
}
```

**Почему это не превращает посторонние `P2002` в «черновик уже существует»:**
матчер требует одновременно `modelName === "Inventory"` **и** `target ∋ "status"`.
Постороннее нарушение DI-010 даёт `modelName: "Product"`, `target: ["skuOzon"]`
**[проверено]** — не проходит. Других unique-ограничений на `Inventory` со `status`
в целевой колонке не существует и не планируется.

### 4.4 Безопасный узкий fallback

Если в будущей версии Prisma `meta.modelName` или `meta.target` окажутся ненадёжны
(изменится форма — Prisma этого не гарантирует контрактом), деградация безопасна
**именно из-за §4.2**: внутри `try` — единственная вставка. Единственные unique-ограничения,
достижимые из неё, — `Inventory_pkey`, `InventoryLine_pkey` (коллизия `cuid()`,
практически невозможна) и новый `Inventory_status_draft_key`.

Fallback (применять только если основной матчер перестал срабатывать, зафиксировав
это тестом 3):

```ts
// Fallback: узкая область try (одна вставка Inventory) делает P2002 однозначным.
if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === "P2002") { ... }
```

Порядок предпочтений: (1) `modelName` + `target`; (2) при отсутствии `modelName` —
только `target ∋ "status"`; (3) при отсутствии обоих — «`P2002` в этом узком блоке».
Реализовывать сразу вариант (1); (2)/(3) — задокументированный путь деградации,
не код.

### 4.5 Текст сообщения

BD-16.2 требует **существующее** доменное сообщение. Фактический текст в коде
(`warehouse.ts:247`) — **«Черновик инвентаризации уже существует»** (в задании он приведён
сокращённо как «Черновик уже существует»). Использовать точный существующий текст,
UX не меняется ни в одном сценарии. Обе точки (предпроверка `:247` и `catch`) должны
ссылаться на **одну** константу `DRAFT_ALREADY_EXISTS`, чтобы тест 3 мог сравнивать
строку без дублирования литерала.

## 5. `deleteInventoryDraft`

Новое admin server action в `src/server/warehouse.ts` (модуль уже `"use server"`).

### 5.1 Критичный факт о FK

FK объявлен **`ON DELETE RESTRICT`** — явно, не по умолчанию:

```sql
-- 20260629154204_init/migration.sql:567
ALTER TABLE "InventoryLine" ADD CONSTRAINT "InventoryLine_inventoryId_fkey"
  FOREIGN KEY ("inventoryId") REFERENCES "Inventory"("id")
  ON DELETE RESTRICT ON UPDATE CASCADE;
```

Подтверждено в живой БД: `pg_constraint.confdeltype = 'r'` **[проверено]**.

Следствие: `prisma.inventory.delete()` при непустых строках падает с
**`P2003`**, `meta = {"modelName":"Inventory","constraint":"InventoryLine_inventoryId_fkey"}`
**[проверено]**. Каскада **нет**.

**Вывод: удаление строк обязано быть явным**, `inventoryLine.deleteMany` **до**
`inventory.delete`. Порядок «строки → заголовок» проверен, отрабатывает чисто
(0 строк, 0 документов) **[проверено]**. FK **не менять** — это была бы правка схемы
вне scope, и `RESTRICT` здесь полезен как страховка от случайного удаления заголовка.

### 5.2 Дизайн

```ts
/**
 * BD-16.3: удаление черновика инвентаризации. Складские остатки НЕ меняются:
 * DRAFT ничего не применял. CONDUCTED удалить нельзя (BD-16.4).
 * BD-16.5: устаревший (STALE_SNAPSHOT) черновик удаляется и создаётся заново;
 * accountedQty никогда не перезаписывается.
 */
export async function deleteInventoryDraft(docId: string): Promise<void> {
  await requireAdmin();

  await prisma.$transaction(async (tx) => {
    const locked = await lockInventoryForUpdate(tx, docId);          // 1
    if (!locked) throw new Error("Инвентаризация не найдена");       // 2
    if (locked.status !== "DRAFT") throw new Error(ALREADY_CONDUCTED); // 3

    const lines = await tx.inventoryLine.count({ where: { inventoryId: docId } });

    await tx.inventoryLine.deleteMany({ where: { inventoryId: docId } }); // 5
    await tx.inventory.delete({ where: { id: docId } });                  // 4

    await writeChangeLog(                                            // 6
      { entity: "Inventory", entityId: docId, oldValues: { status: "DRAFT", lines } },
      tx,
    );
  });                                                                 // 7 commit

  revalidatePath(PATH);                                               // 8
}
```

| Требование | Реализация |
| --- | --- |
| `requireAdmin` первым исполняемым | строка 1 тела, до любого обращения к БД. Требование `check-server-action-source.mjs` (`startsWithGuard(..., "requireAdmin")`) выполнено |
| lock `Inventory` FOR UPDATE | `lockInventoryForUpdate(tx, docId)` — **тот же** мьютекс, что у `conductInventory:347` и `updateInventoryLineActual:315` (`inventory-integrity.ts:135`, `SELECT ... FOR UPDATE`) |
| not found → controlled | `"Инвентаризация не найдена"` — существующий текст (`warehouse.ts:316`, `:348`, `:355`) |
| `status !== DRAFT` → reject | `ALREADY_CONDUCTED` = «Инвентаризация уже проведена» — существующая константа. Покрывает CONDUCTED и (недостижимый) CLOSED |
| удаляется только DRAFT | гарантировано шагом 3 **под блокировкой строки** |
| `InventoryLine` | явный `deleteMany` (§5.1) — каскада нет |
| ChangeLog в той же TX | `writeChangeLog(..., tx)` |
| revalidate после commit | `revalidatePath(PATH)` вне `$transaction` |
| stock-локи | **не берутся** — записей в stock нет (BD-16.3). Обоснование в §6 |
| возвращаемый тип | `void`; UI убирает документ из локального состояния |

Порядок внутри TX: `deleteMany` (строки) → `delete` (заголовок) — иначе `P2003`.

### 5.3 Чего действие НЕ делает (BD-16.3, проверяется тестом 6)

Ни одного обращения к `productStock`, `detailStock`, `blankStock`, `nomenclatureStock`,
`railLot`, `productionOperation`, `operationDetailLine`, `operationNomenclatureLine`,
`batch`, `batchCost`, `payment`, `cashFlow`. Никаких `lockInventoryStockRows`,

## 6. CONCURRENCY SEMANTICS

Все четыре сценария разобраны до сериализуемых исходов. Общая основа: **три из четырёх
writer'ов держат один и тот же мьютекс** — `SELECT ... FROM "Inventory" WHERE id = $1 FOR UPDATE`.
`createInventoryDraft` — единственный, кто его не держит (блокировать нечего, строки нет);
за него отвечает partial UNIQUE.

### A) `create || create`

| | |
| --- | --- |
| Механика | Оба проходят `findFirst` (оба видят «нет DRAFT»), оба вставляют. Второй INSERT конфликтует по `Inventory_status_draft_key`. |
| Исход | **Ровно один DRAFT.** Одна операция успешна; вторая получает `P2002` → матчер (§4.3) → **«Черновик инвентаризации уже существует»**. |
| Доказательство | `01.8` §7 опыт G: `outcomes: ['ok', 'P2002 target=status']`, `DRAFT count = 1` **[проверено]**. До индекса тот же сценарий давал 2 DRAFT (опыт A/B). |
| Zero partial state | Вложенный `create` (заголовок + строки) — одна неявная TX Prisma; при конфликте не остаётся ни заголовка, ни строк. |

### B) `delete || conduct` одного DRAFT

Оба берут `Inventory FOR UPDATE` на **одну и ту же** строку → строгая сериализация.

| Победитель | Проигравший | Итог |
| --- | --- | --- |
| **conduct** | `delete` ждёт lock; после commit conduct перечитывает строку под блокировкой и видит `status = 'CONDUCTED'` → шаг 3 → `ALREADY_CONDUCTED`, **zero writes** | Документ остаётся **CONDUCTED**, остатки скорректированы один раз, строки целы. BD-16.4 соблюдён |
| **delete** | `conduct` ждёт lock; после commit delete строки **нет** → `lockInventoryForUpdate` вернёт `null` → `"Инвентаризация не найдена"`, **zero stock writes** | Документа нет, **ни одной записи в stock**. `conduct` падает до `lockInventoryStockRows` и до `assertLiveEqualsAccounted` |

Критично: проверка `status` в `delete` выполняется **после** `FOR UPDATE`, а не до —
иначе TOCTOU. В `conduct` дополнительно есть атомарный `updateMany where status='DRAFT'`
+ `count !== 1` (`warehouse.ts:434-438`), который остаётся нетронутым.

Deadlock невозможен: `delete` берёт **ровно один** объект блокировки (`Inventory`),
т.е. не может образовать цикл с канонической цепочкой `conduct`
(`Inventory` → `Detail` → `BlankStock` → `NomenclatureStock` → `ProductStock`).
`delete` — префикс этой цепочки.

### C) `delete || updateActual`

Тот же мьютекс `Inventory FOR UPDATE` (`updateInventoryLineActual:315`).

| Победитель | Проигравший | Итог |
| --- | --- | --- |
| **updateActual** | `delete` ждёт; после commit видит `status = 'DRAFT'` → удаляет документ **целиком**, вместе с только что записанным `actualQty`. **Разрешено** (BD-16.3/16.5: черновик — не факт учёта) | Документа нет. Потери данных учёта нет: DRAFT ничего не применял |
| **delete** | `updateActual` ждёт; после commit `delete`: сначала `inventoryLine.findUnique` (`:309`) вернёт `null` → `"Строка не найдена"`. Если строка была прочитана до commit — `lockInventoryForUpdate` вернёт `null` → `"Инвентаризация не найдена"`. В обоих случаях **zero writes** | Документа нет |

**No partial surviving lines** гарантировано: `deleteMany` + `delete` в одной TX;
`updateActual` пишет только `actualQty` существующей строки и не создаёт строк.
Осиротевших `InventoryLine` не возникает ни в одной сериализации — FK `RESTRICT`
дополнительно исключает удаление заголовка при живых строках.

### D) `delete` старого DRAFT `||` `create` нового DRAFT

Единственный сценарий, где participants **не** делят мьютекс: `create` не блокирует
строку старого документа. Дружелюбный `findFirst` **и** partial UNIQUE оба участвуют.
Тест 10 **не** требует, чтобы `create` всегда успевал.

Валидные сериализации:

| | Исход | Почему |
| --- | --- | --- |
| **A** | delete коммитится первым → create доходит до INSERT → новый DRAFT успешен | индекс свободен |
| **B** | `findFirst` create видит ещё живой DRAFT (до commit delete) → **«Черновик инвентаризации уже существует»** | предпроверка, не ошибка БД |
| **C** | INSERT доходит до БД, пока delete не закоммичен | PostgreSQL ждёт xid удаления. Delete **commit** → INSERT успешен. Delete **rollback** → `P2002` → матчер §4.3 → то же доменное сообщение |

Инвариант во всех случаях: `COUNT(DRAFT) <= 1`; проигравший create **никогда** не отдаёт
сырой `P2002`; orphan `InventoryLine` нет.

Штатный UI-порядок последовательный (удалить → затем создать). Гонка — нештатный
тайминг двух вкладок/админов.

## 8. CHANGELOG

Конвенция проекта для удаления — **`oldValues` = состояние до, `newValues` отсутствует**
(`writeChangeLog` JSDoc `change-log.ts:15`: «Состояние после изменения (для delete — null)»).
Эталон в коде — `deleteBatch` (`purchases.ts:493-497`): пишет только `oldValues`,
`newValues` не передаёт вовсе.

Дизайн для удаления черновика:

```ts
await writeChangeLog(
  {
    entity: "Inventory",
    entityId: docId,
    oldValues: { status: "DRAFT", lines: lineCount },
    // newValues намеренно отсутствует → NULL = удаление (конвенция deleteBatch)
  },
  tx,
);
```

Что делает запись однозначной:

| Требование задания | Как обеспечено |
| --- | --- |
| entity `Inventory` | `entity: "Inventory"` |
| inventory id | `entityId: docId` |
| prior status `DRAFT` | `oldValues.status = "DRAFT"` |
| line count | `oldValues.lines = <count до удаления>` |
| deletion reason/type | `newValues IS NULL` при непустом `oldValues` = удаление. Различимо от остальных двух событий `Inventory` (см. таблицу ниже) |

Все три события `entity = "Inventory"` различимы без новых полей:

| Событие | `oldValues` | `newValues` |
| --- | --- | --- |
| создание DRAFT (`:292`) | — (null) | `{ status: "DRAFT", lines: N }` |
| проведение (`:440`) | `{ status: "DRAFT" }` | `{ status: "CONDUCTED", lines: N }` |
| **удаление DRAFT (новое)** | `{ status: "DRAFT", lines: N }` | — (**null**) |

- **Никакого фиктивного лога корректировки склада** — ни одной записи с
  `before`/`after`/`delta`, потому что склад не менялся.
- **Per-line ChangeLog не пишется.** Действующая конвенция требует его только при
  проведении (BD-9.6: `InventoryLine` — SoT корректировки, `conductInventory:449-470`).
  При удалении корректировки нет, поэтому per-line записи были бы шумом. Совпадает с
  `deleteBatch`, который не логирует удаляемые дочерние строки.
- Запись выполняется **внутри той же TX** (`writeChangeLog(..., tx)`), т.е. лог не
  может остаться без удаления и наоборот. Это строже, чем `createInventoryDraft`,
  который пишет лог вне TX (`:292`) — существующее поведение не меняем.
- `userId` не передаётся — как во всех остальных вызовах `writeChangeLog` в
  `warehouse.ts` (сохраняется `null`).

## 11. DEPLOY

### 11.1 Последовательность

Штатный поток `scripts/ci-prod-remote.sh` уже даёт нужный порядок; новых стадий не требуется.

| # | Шаг | Механика |
| --- | --- | --- |
| 1 | **preflight на текущем проде** | стадия `preflight`: `git show "${EXPECTED_SHA}:scripts/preflight-prod.sh"` во временный каталог → `bash`. Новый DI-016-блок берётся из **нового** SHA и выполняется **до** checkout. `> 1 DRAFT` → `PRECHECK FAILED`, deploy останавливается, БД не тронута |
| 2 | **фиксация SHA** | `PREVIOUS_SHA="$(git rev-parse HEAD)"` до checkout; стадия `checkout`: `git reset --hard "$EXPECTED_SHA"` |
| 3 | **миграция** | стадия `deploy` → `scripts/deploy.sh` шаг «[3/5] Сборка и запуск (migrate deploy выполнит entrypoint контейнера)». Recheck внутри миграции — второй барьер |
| 4 | **деплой приложения** | тот же шаг: сборка образа + перезапуск `app` |
| 5 | **verify SHA** | стадия `verify`: `deployed_sha == EXPECTED_SHA` |
| 6 | **health** | стадия `health`: `fetch(/api/health)` изнутри контейнера |
| 7 | **post-deploy read-only проверка** | вручную, §11.3. Только `SELECT` |

Автоматического DB-rollback нет (§2.3) — это учтено: миграция аддитивна и обратима
одним `DROP INDEX`.

### 11.2 Порядок «миграция перед кодом» безопасен

Индекс появляется раньше нового кода приложения (миграция выполняется entrypoint'ом
при старте контейнера новой сборки). В окне, когда индекс есть, а старый код ещё
жив, поведение корректно: старый `createInventoryDraft` не создаёт второй DRAFT
намеренно; в невозможном для него сценарии гонки получит сырой `P2002` вместо
доменного текста. Порчи данных нет.

### 11.3 Post-deploy read-only SELECT

Через уже используемый безопасный путь: `docker compose -f docker-compose.prod.yml
exec -T db psql -U stell22 -d stell22` при `SET default_transaction_read_only = on`.
**Ни одной записи.**

```sql
SET default_transaction_read_only = on;
SHOW default_transaction_read_only;              -- ожидается: on

-- 1. счётчики по статусам
SELECT status, count(*) FROM "Inventory" GROUP BY status ORDER BY status;

-- 2. инвариант BD-16.1 (ожидается 0 или 1)
SELECT count(*) AS draft_count FROM "Inventory" WHERE status = 'DRAFT';

-- 3. запрос дубликатов (ожидается 0 строк)
SELECT count(*) AS duplicate_drafts
FROM (SELECT 1 FROM "Inventory" WHERE status = 'DRAFT') d
HAVING count(*) > 1;

-- 4. индекс существует и он частичный + уникальный
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'Inventory'
ORDER BY indexname;
-- ожидается строка Inventory_status_draft_key с
--   USING btree (status) WHERE (status = 'DRAFT'::"InventoryStatus")

-- 5. осиротевшие InventoryLine (ожидается 0; FK RESTRICT это и так исключает —
--    запрос осмыслен как контроль, что deleteInventoryDraft не оставляет мусор)
SELECT count(*) AS orphan_lines
FROM "InventoryLine" l
LEFT JOIN "Inventory" i ON i.id = l."inventoryId"
WHERE i.id IS NULL;

-- 6. миграция зарегистрирована
SELECT migration_name, finished_at
FROM "_prisma_migrations"
ORDER BY finished_at DESC
LIMIT 3;
```

Критерии приёмки: `draft_count <= 1`; `duplicate_drafts` — 0 строк;
`Inventory_status_draft_key` присутствует и содержит `WHERE`; `orphan_lines = 0`;
миграция `di016_inventory_single_draft` в списке применённых.

Ожидаемое стартовое состояние (по `01.8` §8): `CONDUCTED 1`, `DRAFT 0`,
`InventoryLine 0` → все проверки проходят тривиально.

### 12.3 Соседние находки — НЕ в этом объёме

**DESIGN RISK / SEPARATE RACE — torn `getWarehouseStock` snapshot.** Не называть это
«без конкурентности». `getWarehouseStock` делает несколько независимых чтений
(`Promise.all` product/detail/blank/nomenclature stock). Conduct или иное изменение
остатка **между** этими чтениями даёт неатомарный snapshot DRAFT. **Вне DI-016.**
Partial UNIQUE и `deleteDraft` **не** делают snapshot атомарным. Операционный тупик
(непроводимый DRAFT без выхода из UI) снимается удалением черновика; атомарность
чтения — отдельная карточка. **Не чинить в этой реализации.**
