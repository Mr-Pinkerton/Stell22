## 2. Final server behavior

`deleteProductionOperation` remains server authority.

Order:

```text
TX
→ lock ProductionOperation
→ load operation
→ paid guard
→ assertPhysicalProductionDeleteAllowed
→ physical reverse by type   (unreachable for TORCOVKA / PRISADKA / UPAKOVKA)
→ hard delete                (HOURS only in this package)
```

End-state server policy:

```text
TORCOVKA  → BLOCK  (existing TORCOVKA_GENERIC_DELETE_BLOCKED)
PRISADKA  → BLOCK  (PRISADKA_PHYSICAL_DELETE_BLOCKED)
UPAKOVKA  → BLOCK  (UPAKOVKA_PHYSICAL_DELETE_BLOCKED)
HOURS     → ALLOW
```

Rejection happens after the operation row is locked and loaded, and **before any physical reverse**. No partial stock mutation occurs on D/E/F rejection.

Helper: `src/lib/production-physical-delete-policy.ts`. This is a narrow shared policy, not a lifecycle framework. Existing TORCOVKA rails message remains valid and is not reused for PRISADKA/UPAKOVKA.

Dead TORCOVKA reverse code is left unreachable.

## 4. G — `deleteBatch` transaction contract

Lock order: **RailLot → Batch**. Do not reverse to Batch → RailLot.

```text
retryOnLockSetChange
  → BEGIN
  → discover candidate RailLot ids for Batch
  → canonical sort
  → lockRailLots
  → lockBatches
  → verify Batch exists
  → re-read current RailLot id set
  → compare candidate set vs current set
  → if changed: LockSetChangedError / retry from scratch
  → evaluate production_cost_flow guard (inside TX)
  → count ProductionOperation inside TX
  → count DealItem inside TX
  → re-read locked RailLots
  → require EVERY remainingQuantity === 0
  → delete permitted BatchCost / RailLot / Batch
  → commit
```

Existing primitives only: `lockRailLots`, `lockBatches`, `sortedUniqueIds`, `sameSortedIds`, `LockSetChangedError`, `retryOnLockSetChange`.

Quantity guard is `remainingQuantity !== 0` (rejects positive and injected/legacy negative). Zero-balance lots may be deleted. No InventoryMovement is emitted.

Preserved inside TX:

```text
production_cost_flow ACTIVE → reject
ProductionOperation count > 0 → reject
DealItem count > 0 → reject
```

Batch parent lock is the serialization anchor for concurrent FK-linked inserts. Even if a DB FK action would technically allow/set-null, the application contract remains: existing operation/deal association → Batch deletion forbidden.

## 5. H — `deleteDetail` transaction contract

```text
BEGIN
→ lock Detail parent FOR UPDATE
→ verify Detail exists
→ re-check ProductDetail usage inside TX
→ lock all existing DetailStock rows for detailId
   ORDER BY id FOR UPDATE
→ re-read DetailStock
→ read/evaluate production_cost_flow
→ apply ACTIVE / INACTIVE guard
→ delete allowed zero stock rows
→ delete Detail
→ commit
```

Parent `Detail FOR UPDATE` is the serialization anchor against concurrent `DetailStock` / `ProductDetail` creation (`ON DELETE RESTRICT` on both FKs). Existing DetailStock rows are still explicitly locked. Parent lock is not replaced by child-only locks.

INACTIVE:

```text
ProductDetail count === 0
AND every DetailStock.quantity === 0
```

Zero DetailStock rows may be removed before deleting Detail. `quantity !== 0` (including injected negative) rejects.

ACTIVE:

```text
ANY DetailStock row → reject
```

even if quantity is zero. ACTIVE is not weakened to quantity-only.

Authoritative ProductDetail check is inside the TX. No outside-TX usage count.
