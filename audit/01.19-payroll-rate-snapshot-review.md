## 3. EARNING FORMULA BY OPERATION TYPE

Единый калькулятор: `operationEarning` (`src/lib/payroll.ts` ~142–172). Округление: JS `number`, затем `Math.round(n * 100) / 100` (**не** Decimal.js) — только итоговая сумма операции.

Чистые `pieceworkEarning` / `hourlyEarning` / `totalSalary` — Decimal, используются тестами и концептуально; **runtime журнал/ЗП/выплата/с/с операции** идут через `operationEarning`.

### 3.1 TORCOVKA

```
quantity = Σ line.quantity
amount   = round2( Σ line.quantity × (line.sort === SORT2 ? rateTorcovkaSort2 : rateTorcovkaSort1) )
```

- Sort линии: `blankSort ?? detailSort[detailId]` (`payroll.ts` `computeOp` ~74–76; `production.ts` `computeAmount` ~87–88). У terminal create `blankSort = p.sort` всегда.
- **Одна операция может содержать SORT1 + SORT2.** Юнит-тест `payroll.test.ts` (10×SORT1 + 5×SORT2). Prod ChangeLog удалённых TORCOVKA (2026-09-01/02) содержит picks обоих сортов в одной Op.
- Считается **по строкам**, не одной ставкой на Op.
- Batch / rail / сечение **не** входят в формулу ЗП.
- `railsTaken` на earning не влияет (влияет на отход/склад). `correctTorcovkaRailsTaken` ставку не трогает.

### 3.2 PRISADKA

```
quantity = Σ line.quantity
amount   = round2( Σ line.quantity × (
             (prisadkaTorcevaya ? ratePrisadkaTorcev : 0)
           + (prisadkaPloskost  ? ratePrisadkaPlosk  : 0)
           ))
```

- Торцевая/плоскостная — флаги на `OperationDetailLine`, не тип операции.
- Terminal `PrisadkaInput.picks[].kind` = `"torcev" | "plosk"` (взаимоисключающе на **одном pick**).
- `applyPrisadkaPick` ставит ровно один флаг (`production-reversal.ts` ~52–53, ~88–89). Writer **никогда** не ставит оба флага на одну линию.
- **Одна операция может содержать оба kind** (несколько picks). Тогда нужны **две** ставки.
- `operationEarning` *умеет* суммировать оба флага на одной линии (тест 4× оба + 2× torcev). Это защита формулы, не текущий writer-path.
- Сорт детали / batch на ставку не влияют.
- Правка qty: `kind = line.prisadkaTorcevaya ? "torcev" : "plosk"` (`production.ts` ~306) — если бы оба флага были true, edit схлопнул бы в torcev. Не баг DI-015; writer не создаёт такие линии.

Расхождение cost vs payroll (не DI-015, зафиксировать): `actualProductionRates` для PRISADKA — `if torcevaya … else if ploskost` (не сумма). Payroll `operationEarning` суммирует флаги. На текущем exclusive-kind writer оба пути совпадают.

### 3.3 UPAKOVKA

```
quantity = productQty
amount   = round2(productQty × rateUpakovka)
```

- Одна ставка на изделие, qty-based.
- UI может отправить несколько изделий; server создаёт **отдельную** `ProductionOperation` на каждый `productId` (`submitUpakovka` ~1255–1266, `clientRequestId:${productId}`).
- `OperationDetailLine` / nomenclature lines у упаковки — **провенанс склада**, не earning. `serializeRow` их в UI не показывает.

### 3.4 HOURS

```
quantity = hours          // Decimal(8,2) → number
amount   = round2(hours × hourlyRate)
```

- Не сдельная. Preview на терминале (`hours-screen.tsx`) — `hours * (employee.hourlyRate ?? 0)` только UX; SoT — server.
- Backdate «за вчера» — **нет** (нет поля даты).

### 3.5 Не «просто qty × rate»

Для TORCOVKA/PRISADKA — сумма по линиям с **разными** ставками. Для UPAKOVKA/HOURS — да, одна ставка × одно qty/hours, после `round2`.

## 9. CONCURRENCY: RATE CHANGE || SUBMIT

`updateEmployee` (`employees.ts` ~123–148): `findUnique` + `update` **без** `$transaction` и без `FOR UPDATE`. Row-lock берёт сам `UPDATE`. ChangeLog после update, вне общей TX с update (щель аудита, не DI-015).

Ни один terminal submit **не** читает и **не** лочит Employee для rates. Таблицы в `lockTableIds`: Account, Deal, Batch, ProductionOperation, RailLot. **Employee в lock-graph нет.**

Изоляция: PostgreSQL READ COMMITTED (Prisma default).

Интерливинг без lock:

```
T1 submit: BEGIN; … SELECT rates (20) …
T2 admin:  UPDATE Employee SET rate=25; COMMIT
T1 submit: INSERT Op storing 20; COMMIT
```

Op **принята после** смены ставки, но хранит 20. Это нарушает «ставка в момент, когда операция принята» (commit успешной TX).

`SELECT` без `FOR UPDATE` внутри TX **недостаточен**.

**Рекомендуемая граница:** `SELECT … FROM "Employee" WHERE id = $id FOR UPDATE` внутри успешной submit TX **после** существующих stock-lock'ов, **до** INSERT Op. Snapshot = значения, прочитанные под этим lock, записанные в том же commit.

Порядок (Employee **после** существующих stock-lock'ов, **до** INSERT Op — иначе snapshot не попадёт в тот же INSERT):

```
TORCOVKA:  RailLot → (optional TorcovkaApproval) → Employee → deduct rails → INSERT Op+snapshots → BlankStock
PRISADKA:  Details → Employee → INSERT Op+snapshots → picks
UPAKOVKA:  prepare all picks + lockDetails (union, sorted) → Employee → loop INSERT Op+snapshots + applyUpakovkaPrepared
HOURS:     Employee → INSERT Op+snapshots → ChangeLog
```

**UPAKOVKA нельзя** лочить Employee в начале TX до Details: сейчас `applyUpakovkaPick` берёт `lockDetails` **после** `create`. Если сначала залочить Employee, получится Employee → Details, а `submitPrisadka` будет Details → Employee → **deadlock**. Реализация обязана **переставить** UPAKOVKA: stock-lock всех picks **до** Employee (повторный `lockDetails` внутри `applyUpakovkaPrepared` в той же TX безопасен).

`updateEmployee` других таблиц не лочит → цикл Employee↔RailLot **не** возникает: submit держит RailLot затем Employee; admin держит только Employee.

**Не** лочить Employee в `markEmployeePaid` (после фикса читает snapshots с уже залоченных Ops). Payroll order `ProductionOperation → Batch` не инвертировать. Freeze/DI-014 не трогать.

`markEmployeePaid` сегодня: lock Ops → reread facts → `buildRefMaps` (live Employee, **без** lock) → amount. Окно «смена ставки между lock Ops и read Employee» существует; после snapshot исчезает само.

Deadlock risk добавления Employee last: **LOW** при текущем графе.

## 13. PAID REPORT DAY BREAKDOWN

```162:178:src/server/payroll.ts
  const paidRows: SalaryReportRow[] = payments.map((p) => {
    const items = p.items
      .map((i) => computed.get(i.operationId))
```

`computed` построен **до** этого из live rates по **всем** ops. Итог paid-строки = `Payment.amount` (стабилен). `days[].torcovka/prisadka/upakovka/hours/total` = live `operationEarning`. После смены ставки:

После фикса: days из snapshots; drift ставок исчезает.

Оставшийся rounding (уже есть, не баг DI-015):

- per-op `round2`;
- Payment = `round2(Σ op.amount)`;
- day.total = `round2(Σ op.amount that day)`.

`Σ day.total` vs `Payment.amount` может отличаться на копейки из-за дневного `round2`. Документировать, не менять rounding в этом этапе.
