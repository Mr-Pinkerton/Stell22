## Isolation

Each run generates a UUID and names the container, volume, and network `stell22-p1wf-<uuid>` with a matching label. Passwords are random, are passed with `--env-file`, and are redacted from captured output. The harness refuses `stell22-db-prod`, `stell22-app`, `stell22-caddy`, a Compose project label, and a port published outside `127.0.0.1`. This image publishes no port. SQL runs with `docker exec` into the container id returned by `docker run`. Before each statement the harness re-reads the Docker endpoint, daemon id, inspect identity, and a database comment that stores the run id.

The database inside that container is named `stell22`. That name is safe only because the container is the one this run created. The existing disposable runner still refuses a database named `stell22` on its own targets. This harness does not weaken that refusal.

## Cleanup ownership

HEAD review `6247664583` rejected the first proof harness. Its failure path listed containers by label and removed every returned id, then removed the volume and network by name. `Config.Image` and the immutable image id were refused only when both differed, so one matching field hid the other. That cleanup is no longer in the harness.

Normal destroy and failure cleanup now use one function. It re-reads the Docker endpoint and daemon id before it inspects a resource and again before it removes that resource. A change, or an unreadable endpoint, stops the cleanup. Nothing is removed on the new daemon.

A container is removed only when `docker run` returned a full id, a later inspect of that exact id succeeded, and the inspect matches all of the following: the id, the expected name, the run label, the expected volume, the expected network, `Config.Image` equal to `postgres:17-alpine`, and the immutable image id captured before `docker run`. Either image mismatch refuses the container. A Compose project label or a production name also refuses it. The harness does not list containers by label and does not remove by name alone.

If `docker run` fails, returns no id, or returns a malformed id, the container is `AMBIGUOUS`. The volume and network created for that attempt are left in place, because an unconfirmed container may still hold them. An inspect failure, a malformed inspect document, or an identity mismatch also leaves the container, volume, and network in place.

A volume or network is removed only after its own inspect matches the name and run label and it is not a Compose or production resource. A network with any other container attached is left in place. A failed removal is recorded once and is not retried. The harness does not prune.

These refusal cases are unit-tested with a fake Docker executor. The tests assert that an uncertain or foreign resource receives no `rm`, `volume rm`, `network rm`, label scan, or `prune`. A confirmed owned container is removed by the captured id. Disposable passwords are not placed in `docker exec` arguments. This audit record does not contain a password.

## Bootstrap

`POSTGRES_USER=stell22` produced role `stell22` with oid 10 and `rolsuper = true`. There was no role named `postgres`. Databases `postgres`, `template0`, and `template1` existed. Those are database names.

`BEGIN; CREATE ROLE p1wf_demote_probe NOLOGIN; ALTER ROLE stell22 NOSUPERUSER; COMMIT` failed with SQLSTATE `0A000`. The server detail says the bootstrap superuser must have the `SUPERUSER` attribute. The location was `AlterRole, user.c:867`. After the failure, `stell22` was still a superuser and `p1wf_demote_probe` did not exist. psql exited 3 because `ON_ERROR_STOP` was set.

A second login role with `SUPERUSER` connected on its own. It created and dropped a probe role. It can terminate an application backend. The application role cannot `CREATE ROLE` (`42501`) and cannot `pg_terminate_backend` a superuser backend (`42501`).

Loss of the break-glass password blocks that login. It does not block `stell22`, because the bootstrap role remains a superuser. A cutover is blocked for a session that has neither secret. It is not blocked for whoever still has the bootstrap password. The classifier does not repair that state.

## Authentication

`pg_hba_file_rules` on this image includes `127.0.0.1|trust`, `::1|trust`, and `all|scram-sha-256`. A wrong password over `127.0.0.1` from inside the container still connects. A wrong password over the container's bridge address fails the client with `password authentication failed`. After `log_error_verbosity = verbose`, the server log contains SQLSTATE `28P01`. The client message at connection time does not include that code. A correct password over the bridge address connects. Trust on loopback is not a passed or failed privilege canary.

## Transactions

On disposable roles and tables, one transaction created a role, altered it, created a table, transferred ownership, granted `SELECT`, and set `ALTER DEFAULT PRIVILEGES`. Commit made all of those visible. Rollback of a later table, revoke, and default-privilege change left the prior grant and removed the new table.

`CREATE DATABASE` inside `BEGIN` failed with SQLSTATE `25001`. The database was absent afterward. `ALTER DATABASE ... OWNER TO` and `ALTER SCHEMA public OWNER TO` committed inside one transaction to the migrator. That is not `CREATE DATABASE`.

`REVOKE` of the application role's write privileges committed while two application transactions were already open. The transaction that had already inserted a row then `COMMIT`ted that row. Revoke did not undo it. `pg_terminate_backend` on the other open transaction returned `true`, the backend disappeared, and its uncommitted insert was absent. A logical row snapshot showed the difference. Equal row counts would not have shown the superuser `UPDATE` below.

## Three roles and the freeze

The application role and the migrator were `LOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS`, and `NOINHERIT`. Neither was `stell22`. There was no membership between the application role, the migrator, and the break-glass role. `SET ROLE` from the application role to either of the others failed with `42501`.

Before the revoke, an application `INSERT` committed. After the revoke and the termination, a new application connection could `SELECT`. `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `nextval`, `setval`, `CREATE TABLE`, and `ALTER TABLE` failed with `42501`.

These later grants, each made by a superuser and then removed, let the application write anyway:

- `GRANT UPDATE (qty)` let it update that column.
- `GRANT INSERT ... TO PUBLIC` let it insert.
- `GRANT` of the migrator role let `SET ROLE` succeed and insert.
- A `SECURITY INVOKER` function failed with `42501`.
- A `SECURITY DEFINER` function owned by the migrator inserted a row.

The migrator, still a non-superuser and still the owner, ran the pinned P1 file bytes. Those bytes are git blob `3e54eaaae450f76edf75163024bebf4d7d70c358` and SHA-256 `47ff9c932aea0a692b81ecfaf6c4a931b431e3e332e3e9c5b3fca96694550fe5`. The working tree checkout on this Windows machine is not those bytes; the test reads `git show` so it does not execute a line-ending conversion and does not edit the file. The application role's attempt failed with `42501`. The migrator inserted into a fixture `_prisma_migrations` table. The application role's insert failed with `42501`.

Restoring ordinary `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, and sequence `USAGE`/`SELECT`/`UPDATE` made an application insert succeed. `rolsuper` stayed false. The table owner stayed the migrator.

`pg_dump --no-owner --no-acl --table=public.p1wf_stock` as the application role exited 0 and contained the committed held row. The same dump of the sequence, after its privileges were revoked, exited non-zero. A second disposable database on the same cluster restored the table dump, and the held row was present. `scripts/backup-db.sh` still defaults to user `stell22`. That script was not changed. On this evidence a frozen application role can dump the tested table and cannot dump the sequence.

## Classification

The pure classifier returns `repair: none` for every case below. It does not grant privileges back.

| Observed case | Class |
| --- | --- |
| Privilege transaction not started, or rolled back | `NORMAL` |
| Revoke committed, application backend still open, canary not run | `REVOKE_COMMITTED` |
| Revoke committed, backends gone, new login writes denied | `FROZEN_VERIFIED` |
| Operator died after commit, catalog unreadable, grants unknown, unexpected superuser write, missing break-glass login, canary write succeeded, or authentication failed | `UNCERTAIN` |
| Ordinary DML granted again, application still not superuser, migrator still owner, write succeeded | `UNFREEZE_AUTHORIZED` |

## What this supports

The disposable results support the database mechanics in candidate Design D. They do not accept it. They do not approve a permanent production role split.

They confirm three limits the candidate already has to treat as gates: the bootstrap superuser cannot be demoted; a superuser session can write during the freeze and can install the bypasses above; an already-executed insert can commit after `REVOKE` until that backend is terminated. None of those results is a reason to demote `stell22`.
