## 3. Lock / write order (implement literally)

**No-code EXTREME must not skip RailLot / post-lock replay.**

Counterexample the old draft allowed: T1 commits Op+consume with a valid code; T2 (same id, no code) skipped the stock TX, called `ensurePendingApproval`, saw `consumedAt`, and could error instead of `CREATED`.

```

  clientRequestId = requireClientRequestId(...)
  validate rails/picks (existing)

  const code = parseApprovalCode(input.approvalCode) // 4 digits or null

  txResult = prisma.$transaction:
    fast ProductionOperation.findUnique(clientRequestId)
      → IDEMPOTENT_REPLAY

    lockRailLots([railLotId])
    post-lock ProductionOperation.findUnique(clientRequestId)
      → IDEMPOTENT_REPLAY

    lot/batch reads
    physics / INV-008
    compute waste metrics

    NORMAL:
      existing path (stock / create / changelog)

    SUSPICIOUS:

      return APPROVAL_NEEDED
      ZERO writes
      NO TorcovkaApproval lock
      NO Notification write

    EXTREME and code !== null:

      verify current row (not expired, attempts<5, snapshot matches,
        HMAC matches, employeeId matches, not consumed)
      wrong HMAC → increment failedAttempts; return WRONG_CODE (commit this increment; no stock)

      consumedAt set → should be unreachable if post-lock Op replay worked;

      else:

        create Op (band HIGH_WASTE, reason null, note null)
        consumedAt = now()
        redact Notification immediately in this same TX
          (“Код использован.” — no digits)
        writeChangeLog without code
        archiveBatchIfDepleted
        return CREATED_NEW

After stock TX:

  if IDEMPOTENT_REPLAY or CREATED_NEW:
    public CREATED

  if APPROVAL_NEEDED:

    opNow = await prisma.productionOperation.findUnique({
      where: { clientRequestId },
      select: { id: true },

    if (opNow) public CREATED                   // commit became visible during ensure
    else public APPROVAL_REQUIRED (expiresAt from ensure; no code)

  if WRONG_CODE && attempts < 5:
    throw "Неверный код подтверждения"

  if WRONG_CODE && attempts >= 5:

    if (opNow) public CREATED

    UI copy: "Старый код больше не действует. Запросите новый код у администратора."
    never return the new code

  if EXPIRED or METRICS_CHANGED:
    ensure = await ensurePendingApproval(...)   // rotate
    opNow = findUnique Op
    if (opNow) public CREATED
    else public APPROVAL_REQUIRED
```

The post-ensure Op recheck is **required** so a consume that committed while `ensurePendingApproval` ran still yields `CREATED`.

`ensurePendingApproval` TX: `TorcovkaApproval` `FOR UPDATE` (if row exists) + Notification write/redact. **No** `lockRailLots`.

Stock TX with a code: `lockRailLots` **then** `TorcovkaApproval FOR UPDATE`. No inverse.

## 3b. `ensurePendingApproval` — lock existing row before rotate

`UNIQUE(clientRequestId)` serializes **initial INSERT** only. Concurrent **rotation** of an existing row requires `FOR UPDATE`.

Race without the lock: generation=1 expired; T1 and T2 both read gen 1; T1 writes code A gen 2; T2 writes code B gen 2; row hash may be B while Notification gen 2 still has plaintext A (`notifyEvent` first-write-wins). Unusable approval.

```ts
type EnsureResult =
  | { kind: "PENDING"; expiresAt: Date; created: boolean }
  | { kind: "CONSUMED" };

export async function ensurePendingApproval(args: SnapshotArgs): Promise<EnsureResult> {
  return prisma.$transaction(async (tx) => {
    let existing = await tx.$queryRaw<TorcovkaApproval[]>`
      SELECT * FROM "TorcovkaApproval"
      WHERE "clientRequestId" = ${args.clientRequestId}
      FOR UPDATE`;
    // Prisma equivalent: findUnique is not enough; use
    // findUnique + interactive TX only after locking, e.g.
    // $queryRaw FOR UPDATE or findFirst with a documented lock helper.

    if (existing.length === 0) {
      try {
        const code = generateApprovalCode();
        const row = await tx.torcovkaApproval.create({ data: { generation: 1, ...hash, notify key gen 1 } });
        await notifyEvent({ key: row.notificationKey, message: formatMsg({ code, expiresAt }), ... }, tx);
        return { kind: "PENDING", expiresAt: row.expiresAt, created: true };
      } catch (e) {
        if (!isUniqueViolation(e)) throw e;
        // P2002: do NOT unlocked-update. Retry/re-enter this helper
        // so the existing row is taken FOR UPDATE.
        throw new RetryEnsureError();
      }
    }

    const row = existing[0];
    const now = new Date();

    // Re-evaluate AFTER the lock:
    if (row.consumedAt) {
      return { kind: "CONSUMED" }; // not a public error
    }

    const pending =
      row.expiresAt > now &&
      row.failedAttempts < TORCOVKA_APPROVAL_MAX_ATTEMPTS &&
      !snapshotDiffers(row, args);

    if (pending) {
      return { kind: "PENDING", expiresAt: row.expiresAt, created: false };
      // no new code, no Notification
    }

    // expired / attempts>=5 / metrics changed — ONE TX, one new code:
    const code = generateApprovalCode();
    const generation = row.generation + 1;
    const notificationKey = `event:torcovka-approval:${args.clientRequestId}:${generation}`;
    await updateEventMessage(row.notificationKey, "Код истёк. Смотрите новое уведомление.", tx);
    const updated = await tx.torcovkaApproval.update({
      where: { clientRequestId: args.clientRequestId },
      data: {
        generation,
        ...fresh snapshot...,
        codeHash: hashApprovalCode(code, secret),
        failedAttempts: 0,
        createdAt: now,
        expiresAt: new Date(now.getTime() + TORCOVKA_APPROVAL_TTL_MS),
        consumedAt: null,
        notificationKey,
      },
    });
    await notifyEvent({
      key: notificationKey,
      title: "Требуется подтверждение высокого отхода",
      message: formatApprovalMessage({ ...args, code, expiresAt: updated.expiresAt }),
      tone: "ERROR",
    }, tx);
    return { kind: "PENDING", expiresAt: updated.expiresAt, created: true };
  });
}

// Caller wraps RetryEnsureError in a small retry loop (same as lock-set retry).
```

On `CONSUMED`: caller **must not** rotate. Read `ProductionOperation` by `clientRequestId`.

- Op exists → public `CREATED`.
- Op missing → **invariant anomaly**: controlled server error, **STOP**. Do **not** issue a new code.

**Expiry vs plaintext in the bell (locked):**

- No cron. `expiresAt` is the **only** validity clock.
- An expired code is **rejected** even if the old Notification still shows digits.
- Successful consume: redact Notification **immediately in the stock TX** (`Код использован.` — no digits).
- Rotate (expiry / 5 attempts / metrics change): redact the **old** Notification **before** creating the new one, in the **same** ensure TX.
- Background cleanup is **not** required.

```ts
import { createHmac, randomInt, timingSafeEqual } from "node:crypto";

export function generateApprovalCode(): string {
  return String(randomInt(0, 10000)).padStart(4, "0");
}

export function parseApprovalCode(raw: unknown): string | null {
  if (typeof raw !== "string") return null;
  const d = raw.trim();
  if (!/^\d{4}$/.test(d)) return null;
  return d;
}

export function hashApprovalCode(code: string, secret: string): string {
  return createHmac("sha256", secret).update(code, "utf8").digest("hex");
}

export function approvalCodeMatches(code: string, codeHash: string, secret: string): boolean {
  const a = Buffer.from(hashApprovalCode(code, secret), "hex");
  const b = Buffer.from(codeHash, "hex");
  if (a.length !== b.length) return false;
  return timingSafeEqual(a, b);
}
```

Secret: same `SESSION_SECRET` already used for JWT (do not add a new env unless owner asks).

### Task 5: Integrity + unit + concurrency gates

**Files:** `src/server/integrity/di-020.integrity.test.ts`, `di-007-008.integrity.test.ts`

Functional:

1. EXTREME no code → `APPROVAL_REQUIRED`, remaining unchanged, no Op, **one** Notification.
2. Same id second call no code → still one notification, same generation.
3. Wrong code 1–4 → error `Неверный код подтверждения`, Op still 0, same generation.
4. 5th wrong code → generation+1, second notification, old message redacted, public `APPROVAL_REQUIRED` (not a generic wrong-code-only outcome).
5. Valid code → `CREATED`, `consumedAt` set, remaining decremented, reason null, band `HIGH_WASTE`, notification redacted in that TX.

**Required concurrency tests (must be in the implementation, not optional):**

**A. INITIAL CREATE RACE**  
Two concurrent no-code EXTREME requests, same `clientRequestId`.

Expected:

- one `TorcovkaApproval` row
- `generation = 1`
- one Notification
- both public `APPROVAL_REQUIRED`, **or** one `CREATED` only if another operation genuinely committed
- Notification plaintext code verifies against current `codeHash`

**B. ROTATION RACE — CRITICAL**  
Existing **expired** approval `generation = 1`. Two concurrent requests trigger rotation.

Expected:

- `generation` exactly **2**, not 3
- exactly one new Notification for generation 2
- plaintext from that Notification verifies against current `codeHash`
- old notification redacted
- no mismatched notification/hash

This test **must fail** if the existing approval row is not locked `FOR UPDATE`.

**C. CONSUME VS NO-CODE RETRY**  
T1: correct code, same `clientRequestId`, successful stock TX.  
T2: same `clientRequestId`, no code, concurrent.

Expected:

- both ultimately `CREATED` if T2 passes the RailLot serialization point after T1 commits
- never «Операция уже подтверждена»
- never `APPROVAL_REQUIRED` after T2 has observed the committed operation

**D. CONSUME VS ROTATE**

- If stock TX locks approval first and consumes: `ensurePendingApproval` waits, then sees `CONSUMED` and does **not** rotate.
- If ensure locks approval first for a **legitimate** expiry rotation: stock TX waits and verifies the **resulting current** generation.
- No deadlock: ensure **never** requests RailLot.
