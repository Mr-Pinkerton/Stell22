## 1. Executive summary

Stell22 already tracks **quantity** along the production chain. It does not move **money** with that quantity. 03.01 showed why the live report is not factual SKU cost.

**Target:** value moves with stock, **by component**.

```
input stock components + piece labor + nomenclature
  = output stock components + explicit loss
```

**Pooled production stock** stores **aggregate value components** (not a single `totalValue` as SoT):

| Pool | Components |
| --- | --- |
| `BlankStock` | `materialValue`, `laborValue` |
| `DetailStock` | `materialValue`, `laborValue` |
| `NomenclatureStock` | `nomenclatureValue` |
| `ProductStock` | `materialValue`, `laborValue`, `nomenclatureValue` |
| `RailLot` | `remainingValue` (raw material only; lot-identified, not a mixed WAC pool) |

**`totalValue` recommendation: A — stored and integrity-checked as the sum of components.** One UPDATE writes qty + every component + `totalValue` + `costVersion`. `COMP-001` fails closed if they drift. **Do not store unit WAC.**

Consume **every component proportionally**. Last-unit consume takes the exact residual of **each** component.

**NEW MODELS = 2:** `CostPeriod` (authoritative month close) and `CostEvent` (losses, purchase variance, bootstrap, explicit manual correction). `ProductCost` already exists and is activated as SKU freeze **belonging to** a `CostPeriod`. **No `EmployeeDayCost` table.**

**HOURS:** piece labor enters stock **only when a piece-rate snapshot exists**. Allocated HOURS do **not** enter Blank/Detail/Product pools. Monthly HOURS monetary pool is summed at `closeMonth` from `ProductionOperation` HOURS × DI-015 `hourlyRateSnapshot` (Decimal). Employee/day analytics are a **read-model** over those same ops — not persisted, not a second money SoT. The ₽/unit **benchmark** is period piece-paid WAC, not the worker’s own missing piece rate.

**Raw wood:** `C` on RailLots via `priceSort1/2 × purchased volume`. TORCOVKA moves only consumed rails. Kerf absorbed into blank **materialValue**. Cutover: `BOOTSTRAP_RAW_TRANSFER` balances RAW-001 without injecting money into current WIP.

**Reversal:** conservative exact reverse. Each fungible pool has monotonic `costVersion`. Normal unpaid edit/delete is allowed only when the output pool version still equals the version stored on the op immediately after its receipt. Then reverse **stored** components exactly. If the pool mutated later: **block**. No current-WAC reverse. No `REVERSAL_VARIANCE` on the ordinary production path. Qty ≥ produced is **not** identity.

## 5. Raw wood valuation

### 5.1 Initial allocation (createBatch / first sync)

Let `C = Batch.totalCost`, `area = sectionAreaM2(width, height)`.

For each RailLot `i`:

```
V_i = lengthM_i × quantity_i × area
W_i = priceSort(sort_i) × V_i
```

```
if Σ V = 0: error (no lots)
if Σ W = 0: share_i = V_i / Σ V
else:       share_i = W_i / Σ W
```

Persistence residual is assigned to the deterministic largest-positive economic-weight lot; zero-share lots never receive residual. `Σ initialValue = C` exactly at persistence scale.

```
RailLot.initialValue    = allocated
RailLot.remainingValue  = allocated
```

Idle lots hold money (fixes COST-001). Lot is **identified**; not a species WAC pool.

### 5.2 Consume N rails (TORCOVKA)

Lock `RailLot`.

```
if N > remainingQuantity: fail
if N == remainingQuantity:
  consumedValue = remainingValue
  remainingValue = 0
else:
  consumedValue = remainingValue × N / remainingQuantity
  remainingValue -= consumedValue
remainingQuantity -= N
```

Store `consumedRawValue` on the TORCOVKA op for RAW-001, exact monetary attribution, and exact `railsTaken` correction. Ordinary delete of a physical TORCOVKA does **not** restore consumed rails.

### 5.3 Reconciliation (RAW-001) after cutover

Post-cutover (new movements only):

```
Σ remainingValue
+ Σ post-cutover transfers into blanks (material)
+ Σ post-cutover TORCOVKA_ZERO_OUTPUT material
+ Σ RAW_WRITEOFF
+ Σ PURCHASE_VARIANCE (consumed-share of late ΔC)
+ BOOTSTRAP_RAW_TRANSFER          // opening, not WIP
= recognized C
```

`BOOTSTRAP_RAW_TRANSFER` is **opening historical transferred value**. It must not be added to current BlankStock. See §20 / RAW-OPEN-001.

### 5.4 Late delivery / ΔC after partial consumption

`totalCost` 100 000 → 110 000 after 30% of rails consumed.

**Accepted (BD-COST-NEW-02 CLOSED):** remaining-stock revaluation + consumed-share variance.

```
ΔC = C_new − C_old
Δ_remaining = ΔC × (Σ remainingValue / C_old)
Δ_variance  = ΔC − Δ_remaining
```

- `Δ_remaining` across lots with remainingValue > 0.
- `Δ_variance` → `CostEvent PURCHASE_VARIANCE` in the **current** month. Not into `ProductStock`. Not into closed `ProductCost`.
- Remaining 0 → 100% variance. `frozenAt` set → no `totalCost` write.

### 5.5 Allocation-driver edits after consumption (technical guard)

`priceSort1` / `priceSort2` / `materialId` / section are allocation drivers. §5.4 defines late ΔC. It does **not** authorize retroactive reallocation after consumed rails have already left raw stock.

Active mode:

- all RailLots completely unconsumed: driver edits may recompute every `initialValue` / `remainingValue` atomically from the new inputs
- any RailLot consumed: changing those drivers **fails closed**

This is an invariant guard, not a new accounting model.

### 5.6 BatchCost FINAL

**ADAPT:** freeze consumed-based wood (remaining, transferred, losses, variance, ₽/m³ of consumed volume). PRELIMINARY: not SoT.

## 6. WAC stock model

### 6.1 Pattern

**Fungible pools:** quantity + **component columns** + stored `totalValue` + monotonic `costVersion Int`.

Pools: `BlankStock`, `DetailStock`, `NomenclatureStock`, `ProductStock`.

**Recommend A:** persist `totalValue` **and** components. `COMP-001`: `totalValue = Σ components` exactly (`Decimal`). One TX writes qty + every component + `totalValue` + increments `costVersion`. Do **not** add a movement ledger.

`RailLot` stays a single `remainingValue` (material). Identified lot; **not** a mixed WAC pool; no `costVersion`. `consumedRawValue` is the exact recorded consume used for conservation, attribution, and `correctTorcovkaRailsTaken` (over-entered rails that were never taken). Ordinary TORCOVKA delete does not restore that consume onto the lot.

Companion:

- Op/lines **record** the component amounts of that movement (consume-time / receipt-time) **and** the output pool `costVersion` **immediately after** this operation’s receipt. Used for ProductCost month sums and for **exact reversal** (§13). Aggregate duplicate lines targeting the **same** pool before mutation so one receipt = one version.
- `CostEvent` for non-flow events only (inventory, write-off, purchase variance, bootstrap, later explicit manual correction). Not for ordinary TORCOVKA/PRISADKA/UPAKOVKA reverse.

### 6.2 Proportional component consume

```
receive(dq, dMaterial, dLabor, dNom=0):
  qty += dq
  materialValue += dMaterial
  laborValue += dLabor
  nomenclatureValue += dNom      // ProductStock / Nom only
  totalValue = materialValue + laborValue + nomenclatureValue
  costVersion += 1

consume(dq):
  if dq == qty:
    take exact residual of EVERY component; all → 0
  else:
    f = dq / qty
    materialOut = materialValue × f
    laborOut    = laborValue × f
    nomOut      = nomenclatureValue × f
    qty -= dq
    subtract outs; totalValue = Σ remaining components
  costVersion += 1
```

Every monetary/quantity mutation (receive, consume, inventory surplus/shortage, bootstrap write, purchase remaining-revalue of a pooled row if any) increments `costVersion` in the **same** TX.

Example: qty=100, material=80000, labor=20000; consume 10 → materialOut=8000, laborOut=2000.

Last unit: exact residual of **each** component (STOCK-002 per component).

Internal: `Decimal.js` precision 40, `ROUND_HALF_UP`. **Persistence scale `COST_VALUE_SCALE = 6` (`q6`).** Do **not** round during intermediate economic formulas. Quantize only at the persistence boundary of a resulting movement/state.

WAC consume (`dq < qty`): `out = q6(component × dq / qty)`; `remaining = component − out` (exact residual of already-persisted 6dp input; do not independently round remaining). `totalValue` = sum of quantized/residual components, never a separately rounded total.

WAC receive: each stored component `= q6(current + receipt)`; `totalValue` = sum of those stored components.

Rail-lot allocation: every lot `persistedValue = q6(C × share)`; persistence residual is assigned to the deterministic largest-positive economic-weight lot (tie-break by largest stable lot id); zero-share lots never receive residual. `remainingLotValue` / `bootstrapRawTransfer` return `q6`. Negative `BOOTSTRAP_RAW_TRANSFER` is refused.

No JS `number` for stock money. Do not round to kopecks internally.

Fail-closed DB CHECKs (follow-up foundation migration): uninitialized `costVersion = 0` ⇒ all money NULL; initialized ⇒ NOT NULL, ≥ 0, `totalValue = Σ components`, STOCK-002 when qty = 0. `CostEvent` EVENT-001 CHECK. `CostPeriod` month-start + exclusive `periodEnd`.

### 6.3 Concurrency

`SELECT FOR UPDATE` on the pool row; `UPDATE … WHERE quantity >= dq AND costVersion = expected` setting **all** component fields + `totalValue` + `costVersion` together. No split commits. Id-sorted locks as today.

### 6.4 CostEvent — component-safe payload

Do **not** use a single opaque `amount` (or JSON) as monetary source-of-truth.

Recommended fields (signed where the event is an adjustment):

| Field | Type |
| --- | --- |
| `materialValue` | `Decimal(18, 6)` |
| `laborValue` | `Decimal(18, 6)` |
| `nomenclatureValue` | `Decimal(18, 6)` |
| `totalValue` | `Decimal(18, 6)` |

**EVENT-001 / COMP-EVENT-001:** `totalValue = materialValue + laborValue + nomenclatureValue`.

Examples:

| Type | Components |
| --- | --- |
| `RAW_WRITEOFF` | material only |
| `PURCHASE_VARIANCE` | material only |
| `TORCOVKA_ZERO_OUTPUT` | material + piece labor |
| `INVENTORY_LOSS` ProductStock | material + labor + nomenclature |
| `BOOTSTRAP_RAW_TRANSFER` | material only |
| `BOOTSTRAP` ProductStock | estimated components |
| `MANUAL_ADJUSTMENT` (later, if required) | explicit components; **not** used to bypass a mutated output pool on ordinary op reverse |

No `REVERSAL_VARIANCE` type on the normal production edit/delete path.

## 7. TORCOVKA value flow

Same TX as `submitTorcovka`.

1. Lock RailLot + BlankStock specs (sorted).
2. `consumedRawValue` = §5.2 → **material**.
3. `pieceLaborCost` = Decimal DI-015 snapshot earning → **labor**. Store on the op. **If that employee has no configured piece rate for this op, snapshot is 0/null → `pieceLaborCost = 0`.** Do not invent a piece wage. Hourly-only TORCOVKA still moves **material** into BlankStock.
4. `Q > 0`: split **material** across output lines by produced metres (persistence residual → largest positive produced metres; stable id tie-break). Split **piece labor** by actual line DI-015 earning (`quantity × that line’s historical sort rate`), **not** by metre share. Zero-weight lines receive 0 of that component. **Aggregate lines to the same BlankStock pool before mutation.** Then:
   - `BlankStock.quantity +=`
   - `materialValue +=` wood share (kerf absorbed here)
   - `laborValue +=` piece labor share
   - `totalValue` = sum
   - `costVersion += 1`
   - store **receipt components** and **output `costVersion` after this receipt** on the op/line
5. `Q = 0`: `CostEvent TORCOVKA_ZERO_OUTPUT` with material + labor components; no blank increment.

**HOURS:** not applied to BlankStock.

Kerf: no separate event.

## 8. HOURS allocation model

Payroll, stock labor, analytics, and the **piecework comparison benchmark** are four different things. Do not collapse them.

### 8.1 Worker UX and configured-rate payroll (BD-COST-NEW-01 CLOSED)

TORCOVKA / PRISADKA / UPAKOVKA / HOURS. No DIRECT/INDIRECT. No new entity on the terminal. Allocated hours are **not** extra pay.

**Payroll/cost follows which rates are configured for the employee.** No automatic substitution. Configured compensation components are additive.

**A. HourlyRate only**

- HOURS are paid: `hours × hourlyRateSnapshot` when a valid snapshot exists.
- Piece production operations create **ZERO** piece payroll cost for rate types where that employee has no configured piece rate.
- Do **not** invent or fallback a piece wage.

**B. Piece rate only**

- Piece operations are paid from their **historical DI-015 piece snapshots**.
- No hourly pay unless a HOURS op exists **and** a valid `hourlyRateSnapshot` exists.

**C. Both hourlyRate and the corresponding piece rate**

- **BOTH** are paid.
- Cost follows actual payroll: piece pay + HOURS pay.
- HOURS does **not** replace piece pay when both rates exist.
- Piece pay does **not** appear when the employee has no such rate.

Live Employee card rates are **not** used for payroll, stock labor, or benchmarks. DI-015 snapshots only.

### 8.2 Actual employee-day labor vs analytical allocation (read-model only)

Separate **ACTUAL COST** from **BENCHMARK**.

**No `EmployeeDayCost` table.** No day-finalization writer. No cache to keep in sync with ops.

`ProductionOperation` + DI-015 snapshots remain the **only** factual source for production payroll facts.

Analytics group existing ops:

```
employeeId + calendar day
  → HOURS pay
  → production operations
  → analytical hour allocation
  → piece-paid benchmark
```

Pure functions over those records. Testable without persistence. The result is **not** monetary SoT and is **not** frozen independently. Closed `CostPeriod` / `ProductCost` already freeze the monthly money.

```
actualPiecePay = Σ real piece earnings from that employee's DI-015 snapshots that day
hourPay        = Σ HOURS.hours × hourlyRateSnapshot
actualLabor    = actualPiecePay + hourPay
```

according to configured rates (§8.1). `hourPay = 0` if no HOURS / no valid hourly snapshot. `actualPiecePay = 0` if no piece snapshots.

**Analytical allocation of `hourPay` onto that employee's real operations** (report only; never payroll; never ProductCost; never stock):

One coherent weighting system **inside an employee-day**. Do **not** mix “rubles of normative value” for one op and raw unit counts for another in the same denominator.

Preferred, when **every** operation bucket in that employee-day has a usable piece-paid benchmark (§8.3):

```
weight_i = pieceBenchmarkPerUnit(bucket, selected period) × units_i
hoursAllocated_i = hourPay × weight_i / Σ weight
```

If **ANY** operation bucket in that employee-day has **no** usable benchmark: fall back to **OUTPUT QUANTITY** weighting for the **WHOLE** employee-day.

Last-op residual so `Σ hoursAllocated_i = hourPay` when the day has production (DAY-001, analytics-only).

If no production that day: allocated hours sit on “no op”; they still belong to month `hourPay` (the monetary pool is still the HOURS ops themselves).

**Do not** create fake piece payroll. `hoursAllocated` is a split of real `hourPay`, not a substitute piece earning.

**Do not** add `hoursAllocated` into BlankStock / DetailStock / ProductStock.

### 8.3 Piecework comparison benchmark (hourly worker vs piece workers)

For the report “hourly worker vs piece workers”, **do not** use the hourly employee’s missing/zero piece rate as the benchmark.

**Benchmark is derived from REAL PIECE-PAID production** in the selected period for the same operation type / bucket.

Example buckets:

- TORCOVKA SORT1
- TORCOVKA SORT2
- PRISADKA TORCEV
- PRISADKA PLOSK
- UPAKOVKA

From operations whose corresponding **DI-015 piece-rate snapshot > 0**:

```
pieceBenchmarkPerUnit =
  Σ actual piece earnings
  / Σ actual units
```

- Historical snapshots only. No live Employee card rates.
- If there are **no** piece-paid observations in the selected period for that bucket: show benchmark as **unavailable**. Do **not** substitute 0.

Then hourly / mixed worker analytics can show:

| Column | Source |
| --- | --- |
| Employee | op |
| Operation / bucket | op type + sort / prisadka kind |
| Units | actual output qty |
| HourPay allocated analytically | `hoursAllocated_i` (§8.2) |
| Actual piece pay | that employee’s DI-015 piece earnings (0 if hourly-only) |
| Actual total labor | `actualPiecePay + hoursAllocated_i` |
| Actual ₽/unit | actual total labor / units |
| Piece benchmark ₽/unit | §8.3 bucket WAC, or **unavailable** |
| Difference ₽/unit | actual − benchmark (blank if benchmark unavailable) |
| Difference % | vs benchmark (blank if unavailable) |

For a **mixed-pay** worker: actual ₽/unit includes **both** their real piece pay and allocated hourly pay.

### 8.4 Monetary product costing — monthly hourly pool

HOURS are **not** pushed retroactively through BlankStock / DetailStock / ProductStock.

Employee/day allocation is **ANALYTICS ONLY** (computed, not stored).

**Monetary source (HOURS-001):**

```
monthlyHourlyPool =
  Σ over HOURS ProductionOperation in the CostPeriod
    hours × hourlyRateSnapshot     // Decimal cost math
```

Not an analytics cache. Not `EmployeeDayCost`.

At `closeMonth` (locks `CostPeriod`):

- Write `CostPeriod.hourlyProductionLaborPool = monthlyHourlyPool`.
- If `Σ packed direct > 0`: allocate **100%** of the pool across products produced in the month on the §15 base (packed `directTotal`). Store each SKU share on `ProductCost.hourlyProductionLabor`. `unallocatedHourlyProductionLabor = 0`.
- If zero production / zero packed direct: entire pool → `CostPeriod.unallocatedHourlyProductionLabor`. Not dropped. Not forced onto catalog SKUs. Month can still be FINAL (PERIOD-003).

No `INDIRECT_HOURS` vs `UNAPPLIED_HOURS` split in stock. Hours-only days are HOURS ops and therefore inside the same monthly pool.

**Timing:** HOURS at 17:00 after packs at 13:00 does not change ProductStock. Month close sums HOURS ops in the period regardless of entry order.

**Conservation:**

- No hour ruble disappears.
- No piece ruble appears when no piece rate exists.
- No ruble is counted twice.

```
period production payroll
  = piece labor carried in production flow
  + monthly HOURS pool
```

subject to actual configured rates (§8.1).

## 9. PRISADKA value flow

Physical semantics unchanged.

1. Consume BlankStock or partial DetailStock with **proportional components** (§6.2). Store **input** components on the line.
2. Record consumed `materialOut` / `laborOut` on the line (consume-time WAC of the pool).
3. `pieceLabor` from DI-015 snapshots → additional **labor** on output (**0** if no piece rate for that employee/op).
4. Aggregate lines to the same output DetailStock pool; credit: `materialValue += materialOut`, `laborValue += laborOut + pieceLabor`, `costVersion += 1`. Store receipt components and **output `costVersion` after receipt**.

Hours: not applied to DetailStock.

## 10. UPAKOVKA value flow

Physical semantics unchanged.

1. Consume details/blanks at **current component WAC**; record component outs on lines.
2. Consume nom: `nomenclatureOut` from `NomenclatureStock.nomenclatureValue`.
3. Packer `pieceLabor` → ProductStock **laborValue** (**0** if no packer piece rate).
4. ProductStock (aggregate lines to the same pool first):

```
quantity += productQty
materialValue += material from WIP
laborValue += labor from WIP + packer pieceLabor
nomenclatureValue += nomOut
totalValue = Σ components
costVersion += 1
```

5. Persist **receipt components** on the UPAKOVKA op (`receiptMaterial`, `receiptLabor`, `receiptNomenclature`) **and** output `costVersion` after this receipt. Also persist **exact input components** restored on reverse (WIP outs + nom outs). Receipts are month-close SoT for that pack — WAC **at consume time**, not a later reconstruction from blended remaining FG.

```
stockDirectWac = ProductStock.totalValue / quantity   // remaining FG
```

Hours: not applied to ProductStock.

**Future supply:** consume ProductStock components proportionally. Not implemented now.

## 13. Reversals / corrections

Unpaid only (unchanged).

**Do not** reverse a fungible pool at current WAC and dump the difference into `REVERSAL_VARIANCE`. That can move the **wrong meaning** of a component even when money still adds up.

Unsafe example: `BlankStock.laborValue` holds TORCOVKA labor. PRISADKA consumes it and adds PRISADKA piece labor. `DetailStock.laborValue` then holds upstream TORCOVKA labor **plus** PRISADKA labor. Reversing PRISADKA by taking **current** DetailStock WAC and crediting all of that labor back to BlankStock can put **PRISADKA labor into unprocessed BlankStock**. Money reconciles; component meaning is wrong.

**No graph unwind. No rewrite of downstream stock. Qty ≥ producedQty never proves identity (REV-002).**

### 13.1 Why quantity availability is not enough

Counterexample (BlankStock, one spec):

- Op A produces 50, material 5000 (100 ₽/pc). Pool: 50 / 5000.
- Op B produces 50, material 15000 (300 ₽/pc). Pool: 100 / 20000 (WAC 200).
- Downstream consumes 50. Pool: 50 / 10000 (WAC still 200).
- Reverse Op A, qty 50. `quantity >= 50` holds.
- Historical receipt material 5000 is **not** sitting in the pool. Remaining 50 units are a mix.

Even `quantity == producedQty` fails after mixed consumes. Architecture does **not** treat qty as monetary identity.

### 13.2 RailLot (identified)

`correctTorcovkaRailsTaken` may restore the **exact corrected portion** of the originally recorded rail consume: those delta rails were entered by mistake and were not actually taken. Provenance is the lot row. Exact.

Ordinary TORCOVKA delete is a different action. Physically cut `RailLot` quantity/value is **not** restored.

### 13.3 Fungible pools — conservative exact reversal (REV-001)

Each of BlankStock / DetailStock / NomenclatureStock / ProductStock has monotonic `costVersion`. Every qty/money mutation increments it in the same TX.

When a production operation credits an output pool, store the **resulting** output pool version on the operation/line (after aggregating duplicate lines to that pool).

Normal edit/delete is permitted **only if**:

```
current output pool costVersion
  == stored version immediately after this operation's receipt
```

That proves the output pool has had **no** later receipt, consumption, inventory adjustment, or other monetary mutation.

**If versions match:** reverse **EXACT stored movement components**. No current-WAC approximation.

**TORCOVKA ordinary delete**

- exact Blank receipt can be removed only when every target pool `costVersion` still equals the stored output version, and the inventory-history boundary permits the mutation
- physically cut RailLot qty/value is **not** restored
- consumed raw becomes explicit `TORCOVKA_ZERO_OUTPUT` material loss (`material = consumedRawValue`, labor = 0, nom = 0)
- unpaid operation piece labor disappears with the deleted operation (it is not preserved as a fake labor loss)

**DELETE OF PHYSICAL TORCOVKA** ≠ **CORRECTION OF OVER-ENTERED `railsTaken`**. Only the latter may return the unused rail chunk to the lot.

**PRISADKA**

- subtract exact stored output receipt components
- restore exact stored **INPUT** components to the recorded source pool
- operation-added PRISADKA piece labor disappears with the deleted operation (it is not written back into BlankStock as if it were unprocessed wood labor)

**UPAKOVKA**

- subtract exact stored ProductStock receipt components
- restore exact recorded WIP input components
- restore exact recorded nomenclature consumed components
- operation-added packer piece labor disappears

Increment `costVersion` on every pool touched by the reverse (it is a mutation).

**If version does NOT match:** **BLOCK** ordinary edit/delete. Factual error, for example:

> Результат операции уже использован или склад изменён. Исправление через корректировку остатков.

Do **not**:

- graph unwind
- rewrite downstream stock
- pretend `quantity >= producedQty` proves identity
- force a `REVERSAL_VARIANCE` to make an unsafe reverse possible

This is intentionally conservative.

Do not reverse HOURS out of stock (they were never in stock). Hour analytics recompute from remaining ops.

### 13.4 REVERSAL_VARIANCE — not on the ordinary path

Remove `REVERSAL_VARIANCE` from normal TORCOVKA / PRISADKA / UPAKOVKA edit/delete.

`CostEvent` may later support an explicit `MANUAL_ADJUSTMENT` / correction if required. Ordinary production reverse must **not** use accounting variance to bypass an already-mutated output pool.

No new owner decision. Inventory shortage/surplus remains BD-COST-05 (explicit document, not a silent reverse).

## 27. Definition of “true production cost”

**Remaining FG direct** = ProductStock `totalValue / qty` with visible material / labor / nom WAC.

**Month SKU true cost** = FINAL `ProductCost` on a FINAL `CostPeriod`: packed qty; material + pieceLabor + nomenclature from **pack-time receipt components**; `hourlyProductionLabor` from the period HOURS pool; `productionOverhead` from tagged CF; full = sum. Frozen against later TORCOVKA, BOM, `unitPrice`, Employee rates, overhead tags.

**True** ≠ FIFO identity. **True** = components conserved in the physical flow, piece labor only where a snapshot exists, HOURS payroll closed on `CostPeriod` from production ops, purchases in nom WAC, losses explicit, month frozen. Ordinary reverse is exact-or-block via `costVersion`.
