9. No path in `deploy.sh`, `docker-entrypoint.sh`, or the P1 SQL drops the column. `restore-db.sh` is a separate manual overwrite. It is not called by deploy. It is not a safe column rollback. See §7.
10. Before any production workflow, the checklist in §8 has to be collected under a separate authorization. This assessment does not collect it. Dispatch remains not authorized.

## 4. Why the candidate sequence is blocked

The candidate sequence was: authorize P1 alone, apply it, verify it, then separately authorize the P2/P3 image, then observe.

The existing scripts do not support that separation.

- `deploy-production.yml` lines 23–37 always resolve `origin/main`.
- That `main` already contains P1, P2, and P3.
- The same container start migrates and then serves the new writer.
- No script runs `prisma migrate deploy` against the old running image while leaving that image in place.

Classification: **DEPLOYMENT BLOCKER**. This assessment does not edit the scripts and does not invent a supported migration-only workflow.

A later package could propose a separate procedure. It is not authorized here. Minimum guardrails, if HEAD later authorizes the design:

- not `workflow_dispatch` of Production Deploy;
- an explicit SHA whose migration directory contains P1, with the running container still on the previous application SHA;
- identity check of host, database name, and app SHA before any statement that changes schema;
- a backup whose checksum is recorded, not merely a non-empty file;
- one `prisma migrate deploy` from that migration set, without recreating the app container from the new SHA;
- a following read-only check of the column, CHECK, trigger, and `_prisma_migrations` row;
- the old process keeps serving until a separate deploy authorization;
- no backfill and no provenance writes by the migration;
- fail closed if the target identity does not match.

Until that procedure exists and is authorized, Stage 2 cannot be executed safely with the current tooling.

## 7. Backup limits

`deploy.sh` lines 81–83 run `scripts/backup-db.sh` before checkout. The backup script (lines 22–31) runs `pg_dump` into gzip and rejects an empty file. It does not record a checksum, does not restore the dump as a test, and does not copy it off the server. Lines 35–36 delete local files older than 14 days.

`restore-db.sh` lines 25–34 ask for a typed confirmation and pipe the dump into `psql` on the existing database. Deploy does not call it. The dump command does not pass `--clean`. A restore is therefore not a proven way to remove only the new column, and a pre-migration dump would also discard every later business write. Using it to erase provenance is prohibited.

A non-empty local gzip is not sufficient go evidence. A future go decision needs a recorded checksum, a restore drill on a non-production copy, and a backup taken at the decision point. Those results are **UNKNOWN** today.
