# Inventory Integrity Remediation Plan (DI-009)

> **For agentic workers:** do not implement until the owner says implement. When implementing: `superpowers:subagent-driven-development` or `executing-plans`. Evidence: `audit/01.6-inventory-provenance-review.md`. Owner lock: 01.6 §15. Findings card: `audit/01-data-integrity-findings.md` DI-009.

**Goal:** `conductInventory` may SET stock to physical `actualQty` only after an in-transaction proof that every line’s live quantity still equals the DRAFT snapshot `accountedQty`; a CONDUCTED document is an immutable physical-truth boundary that old reverse/delete must not cross; historical `deviationSum` stays frozen.

**Architecture:** Keep READ COMMITTED. No new tables, no new `InventoryLine` columns, no ledger. Snapshot guard = `Inventory` FOR UPDATE, then `Detail` parent FOR UPDATE (prisadka DETAIL lines), then ensure+FOR UPDATE on `BlankStock` / `NomenclatureStock` / `ProductStock` in **consumption-first** table order (see §2). Absolute SET remains the write. Boundary refs for PRISADKA are computed from dest/source **ready** buckets (`isReady`), not “any DetailStock row”.

**Tech Stack:** Prisma 6, PostgreSQL 17, `Decimal` via `D()` from `src/lib/cost.ts`, Vitest integrity harness (`INTEGRITY_TEST_DATABASE_URL`). Isolation stays READ COMMITTED.

**HEAD this plan assumes:** `931efe87f98431e8fb27dd11f4e3dd7e61738a03`

## 1. What “live quantity” means (must match DRAFT snapshot)

`createInventoryDraft` (`warehouse.ts:233-257`) snapshots:

| `refType` | accountedQty today | liveQty in the guard **must equal** |
| --- | --- | --- |
| `PRODUCT` | `ProductStock.quantity` or 0 | same |
| `NOMENCLATURE` | `NomenclatureStock.quantity` or 0 | same |
| `DETAIL` with at least one prisadka | sum of **ready** `DetailStock` buckets (`isReady`) | same sum **while holding `Detail` FOR UPDATE** (§2.3) |
| `DETAIL` with **no** prisadka | `BlankStock.quantity` for `(materialId,lengthM,detailType,sort)` or 0 | same |

WIP `DetailStock` rows are **not** part of `accountedQty` and **must not** be written by conduct (unchanged: `normalizeReadyBuckets` skips non-ready). `RailLot` is not a line.

Missing stock row ⇒ live `0` **only after** the mutex/ensure in §2.3. Do **not** `SELECT` empty `DetailStock` and treat as live 0 without holding `Detail` FOR UPDATE — a concurrent upsert can insert a ready bucket (blocker 2).

## 2. LOCK / WRITE GRAPH (plan review — replaces Product-first order)

### 2.1 Why the draft order was rejected

Draft 01.7 had `ProductStock → Nom → Blank → Detail`.

`applyUpakovkaPick` implicit locks are the opposite on GP vs details:

1. `DetailStock`/`BlankStock` (composition loop)
2. `NomenclatureStock` (fasteners → packaging → extras)
3. `ProductStock` upsert **last** (`production-reversal.ts:299`)

So:

```
conduct (draft):  ProductStock → … → DetailStock
submitUpakovka:   DetailStock  → … → ProductStock
```

**Cycle is real.** Do not implement Product-first.

`applyPrisadkaPick` is `DetailStock` (src) → `BlankStock` → `DetailStock` (dest). Blank-before-Detail in conduct would cycle with prisadka. Detail-before-Blank matches prisadka.

`reverseUpakovkaOperation` today is **ProductStock first** (`:323`) then details/nom — already inverted vs apply (pre-existing). DI-009 reverse **must acquire** locks in the apply-compatible order **before** those writes (fixes that inversion as a side effect).

### 2.2 Actual current writers (HEAD `931efe8`)

`E` = explicit `SELECT … FOR UPDATE`. `I` = implicit row lock from `UPDATE`/`UPSERT`/`updateMany`. Reads (`findMany` without FOR UPDATE) do **not** lock.

| Writer | Order of tables/rows |
| --- | --- |
| `submitTorcovka` | **E** `RailLot` id ASC (`lockRailLots`) → **I** `RailLot` decrement → **I** `BlankStock` upsert per pick (input order, not sorted) |
| `applyPrisadkaPick` | read `Detail` (no lock) → **I** `DetailStock` src `updateMany` (findMany `orderBy id`) → **I** `DetailStock` dest upsert → maybe **I** `BlankStock` decrement → **I** `DetailStock` dest upsert |
| `submitPrisadka` | `ProductionOperation` insert → `applyPrisadkaPick` per pick (**input order**) |
| `applyUpakovkaPick` | read `Product`+composition (no lock) → per `product.details` order: **I** `BlankStock` **or** **I** `DetailStock` ready → **I** `NomenclatureStock` fasteners, packaging, extras (**composition order**) → **I** `ProductStock` upsert |
| `submitUpakovka` | `ProductionOperation` insert per pick → `applyUpakovkaPick` |
| `reversePrisadkaLine` | **I** dest `DetailStock` decrement → **I** `BlankStock` upsert **or** source `DetailStock` upsert |
| `reverseUpakovkaOperation` | **I** `ProductStock` decrement **first** → **I** `BlankStock`/`DetailStock` increment → **I** `NomenclatureStock` increment |
| `updateProductionLineQuantity` UPAKOVKA/PRISADKA | **E** `ProductionOperation` → reverse* → apply* |
| `updateProductionLineQuantity` TORCOVKA | **E** Op → **I** `BlankStock` − or upsert + |
| `deleteProductionOperation` | **E** Op [+ **E** Batch if TORCOVKA] → TORCOVKA **I** `BlankStock` − / PRISADKA reverse* / UPAKOVKA reverse* |
| `createSimplePurchase` | **I** `NomenclatureStock` upsert only |
| `applySupplyDeduction` | **E** `Supply` sorted (`lockSuppliesInOrder`) → **E** `ProductStock` (`lockProductStockQty`; **no lock if row missing**) → **I** `ProductStock` decrement |
| Ozon restore | **E** `Supply` keys → **E** `ProductStock` (skip if missing) → **I** `ProductStock` upsert increment |
| `conductInventory` **today** | no FOR UPDATE; **I** upsert SET in line order (Product / Nom / Blank / Detail) |

`correctTorcovkaRailsTaken`: **E** Op → **E** RailLot → **E** Batch → **I** `RailLot` increment. No inventory stock tables.

### 2.3 Chosen global order (implement this)

Table sequence — **consumption first, GP last**, matching `applyUpakovkaPick` / `applyPrisadkaPick`:

```
1. Inventory            (conduct only)  FOR UPDATE
2. Detail               (parent mutex)  FOR UPDATE, id ASC
3. BlankStock           ensure qty=0 + FOR UPDATE, unique key ASC
4. NomenclatureStock    ensure qty=0 + FOR UPDATE, nomenclatureId ASC
5. ProductStock         ensure qty=0 + FOR UPDATE, productId ASC
```

Never lock `ProductionOperation` / `Batch` / `RailLot` / `Supply` from `conductInventory`.

**Detail parent mutex (blocker 2):** `SELECT id FROM "Detail" WHERE id IN (…) ORDER BY id FOR UPDATE` **before** any `DetailStock` / that-detail `BlankStock` write. Postgres cannot FOR UPDATE a missing `DetailStock` row; the **Detail** row always exists for an inventory DETAIL line. Any writer that can change that detail’s ready qty must take the same mutex.

Who must call `lockDetails(tx, ids)` (new helper, same SQL pattern as `lockTableIds` in `finance-operations.ts`):

| Function | When |
| --- | --- |
| `conductInventory` | all `refType=DETAIL` `refId`s on the document |
| `applyPrisadkaPick` | that `detailId` (or once in `submitPrisadka` for all pick ids) |
| `reversePrisadkaLine` | `line.detailId` (or once per op in `delete`/`update`) |
| `applyUpakovkaPick` | all `neededByDetail` keys, **sorted**, **before** the consumption loop |
| `reverseUpakovkaOperation` | all detailIds on the op lines, **sorted**, **before** `ProductStock` decrement |

`deleteDetail` already deletes the parent; out of DI-009 scope.

**Within-table sort (prevents Nom/Detail inversion vs conduct):**

- `applyUpakovkaPick`: `lockDetails` on sorted ids; decrement `NomenclatureStock` in **nomenclatureId ASC** (fasteners+packaging+extras collected then sorted). Semantics unchanged (same rows, same qty).
- `submitPrisadka`: lock all pick `detailId`s ASC before the loop.
- `submitTorcovka`: upsert `BlankStock` in unique-key ASC (same increments).
- TORCOVKA delete/qty: `BlankStock` updates in unique-key ASC.
- `reverseUpakovkaOperation`: **acquire** Detail mutex + Nom/Product stock locks in this global order, then existing write sequence is safe.

**Product/Nom/Blank missing rows:** unique key exists (`ProductStock.productId`, `NomenclatureStock.nomenclatureId`, `BlankStock` 4-tuple). Conduct `createMany skipDuplicates` qty 0 then `SELECT … FOR UPDATE`. Concurrent upsert hits the row and waits. No parent mutex required for those three.

**Supply / Ozon** only touch `ProductStock` (after `Supply`). Subset of step 5. They never lock `Detail`. No cycle with conduct (conduct holds Detail before Product; supply never needs Detail).

**Torcovka** holds `RailLot` then `BlankStock`. Conduct never takes `RailLot`. Shared resource is only `BlankStock` → serialized, no cycle.

### 2.4 Why no deadlock (after alignment)

Hold-and-wait edges that remain:

- All aligned writers: `Detail` → `BlankStock` → `NomStock` → `ProductStock` (skipping unused tables).
- Conduct prefixes `Inventory` (nobody else locks `Inventory`).
- Torcovka prefixes `RailLot` (nobody in this set locks `RailLot` after stock).
- Supply prefixes `Supply` then `ProductStock` only.

The rejected cycle (Product vs Detail) is gone because **nobody acquires ProductStock while later needing Detail**. Reverse is changed to take `Detail` **before** `ProductStock`.

Residual **pre-existing** (out of DI-009 except the sort we add): two `submitUpakovka` of two products whose unsorted extra/detail orders inverted Nom/Detail ids. Sorting Nom and locking Details ASC **removes** that class of deadlock for packing vs packing and packing vs conduct.

Test 13: `conductInventory` ‖ `submitUpakovka` and ‖ `submitPrisadka` with 20s timeout; no deadlock; **at least one side succeeds** in the seeded scenario; final stock matches exactly one allowed serialization (see tests 13).

### 2.5 Residual in-flight after SET

A writer waiting on a stock/parent lock held by conduct applies **after** commit (looks like post-inventory movement). Snapshot guard covers **committed** movements between draft and conduct.

### A. Authoritative snapshot guard

New helpers (signatures):

```ts

/** Ensure Product/Nom/Blank rows exist (qty 0) then FOR UPDATE. Not used for DetailStock phantoms. */

  tx: Prisma.TransactionClient,

  tx: Prisma.TransactionClient,

```

`lockInventoryForUpdate`:

```sql
SELECT id, status FROM "Inventory" WHERE id = $id FOR UPDATE
```

If no row → existing «Инвентаризация не найдена». If `status !== 'DRAFT'` → `ALREADY_CONDUCTED` (zero stock writes).

Ensure-row for missing `ProductStock` / `NomenclatureStock` / `BlankStock` (unique key, so a concurrent upsert cannot sneak an insert):

```ts
await tx.productStock.createMany({
  data: [{ productId: line.refId, quantity: 0 }],
  skipDuplicates: true,
});
await tx.$queryRaw`
  SELECT id FROM "ProductStock" WHERE "productId" = ${line.refId} FOR UPDATE
`;
```

Same pattern for `NomenclatureStock` (`nomenclatureId`) and `BlankStock` (unique tuple from the Detail).

**DETAIL with prisadka (blocker 2) — do not rely on locking existing `DetailStock` rows.** Unique key is `@@unique([detailId, torcevayaDone, ploskostDone])` — four possible buckets. `FOR UPDATE` on zero rows locks nothing. Concurrent `applyPrisadkaPick` / `applyUpakovkaPick` **upserts** a dest/ready bucket (`production-reversal.ts:33`, `:246`).

Chosen mutex (no schema): `lockDetails` on that `refId` **before** summing ready qty and before SET. All ready-qty writers listed in §2.3 take the same lock first. While conduct holds `Detail`, nobody can insert/update that detail’s `DetailStock` or consume its blanks via apply/reverse. Then `findMany` `DetailStock` for ready sum is authoritative.

Rejected alternatives:

- Lock only existing `DetailStock` — fails phantom insert (this blocker).
- Ensure all 4 buckets + `ORDER BY id FOR UPDATE` without parent mutex — `id` (cuid) order ≠ apply’s src-then-dest unique-key order → intra-detail deadlock.
- `Material` FOR UPDATE — too coarse; not all writers take it.

`liveQtyForLine` **after** mutex/ensure. Integer equality vs `accountedQty`.

### B. All-or-nothing transaction

Single `prisma.$transaction`. Order inside:

1. `lockInventoryForUpdate` — must be DRAFT.
2. `lockDetails` for DETAIL lines; ensure+FOR UPDATE Blank/Nom/Product in §2.3 order.
3. `assertLiveEqualsAccounted` — if throw, Prisma rolls back: no stock, no line updates, no CONDUCTED, no ChangeLog.
4. `getUnitCostSnapshot` **after** the guard (cheap abort on stale). Using global prisma read for cost is acceptable; do not expand cost-freeze into this TX.
5. For each line: `deviation = actualQty - accountedQty`; `deviationSum = Decimal`; existing SET branches (`warehouse.ts:331-393`); `inventoryLine.update({ deviation, deviationSum })`.
6. `inventory.updateMany({ where: { id: docId, status: "DRAFT" }, data: { status: "CONDUCTED", date: new Date() } })`. If `count !== 1` → `ALREADY_CONDUCTED` (rollback).
7. ChangeLog: one header row as today **plus** one row per line (§H).
8. Commit. Then `revalidatePath`.

No writes before step 5. Valuation failure after the guard still rolls back — document stays DRAFT, stock untouched.

## 5. I: Inventory-boundary protection

### 5.1 Matching rule

Block iff **all** of:

1. There exists `Inventory` with `status = 'CONDUCTED'`.
2. `Inventory.date > occurredAt` (`occurredAt = ProductionOperation.createdAt`).
3. At least one `InventoryLine` of that document has `(refType, refId)` in the reverse’s **affected ref set**.

Then throw `INVENTORY_BOUNDARY` **before** any stock increment/decrement. Zero stock mutation.

```ts
export async function assertInventoryBoundary(
  tx: Prisma.TransactionClient,
  occurredAt: Date,
  refs: InventoryRef[],
): Promise<void>;
```

SQL:

```sql
SELECT i.id
FROM "Inventory" i
JOIN "InventoryLine" l ON l."inventoryId" = i.id
WHERE i.status = 'CONDUCTED'
  AND i.date > $occurredAt
  AND (l."refType", l."refId") IN ( ... )
LIMIT 1
```

Empty `refs` → no-op (HOURS).

### 5.2 Mapping stock writes → inventory refs

| Stock mutation | Inventory ref | Notes |
| --- | --- | --- |
| `ProductStock.productId` ± | `{ PRODUCT, productId }` | UPAKOVKA reverse always |
| `NomenclatureStock.nomenclatureId` ± | `{ NOMENCLATURE, nomenclatureId }` | UPAKOVKA reverse always |
| `BlankStock` spec ± | `{ DETAIL, id }` of **no-prisadka** details with that spec | only those inventory lines SET BlankStock |
| Ready `DetailStock` bucket ± | `{ DETAIL, detailId }` | see §5.2.1 |
| WIP `DetailStock` bucket ± only | **no DETAIL ref** | inventory did not cover WIP (BD-9.3) |

### 5.2.1 PRISADKA dest/source vs `isReady` (blocker 3)

`reversePrisadkaLine` (`production-reversal.ts:111-180`):

```
kind = line.prisadkaTorcevaya ? "torcev" : "plosk"

destT = sourceIsBlank ? (kind==torcev) : (kind==torcev ? true : sourceTorcevayaDone)
destP = sourceIsBlank ? (kind==plosk)  : (kind==plosk  ? true : sourcePloskostDone)

decrement DetailStock (detailId, destT, destP)
then if sourceIsBlank: increment BlankStock
else: increment DetailStock (detailId, sourceTorcevayaDone, sourcePloskostDone)
```

Evaluate `isReady(detail, t, p)` with **current** `Detail.prisadkaTorcevaya` / `prisadkaPloskost` (same flags live production uses).

**DESIGN LIMITATION / CURRENT-MODEL ASSUMPTION:** Inventory boundary for DETAIL is determined from current prisadka flags because `InventoryLine` has no historical snapshot of those flags. This can become imprecise if Detail configuration changes after inventory. DI-009 does not extend schema for this.
