## 1. What a future implementation must do

For each new `createBatch`, store the full original set `{ railLotId, quantity }[]` on `BatchCreationCommand` in the same transaction, after the lot ids exist. The fact must survive remaining-quantity changes, write-off, `deleteBatch`, and replay. It must not be copied from `InventoryMovement`.

## 3. Database guard readiness

`audit/08.31` §6 is the guard. A future migration adds one trigger on `UPDATE` and `DELETE` of `"BatchCreationCommand"`. It does not reject `INSERT` of SQL `NULL`.

| Attempt | Required result |
| --- | --- |
| object replaced by a different object | reject |
| object replaced by SQL `NULL` | reject |
| legacy SQL `NULL` replaced by an object | reject |
| `id`, `requestId`, or `batchId` changes while an object is stored | reject |
| `DELETE` of a row that stores an object | reject for an ordinary role |
| `UPDATE` that leaves provenance, `id`, `requestId`, and `batchId` unchanged | allow |
| object written back as the same JSON value, identities unchanged | allow |
| legacy SQL `NULL` left SQL `NULL` | allow |
| `INSERT` of SQL `NULL` | allowed. This is the mixed-version window |

Comparison must use null-safe inequality. In PostgreSQL, `IS DISTINCT FROM` is false for SQL `NULL` compared with SQL `NULL`, and JSONB `=` ignores object key order. A trigger that uses `IS NULL` alone will mis-classify a legacy row. A trigger that compares JSON text will reject a same-value update that differs only by key order.

The function should be invoker-rights. It only raises. It does not need definer rights. Install it in the same migration transaction as the column, after the check.

Prisma does not emit this trigger. `prisma generate` will not create it and will not drop it if the migration owns it. The only current write of the model is `batchCreationCommand.create` (`purchases.ts` line 356). There is no `update` in `src/`. The trigger is what stops a direct `UPDATE` or `DELETE`.

**Not claimed.** A superuser, a disabled trigger, or `session_replication_role = replica` can bypass an ordinary trigger. The PASS criterion is narrower: connected as the ordinary application role, with user triggers enabled, the reject rows above fail and the allow rows above commit, and a stored object is still readable after `deleteBatch`.

Integrity tests must use the disposable database already used by CI (`.github/workflows/ci.yml` job `PostgreSQL-backed integrity suite`, database `stell22_integrity`). They must not set `session_replication_role`. They must not be unit mocks.

## 4. Writer and transaction readiness

Observed `createBatch` (`purchases.ts` lines 288–385):

1. Outside the transaction: admin, `requestId`, `validateBatch` (lines 234–241; no positive-quantity rule), `canonicalBatchCreateSnapshot`.
2. Inside one transaction: SHADOW gate read, advisory lock namespace `8326` (`purchase-command-identity.ts` lines 15 and 35–42), replay lookup, batch insert with nested lots (lines 334–348), optional cost init, command insert (lines 356–363), SHADOW append, `ChangeLog`.
3. After commit: revalidate and reload.

`batchCreateReceiptEffects` skips `quantity === 0` and throws on a negative or non-integer (`raw-purchase-shadow-write.ts` lines 75–82 and 158–172). That throw runs after the command insert but inside the same transaction (lines 337–338), so a negative quantity does not commit today.

**Future writer change, not made here.**

- Supply `commandId` before the insert. `@default(cuid())` (`schema.prisma` line 307) does not give the application the id until the insert returns, so the caller must pass `id`.
- After `railLots` exist, build pairs from those rows, including zeros. Sort by `railLotId` with `localeCompare`, the same order as `sortByRailLotId` (lines 92–94).
- Validate the object before the command insert: unique `railLotId`, integer `quantity >= 0`, `commandId` and `batchId` equal to the row being inserted.
- Put the object in the same `batchCreationCommand.create`. Leave `requestSnapshot` as it is.
- Leave the SHADOW append and the `ChangeLog` where they are.
- One commit. A validation throw rolls back lots, command, provenance, and movements.

| Case | Required future result |
| --- | --- |
| `quantity = 0` | lot and pair stored; no `RECEIPT` effect |
| negative or non-integer | transaction rolls back; no command |
| two rails with the same specification | two ids, two pairs |
| duplicate `railLotId` in the object | reject before commit |
| same `requestId` while the batch exists | return lines 304–313; no second insert and no provenance update |
| same `requestId` after `deleteBatch` | `PURCHASE_REPLAY_TARGET_MISSING`; original object remains |
| gate active | existing append still runs; provenance is still written |
| gate inactive | provenance is still written; zero movements; later checker returns `GATE_UNKNOWN` for a positive set |

Do not read `InventoryMovement` or `causationSnapshot` to build the pairs. Do not change `isInventoryMovementShadowWriteActiveForWriter` (`inventory-movement-shadow-write.ts` lines 80–84). That function takes shared advisory lock `(8322, 1)`. The purchase lock stays `(8326, hashtext)`. The new column is not a new lock. Reset stays the exclusive control lock (`inventory-movement-shadow-coordination.ts` lines 50–70) and is not part of this writer.

## 6. Read-only checker boundary

A later checker, not Slice 1. Slice 1 contours are R-05, write-off, and SimplePurchase (`psr-p3-slice1-invariant-a.ts` lines 7–12). Do not add Option A and do not read live `RailLot.quantity` as Expected.

Expected comes only from a valid provenance object. Observed comes from `InventoryMovement` rows for `causationKind = BATCH` and `causationId = command.id`. Observed rows must not be copied into Expected.

| Case | Status |
| --- | --- |
| sets equal, including a proven zero effect and an empty observed set | `MATCH_OBSERVED` |
| sets known and different, including an extra movement | `MISMATCH` |
| nonempty expected, empty observed, preservation not proved | `GATE_UNKNOWN` |
| command row absent | `SOURCE_UNAVAILABLE` |
| command present, SQL `NULL` | `NOT_EVALUABLE` |
| malformed object, duplicate id, bad quantity, or binding mismatch | `INVALID_SOURCE` |
| database read does not finish | execution error, not a status |
| every result | Invariant B `NOT_EVALUABLE` |

`MATCH_OBSERVED` does not prove a warehouse quantity changed. SQL `NULL` is not rewritten into `pairs: []` or an all-zero list. Empty expected plus empty observed is `MATCH_OBSERVED` only when the object itself proves the zero effect (`audit/08.28` §5 item 5).

The checker runs in a read-only transaction, the same pattern as `readSlice1InvariantA` (lines 585–587). It inserts, updates, and deletes nothing.

SHADOW reset and preservation proof stay **DEFERRED**. This gate does not upgrade `GATE_UNKNOWN` to `MISMATCH`.

**Schema merged, writer not deployed.** If P1 is merged and not deployed, production is unchanged. If P1 is deployed and P2 is not, the old application keeps inserting SQL `NULL`. That is the accepted rollout, not a backfill, and not a proven zero. The risk is operational confusion, not a false `MATCH_OBSERVED`, as long as P3 treats `NULL` as `NOT_EVALUABLE`.

**Mixed versions.** After P2 is deployed, an old process can still insert `NULL` until it is gone. `recordedAt` does not identify which process wrote the row. Those rows stay `NOT_EVALUABLE`. The deferred alert is not required to start P1.
