## Isolation

The database cluster is the Package A disposable cluster: `postgres:17-alpine`, `POSTGRES_USER=stell22`, no published port, names `stell22-p1wf-<uuid>`. The application image is built from `git archive` of the historical commit with `core.autocrlf=false`, so the Linux entrypoint keeps the blob's LF bytes. A Windows archive without that setting writes CRLF and the container exits 255 with `exec ./docker-entrypoint.sh: no such file or directory`. That is a harness conversion, not a change to the historical blob.

The application container joins only that network, publishes `3000/tcp` on `127.0.0.1`, and receives `DATABASE_URL` for `p1wf_app` from an env file. The bootstrap password is not that URL. Cleanup deletes an application container only after inspect of the id returned by `docker run`. A wrong image field, a foreign id, a Compose label, a production name, a public port, a bootstrap URL, or a changed Docker endpoint or daemon leaves the container in place.

## Database preparation

`stell22` stayed the bootstrap superuser, oid 10. The rehearsal created `p1wf_breakglass` as a superuser and `p1wf_migrator` and `p1wf_app` as `LOGIN` non-superusers. `p1wf_app` had no membership. The database and `public` were owned by `p1wf_migrator`. Every public table was owned by `p1wf_migrator` after the migrator ran the historical `prisma migrate deploy` from the built image: 45 migrations, exit 0. The application role received ordinary `SELECT`, `INSERT`, `UPDATE`, `DELETE`, and `TRUNCATE` on those tables, plus sequence `USAGE`, `SELECT`, and `UPDATE`. `INSERT`, `UPDATE`, `DELETE`, and `TRUNCATE` on `_prisma_migrations` were revoked. The application role kept `SELECT` on that table. It was not granted schema `CREATE` except through the absence of a DDL grant. `CREATE` on `public` was revoked from `PUBLIC`.

## Entrypoint

The historical `docker-entrypoint.sh` ran unchanged: `npx prisma migrate deploy`, then `npm run start`. As `p1wf_app`, with the historical migrations already applied and no pending migration in the image, Prisma reported `No pending migrations to apply.` The server started. `GET /api/health` returned 200.

After the migrator applied the pinned P1 file, `docker restart` of the same application container changed `StartedAt` and ran the entrypoint again. That start also stayed up. The historical image does not contain the P1 directory. This run does not show that the application role can apply a new migration. It shows that `migrate deploy` exits 0 when the image has nothing pending, including after additive P1 SQL that is not one of the image's migration directories.

## Application operation and freeze

The historical Prisma client in the running container read the baseline `Setting` row and created a `Notification`. `SET ROLE p1wf_migrator` and `SET ROLE p1wf_breakglass` from `p1wf_app` returned `42501`. A sequence `nextval` succeeded while sequence privileges were granted.

With the application and database containers still running, `REVOKE` removed the application role's business write and sequence privileges and left `SELECT`. Container id, `StartedAt`, and pid stayed the same. Health returned 200. A Prisma notification create failed. A direct `INSERT` into `Setting` returned `42501`. The pre-freeze rows remained.

An open Prisma transaction had inserted `p1wf_hold` and was waiting on `pg_sleep`. `pg_terminate_backend` from the break-glass role returned true. That row was absent afterward. The baseline row remained. Terminating the remaining `p1wf_app` backends did not change `StartedAt` or the container pid. Health returned 200 again. The pool class was `RECONNECTED`, not a process exit and not a container restart.

Restoring ordinary DML and sequence privileges left `p1wf_app` non-superuser and left `Setting` owned by `p1wf_migrator`. A new Prisma setting write and a new notification insert succeeded. `StartedAt` was still the pre-freeze value until the later P1 restart.

## Backup

After unfreeze, `pg_dump --no-owner --no-acl` as `p1wf_app` exited 0, and the same dump as `p1wf_migrator` exited 0. The migrator dump contained the baseline row. Restoring that dump into a new disposable database, `p1wf_restore`, owned by the migrator, reproduced the row. This was a database dump, not a single-table dump. The application-role dump was not repeated while sequence privileges were revoked.

## What this does not prove

The authenticated `getNotifications` server action, in-process dashboard cost recalculation, and warehouse or production HTTP actions were not executed. Those paths need an admin session and more fixtures than this rehearsal created. No mail account and no marketplace API were configured. A historical image that contains a pending migration was not started as the application role, so this package does not show `migrate deploy` succeeding at DDL. Production `pg_authid`, the running production containers, and packages C through G were not touched.

Design D's disposable database and historical-process mechanics measured here are supported. That is not acceptance of the design and not Owner approval of a permanent role split.
