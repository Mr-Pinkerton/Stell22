## 1. PSR-Q-004 — SHADOW write gate — CLOSED

Accepted mechanism: a dedicated DB `Setting`. Completely independent from `production_cost_flow`. Never reuse that key. Never activate or mutate `production_cost_flow`.

| | |
| --- | --- |
| Key | `inventory_movement_shadow_write` |
| Value | `{ "version": 1, "active": boolean }` |
| Missing Setting | inactive |
| `active: false` | inactive |
| `active: true` | active |
| Malformed value | fail closed (`InventoryMovementShadowWriteConfigError`) |
| UI | none |
| Startup / module cache | none — runtime read per call |
| Transaction | writer/read/mutate require `Prisma.TransactionClient` |
| Writer | SHARED advisory TX lock then read |
| Supported mutation | EXCLUSIVE control lock then upsert `{version:1, active}` via `setInventoryMovementShadowWriteGate(tx)` |
| Operator ON/OFF | maintenance CLI only (`scripts/set-inventory-movement-shadow-write.ts`) |
| Ad-hoc SQL | **not** a supported application/maintenance path |

Implementation: `src/server/internal/inventory-movement-shadow-write.ts`. Supported mutation is the transaction-only setter plus the dedicated ON/OFF CLI. Direct ad-hoc SQL against this Setting key is **not** a supported path.

This gate is **not** wired into physical writers in this task. There are still **no** InventoryMovement runtime writers.

## 3. R-10 — controlled SHADOW reset — CLOSED

Rejected (not introduced): run discriminator, `runId`, uniqueness changes, `epochId` in causal uniqueness, run data in `effectKey`.

Causal identity remains exactly:

`UNIQUE(causationKind, causationId, effectKey)`

`epochId` semantics unchanged.

Dedicated maintenance script (no UI / API / Server Action):

`scripts/reset-inventory-movement-shadow.ts`

Safety:

1. Explicit operator `--confirm=INVENTORY_MOVEMENT_SHADOW_RESET`.
2. Reads `inventory_movement_shadow_write`; refuses unless SHADOW writing is inactive (missing Setting = inactive; malformed fails closed).
3. Refuses if any `AUTHORITATIVE` InventoryMovement row exists.
4. Deletes **only** `authority = SHADOW`.
5. Never issues unrestricted `DELETE FROM "InventoryMovement"`.
6. One DB transaction.
7. Reports deleted SHADOW row count.

Coordination (transaction-scoped PostgreSQL advisory locks, two-int key `8322, 1`):

- Future SHADOW writers: SHARED `pg_advisory_xact_lock_shared` then read the gate, all in the same TX. Helper: `isInventoryMovementShadowWriteActiveForWriter(tx)` (`Prisma.TransactionClient` only). **Not wired** into physical writers in this task.
- SHADOW gate ON/OFF: same EXCLUSIVE `pg_advisory_xact_lock` as reset. Helper: `setInventoryMovementShadowWriteGate(tx, active)` acquires `acquireInventoryMovementShadowControlLock` then upserts. Maintenance CLI only; no UI / API / Server Action.
- Reset: EXCLUSIVE control lock **first** (`acquireInventoryMovementShadowControlLock`, alias `acquireInventoryMovementShadowResetLock`), then read the gate, then AUTHORITATIVE count, then SHADOW-only DELETE.
- Shared writers may run concurrently. Reset and gate mutation are mutually exclusive with each other and with every SHADOW writer. Locks are transaction-scoped.

The reset and ON/OFF scripts were **not** executed against production in this task.

## 4. R-11 — application append-only static guard — CLOSED

Normal application runtime must not mutate an existing InventoryMovement row.

CI/static policy: `scripts/security/check-inventory-movement-append-only.mjs`

`package.json` script: `security:inventory-movement-append-only`

Wired into `.github/workflows/ci.yml`.

Separate control-path policy: `scripts/security/check-inventory-movement-shadow-write-control.mjs` (`security:inventory-movement-shadow-write-control`). Direct Setting mutation of `inventory_movement_shadow_write` is allowed only in `setInventoryMovementShadowWriteGate` (`src/server/internal/inventory-movement-shadow-write.ts`). The ON/OFF CLI must call that setter and must not mutate Setting directly. `readInventoryMovementShadowWriteGate` is reset-only after exclusive lock. Ordinary runtime must not call the unlocked reader or the setter.

Rejects application source use of:

- `inventoryMovement.update(` / `updateMany(` / `delete(` / `deleteMany(` / `upsert(`
- raw SQL `UPDATE` / `DELETE` against `InventoryMovement`

Allowed non-runtime locations:

- migrations
- tests / integrity tests
- the dedicated R-10 SHADOW reset script

No broad exception mechanism. `create` / `createMany` / reads are **not** forbidden by R-11; this task does **not** add them.

DB-level immutability remains a **separate** later hardening before first AUTHORITATIVE use.
