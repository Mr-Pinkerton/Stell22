## Chain

```
CashFlow.amount
  → only if account.confirmed and flowType = EXPENSE     (deal-cost.ts:19–26)
  → Deal.total = purchase + max(0, expense − purchase)   (finance-operations.ts:337–341)
  → deal extra, shared by purchase weight                 (deal-cost.ts:33–55)
  → Batch.totalCost = purchase + extra, stored toFixed(2) (finance-operations.ts:311–315)
  → if production_cost_flow is active:
       applyActiveLateDeltaC(cOld, unrounded newTotal)   (finance-operations.ts:318–319)
  → BatchCost FINAL on freeze                            (cost.ts:372–386)
  → getCostReport reads FINAL columns for a frozen batch (cost-report.ts:201–215)
```

`Account.balance` is a cache. The balance used for display is `openingBalance` plus signed flows on and after `balanceAsOf` (`src/lib/account-balance.ts:37–41`), in JavaScript `number`. Confirmed and unconfirmed flows both move that balance (`finance.ts:238–241`). Deal cost, DDS rows, and KPI exclude unconfirmed accounts (`finance.ts:255–263`, `deal-cost.ts:19–26`).

The live report does not read `CostEvent` or `RailLot.remainingValue`. Those move only when the gate is on. The gate was on only in the disposable database.

## Invariants

| Invariant | Result |
| --- | --- |
| Sum of distributed extras = source extra | **Fail** when the extra does not split evenly at 2 dp. `100.00 / 3` persisted `99.99`. `0.01 / 2` persisted `0.02`. An unequal `100.01` persisted exactly `120100.01`. |
| Account debit = change in the computed balance | Holds in `account-balance.ts` for the signed amount, including transfers. The stored `Account.balance` cache is not that formula. Not re-executed as a transaction. |
| A transfer does not create income or expense | Holds on `createTransfer` and on `convertCashFlowToTransfer`, which clear the deal. **Fails** inside `sumConfirmedExpense` if a transfer row still has a `dealId` (`BA-P02-002`). The cashflow screen does not offer that link. |
| Cancel leaves no partial state | `deleteCashFlow` and `deleteDeal` resync inside the same transaction. Not executed here. |
| Repeating the same command does not double the money | **Holds** with the gate off: the second sync stayed on `129.99`, and `20 → 15 → 20` returned to `20`. **Fails** with the gate on: the same cash moved `remainingValue` on every sync (`BA-P02-001`). |
| Rounding keeps the sum | **Fails** for `Batch.totalCost` across batches and for FINAL `costSort1 + costSort2`. |
| PRELIMINARY vs FINAL | Report reads FINAL only. PRELIMINARY is deleted on freeze. A second freeze did not insert another FINAL. |

## Active contour

With the gate off, line 319 does not run. `Batch.totalCost` can be wrong by a kopeck and stays wrong; it does not walk further.

With the gate on, the kopeck (or the sub-kopeck fraction) is applied to `RailLot.remainingValue` from the unrounded total, then applied again because the next `cOld` is the rounded column. Details and the event rows are in `audit/09.06-cost-integration-tests.md`. This is `BA-P02-001`. It does not affect the live report while the setting is absent or `{active:false}`. Turning the gate on in production was not done and is not authorized.

## Phase 02B

The actions named in the tables above were called on `p1iso_98ec8238` (PostgreSQL 17.11). The gate stayed off. Numbers are in `audit/09.06-cost-integration-tests.md`. The pass/fail gate is in `audit/09.04-coverage-matrix.md`. This file does not call the domain complete.

What the run changed about the earlier read:

- `reapplyAutoRules` is a live way onto `BA-P02-002`. It does not skip `isTransfer`. One call linked two transfer expenses. KPI stayed at zero while `totalCost` became `130.00`.
- `assignCashFlow` does the same when given a `dealId`.
- Import of a payment between two of our accounts does not take the deal, even when a rule matches the purpose.
- `convertCashFlowToTransfer` and `deleteDeal` put the extra back.
- `Account.balance` is not updated by `createCashFlow` or `createTransfer`. The figure on `getFinanceData` is `computeAccountBalance`. After a transfer of `60` and an expense of `25` it was `-85` and `+60`.
- Two creates of a cashflow are two payments. There is no request id on `createCashFlow`. Deleting the second one returns the batch to the first amount.
- A package edit below the already consumed quantity was rejected and left the remaining quantity in place. The consumed quantity was written on the lot before the edit. The terminal operation that would have consumed it was not run.
- `writeOffBatchRemainder` of the same request id did not drive the lot negative. A different request id was rejected once the remainder was zero. The batch became `ARCHIVED`.
- Two concurrent assigns left the cashflow on exactly one deal. A second connection holding the deal row made `updateDeal` wait.

`BA-P02-003` was checked on the action: `0` and `-5` throw and insert nothing. The column still has no sign check. That remains an improvement.
