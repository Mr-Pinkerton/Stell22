### 1.1 `decideTorcovkaSubmit`

Файл `src/lib/torcovka-plausibility.ts`.

| Band | Нет ack | Неверный ack | Верный ack → persist |
| --- | --- | --- | --- |
| NORMAL | CREATED, все persist null | throw «Подтверждение отхода не требуется» | — |
| SUSPICIOUS | `{status:"ACK_REQUIRED", band:"SUSPICIOUS", railsTaken, takenM, producedM, wastePct}` | kind≠SUSPICIOUS или echo mismatch | band=`SUSPICIOUS`, reason=null, note=null |
| EXTREME | `{status:"ACK_REQUIRED", band:"EXTREME", ...canon}` | kind≠HIGH_WASTE; нет/невалидный `reason`; OTHER без trim note | band=`HIGH_WASTE`, reason=enum, note=trim или null |

Echo: `ack.railsTaken/takenM/producedM/wastePct` должны **байт-в-байт** совпасть с каноном (`takenM` 4dp, `wastePct` 2dp).

Причины: `CURVATURE|CRACKS|KNOTS|MATERIAL_DEFECT|COLOR_TEXTURE|WRONG_SIZE|OTHER`. OTHER → `reasonNote` обязателен.

### 1.2 `submitTorcovka` TX order (production `327b4ae`)

`src/server/terminal.ts` `submitTorcovka`:

1. `requireTerminalEmployee(employeeId)` — первым.
2. `requireClientRequestId`.
3. Валидация rails/picks (вне TX).
4. TX:
   1. fast `productionOperation.findUnique({ clientRequestId })` → `IDEMPOTENT_REPLAY`
   2. `lockRailLots(tx, [railLotId])`
   3. post-lock `findUnique` → replay
   4. lot/batch read, длина заготовки ≤ длина рейки
   5. `computeTorcovkaWasteMetrics` + INV-008 `producedM ≤ takenM`
   6. **`decideTorcovkaSubmit`** — `ACK_REQUIRED` = **return из TX без writes** (пустой commit)
   7. stock decrement `updateMany gte`
   8. `productionOperation.create` + lines + BlankStock
   9. `writeChangeLog` `{ type, batchId, railLotId, railsTaken, picks }` — **без reason/band/code**
   10. `archiveBatchIfDepleted`
5. Снаружи: duplicate unique → replay; `CREATED_NEW` → `enqueueRecalcBatchCosts`; `ACK_REQUIRED` **не** вызывает `revalidatePath`.
6. Публичный успех: всегда `{ status: "CREATED" }` (replay и новый insert неразличимы для UI).

DI-007 закрыт: committed тот же `clientRequestId` без ack → `CREATED`, не `ACK_REQUIRED`. Evidence: `src/server/integrity/di-007-008.integrity.test.ts` case 5.

## 3. APPROVAL MODEL (рекомендация)

Один активный approval на **один** `clientRequestId` (TORCOVKA EXTREME attempt).

Привязка обязательна ко всем сразу:

- `clientRequestId` (UNIQUE)
- `employeeId` (нельзя подтвердить чужую операцию чужим кодом)
- `batchId` + `railLotId`
- snapshot метрик: `railsTaken`, `takenM`, `producedM`, `wasteM`, `wastePct` (канонические строки как echo DI-020)

Не привязывать «только к сотруднику» или «только к цифрам кода».

`ProductionOperation` в момент запроса кода **ещё нет** → approval **нельзя** повесить на Op как обязательный FK в create-time. После успеха: `consumedAt` + ChangeLog `approvalId`; опциональный FK на Op **не обязателен** (лишняя колонка).

Состояния через timestamps, без enum:

- PENDING: `consumedAt IS NULL` AND `expiresAt > now()`
- CONSUMED: `consumedAt IS NOT NULL`
- EXPIRED: `consumedAt IS NULL` AND `expiresAt <= now()` (или `failedAttempts >= 5` форсирует expiry)

`CANCELLED` не нужен.

## 4. CODE GENERATION AND STORAGE

| | |
| --- | --- |
| Алфавит | `0000`–`9999`, leading zero. 4 символа, не number. |
| RNG | `node:crypto` `randomInt(0, 10000)` + `padStart(4,"0")`. В проекте уже `randomBytes` / `timingSafeEqual` (`src/lib/password.ts`). **Не** `Math.random()`, не PIN, не хвост `clientRequestId`. |
| Клиент | **Не** генерирует код. |

Сравнение A/B/C:

| | A plaintext в approval-строке | B hash/HMAC в approval-строке | C stateless signed token |
| --- | --- | --- | --- |
| Админ всё равно видит plaintext | в Notification.message | там же | в message или токене |
| Дамп `TorcovkaApproval` | живой код | не код | не код |
| 4-digit entropy | ~13 бит; offline brute hash тривиален если нет pepper **или** если plaintext в Notification | HMAC(`SESSION_SECRET`) чуть лучше при утечке только approval-таблицы | сложнее, хуже дедуп/consume |
| Простота киоска | макс | достаточна | избыточно |

**Рекомендация: B на строке approval** (`createHmac("sha256", SESSION_SECRET).update(code)`) + **plaintext только в `Notification.message`**. Verify: HMAC + `timingSafeEqual`. Не scrypt (это пароли; 4 цифры не выигрывают). Не сверка по тексту Notification.

Честность: пока код жив, он **есть plaintext в `Notification`**. Это требование владельца («админ видит код в колокольчике»), не дыра реализации. После consume/expiry — затереть message («код использован» / «код истёк») без цифр.

## 5. ONE-TIME + TTL

В проекте **нет** конвенции `expiresAt` (grep по `src/` пустой). **Рекомендация владельца 10 минут — принять.**

Инварианты:

- Код одноразовый: `consumedAt` только в том же TX, что успешный `productionOperation.create`.
- Не consume на validation error, нехватке реек, 500, rollback.
- Replay уже committed id **без кода** → `CREATED` (DI-007).
- Не регенерировать при повторном открытии диалога / повторном submit **с теми же метриками** до expiry.
- После expiry (или 5 неверных попыток, или смена метрик на том же id): **новый код + новая Notification**; старую message затереть.

## 6. DEDUP SAME `clientRequestId`

Первый EXTREME без валидного кода:

- `ensurePendingApproval`: find UNIQUE `clientRequestId`; если PENDING — вернуть as-is, **0 новых Notification**;
- если нет строки — insert + `notifyEvent` с `key = event:torcovka-approval:${approvalId}` (или `${clientRequestId}:${generation}`);
- public `{ status: "APPROVAL_REQUIRED", band:"EXTREME", echo metrics }` **без кода**.

Второй вызов тот же id, тот же PENDING: тот же код, без второго колокольчика.

Две одновременные первых попытки: `UNIQUE(clientRequestId)` + catch P2002 → find; `notifyEvent` first-write на generation key.

`ACK_REQUIRED` сегодня **не** делает `revalidatePath`. Admin увидит событие на poll ≤10 с или при открытии панели. Допустимо; опционально `revalidatePath("/", "layout")` на `APPROVAL_REQUIRED` ускорит SSR шапки.

## 8. LOCK / TX ORDER

Канонический `FOR UPDATE` набор: Account → Deal → Batch; RailLot и ProductionOperation — отдельные таблицы, сортировка id внутри таблицы. **Notification в набор не входит.**

Payroll/cost: `lockBatches` → `notifyEvent` (Notification upsert без `FOR UPDATE`).

**Нельзя:** Approval/Notification lock → потом RailLot (обратный порядок к stock TX).

Рекомендуемое разделение:

**TX-A `ensurePendingApproval` (нет RailLot):**  
read lot/batch (без lock) только для текста уведомления и snapshot → insert/find `TorcovkaApproval` UNIQUE → если новая generation: `notifyEvent` `isSystem=false`.

**TX-B stock (как сейчас + approval в конце цепочки):**

```
fast Op replay
lockRailLots
post-lock Op replay          ← DI-007
physics / INV-008
waste decision
  NORMAL / SUSPICIOUS ack — как сейчас
  EXTREME: SELECT TorcovkaApproval WHERE clientRequestId FOR UPDATE
           (после RailLot, никогда раньше)
           verify employee, snapshot metrics, not expired, not consumed,
           HMAC code, failedAttempts
           mismatch metrics / expired → не consume; outer path rotate
           wrong HMAC → increment failedAttempts в ЭТОМ TX и return WRONG_CODE
             (commit без stock — иначе increment откатится вместе с throw)
lock ProductionOperation не требуется на insert
stock decrement
create Op (reason/note = null, band = HIGH_WASTE)
consume approval (consumedAt)
ChangeLog без кода
archiveBatchIfDepleted
```

WRONG_CODE при `failedAttempts >= 5`: после commit TX-B-lite вызвать TX-A rotate.

Concurrent тот же id с правильным кодом: оба ждут RailLot; первый создаёт Op и consume; второй post-lock replay → CREATED; approval уже consumed — второй **не** должен снова verify, если replay сработал первым.

| Код в логах | Не логировать `approvalCode` / input целиком. Не класть в ChangeLog `newValues`. |
| Toast / URL | Кода нет в client response. Query запрещён. |

Новый Server Action **не нужен** (поле на существующем `submitTorcovka`). Ожидаемые counts: 113 public / 103 admin / 6 terminal / 4 auth.

## 15. AUDIT / TRACEABILITY

При успешном EXTREME ChangeLog (расширить текущий объект, **без кода**):

- `approvalRequired: true`
- `approvalId`, `generation`
- `consumedAt`
- `takenM`, `producedM`, `wasteM`, `wastePct`

`writeChangeLog.userId` сегодня на терминале **null** (нет admin session). Клики по колокольчику — только `isRead`, не approve.

**ADMIN IDENTITY ACTUALLY RECORDED: NO.** Любой админ, видящий общий список, может назвать код вслух. Система фиксирует «код совпал», не «User X нажал Approve». Не писать фальшивый `approvedBy`. Если владельцу понадобится именная авторизация — это **другой** UX (кнопка Approve в админке), вне текущего решения «код в колокольчике».
