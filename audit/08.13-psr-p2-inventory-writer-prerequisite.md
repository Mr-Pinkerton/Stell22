## 2. Transaction order

Authenticated admin is captured **outside** the transaction.

```text
const admin = await requireAdmin()
actor = userMovementActorFromAdmin(admin)
        ↓
BEGIN TX
        ↓
SHARED InventoryMovement advisory TX lock
  via isInventoryMovementShadowWriteActiveForWriter(tx)
        ↓
read/validate inventory_movement_shadow_write (inside that helper)
        ↓
evaluate Inventory SHADOW safety
        ↓
read production_cost_flow
        ↓
fail closed if unsafe
        ↓
ONLY THEN Inventory row FOR UPDATE
        ↓
legacy DRAFT fail-closed / load lines
        ↓
stock locks (global BlankStock set, then Nom/Product or ACTIVE pools)
        ↓
STALE_SNAPSHOT validation / physical plan from deriveInventoryPhysicalEffects
        ↓
existing physical projection behavior
        ↓
status / ChangeLog with retained USER actor
        ↓
COMMIT
```

Ordinary writer-facing SHADOW gate access uses only `isInventoryMovementShadowWriteActiveForWriter(tx)`. Inventory does not read `inventory_movement_shadow_write` directly.

## 4. Global BlankStock lock plan

### 4.1 Previous two-stage shape (removed)

```text
lockBlankSpecs(no-prisadka DETAIL specs)
then
lockBlankStockByIds(BLANK InventoryLine ids)
```

The package removes that two-stage / latent lock shape and structurally guarantees **one global canonical BlankStock acquisition pass**, as required by accepted `audit/08.11`.

This is **not** a claim that the old shape produced a proven reachable AB-BA deadlock in production. Independent review (P2-01) recorded that `assertNotLegacyInventoryDraft` emptied the first inactive batch on the conduct path, and that the ACTIVE second batch re-locked a subset of already-held rows in the same spec order. The change is structural/defensive, not a historical production-deadlock fix.

### 4.2 New plan

`planInventoryBlankStockLockSpecs` / `collectInventoryBlankLockSpecs`:

1. Direct `BLANK` InventoryLine `BlankStock.id` → physical tuple `(materialId, lengthM, detailType, sort)`.
2. DETAIL-related shared BlankStock tuples that the current Inventory lock plan can require (no-prisadka DETAIL aliases).
3. Deduplicate by canonical physical tuple.
4. Canonicalize `lengthM` with `canonicalLengthFixed4` / `canonicalLengthDecimal`.
5. Globally sort with `uniqueSortedBlankSpecs`.
6. Acquire BlankStock locks **once** for that set.

Input line order is irrelevant. Duplicate aliases collapse. `1.8` and `1.8000` are one target. Direct BLANK + no-prisadka DETAIL alias of the same tuple is one lock target. Missing BLANK ids are omitted (no invented tuple). Prisadka DETAIL lines do not add BlankStock targets.

`lockBlankSpecs` may still `createMany(... quantity: 0, skipDuplicates: true)` for a missing lock/projection row. That zero placeholder is **not** a physical movement and is **not** classified as an InventoryMovement writer.

### 4.3 ACTIVE cost-flow path

`ensureAndLockActiveBlankPools` locks the **same physical BlankStock rows** (FOR UPDATE by spec, with qty=0 ensure including cost fields). `lockActiveInventoryWriteSet` previously then called `lockBlankStockByIds` again — a second BlankStock batch on the same dependency.

That second batch is removed. ACTIVE Inventory now:

```text
lockDetails
collectInventoryBlankLockSpecs → ensureAndLockActiveBlankPools (one BlankStock pass)
ensureAndLockActiveDetailPools   // DetailStock cost pools, not BlankStock
ensureAndLockActiveNomPools
ensureAndLockActiveProductPools
```

Cost-flow valuation/accounting semantics, CostPool business behavior, and `production_cost_flow` activation are unchanged.

### 4.4 Cross-resource order (inactive)

```text
SHADOW advisory lock
→ Inventory row
→ Detail catalog
→ global BlankStock physical set
→ NomenclatureStock
→ ProductStock
```

ACTIVE keeps the already-established cost-flow pool order after the unified BlankStock pass. No new AB-BA relationship is introduced: every Inventory caller that locks BlankStock now uses the same global canonical spec order.

## 5. Retained USER actor

`conductInventory` captures `const admin = await requireAdmin()` before the transaction and builds `userMovementActorFromAdmin(admin)`.

The transaction core `conductInventoryInTransaction(tx, { docId, actor })` requires `actorKind = USER` with authenticated `User.id` and `actorDisplaySnapshot`. It does not re-resolve the user from the DB inside the TX. It does not hardcode `"Admin"`. It does not treat a marketplace/provider as actor.

The actor is written onto the Inventory CONDUCTED ChangeLog (`userId` + `actorKind` / `actorDisplaySnapshot` in `newValues`) and onto InventoryLine conduct ChangeLog `userId`. No InventoryMovement is created.
