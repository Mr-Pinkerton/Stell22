# P1 Data Integrity Remediation Plan

> **For agentic workers:** do not implement until this document is reviewed. When implementing: `superpowers:subagent-driven-development` or `executing-plans`. This file is the spec; `audit/01-data-integrity-*.md` is evidence.

**Goal:** Close DI-001, DI-002, DI-013, DI-003, DI-004, and DI-010 so source money/stock mutations cannot commit without the derived invariant, and concurrent imports/syncs cannot double-write. DI-011 stays out of scope.

**Architecture:** Reuse `syncBatchTotalCostInternal` / `syncDealInternal` semantics (full recompute, not increment). Give them an optional `Prisma.TransactionClient`. Wrap each source writer in one `$transaction` with derived writes. **CashFlow / `Account.confirmed` writers:** `SELECT Account … FOR UPDATE` (ids sorted) → Deal ids sorted → Batch ids sorted. **`updateBatch` stays Deal→Batch** (no Account lock; do not invert). Recalc queue and `revalidatePath` stay **after commit in Next/admin callers** — never inside `src/server/internal/*` (IMAP/CLI). Marketplace: lock the **union** of affected Supply keys in one deterministic order, lock/read live ProductStock, `computeSupplyDeduction` from that quantity. Import: DB UNIQUE on `Account.accountNumber` (non-null) **then** `CashFlow (accountId, importKey)`, plus empirically verified P2002 handling. Integrity DB: **`prisma migrate deploy` only** (no `db push`).

**Tech Stack:** Prisma 6.19.3, PostgreSQL 17, Vitest. Isolation remains READ COMMITTED (no Serializable rewrite).

**HEAD this plan assumes:** `5479580bdb1a33f53dec8005a2354456537ec8d4`

## 1. Unified invariant: purchase / total / deal / confirmed extras

### 1.1 What the fields are **today** (code, not v2 wish)

| Field | Meaning in running code |
| --- | --- |
| `Batch.purchaseCost` | Закупочная по счёту (лес). Schema L172 «ИСТИНА Стоимость партии». Used as **weight** for delivery share and as **mismatch** base vs P·V (`purchases.ts:47-59` uses purchaseCost, **not** totalCost). |
| `Batch.totalCost` | **C** for cost distribution: `lib/cost.ts` `const C = D(input.totalCost)`. Purchases column «Общая». createBatch initializes `totalCost = purchaseCost`. |
| `Deal.total` | `purchaseTotal + max(0, confirmedExpense − purchaseTotal)` i.e. purchase of linked batches + deal delivery extra. Written **only** by `syncDealInternal`. |
| Confirmed extras | `sumConfirmedExpense`: Σ `CashFlow.amount` where `flowType === "EXPENSE"` **and** `account.confirmed === true`. INCOME ignored **for Deal/C only**. **`isTransfer` is not filtered** (import does not assign deals to transfers; convert clears `dealId`). Unconfirmed Account is a **full** quarantine for all other finance aggregates — §1.7. |

Naming drift: `types/domain.ts` still calls `purchaseCost` «истина стоимости партии», while C for себестоимость is `totalCost`. Remediation does **not** rename columns.

### 1.2 Exact formula `Batch.totalCost` (`syncBatchTotalCostInternal`)

Let batch `B` with `purchaseCost = P`.

Let `Deals(B)` = all deals that have a `DealItem` with `batchId = B.id`.

For each deal `D` in `Deals(B)`:

```
expense(D)      = sumConfirmedExpense(D.cashFlows)   // EXPENSE ∧ account.confirmed
purchaseTotal(D)= Σ item.batch.purchaseCost           // null batch → 0
extra(D)        = max(0, expense(D) − purchaseTotal(D))
share(D, B)     = extra(D) * (P / purchaseTotal(D))   // if purchaseTotal>0
                  extra(D) / count(D.items)           // else equal split
```

```
B.totalCost = P + Σ_{D in Deals(B)} share(D, B)
```

If `Deals(B)` is empty: `totalCost = P`.

If `B.frozenAt != null` at **read**: function returns **without writing** (today). After this plan: also `updateMany where { id, frozenAt: null }` so a freeze race cannot write C.

`Deal.total` (same extras, not a sum of batch totals):

```
Deal.total = purchaseTotal(D) + extra(D)
```

A batch in two deals accumulates both shares into `totalCost`. That is current behavior; keep it.

### 1.4 Target invariant (one sentence)

**After any committed mutation of `purchaseCost`, Deal membership, CashFlow↔Deal, or `Account.confirmed`, every affected unfrozen `Batch.totalCost` and affected `Deal.total` equal the formula in §1.2, computed from the same snapshot as the source rows.**

```ts
type Db = Prisma.TransactionClient | typeof prisma;

  batchId: string,

  // return batchId if totalCost written (caller enqueues AFTER outer commit)

export async function syncDealInternal(
  dealId: string,
  db: Db = prisma,

  // return batchIds written; do NOT revalidatePath / enqueue here

```

Inside `syncBatchTotalCostInternal` (after locks in §1.5a):

1. Lock/read batch on `db` (`FOR UPDATE`). If missing or `frozenAt` set → return `null`.
2. Compute `newTotal` from **post-lock** rows (reads via `db`).
3. `db.batch.updateMany({ where: { id: batchId, frozenAt: null }, data: { totalCost } })`. If `count === 0` → freeze won, return `null`.
4. Do **not** call `enqueueRecalcBatchCosts` or `revalidatePath`. This module stays Next-free.

### 1.5a Concurrent Deal / Account writers (READ COMMITTED)

One TX that writes source+derived is **not** enough if two TXs attach CashFlows to the **same** Deal: both can read expense=0, both write `Deal.total` from a stale snapshot, last commit wins → one CF missing from C.

Deal→Batch alone is **also** not enough for `setAccountConfirmed`: it can snapshot `dealIds` **before** a concurrent `createCashFlow` / `assignCashFlow` / `reapplyAutoRules` inserts a new `dealId` on that Account, then set `confirmed=true` without syncing the new Deal.

**Canonical lock order — CashFlow / Account.confirmed mutations** (`createCashFlow`, `assignCashFlow`, `deleteCashFlow`, `createTransfer`, `convertCashFlowToTransfer`, `importStatementInternal`, `reapplyAutoRules`, `setAccountConfirmed`):

1. Collect affected **Account** IDs → `dedupe` → **sort by id ASC**, then
   `SELECT id FROM "Account" WHERE id IN (…) ORDER BY id FOR UPDATE`
2. Collect affected **Deal** IDs → `dedupe` → **sort by id ASC**, then
   `SELECT id FROM "Deal" WHERE id IN (…) ORDER BY id FOR UPDATE`
3. Collect affected **Batch** IDs (DealItems of those deals) → `dedupe` → **sort by id ASC**, then
   `SELECT id FROM "Batch" WHERE id IN (…) ORDER BY id FOR UPDATE`
4. Only then mutate source rows and recompute.

Several accounts (transfer, convert, import bind, reapply across accounts): lock **all** of them in sorted id order. Never lock a Deal before its Accounts on these paths. Never lock a Batch before its Deals.

**Canonical lock order — `updateBatch` only:** Deal ids sorted `FOR UPDATE` → Batch ids sorted `FOR UPDATE`. **Do not** lock Account here. `updateBatch` does not read/write `Account.confirmed` or CashFlow; adding Account would create a **reverse** order vs CF writers (Deal then Account) and deadlocks. CF writers already lock Deal after Account, so they serialize with `updateBatch` on the Deal row.

**`syncDealInternal(dealId, db)`:** must **not** compute from an unlocked Deal. Either the caller already holds the Deal lock (preferred for multi-deal fan-out) or the function locks `dealId` first. Then lock that deal’s batches (sorted) if not already held. **Then** read CFs/items and write `Deal.total` + per-batch C.

**`syncBatchTotalCostInternal(batchId, db)`:** `FOR UPDATE` that Batch (if not already held), **then** read `purchaseCost` / `frozenAt` / deals and compute C. Do not compute from a snapshot taken before the lock.

Helpers (internal, Next-free): `lockDealsThenBatches(tx, dealIds)` for `updateBatch`; `lockAccountsThenDealsThenBatches(tx, accountIds, dealIds)` for CF/account paths (`dealIds` may be empty — still lock Accounts).

**Do not** put `revalidatePath` in `finance-operations.ts`. A helper that calls Next APIs belongs in the `"use server"` module, not internal:

```ts
// src/server/finance.ts or purchases.ts — NOT internal
async function afterTotalsCommit(batchIds: string[]): Promise<void> {
  for (const id of [...new Set(batchIds)]) await enqueueRecalcBatchCosts(id);
  revalidatePath("/purchases");
  revalidatePath("/reports");
  revalidatePath("/finance");
}
```

IMAP/CLI (`statement-mail.ts`, `scripts/fetch-statements.ts`): after `importStatementInternal` returns affected batchIds, call **only** `enqueueRecalcBatchCosts` (no `revalidatePath`). Admin `importStatement` in `finance.ts` may enqueue + revalidate.

**Out of scope:** filtering `isTransfer` in `sumConfirmedExpense`. Do not change the formula except confirmed-account semantics already in place.

### 1.6 `updateBatch` (DI-001)

Changing `B.purchaseCost` changes `purchaseTotal(D)` for **every** deal that contains `B`. That changes `Deal.total`, `extra(D)`, and **weights for every other batch in those deals**, hence their `totalCost`. Syncing only `B` is insufficient.

```
ENTRY updateBatch
→ requireAdmin + validate
→ if frozenAt: reject if purchaseCost / priceSort1 / priceSort2 differ from stored
     (descriptive fields still allowed)
→ $transaction:
     dealIds = DealItem.dealId WHERE batchId = id  // before mutating
     if dealIds.length > 0:
       lockDealsThenBatches(tx, dealIds)          // Deal→Batch only; no Account
       tx.batch.update scalars                    // AFTER Deal locks
       for each dealId (sorted): syncDealInternal(dealId, tx)  // compute after locks
     else:
       lock this Batch FOR UPDATE (no deals)
       tx.batch.update scalars
       syncBatchTotalCostInternal(id, tx)         // no deals: C = P
     collect returned batchIds
→ AFTER COMMIT: enqueueRecalcBatchCosts for [...new Set(batchIds)]
→ changelog + revalidate (purchases.ts is admin/"use server" — revalidate OK here)
```

Must **not** `UPDATE Batch` before locking affected Deals: a concurrent `createCashFlow` could lock the Deal, read old `purchaseCost`, and commit extras while this TX still has the uncommitted new P. `updateBatch` still does **not** lock Account (§1.5a).

`syncDealInternal` already loops `item.batchId` → `syncBatchTotalCostInternal`. Calling it per affected deal is the minimal correct fan-out. Deduplicate batch IDs before enqueue (a batch in two deals would be returned twice).

Do **not** only call `syncBatchTotalCostInternal(id)` after a purchaseCost change when deals exist: sibling batches would keep stale C.

**Frozen:** locked decision — money fields forbidden; skip sync of C for that batch remains (frozen skip inside sync). Sibling unfrozen batches in the same deal still get syncDeal if we ever allowed P change — we will not, because P cannot change. If only name/note change on a frozen batch: **no** totals sync required.

### 1.7 Full financial quarantine (`Account.confirmed`) — DI-002

**Locked (owner, 2026-09-04):** `confirmed=false` is a **complete financial quarantine** of that Account, not only «не считать extras в Deal».

CashFlow of an unconfirmed Account **may**:

- be stored;
- be shown for **verification** (Settings → Счета per-account preview; `getStatementDetail`; statement row counters);
- have Article / `dealId` / auto-classification (`reapplyAutoRules`, import rules).

Until confirm they **must not** enter **any** business aggregate.

`false → true`: the whole already-loaded history of the account starts counting **by original `CashFlow.date` / `balanceAsOf`**, not by the confirm timestamp.

`true → false`: the account’s entire contribution is excluded again; **do not** delete CashFlow.

Future imports: if the Account is already `confirmed=true`, new operations participate **immediately** (same as today after import + `syncDealInternal`).

Opening / initial balance: if it feeds company «Остаток на счетах», it **must not** move company totals while `confirmed=false`. Local preview of that account’s own balance in Settings is allowed and is **not** a business aggregate.

#### 1.7.3 `setAccountConfirmed` writer

UI already toggles both ways (`settings-accounts-tab.tsx` L193-199). Same code path for confirm and unconfirm. **Do not** delete/rewrite CashFlow dates. **Do not** recalc every batch in the company — only deals that have a CF on this account **as of after the Account lock**.

**Race:** reading `dealIds` *then* locking Deals is wrong. Concurrent `createCashFlow` / `assignCashFlow` / `reapplyAutoRules` can attach a new `dealId` after that snapshot; confirm would set `confirmed=true` without `syncDealInternal` for the new Deal.

```
ENTRY setAccountConfirmed(id, confirmed)
→ requireAdmin
→ $transaction:
     SELECT id FROM "Account" WHERE id = $id FOR UPDATE
     dealIds = CashFlow.dealId WHERE accountId = id AND dealId IS NOT NULL
       // MUST be after Account lock, not before
     lock remaining: Deals sorted FOR UPDATE, then Batches sorted FOR UPDATE
     tx.account.update({ confirmed })
     each syncDealInternal(dealId, tx)   // compute after locks; sees new flag
→ AFTER COMMIT: enqueueRecalc for returned batchIds
→ changelog + revalidate /finance /purchases /reports /settings /dashboard
```

INCOME / `dealId=null` CFs are not in the Deal set; they still appear/disappear from ДДС/KPI/overhead/company balance via the confirmed filter on the next read — no Deal write needed. Empty `dealIds` is valid: still hold the Account lock for the duration of the flag update so a concurrent CF-with-deal waits, then that writer syncs with the new `confirmed`.

`false → true`: quarantined EXPENSE enter `sumConfirmedExpense` → extras/C may rise; INCOME/opening enter company/KPI/overhead by **operation dates**.

`true → false`: symmetric exclusion. CF rows remain.

#### 1.7.4 Client mutation leak (same finding)

`createCashFlow`: if the target Account is unconfirmed, **do not** prepend the row onto Finance DDS/`cashFlows` KPI state. Persist is fine.

`createTransfer` (two legs, possibly confirmed↔unconfirmed): filter **each returned leg by its own Account**. Confirmed leg **may** enter DDS state. Unconfirmed leg **must not**. Do **not** drop both legs only because one side is in quarantine. Convert-to-transfer already picks confirmed accounts only for the *other* side (~L691); if a convert ever involved a quarantined account, apply the same per-leg filter.

Settings/statement preview can still show unconfirmed legs after reload.

### 1.8 Other finance writers (DI-013) — same boundary

CashFlow writers of an Account **must join Account serialization** (§1.5a): lock that Account (or all involved Accounts, sorted) **before** inserting/updating/deleting CF and **before** Deal/Batch locks. Otherwise they race `setAccountConfirmed` on `dealIds`.

`createCashFlow`: lock Account → lock Deal (if `dealId`) → lock Batches → insert CF → `syncDealInternal`. Two concurrent creates on the same deal serialize on Account then Deal so the second recompute includes **both** CFs.

| Caller | Lock + how |
| --- | --- |
| `createCashFlow` | Account → Deal → Batch; insert CF then `syncDealInternal` if dealId |
| `assignCashFlow` | old+new Account (sorted) → old+new Deal → Batch; update CF then sync both deals |
| `deleteCashFlow` | Account(s) of deleted legs (sorted) → Deal → Batch; deleteMany then sync deal |
| `createTransfer` | both Accounts sorted → Deals if any → Batch; insert two legs; per-leg DDS filter §1.7.4 |
| `convertCashFlowToTransfer` | both Accounts sorted → Deal → Batch; legs + sync old deal |
| `createDeal` | Deal→Batch (no Account unless it also writes CF) |
| `updateDeal` | already I: add sync unlinked batches + new deal **inside**; Deal→Batch |
| `deleteDeal` | already I: add `syncBatchTotalCostInternal` per former batch **inside**; Deal→Batch |
| `importStatementInternal` | statement Account (sorted if several) **FOR UPDATE first**; after CF loop, `syncDealInternal` for `affectedDeals` **inside** same TX (new auto-accounts `confirmed=false` — extras 0; OK) |
| `deleteStatement` | Account of the statement → Deals of removed CFs → Batch; deal sync **inside** |
| `reapplyAutoRules` | one TX (or per-CF TX): lock **all** touched Account ids sorted, then Deal ids, then Batch; then apply article/`dealId` + sync. Per-CF TX is simpler and still atomic per row **if** each TX locks that CF’s Account first |

`enqueueRecalc` / `revalidatePath` always after the outer TX, and **only in the Next/admin or CLI wrapper**, not in `importStatementInternal` / `finance-operations`.

`importStatementInternal` already I: after CF loop, `syncDealInternal` for `affectedDeals` **inside** same TX. Return `{ statementId, affectedBatchIds, ... }`. `finance.ts:importStatement` enqueues + revalidates. IMAP (`statement-mail.ts`) enqueues only.

## 2. DI-003 — statement import idempotency

### 2.0 Prerequisite: canonical bank Account identity (first-import race)

`(accountId, importKey)` UNIQUE only serializes CashFlow **after** both TXs share one `Account.id`. First import of a bank account that **does not exist yet** never reaches that.

**Actual identity (code, not guess):**

| Piece | Role today |
| --- | --- |
| `Account.accountNumber` | **Canonical bank identity.** Parser: header `РасчСчет` (`bank-statement-1c.ts` L171-172). Import lookup: `findFirst({ where: { accountNumber: ourNumber } })` (`statement-import.ts` L198). UI preview match: `a.accountNumber === st.accountNumber`. Missing `РасчСчет` → throw (L179-180). |
| `Account.bik` | Stored on auto-create / patched if empty (L213, L224). Parser reads `БИК`. **Not** in `findFirst`. Not part of match. |
| `(accountNumber, bik)` | **Not** used. Do not invent it. |
| `Account.id` | After the row exists. `bindAccountId` is a fallback only when findFirst misses (manual account without number yet). |
| Manual `createAccount` | Does **not** set `accountNumber` (`finance.ts` L318-324) → `NULL`. Many NULL numbers are legitimate (cash / unlinked). |

Schema: `accountNumber String?`, **no** `@@unique`, no DB index beyond heap. Audit invariants already mark this WEAK.

**Race (READ COMMITTED), DB has no row for this `РасчСчет`:**

1. IMAP `importStatementInternal` and UI `importStatementInternal` of the **same** 1С file.
2. Both `findFirst` miss.
3. Both `account.create({ accountNumber, confirmed: false, … })`.
4. Two Account ids. Each TX inserts the same documents with the same `importKey` under **its** `accountId`.
5. `(accountId, importKey)` UNIQUE **does not fire**. Result: duplicate Account + duplicate CashFlow + two Statement headers.

This is **not** a legitimate two-Account model. Import, UI match, and «свои счета» transfer detection (`ourNumbers` from all non-null `accountNumber`) treat one `РасчСчет` as one Account. `findFirst` with duplicates is non-deterministic.

**Remediation (same DI-003, prerequisite before CF unique is sufficient):**

```sql
CREATE UNIQUE INDEX "Account_accountNumber_key"
  ON "Account" ("accountNumber")
  WHERE "accountNumber" IS NOT NULL;
```

Partial: NULL numbers stay allowed (manual accounts). Empty string would collide — import never stores empty (`!parsed.accountNumber` throws).

App: keep `findFirst({ accountNumber })` as **fast path**. UNIQUE is the authority. On P2002 for this index: **retry the entire import once** (winner committed; retry finds the Account and skips CFs). Measure the real Prisma P2002 `meta` for this index the same way as for CashFlow (§2.3) — do not assume `meta.target`.

Auto-create stays `confirmed: false`. Quarantine semantics (§1.7) **unchanged**. The surviving Account after a first-import race is still unconfirmed.

`bindAccountId` patch of `accountNumber` onto an existing row: if another Account already holds that number, UNIQUE fails — **throw**, no auto-merge.

Do **not** unique on `(accountNumber, bik)`: that would allow two rows with the same `РасчСчет` and different/null BIK, which current lookup would still collapse via `findFirst` on number only.

### 2.1 `importKey` semantics (actual)

`statementImportKey` (`src/lib/statement-import.ts:18-25`):

```
docNumber|date|amount.toFixed(2)|payerAccount|payeeAccount
```

Missing pieces become `""`, never `null`. Imported rows **always** set `importKey: key` (non-null string).

Manual `createCashFlow` does **not** set `importKey` → SQL `NULL`.

**Scope of uniqueness:** one bank document is one row **per account**. The same document can appear on **two** accounts (перевод: две выписки, одинаковые doc/date/amount/payer/payee, разные `accountId`). That is legitimate → uniqueness is **`(accountId, importKey)`**, not global `importKey`.

**NULL keys:** many manual CFs per account. PostgreSQL UNIQUE treats NULLs as distinct → `(accountId, NULL)` may repeat. Required.

**Empty string keys:** theoretically `"||||"` if parse produced empty doc; two such on one account would collide under UNIQUE. Acceptable (garbage-in).

### 2.2 Desired DB invariant

```sql
CREATE UNIQUE INDEX "CashFlow_accountId_importKey_key"
  ON "CashFlow" ("accountId", "importKey")
  WHERE "importKey" IS NOT NULL;
```

Partial unique is the precise invariant. Drop non-unique `CashFlow_accountId_importKey_idx` (`20260630164144`) in the same migration (redundant once unique exists; keep a matching Prisma `@@unique` if we use a full unique instead).

**Prisma schema:** `@@unique([accountId, importKey])` is acceptable on PostgreSQL (NULLs allowed). Prefer **partial** unique via raw SQL so we do not depend on NULL semantics of other providers. If using Prisma `@@unique`, do not also leave the old non-unique index.

App: keep `findFirst` as a **fast path** for sequential re-import (avoid throwing inside a 500-doc TX). UNIQUE is the race authority. **Never** rely on findFirst alone.

### 2.3 Race + loser behavior

READ COMMITTED, two import TXs, same account+key:

1. Both `findFirst` miss.
2. A `INSERT` commits.
3. B `INSERT` → unique violation → PostgreSQL **aborts B’s whole TX** (one import file = one I TX today).

Loser: **do not** catch P2002 per document without a savepoint (the rest of the file cannot continue in an aborted TX).

**P2002 metadata is not assumed** (CashFlow **or** Account unique). Prisma `meta.target` for a **raw/partial unique index** may be the index name, column list, or absent. Before writing the retry branch:

1. Apply **both** unique indexes on the integrity-test DB.
2. Snapshot P2002 for duplicate `Account.accountNumber` **and** duplicate `CashFlow (accountId, importKey)` separately (code/meta/constraint/target).
3. Retry/idempotent path matches **that** evidence. Import TX can hit Account unique (first-import) **or** CashFlow unique (existing Account) **or** Counterparty/Statement uniques — do not retry-blind on every P2002. Match measured Account-number and importKey discriminators; otherwise throw.

Outer handler on `importStatementInternal` (internal, **no** Next):

- On the empirically identified duplicate-**accountNumber** or duplicate-**importKey** error:
  - **Retry the entire import once** (winner already committed; retry is sequential skip / findFirst hits the Account).
  - If retry succeeds → return skipped/imported counts as usual.
  - If retry still conflicts → throw (unexpected).
- Sequential UI+UI after first success: findFirst skips, `skippedCount` increases, **one** extra `Statement` header today (no unique on Statement). Leave Statement duplication as P3 (out of this P1).

## 3. DI-004 — ProductStock / Supply concurrency

### 3.1 Algorithm today

Per normalized supply inside **one** big sync `$transaction`:

```
target     = (status in SHIPPED|ACCEPTED) ? quantity : 0
already    = deductedQty + shortfallQty
if target <= already || !productId → skip stock
available  = ProductStock.quantity or 0
{ toRemove, shortfall, newDeducted, newShort } = computeSupplyDeduction(...)
if toRemove > 0:
    productStock.update({ decrement: toRemove })   // NO gte
supply.update({ deductedQty: newDeducted, shortfallQty: newShort })
```

`computeSupplyDeduction` (`src/lib/supply-stock.ts`):

- Never requests `toRemove > available`.
- Never uses negative `available`.
- Does **not** fail the sync if stock is short: remainder → `shortfallQty` («потеря ГП»).
- Sequential retry: `target <= already` → no-op.
- **Does not restore** when `target = 0` (DI-011).

**Current business logic (do not change in DI-004):**

1. Sync is **not** refused when GP is insufficient.
2. Deduct what is available; record shortfall; **never go negative** (intent; implementation fails under concurrency).
3. Shortfall is **not** retried later even if stock is replenished (test «учтённая недостача не списывается повторно»). Keep that.

### 3.2 Race (READ COMMITTED) — gte on stock alone is not enough

Supply qty to ship = 8. `ProductStock = 100`. Two sync TXs:

| T | TX A | TX B |
| --- | --- | --- |
| 1 | read deductedQty=0, available=100, toRemove=8 | read deductedQty=0, available=100, toRemove=8 |
| 2 | `UPDATE ProductStock SET qty=qty-8 WHERE qty>=8` → 92 | waits on row lock |
| 3 | A not committed | `WHERE qty>=8` → 92≥8 → 84 (**second deduct**) |
| 4 | CAS/write deductedQty=8 | write deductedQty=8 |

Result: stock −16, supply says −8. **gte prevents negative when 10 vs 8+8, not double-apply when stock is ample.**

Need **one Supply delta applied once**: serialize on the Supply row **or** CAS `deductedQty`/`shortfallQty`.

### 3.3 Minimal atomic scheme (no `available=0` fallback)

Keep the existing outer sync TX.

**Deadlock vs two loops:** sorting the deduct list and sorting the cancel list **separately** is **not** a global lock order. TX A may lock deduct keys `{S1,S2}` then cancel `{S3}`; TX B may lock cancel `{S3,S1}` first → deadlock.

**Required:** at the start of the stock-mutating part of the TX, compute the **union** of:

- Supply keys that will be deducted (`marketplace, externalId, sku` from shipped supplies with a productId), and
- Supply keys that the Ozon cancel-restore loop will touch (`OZON` + cancelled externalId + sku of rows with `deductedQty > 0`),

then `FOR UPDATE` those Supply rows in **one** order `(marketplace, externalId, sku)` **before** any ProductStock change. Cancel restore stays the existing Ozon-list semantics (DI-011 unchanged: **no** generic PENDING→restore). If a key is only discovered after upsert, lock it immediately in the same comparator (insert into a sorted worklist, or lock remaining keys only if they sort **after** already-held keys; if a newly seen key sorts **before** a held key, abort TX and retry rather than lock backward).

**Fallback if union-at-start is too awkward for upsert-created rows:** document deadlock (`40P01` / Prisma `P2034`) as a **retryable** failure of the whole sync TX (one retry). Do not change deduct/shortfall/DI-011 semantics on retry.

Per supply, after `upsert` metadata (do **not** put deductedQty in that upsert), the row must already be in the locked set (or locked now per the rule above):

```sql
SELECT id FROM "Supply"
WHERE marketplace = $1 AND "externalId" = $2 AND sku = $3
FOR UPDATE;
```

Reload the locked Supply (`deductedQty`, `shortfallQty`). Then lock ProductStock if `productId` is set:

```sql
SELECT id, quantity FROM "ProductStock" WHERE "productId" = $id FOR UPDATE;
```

If no ProductStock row: treat `currentQty = 0` (same as today `ps?.quantity ?? 0`). Do **not** invent a failed-gte path.

```
available = currentQty from the locked row (or 0 if missing)
{ toRemove, shortfall, newDeducted, newShort } =
  computeSupplyDeduction({ targetQty, alreadyDeducted, alreadyShort, available })
if toRemove > 0:
  updateMany ProductStock
    where { productId, quantity: { gte: toRemove } }
    decrement toRemove
  // After FOR UPDATE on the same row, gte should succeed if currentQty was consistent.
  // If count===0 (should be impossible if we locked this row and computed from its qty):
  // throw — do NOT recompute with available=0. That would mark the whole delta as
  // shortfall while another TX may have the stock, violating current shortfall semantics.
await supply.update({ deductedQty: newDeducted, shortfallQty: newShort })
```

**Why not `available=0` after failed gte:** current semantics are «списать доступное, остаток дельты → shortfall». Forcing available=0 converts a lock/read race into «nothing deducted, everything shortfall» even when stock existed. After locking ProductStock, `computeSupplyDeduction` already uses the true remaining qty (e.g. 3 of 8 → toRemove=3, shortfall=5). That **is** the existing unit-test behavior.

`FOR UPDATE` on Supply: TX B waits until A commits, then sees `deductedQty=8`, `delta=0`, skip. **One apply.**

`FOR UPDATE` on ProductStock then compute: concurrent packing/inventory that also locks the stock row serializes; we deduct `min(delta, actual qty)`.

Supply **create** race: UNIQUE `(marketplace, externalId, sku)` already exists. Loser waits; then locks and sees A’s deductedQty.

Extract `applySupplyDeduction(tx, …)` from `marketplace-sync.ts` for tests. That helper stays in `internal/` (no Next).

**Do not** switch to failing the whole sync on shortfall.

Ozon cancel restore: only after the union lock; increment GP from `deductedQty`. **Do not** add generic PENDING→restore (DI-011 out of scope).

### 3.4 DI-010 / DI-011 vs DI-004

See §4–§5. **DI-004 does not require DI-011.** **DI-010 is not required for single-delta CAS**, but duplicate SKU makes `productIdForRecord` last-wins and can debit the **wrong** ProductStock even after a perfect CAS. Include DI-010 in this remediation as P1.

## 5. DI-011 — SHIPPED → PENDING (leave P2)

### 5.1 How status becomes PENDING

| Path | What happens to GP |
| --- | --- |
| Ozon `mapOzonSupplyStatus` default branch: `cancelled`, `created`, `READY_TO_SUPPLY`, `DATA_FILLING`, unknown → `PENDING`. Upsert `status`. Deduct branch `target=0` **skips**; **does not restore**. | leftover deductedQty |
| WB `mapWbSupplyStatusFromId` default (not 3/4/5/6) → `PENDING`. Same skip. **No WB cancel restore.** | leftover deductedQty |
| `fetchOzonCancelledSupplyOrderIds` → after deduct loop, restore `deductedQty`, zero counters, set `PENDING`. | GP returned (Ozon only) |

Ozon **happy path**: cancelled IDs restore even if the supplies list also mapped PENDING. If cancel-list fetch **fails**, supplies may still upsert PENDING **without** restore.

### 5.2 Business meaning

- Dedicated cancel loop = **real отмена отгрузки** for Ozon; GP **should** return (`marketplace-sync.ts:571-574`).
- Generic SHIPPED→PENDING from status mapping is **technical** (unshipped / unknown / cancelled without cancel-list). Treating every PENDING as restore would also restore when a supply was **never shipped** (`deductedQty=0` no-op) **and** when mapping flaps. Restoring on every `target=0 && deductedQty>0` is the correct *idempotent inverse* of deduct, and would fix WB + failed cancel-list.

That inverse would be a behavior change. **Keep DI-011 P2 / out of scope.** This remediation implements **no** generic PENDING→restore and **no** marketplace-agnostic inverse of deduct. Only the existing Ozon cancel-list restore remains.

## 7. Migration safety

### 7.1 DI-003 UNIQUE Account.accountNumber then CashFlow importKey

Account unique is a **prerequisite**: apply it in the **same** migration **before** the CashFlow unique (or in an earlier migration of the same release). CF unique alone does not close first-import.

| Step | Action |
| --- | --- |
| Preflight | SQL §2.4 (Account dupes **then** CF dupes); **STOP + print rows** if either; add to `scripts/preflight-prod.sh`. Does **not** close the race until migrate. |
| Migration | **One explicit PostgreSQL transaction** (`BEGIN;` … `COMMIT;` in `migration.sql`). Prisma 6 classic PostgreSQL `migration.sql` is **not** wrapped in a transaction automatically. **Not** `CREATE INDEX CONCURRENTLY`. Order: `LOCK TABLE "Account"` → recheck number dupes → `RAISE` or `CREATE UNIQUE INDEX … WHERE "accountNumber" IS NOT NULL` → `LOCK TABLE "CashFlow"` → recheck importKey dupes → `RAISE` or drop old CF index + create unique. **No auto-fix / auto-merge.** |
| App | Same release: findFirst + outer retry using **measured** P2002 for **both** indexes. **Order:** preflight → pull/rebuild → entrypoint `migrate deploy` → start. |
| Rollback | `DROP INDEX` both uniques; restore non-unique CF index. Cannot un-create rows. |
| Limitation | Dupes at migrate time → migration **fails**, container does not boot. Never auto-fix data. |

Sketch (same `migration.sql`, Account first):

```sql
BEGIN;

LOCK TABLE "Account" IN ACCESS EXCLUSIVE MODE;

DO $$
DECLARE
  dup text;
BEGIN
  SELECT string_agg(format('%s (%s)', id, "accountNumber"), ', ')
  INTO dup
  FROM "Account"
  WHERE "accountNumber" IS NOT NULL
    AND "accountNumber" IN (
      SELECT "accountNumber" FROM "Account"
      WHERE "accountNumber" IS NOT NULL
      GROUP BY 1 HAVING COUNT(*) > 1
    );

  IF dup IS NOT NULL THEN
    RAISE EXCEPTION
      'DI-003: duplicate Account.accountNumber: %; resolve before migrate (no auto-merge)',
      dup;
  END IF;
END $$;

CREATE UNIQUE INDEX "Account_accountNumber_key"
  ON "Account" ("accountNumber")
  WHERE "accountNumber" IS NOT NULL;

LOCK TABLE "CashFlow" IN ACCESS EXCLUSIVE MODE;

DO $$
DECLARE
  dup text;
BEGIN
  SELECT string_agg(format('%s / %s', "accountId", "importKey"), ', ')
  INTO dup
  FROM (
    SELECT "accountId", "importKey"
    FROM "CashFlow"
    WHERE "importKey" IS NOT NULL
    GROUP BY "accountId", "importKey"
    HAVING COUNT(*) > 1
  ) d;

  IF dup IS NOT NULL THEN
    RAISE EXCEPTION
      'DI-003: duplicate CashFlow (accountId, importKey): %; resolve before migrate (no auto-fix)',
      dup;
  END IF;
END $$;

DROP INDEX IF EXISTS "CashFlow_accountId_importKey_idx";

CREATE UNIQUE INDEX "CashFlow_accountId_importKey_key"
  ON "CashFlow" ("accountId", "importKey")
  WHERE "importKey" IS NOT NULL;

COMMIT;
```
