## 2. INVENTORY FLOW

```
[создание черновика]  createInventoryDraft(includeAllActive)
   getWarehouseStock()                      ← ЧТЕНИЕ живых остатков
   findFirst({status: DRAFT})                 (не unique в БД — DI-016)
   Inventory.create({ status: DRAFT, lines: [...] })
        для каждой строки:
          accountedQty = живой остаток на этот момент
          actualQty    = accountedQty          (предзаполнение)
          deviation    = 0
          deviationSum = 0
   ChangeLog { entity: "Inventory", newValues: { status: DRAFT, lines: N } }

[подсчёт]  updateInventoryLineActual(lineId, qty)  × N раз, в произвольный момент
   InventoryLine.actualQty = qty
   ChangeLog { entity: "InventoryLine", oldValues: {actualQty}, newValues: {actualQty} }
   accountedQty НЕ обновляется. Inventory.date НЕ обновляется.

[проведение]  conductInventory(docId)
   ── ВНЕ транзакции ──
   doc = Inventory.findUnique({ include: lines })
   if (doc.status !== "DRAFT") throw
   valuation = getUnitCostSnapshot()          ← тяжёлое чтение, период = ТЕКУЩИЙ месяц
   ── $transaction (READ COMMITTED, без lock’ов) ──
   для каждой строки:
      deviation    = actualQty − accountedQty       ← accountedQty СТАРЫЙ, из черновика
      deviationSum = round(deviation × unitCost, 2) ← float-арифметика
      *Stock.upsert(... update: { quantity: actualQty })   ← АБСОЛЮТНЫЙ SET
      InventoryLine.update({ deviation, deviationSum })
   Inventory.update({ where: { id: docId }, data: { status: CONDUCTED } })
                       ↑ БЕЗ guard’а status: "DRAFT"
   ChangeLog { entity: "Inventory", oldValues:{status:DRAFT}, newValues:{status:CONDUCTED, lines:N} }
   ── commit ──
```

Ключевое: между созданием черновика и проведением проходит произвольное время (в production — **59 дней**, §8), и `accountedQty` за это время не пересчитывается, а живой остаток на момент проведения **не читается вообще**.

## 4. CONDUCT SEMANTICS

### 4.1 Разбор по каждому изменяемому остатку

Обозначения: `A` = `accountedQty` (снимок при создании черновика), `F` = `actualQty` (введённый факт), `L` = живой остаток в БД на момент проведения.

| refType | BEFORE (что реально в БД) | counted | delta, который применён | AFTER | delta, который записан в `InventoryLine.deviation` |
| --- | --- | --- | --- | --- | --- |
| `PRODUCT` | `L` | `F` | `F − L` (неявно) | `F` | `F − A` |
| `NOMENCLATURE` | `L` | `F` | `F − L` (неявно) | `F` | `F − A` |
| `DETAIL` без присадок | `L` (пул `BlankStock`) | `F` | `F − L` | `F` | `F − A` |
| `DETAIL` с присадками | `L = Σ` готовых корзин | `F` | `F − L` | канон = `F`, прочие готовые = `0`, НЗП без изменений | `F − A` |

Если `L ≠ A` (остаток двигался после создания черновика), то **применённый delta ≠ записанный delta**. Записанный `deviation` в этом случае не описывает произошедшее.

Проверка корректности `normalizeReadyBuckets` (`detail-stock.ts:88`): `createInventoryDraft` берёт `accounted = d.ready` (`warehouse.ts:249`, `:252`), где `ready` = сумма **готовых** корзин (`detail-stock.ts:162`). Проведение приводит сумму готовых корзин ровно к `F`. Суммы согласованы, двойного счёта готовых нет — **A9 реализован корректно**, это не находка.

### 4.3 Побочные находки в проведении

1. **`Inventory.date` не обновляется при проведении.** Ставится `new Date()` в `createInventoryDraft` (`warehouse.ts:261`) и больше не меняется. В production документ имеет `date = 2026-07-06`, а проведён `2026-09-03` (§8). UI истории показывает `doc.date`, т.е. дату черновика, а не дату применения корректировки.
2. **`deviationSum` пишется, но никогда не читается.** `serializeDoc` (`warehouse.ts:172-208`) возвращает `unitCost`, но **не** `deviation` и **не** `deviationSum`; `InventoryLineRow` этих полей не содержит (`warehouse-fixtures.ts:40-49`). UI пересчитывает сумму на лету через `inventoryDeviationSum(deviation, line.unitCost)` (`warehouse-inventory-tab.tsx:320-323`, `:380`), где `unitCost` берётся из `getUnitCostSnapshot()` **текущего месяца** (`cost.ts:299`, дефолт `getMonthPeriod()`). Следствие: денежная оценка исторической инвентаризации **дрейфует** вместе с текущей себестоимостью; замороженное значение из БД игнорируется. Прямая параллель с DI-006 («PRELIMINARY не SoT»).
3. **Деньги считаются во `float`.** `Math.round(deviation * unitCost * 100) / 100` — `warehouse.ts:327-329` и `warehouse-stock.ts:31`. `.cursor/rules/cost-integrity.mdc` требует `Decimal` для сумм. SPEC DRIFT (масштаб — копейки на строке).
4. **`valuation` читается вне транзакции** (`warehouse.ts:322`), как и проверка `status` (`warehouse.ts:317`). Подтверждает запись в `01-data-integrity-map.md:90`.
5. **Aliasing пула заготовок.** `Detail` **не** имеет unique на `(materialId, lengthM, detailType, sort)` (`schema.prisma:260-284`, только не-unique `@@index([materialId, detailNumber])`). Если две детали **без присадок** делят одну спецификацию, то (а) `buildStockSnapshot` начисляет один и тот же пул в `detailsReady` каждой из них (`detail-stock.ts:150-154`) → `accountedQty` двойной; (б) проведение делает `SET` в одну и ту же строку `BlankStock` дважды → выигрывает последняя строка документа. В production **недостижимо**: деталей без присадок 0 (§8). DESIGN RISK.

## 5. PROVENANCE TODAY

Задачи A и B, как их требовалось разделить.

### A. Физическая инвентаризация — «на складе реально X, система должна стать X»

Реализована и по существу работает: черновик, ввод факта, абсолютное приведение остатка к факту, фиксация отклонения. Для плоских обезличенных пулов (`ProductStock`, `NomenclatureStock`, готовые корзины `DetailStock`) абсолютный SET — **корректная и естественная** семантика. Это **EXPECTED / INTENTIONAL DESIGN**, а не баг.

Дефект не в SET как таковом, а в том, что SET применяется к **устаревшей базе**: `A` заморожен при создании черновика, `L` не читается, блокировок нет.

### B. Provenance — «из каких операций / партий / поступлений образовался X»

| Уровень | Нужен ли provenance | Обоснование |
| --- | --- | --- |
| `RailLot` / партия | **да, есть** | `batchId`, `Batch.totalCost`, распределение по сортам. Инвентаризация сюда не лезет. |
| `BlankStock` (пул заготовок) | **нет — явное решение владельца** | `cost-integrity.mdc`: «усреднение ограничено одной породой, суммы сходятся. Не “чинить” блендинг… без перехода на FIFO-слои». |
| `DetailStock` | **нет** | ключ — стадия присадки, не партия. Себестоимость детали считается через WAC ₽/м по породе. |
| `ProductStock` / `NomenclatureStock` | **нет** | плоские счётчики; для реверса операции provenance берётся из `OperationDetailLine` / `OperationNomenclatureLine`, а не из остатка. |

**Вывод:** per-lot / per-piece provenance в пулах, которые пишет `conductInventory`, бизнесу **не нужен** и в текущей модели отсутствует намеренно. Формулировка исходной гипотезы «ломает provenance» в этой части **не подтверждается**: ломать нечего.

Что действительно требуется для корректности — **не** provenance, а **adjustment record**: зафиксированные `before` / `after` / `applied delta` / `reason`, чтобы соотношение

```
остаток = Σ(движений по журналу операций) + Σ(корректировок инвентаризации)
```

было проверяемым. Сегодня правая часть неполна: applied delta не сохраняется, `before` не сохраняется, `reason` не существует. Поэтому после любого проведения с ненулевым отклонением расхождение «склад vs журнал производства» становится **необъяснимым по данным** — не потому что потерян provenance, а потому что не записана сама корректировка.

| 5 | `deleteProductionOperation` (UPAKOVKA) `production.ts:443-446` → `reverseUpakovkaOperation` | сначала `productStock.updateMany({ where: { productId, quantity: { gte: productQty } }, data: { decrement } })` `production-reversal.ts:323-326` — **gte-guard**, бросает «Нельзя изменить/удалить: изделие уже отгружено/продано» при нехватке. Затем по каждой detail-строке `detailStock.upsert({ update: { quantity: { increment: 20 } } })` `production-reversal.ts:362-377` — **increment без guard’а, всегда проходит** | **95** |

**Ответ: система даёт 95.** Не 100 и не 75.

Что система «считает правильным»: у неё нет мнения. `reverseUpakovkaOperation` возвращает ровно то, что зафиксировано в `OperationDetailLine`, безусловным `increment`, ничего не зная о проведённой инвентаризации. Инвентаризация, в свою очередь, ничего не знает об операциях.

Бизнес-смысл 95 зависит от того, чего система различить не может:

- если УПАКОВКА **физически была**, а изделие потом разобрали → 95 **верно**;
- если запись об УПАКОВКЕ была **ошибочной** (детали никуда не уходили) → они лежали на полке и уже вошли в пересчёт 75; `+20` — **двойной счёт**, верно 75.

Это **NEEDS BUSINESS DECISION**, а не автоматический баг: правило «что есть истина после инвентаризации» не задано ни кодом, ни JSDoc, ни v2.

## 7. CONCURRENCY

Изоляция подтверждена на production: `SHOW transaction_isolation` → **`read committed`**. Override в коде отсутствует — `src/server/db.ts` создаёт `PrismaClient` без `transactionOptions`; grep `isolationLevel|Serializable` по `src` — совпадений нет.

Блокировки в `conductInventory`: **ни одной**. Ни `lockBatches` / `lockProductionOperations` / `lockRailLots` (`finance-operations.ts:118-137`, `SELECT … FOR UPDATE`), ни `lockProductStockQty` (`supply-deduct.ts:65`). Для сравнения — соседние write-path’ы блокировки берут: `terminal.ts:363`, `production.ts:403/484/499/503`, `payroll.ts:202/240`, `purchases.ts:444`, `supply-deduct.ts:130`, `marketplace-sync.ts:595`.

### 7.1 Главный механизм: stale read → absolute SET

Окно потери **не микросекундное**. Она возникает из-за разрыва между двумя разными моментами:

```
t0  createInventoryDraft:  accountedQty := L(t0)
        ... часы / дни ...  (в production: 59 дней)
t1  любое движение:        L меняется на L(t1)
t2  conductInventory:      SET quantity = actualQty
                           L(t2) не читается, delta не считается
```

Всё, что произошло между `t0` и `t2`, стирается без следа и без ошибки. Это **lost update**, но реализуемый обычным использованием, без гонки.

### 7.2 Матрица сценариев

| Сценарий | Строки конкурента | Результат |
| --- | --- | --- |
| `conduct` ‖ `submitUpakovka` (потребление деталей/крепежа) | `production-reversal.ts:246`, `:267` | Списание конкурента **теряется**, если он успел между `t0` и `t2`. Внутри TX conduct’а строковая блокировка Postgres сериализует записи, но абсолютное значение всё равно перезаписывает. **Lost update — подтверждён.** |
| `conduct` ‖ `submitUpakovka` (приход `ProductStock`) | `production-reversal.ts:299` | То же: `increment` конкурента затирается абсолютным SET. |
| `conduct` ‖ `submitTorcovka` (приход `BlankStock`) | `terminal.ts:418` | Затрагивается только для деталей без присадок. В prod недостижимо. |
| `conduct` ‖ `createSimplePurchase` (приход крепежа) | `purchases.ts:528` | Приход теряется. |
| `conduct` ‖ `applySupplyDeduction` (списание МП) | `supply-deduct.ts:130-143` | `FOR UPDATE` конкурента **не спасает**: он блокирует строку, conduct ждёт, затем пишет свой устаревший абсолют. Обратный порядок (conduct раньше) безопасен — конкурент прочитает уже скорректированное значение. Итог зависит от порядка. |
| `conduct` ‖ Ozon cancel restore | `marketplace-sync.ts:595-602` | Аналогично: возврат теряется, если conduct коммитится позже. |
| Два `conduct` одного документа | `warehouse.ts:317` (проверка вне TX) + `:402` (`where` без `status`) | Оба проходят. Остаток сходится (идентичный абсолют дважды), документ и `ChangeLog` дублируются. **Порчи остатка не подтверждено.** |
| Два DRAFT одновременно | `warehouse.ts:230` `findFirst`, в БД unique нет (проверено `pg_indexes`) | Два черновика; проведение обоих = два абсолютных SET, второй затирает первый. Это **DI-016**, здесь усиливается: два DRAFT делают потерю детерминированной, а не гоночной. |
| `conduct` ‖ `deleteProductionOperation` | `production.ts:402` | Реверс берёт `lockProductionOperations` + при TORCOVKA `lockBatches`, но **не** блокирует stock-строки. Порядок коммитов определяет исход; абсолютный SET побеждает. |

Row-level lock’и Postgres гарантируют, что записи не «порвутся». Они **не** предотвращают lost update, потому что conduct не перечитывает значение под блокировкой и не использует условный `updateMany`, как остальные write-path’ы.

### f-1. Потеря движений за время открытого черновика (главный сценарий)

```

...    submitUpakovka × 12         ProductStock(P) = 112   (increment, production-reversal.ts:299)
...    applySupplyDeduction −30    ProductStock(P) =  82   (gte decrement, supply-deduct.ts:140)
03.09  кладовщик считает полку:    физически 82, вводит actualQty = 82

                                   deviation = 82 − 100 = −18
                                   deviationSum = −18 × unitCost  ✘ ложная «потеря ГП» на 18 шт
```

Остаток случайно верен (кладовщик считал после всех движений), но **записана недостача 18 единиц, которой не было**: 12 прихода и 30 списания просто не учтены в базе сравнения. Обратный вариант — кладовщик считал 07.07 (`actualQty = 100`), провёл 03.09: `SET quantity = 100` **уничтожает** и 12 прихода, и 30 списания, `deviation = 0`, «расхождений нет». Оба исхода без единой ошибки в логах.

### f-2. Два DRAFT (DI-016) делают потерю детерминированной

`findFirst({status: DRAFT})` без БД-unique (`warehouse.ts:230`, подтверждено отсутствие индекса на проде). Два черновика A (accounted 100) и B (accounted 100). Считают разные люди в разное время: A → 95, B → 98. Проводят A, затем B: `SET 95`, затем `SET 98`. Итог 98, отклонения записаны оба (`−5` и `−2`), физическая реальность одна. Потеря не гоночная — просто «последний провёл».

### f-3. Реверс после инвентаризации вниз — блокировка с неверным сообщением

`DetailStock(D, (t,f)) = 40`. PRISADKA-операция создала 15 из них. Инвентаризация: факт 30 → `SET 30`. Админ удаляет ту PRISADKA → `reversePrisadkaLine` `production-reversal.ts:122-133`: `updateMany where quantity gte 15` на корзине `(t,f)` — проходит (30 ≥ 15), остаток 15, `+15` в источник. Если бы факт был 10 → `dec.count === 0` → **«Нельзя изменить/удалить: деталь уже использована в упаковке или дальнейшей присадке»**. Причина не в упаковке, а в инвентаризации. Админ не может ни удалить операцию, ни понять почему.

### f-4. Реверс после инвентаризации — раздувание пула

Полный разбор в §6.1: 100 → 80 → инвентаризация 75 → реверс УПАКОВКИ `+20` безусловным `increment` → **95**. Если операция была записана ошибочно, 20 единиц в системе появились из ничего. `ProductStock` при этом gte-защищён, поэтому реверс либо пройдёт целиком, либо упадёт до начала возврата деталей — «половинного» состояния не будет.

### f-5. Двойное проведение

Два клика / два запроса. Оба читают `status = DRAFT` вне TX (`warehouse.ts:315-317`), оба входят в TX, `Inventory.update` без guard’а `status` (`warehouse.ts:402`). Остатки: одинаковый абсолют дважды → результат тот же. `ChangeLog`: два события `DRAFT → CONDUCTED`. `deviationSum`: два независимых `getUnitCostSnapshot()` → значения могут отличаться, побеждает последний. **Порча остатка не подтверждена.**

### f-6. Aliasing пула заготовок (сегодня недостижим)

Две активные детали без присадок с одной спецификацией. Черновик: обе строки `accounted = blanksQty` (двойной счёт одного пула, `detail-stock.ts:150-154`). Проведение: два `SET` в одну строку `BlankStock` → побеждает последняя строка документа. В production деталей без присадок 0 (§8.3) — сценарий не реализуем без изменения справочника.

### f-7. Дрейф исторической оценки

Документ проведён в июле, `deviationSum` записан по июльской себестоимости. Открываем историю в сентябре: UI берёт `unitCost` из `getUnitCostSnapshot()` за **сентябрь** и пересчитывает сумму (`warehouse-inventory-tab.tsx:320-323`). Замороженное значение в БД не читается. Сумма «потери ГП» в июльском документе меняется от месяца к месяцу.

### f-8. Неинвентаризируемые остатки

`BlankStock` для деталей с присадками, НЗП-корзины `DetailStock`, `RailLot`, `MpStock` — привести к факту нельзя ни одним действием. Для `RailLot` это документированное решение (INV-061). Для заготовок и НЗП — **не документировано**; расхождение по ним неустранимо в приложении.

## 11. DI-009 VERDICT (после owner decisions 2026-09-04)

Нормальный бизнес-процесс: остановить производство и все движения → создать DRAFT → пересчитать → ввести факт → провести → возобновить работу. `conductInventory || production/purchase/marketplace` **не** является поддерживаемым процессом и **не** классифицируется как основной finding «CONFIRMED RACE». Код технически допускает одновременность — это **INVARIANT WEAKNESS** (нет guard’а процесса), а не описание штатной гонки.

### 11.1 Проверка исходной гипотезы

Гипотеза *«`conductInventory` ставит qty=X, ломает reverse/provenance»*:

| Утверждение | Вердикт |
| --- | --- |
| «ставит qty = X» | **EXPECTED / INTENTIONAL.** Абсолютный SET — правильная семантика после guard `live == accountedQty`. |
| «ломает reverse» | **INVARIANT WEAKNESS**, закрывается BD-9.2: reverse старой операции не должен пересекать более позднюю CONDUCTED inventory по затронутому ref. Раздувание 75+20=95 — нарушение границы, не «баг provenance». |
| «ломает provenance» | **НЕ ПОДТВЕРЖДЕНО.** Пулы обезличены намеренно. Lot/FIFO/ledger не требуются. |

### 11.2 Главный дефект (переформулирован)

Не «lost update из-за параллельного packing». Главное: **устаревший DRAFT можно провести**. `accountedQty` — база снимка; live при проведении не сверяется; `deviation`/`deviationSum` могут описывать не ту корректировку; история пересчитывает сумму по live cost. Production: черновик 59 дней, но **строк 0 — исторической порчи нет**.

| # | Компонент | Классификация |

## 12. BUSINESS DECISIONS — ЗАФИКСИРОВАНЫ

| ID | Решение владельца 2026-09-04 |
| --- | --- |
| Процесс | На время инвентаризации производство и движения **физически останавливаются**. Concurrent conduct \|\| production/purchase/MP — не штатный процесс. Приложение всё равно обязано **защищать** от нарушения (snapshot guard). |
