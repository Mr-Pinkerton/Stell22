## 2. Executive summary

Stell22 is a **modular monolith** (Next.js 16 Server Actions → Prisma 6 → PostgreSQL 17) that already runs a real production chain:

```text
Batch/RailLot → TORCOVKA → BlankStock → PRISADKA → DetailStock → UPAKOVKA → ProductStock
                                                      ↘ NomenclatureStock
Finance/Deal ──► Batch.totalCost ──► BatchCost FINAL (wood history)
Payroll ──► Payment + DI-015 rate snapshots
Inventory ──► absolute qty SET + CONDUCTED boundary
```

**Current accepted runtime** (gate inactive) is quantity-first MES plus live cost reconstruction. Data-integrity P1/P2 cards DI-001…010, 013–016, 018–020 are **CLOSED IN PRODUCTION**. Security P0 admin-mutation holes from 00.5 are **remediated in code** (`requireAdmin` / `requireTerminalEmployee` in action bodies; secrets and reverse helpers moved to `src/server/internal/`). The 00.5 findings file itself still does not record CLOSED — that is a documentation lag, not a new exploit.

**The system is not yet one monetary ERP.** Package 2/3 cost-flow writers exist behind `production_cost_flow` but:

- `CostPeriod` / `ProductCost` have **no closeMonth writers**;
- `getCostReport` still rebuilds live species WAC + period labor + CF overhead;
- stock `materialValue`/`laborValue`/`costVersion` are uninitialized (`costVersion=0`) until activation + bootstrap.

That split is **intentional package sequencing** (`audit/03.02`, `PROJECT.md` activation `BLOCKED`), not a current-production dual-write bug.

**Adversarial review (2026-09-09, accepted):** P1 on active UPAKOVKA qty edit **kept** (`NEWLY CONFIRMED FROM PREVIOUS CANDIDATE`). P2 / missing / questions reclassified or rejected (history in §16–19). Dual writer tree kept as **temporary migration debt**.

**Final architecture assessment**

- Whole-system architecture did **not** show a P0 systemic failure.
- Major existing integrity/security findings are already in the canonical audit program (SEC/DI registers). This pass did not reopen them without new evidence.
- The one new systemically significant defect is **`ARCH-P1-001`** (active UPAKOVKA quantity edit skips `old ∪ current` inventory-boundary refs after a BOM change). It is **OPEN / CONFIRMED**, not fixed.
- Cost-flow dual inactive/active writer trees are **temporary rollout debt**, not a reason to rewrite the architecture.
- Stell22 does **not** need a different architectural paradigm (no CQRS / microservices / generic workflow engine).
- The **modular monolith** remains an acceptable current architecture.
- Further audits should follow **business contours** (finance, payroll, warehouse, activation), not generic architecture patterns.

This is not a claim that the system is fully safe. Deferred marketplace items (DI-011/017), irreversible Payment (REVIEW-023), live SKU-cost reconstruction (03.01), and `ARCH-P1-001` remain real residual risk.

#### Exact current paths

**1. Active UPAKOVKA quantity edit (entry)**

**5. Actual mutation sequence (active)**

#### Two orders (only one proves P1)

**Order that does *not* prove corruption** (op → inventory of **packed/old** refs → BOM change → qty edit):

1. UPAKOVKA exists (consumes A, details, P).
2. `conductInventory` on those affected old refs.
3. `updateProduct` BOM A→B.
4. Qty edit: `reverseActiveUpakovkaOperation` builds old refs {P, A, details} → `INVENTORY_BOUNDARY` → **zero stock writes**. Current-ref hole is not reached.

**Order that *does* prove reachable corruption after activation** (op → BOM change → inventory of **new current-BOM** ref → qty edit):

#### Concrete reachable scenario (gate **active**)

Numbers:

| t | Event | NomenclatureStock A | NomenclatureStock B | ProductStock P |
| --- | --- | ---: | ---: | ---: |
| t0 | `submitUpakovka` qty=2, BOM fastener **A** ×1/unit | 20→18 | 10 | 0→2 |
| t1 | `updateProduct` BOM A→**B** | 18 | 10 | 2 |
| t2 | `conductInventory` line **B** only, actual=10, CONDUCTED | 18 | **10 frozen in doc** | 2 |
| t3 | `updateProductionLineQuantity` UPAKOVKA 2→3 | 18→20 (reverse restores 2×A) | **10→7** (apply 3×B) | 2→0→3 |

- **Old refs checked:** PRODUCT P, NOMENCLATURE A, DETAIL/blank of the pack. Inventory at t2 did **not** cover those → reverse **allowed**.
- **Current refs that 01.7 requires:** P ∪ A ∪ **B** ∪ details.
- **Skipped ref:** NOMENCLATURE **B**.
- **Inconsistency:** CONDUCTED document says B=10; live B=7. An op with `createdAt < inventory.date` mutated a ref the inventory covered. BD-9.2 / DI-009 boundary.

Inactive path at t3: `prepareUpakovkaEdit` unions B → `INVENTORY_BOUNDARY`, zero stock writes.

#### Counter-evidence checked

- Inactive `prepareUpakovkaEdit` **does** union — not this bug.
- `reverseActiveUpakovkaOperation` **does** boundary old refs — insufficient when BOM changed.
- `applyActiveUpakovkaPrepared`: no `assertInventoryBoundary` (grep: only prisadka ~L711 and reverse UPAKOVKA ~L1150 in `cost-flow-downstream.ts`).
- Product `costVersion` mismatch blocks reverse of **P**, not consume of **B**.
- Uninitialized nom pool can fail-closed if B never received money — **defeated** if t2 `conductInventory` (active) initialized B, or SimplePurchase received B.
- `cost-flow-package3.integrity.test.ts`: UPAKOVKA qty edit exists; **no** BOM-change + inventory-on-new-ref case.
- Gate **inactive** today: not reachable in current production. Still P1 for **activation**.
- DI-009 CLOSED remains valid for inactive/generic SET+boundary.

#### Operational restriction (mitigation, not a fix)

Until `ARCH-P1-001` is fixed, **avoid** this sequence (gate active or when preparing activation):

1. A historical UPAKOVKA operation exists.
2. Product BOM/composition is changed.
3. Inventory is conducted on refs of the **new** BOM.
4. Quantity of the **old** UPAKOVKA operation is then edited.

**Reason:** the active edit path may skip the current-ref inventory boundary, so inventoried new-BOM stock can move. Inactive path already unions refs; this restriction is extra caution around activation and around any environment where the gate is on.

This is an **operational mitigation**, not a code fix. `ARCH-P1-001` stays **OPEN / CONFIRMED**.
