# Cost-Freeze Remediation Plan (DI-005 / 006 / 018 / 019 / BD-3)

> **For agentic workers:** do not implement until this document is reviewed. When implementing: `superpowers:subagent-driven-development` or `executing-plans`. Evidence: `audit/01.2-cost-freeze-review.md`, `audit/01-data-integrity-findings.md`, `audit/01-data-integrity-invariants.md`. This file is the spec.

**Goal:** After a correct freeze, `BatchCost` FINAL is an immutable snapshot of the same cost inputs as committed `Batch` + TORCOVKA fact; concurrent finance, recalc, payroll, and TORCOVKA edit/delete cannot leave FINAL, `totalCost`, lines, and `frozenAt` disagreeing, and a closed batch with unpaid TORCOVKA=0 cannot stay unfrozen forever.

**Architecture:** Keep READ COMMITTED. Serialize with `SELECT … ORDER BY id FOR UPDATE` (same pattern as P1 `lockTableIds`). Canonical order: **ProductionOperation → Batch → stock/lines**. Freeze decides and computes **only after** Batch row lock, from a fresh read. Recalc is one TX per batch holding that Batch lock through delete+create PRELIMINARY. PRELIMINARY stays a disposable cache (no UNIQUE). FINAL gets a **partial unique**. Existing FINAL vs `totalCost` mismatches are **not** rewritten.

**Tech Stack:** Prisma 6.19.3, PostgreSQL 17, Vitest + existing integrity harness (`INTEGRITY_TEST_DATABASE_URL`, two `PrismaClient`s). Isolation stays READ COMMITTED.

**HEAD this plan assumes:** `9b5ed66da36543c3a58d7ab8e392fcd19e78b9c1`

## 1. What freeze actually snapshots today

`freezeBatch` → `computeBatchSnapshot` → `buildBatchSnapshots` → `distributeBatchCost` (`src/lib/cost.ts`).

Inputs of **FINAL** (actual fields, not v2 names):

| Source | Schema / fact fields |
| --- | --- |
| C | `Batch.totalCost` |
| Sort prices | `Batch.priceSort1`, `Batch.priceSort2` |
| Section area | `Batch.sectionWidthMm`, `Batch.sectionHeightMm` (`sectionAreaM2`) |
| Produced fact | TORCOVKA `OperationDetailLine`: `quantity`, `blankLengthM`, `blankSort` (via ops `type=TORCOVKA`) |

`Batch.purchaseCost` is **not** read by `distributeBatchCost`. It still must stay frozen (P1): it is the weight for later `syncBatchTotalCostInternal` and purchases mismatch. After freeze, sync already refuses to write `totalCost`.

`Batch.materialId` is **not** an input to `distributeBatchCost`, but it **is** a cost-classification input: live product WAC (`blendedCostPerMeterByMaterial`) groups FINAL by `materialId`. After `frozenAt`, **`materialId` must not change**, even if the new Material has the same section millimetres. No historical correction / reopen workflow in this pass.

## 2. LOCK ORDER (mandatory)

```
ProductionOperation  (ids sorted ASC, FOR UPDATE)
→ Batch              (ids sorted ASC, FOR UPDATE)
→ BlankStock / OperationDetailLine / other stock
```

| Path | Order after this plan |
| --- | --- |
| `markEmployeePaid` | Ops FOR UPDATE (sorted) → reread facts → **recompute Payment amount** → claim → Payment/PBI → Batches FOR UPDATE (sorted) → `maybeFreezeBatch` (lock already held) |
| `maybeFreezeBatch` / `freezeBatch` | Batch FOR UPDATE **unless caller already holds it** → fresh read → count/compute/write. Never lock Op here (payroll already holds Ops). |
| `archiveBatchIfDepleted` | already `UPDATE Batch` (row lock) → `maybeFreezeBatch({ batchAlreadyLocked: true })`. **Do not** lock Ops in archive. |
| `updateProductionLineQuantity` | Op FOR UPDATE → reread + `isPaid` → BlankStock + line. **No Batch lock** (DI-019). |
| `deleteProductionOperation` | Op FOR UPDATE → reread + `isPaid` → stock reversal → delete children → delete Op. **No Batch lock**. |
| `recalcBatchCosts` | per-batch TX: Batch FOR UPDATE → frozenAt → PRELIMINARY delete/create. **No Op lock.** |
| `updateBatch` / finance sync | unchanged P1: Deal→Batch (or Account→Deal→Batch). **Never** lock Op. |

**Forbidden**

- Batch then ProductionOperation (deadlock vs payroll).
- TORCOVKA edit taking Batch lock “just in case”.
- `maybeFreezeBatch` locking Ops (would invert vs a future Batch-only caller, and is redundant inside payroll).
- Recalc locking Ops.

**Same-TX re-lock:** `SELECT … FOR UPDATE` on a row the TX already holds is a no-op hold. Safe for archive → maybeFreeze and payroll → maybeFreeze.

**Helpers**

- Reuse P1 `lockTableIds` SQL. Today it is **private** in `finance-operations.ts` and only knows Account/Deal/Batch.
- **Export** `lockBatches(db, ids)` (Batch, sorted, `FOR UPDATE`).
- **Add** `lockProductionOperations(db, ids)` in the same module (or `src/server/internal/row-locks.ts` if that avoids growing finance-operations — implementer’s choice; SQL must be `SELECT id FROM "ProductionOperation" WHERE id IN (…) ORDER BY id FOR UPDATE`).
- Empty id list = no-op (same as today).

## 4. Target writers (exact TX shape)

### 4.1 `maybeFreezeBatch` / `freezeBatch`

`src/server/internal/cost.ts`

```
maybeFreezeBatch(tx, batchId, opts?: { batchAlreadyLocked?: boolean }): Promise<boolean>
  if !opts.batchAlreadyLocked: lockBatches(tx, [batchId])
  batch = findUnique(batchId)          // FRESH after lock
  if !batch || frozenAt || !closedAt → false
  unpaid = count TORCOVKA isPaid=false  // FRESH, lock held
  if !canFreezeBatch(...) → false
  freezeBatch(tx, batchId)              // id only, not stale PrismaBatch
  return true

freezeBatch(tx, batchId): Promise<void>
  // precondition: Batch row locked in this TX
  batch = findUnique(batchId)           // FRESH: totalCost, priceSort1/2, sectionWidthMm/HeightMm, frozenAt, closedAt, name
  ops = TORCOVKA + lines                // FRESH
  snapshot = computeBatchSnapshot(fresh batch, lines)
  if already frozenAt: return           // idempotent no-op (do not rewrite FINAL)
  UPDATE frozenAt = now()
  deleteMany BatchCost PRELIMINARY only  // do not delete FINAL if a unique race; first freeze: none
  if snapshot: create FINAL
  changelog + notify (existing)
```

**Do not** pass a pre-lock `PrismaBatch` into `freezeBatch` as authority.

**FINAL write:** `deleteMany` all statuses is today’s behavior and races with late PRELIMINARY (DI-006). After this plan, recalc cannot insert PRELIMINARY while Batch is locked and frozen. Freeze should:

- `deleteMany { batchId, status: PRELIMINARY }`
- `create FINAL` (partial unique makes a second FINAL fail — treat as bug / rollback)

If `snapshot == null` (no TORCOVKA lines): keep today’s semantics — set `frozenAt`, **no** FINAL row. Unique allows zero FINAL. Post-deploy report lists these (BD-2, no auto-insert).

`archiveBatchIfDepleted`: after `UPDATE` closedAt, `await maybeFreezeBatch(tx, batchId, { batchAlreadyLocked: true })`.

### 4.2 `markEmployeePaid` (DI-018 + freeze freshness + amount authority)

`src/server/payroll.ts`

**Amount authority is inside TX after Op lock.** Pre-TX work identifies **candidate operation IDs only**. A UI/preliminary amount may still be computed for display, but it is **not** written to `Payment`.

Do **not** introduce rate snapshots on operations. Do **not** solve DI-015. Rates remain **live Employee** rates at payment time (may be re-read inside TX — still live, not a snapshot field on `ProductionOperation`).

```
pre-TX
→ find unpaid ops for employee → candidate opIds only (sorted unique)
→ if empty → existing throw «Нет невыплаченных операций»
→ (optional UI amount: discarded; not Payment.amount)

TX
→ lockProductionOperations(tx, opIds)     // sorted FOR UPDATE
→ reread those operations + lines + all facts computeOp uses
  (type, hours, productQty, lines: quantity/sort/prisadka flags, employeeId)
→ if any missing or isPaid=true → throw «Операции уже выплачены…»
→ load current Employee rates (live; same maps as today, not op snapshots)
→ amount = round2(sum computeOp(fresh op, live rates))
→ updateMany { id in opIds, isPaid: false } → true
→ if count !== opIds.length → throw (keep all-or-nothing contract; no partial pay)
→ Payment.create({ amount: amount.toFixed(2), ... }) + PaymentBatchItem
→ torcovkaBatchIds = unique batchId of claimed TORCOVKA ops (from reread)
→ lockBatches(tx, sorted torcovkaBatchIds)
→ for batchId of that sorted list:
     maybeFreezeBatch(tx, batchId, { batchAlreadyLocked: true })
→ notify (use authoritative amount)
COMMIT
enqueue: none (today none)
```

Race vs `updateProductionLineQuantity` (mandatory test 6a/6b): they serialize on the Op row. Edit-before-lock → payroll rereads qty=B → `Payment.amount` is amount(B). Payroll-before-edit → amount(A), later edit sees `isPaid` and rejects.

Two concurrent last TORCOVKA payments (DI-018): both lock Ops in id order (no deadlock), then both want Batch. Second waits, then `unpaid count=0` and `!frozenAt` or already frozen. First freeze wins; second `maybeFreeze` no-ops if `frozenAt` set. Both Payments commit. One FINAL.

### 4.3 `recalcBatchCosts` (DI-006)

`src/server/internal/cost.ts` — keep the name `recalcBatchCosts`. Do **not** add `recalcBatchCostsInternal`. Do **not** add `opts.db` / outer-TX mode (today’s `opts.db` is unused by production; **delete the parameter** rather than invent a test-only injection).

Exact signature:

```ts
export async function recalcBatchCosts(opts: { batchId?: string } = {}): Promise<void>
```

`cost-queue.ts` keeps `await recalcBatchCosts(batchId ? { batchId } : {})` **after** writer commit.

Shape:

1. Resolve target ids on `prisma` (no lock yet): if `opts.batchId` then `[opts.batchId]`, else `findMany` `{ frozenAt: null }` ids.
2. Sort ids ASC.
3. **For each id:** `await prisma.$transaction(async (tx) => { ... })` — **one new transaction per batch**. Never one TX for all batches. Never inherit a caller TX.

Inside each TX:

```
lockBatches(tx, [batchId])
batch = findUnique
if !batch → return
if batch.frozenAt:
     deleteMany PRELIMINARY for batchId
     do not create PRELIMINARY
     return
read TORCOVKA ops+lines
snapshot = compute from FRESH batch + lines
deleteMany PRELIMINARY
if snapshot: create one PRELIMINARY
```

Hold the Batch lock through delete+create. Two concurrent recals serialize on Batch → **at most one PRELIMINARY** without UNIQUE PRELIMINARY.

Do **not** run recalc inside payroll/freeze TX. Integrity tests call `recalcBatchCosts({ batchId })` like production (standalone per-batch transactions), not `recalcBatchCosts({ db: tx })`.

### 4.4 `updateProductionLineQuantity` (DI-019)

Applies to **all** types in this ENTRY (same `isPaid` hole). FINAL only depends on TORCOVKA; still lock every type so paid HOURS/PRISADKA/UPAKOVKA cannot mutate after pay.

```
TX
→ lockProductionOperations(tx, [id])
→ reread operation + lines (orderBy id asc as today)
→ if !op → throw not found
→ if op.isPaid → throw existing «Нельзя изменить — операция уже выплачена»
→ existing type branches (HOURS / UPAKOVKA / PRISADKA / TORCOVKA)
   TORCOVKA: BlankStock ± then operationDetailLine.update
→ changelog in TX
COMMIT
→ enqueueRecalcBatchCosts(batchId) if TORCOVKA && batchId
```

**No Batch lock.** Paid check **after** Op lock is the authority; pre-TX findUnique may stay as a fast-fail but is not sufficient.

### 4.5 `deleteProductionOperation` (DI-019 defense)

```
TX
→ lockProductionOperations(tx, [id])
→ reread op + lines + nomenclatureLines
→ if isPaid → throw «Нельзя удалить — операция уже выплачена»  // business guard
→ existing stock reversal
→ delete lines, delete op
COMMIT
→ enqueue if batchId
```

`PaymentBatchItem.operationId` ON DELETE RESTRICT remains **defense-in-depth**. Do **not** rely on P2003 as the user-facing rule. If paid, throw the existing Russian error **before** stock writes.
