## 1. Storage model

**HEAD DECIDED.** Add one nullable versioned JSON field on `BatchCreationCommand`. Do not change the meaning of `requestSnapshot`. Do not add a foreign key to `RailLot` or `Batch`. Store the full original lot set, including zero quantities. Generate `commandId` before the insert so the stored object binds that command and that batch. No historical backfill.

| Item | Proposal |
| --- | --- |
| Model | `BatchCreationCommand` (`prisma/schema.prisma` lines 306–313) |
| Field name | `receiptProvenanceSnapshot` |
| Prisma type | `Json?` |
| PostgreSQL type | `JSONB` **NULL** |
| Existing column | `requestSnapshot` stays the v1 rail specification without `railLotId` (`purchase-command-identity.ts` lines 58–123) |

`BatchCreationCommand` already has no FK and survives `deleteBatch` (`schema.prisma` lines 300–305; `purchases.ts` lines 687–689 delete lots and the batch only). A new FK to `RailLot` with `ON DELETE CASCADE` would destroy the retained fact. A new FK to `Batch` would either block `deleteBatch` or delete the command. Both are rejected.

A separate child table is not the storage model. The command row is already one-to-one with the batch (`batchId` unique, migration `20260920120000` lines 23–24). The provenance is a column of that same insert. Database retention of the column is the trigger in §6, not a second table.

## 2. Provenance shape

**HEAD DECIDED.** Version 1 object:

```text
{
  v: 1,
  d: "BATCH_RECEIPT_PROVENANCE",
  commandId: BatchCreationCommand.id,
  batchId: Batch.id,
  pairs: [{ railLotId, quantity }]
}
```

| Rule | Contract |
| --- | --- |
| Mandatory keys | `v`, `d`, `commandId`, `batchId`, `pairs` |
| `pairs` item | `railLotId` non-blank string, `quantity` integer `>= 0` |
| `railLotId` uniqueness | one occurrence. A duplicate is `INVALID_SOURCE` |
| Canonical order | `pairs` sorted by `railLotId` using the same `localeCompare` as `sortByRailLotId` (`raw-purchase-shadow-write.ts` lines 92–94). Input order and package-code order are not the receipt identity |
| Zero quantity | stored. It is part of the original lot set and is not a `RECEIPT` effect (§3) |
| Negative or non-integer | not stored. A future writer rejects them before commit. A stored value of that shape is `INVALID_SOURCE` |
| Binding | `commandId` and `batchId` inside the object must equal the command row. A mismatch is `INVALID_SOURCE` |
| SQL `NULL` | the column is absent. This is not an empty set and not a proven zero |
| JSON `null`, a JSON array, or a JSON scalar | rejected by the shape `CHECK` in §10. Not a provenance object |
| `pairs: []` | a present object that proves no lots were inserted. Unreachable through current `createBatch` validation (§3) |
| Later mutation | the create path inserts the object once. A later `UPDATE` cannot replace it (§6) |

The command id is client-generated today (`@default(cuid())` on `schema.prisma` line 307). The future writer must supply that id before the insert so the snapshot can contain it in the same `INSERT`. An update after insert is not the way to add `commandId`.

## 3. Zero-quantity semantics

Observed on this tree. Not changed by this file.

| Step | Behavior | Evidence |
| --- | --- | --- |
| `validateBatch` | requires a name, a material, a positive purchase cost, and, for create, at least one package. It does not require `quantity > 0` | `purchases.ts` lines 234–241 and 295 |
| `createBatch` | inserts every rail, including `quantity = 0`, and sets `remainingQuantity` to the same value | `purchases.ts` lines 334–348 |
| `batchCreateReceiptEffects` | skips `quantity === 0`. `quantity < 0` or a non-integer throws `RAW_PURCHASE_SHADOW_INVALID_QUANTITY` | `raw-purchase-shadow-write.ts` lines 75–82 and 158–172 |
| Effect construction | runs before the inactive-gate return, so a negative quantity aborts the transaction even when the gate is inactive | `appendBatchCreateShadowMovements` lines 337–338 calls the effect builder before `appendRawPurchaseShadowMovements` line 307 returns early |

**HEAD DECIDED.** Keep the behavior above. The snapshot stores the full inserted lot set, zeros included. `ExpectedEffects` are derived only from pairs with `quantity > 0`, by the same skip rule as `batchCreateReceiptEffects`. A zero row proves that a lot was created and that it had no receipt movement. It is not omitted, and it is not turned into a movement. A `NULL` column is never rewritten into `pairs: []` or into an all-zero list. That would be a synthetic zero.

| Stored value | Meaning | Invariant A |
| --- | --- | --- |
| SQL `NULL` | no independent source | `NOT_EVALUABLE`. Not `MATCH_OBSERVED`. Not a synthetic zero |
| object, `pairs: []` | independently proven empty lot set. Current `createBatch` cannot commit it, because create requires a package | empty `ExpectedEffects`. Empty observed set may be `MATCH_OBSERVED` only under §8 |
| object, every `quantity = 0` | independently proven zero receipt effect. The lots existed and none of them is a `RECEIPT` | same empty-effect rule as `pairs: []`, but the stored set is not empty |
| object, one or more `quantity > 0` | those pairs are the receipt effects | nonempty `ExpectedEffects` |

A negative or non-integer quantity must keep failing inside the same transaction, so no command row and no movement are committed. That is existing behavior. An earlier `validateBatch` rejection is outside this Slice 2-B contract. It is not a prerequisite for the storage model.

## 4. Transaction and atomicity

Observed `createBatch` order (`purchases.ts` lines 288–385):

1. Outside the transaction: admin, actor, `requestId` check, `validateBatch`, `canonicalBatchCreateSnapshot`.
2. Inside one `prisma.$transaction`:
   - SHADOW gate read (`isInventoryMovementShadowWriteActiveForWriter`).
   - `pg_advisory_xact_lock` in namespace `8326` (`purchase-command-identity.ts` lines 15 and 35–42).
   - replay lookup by `requestId`.
   - batch insert with nested `RailLot` insert.
   - optional cost initialization when cost flow is active.
   - `batchCreationCommand.create`.
   - SHADOW movement append from the created lots.
   - `ChangeLog`.
3. After commit: `revalidatePath` and `loadRow`.

**HEAD DECIDED.** The future `createBatch` writer must build `receiptProvenanceSnapshot` from `batch.railLots` after those ids exist, supply `commandId` before insert, and write the object in the same `batchCreationCommand.create` call (lines 356–363). Do not read `InventoryMovement` or `causationSnapshot` to fill it. For that writer, a command without the object is a failed transaction, not a committed `NULL`.

| Guarantee | Why it holds if the future writer follows this point |
| --- | --- |
| Same transaction | the snapshot is a column of the command insert already inside the transaction |
| No partial command | a throw before or during that insert rolls the lots back with it. PostgreSQL commits the transaction or none of it |
| Provenance failure rolls back the receipt | a thrown validation error aborts the same transaction, including the batch, the lots, and any SHADOW append that already ran |
| Writer-level provenance | the future writer refuses to commit `createBatch` without a valid object. This is application code |
| Database-level insert | nullable `JSONB` still accepts SQL `NULL` on `INSERT`. The column type does not stop an old application instance from inserting `NULL` (§10) |
| Replay writes nothing | the existing branch returns at lines 304–313 before lot and command insert. `appendBatchCreateShadowMovements` is documented as replay-forbidden (line 327). The future writer must not update provenance on that branch |
| Gate coordination unchanged | the gate is still read once and passed into the existing append. Provenance is a business column, not a second gate read |
| No new deadlock path | no new advisory lock and no new `RailLot` `FOR UPDATE`. The only new write is a column on the insert that already happens |
| No ledger copy | pairs come from the `RailLot` rows just inserted in this transaction |

`ChangeLog` on create still stores name, cost, `requestId`, and `commandId` (lines 370–383). It is not the provenance source.

## 5. Replay and idempotency

**HEAD DECIDED.**

- The same `requestId` returns the existing command and does not insert a second lot set, a second command, or a second provenance object (`purchases.ts` lines 304–313).
- Replay compares `requestSnapshot` only (`assertPurchaseCommandMatch` at lines 305–310). It must not require the new column to equal the incoming form snapshot. The form snapshot still has no `railLotId`.
- If the batch row is gone, replay throws `PURCHASE_REPLAY_TARGET_MISSING` and does not create a replacement batch (lines 311–312). The original command, including a future provenance object, remains.
- The checker addresses `BatchCreationCommand.id`, not the replay attempt (`audit/08.28` §6).

## 6. Retention and immutability

The only `batchCreationCommand.create` in `src/` is `purchases.ts` line 356. There is no `update` of that model.

| Later action | Effect on a future provenance column | Evidence |
| --- | --- | --- |
| `deleteBatch` | command is not deleted. Lots are deleted only when every `remainingQuantity` is 0, cost flow is inactive, and there is no production operation or deal item | `purchases.ts` lines 670–689 |
| `writeOffBatchRemainder` | writes `BatchRemainderWriteOff` and sets remaining to 0. It does not load `BatchCreationCommand` | `purchases.ts` lines 583–619 |
| `remainingQuantity` changes | terminal and cost-flow updates of remaining quantity are not this column | not a writer of `BatchCreationCommand` |
| money edits | `updateBatch` edits scalar batch fields and does not edit rails or the command | `purchases.ts` lines 391–394 |
| replay | returns before insert | lines 304–313 |

**HEAD DECIDED.** The future migration must include a narrowly scoped PostgreSQL trigger on `BatchCreationCommand`. This file specifies the guard. It does not contain the SQL.

The trigger fires on `UPDATE` and `DELETE`. It does not turn a nullable column into a `NOT NULL` column, and it does not reject an `INSERT` of SQL `NULL`.

| Operation | Old provenance | Attempt | Guard |
| --- | --- | --- | --- |
| `UPDATE` | SQL `NULL` | column stays SQL `NULL` | allow, including an unrelated column change |
| `UPDATE` | SQL `NULL` | `NULL` replaced by an object | reject. This is the backfill path |
| `UPDATE` | object | object replaced by a different object | reject |
| `UPDATE` | object | object replaced by SQL `NULL` | reject |
| `UPDATE` | object | object written back as the same JSON value, and `id`, `requestId`, and `batchId` unchanged | allow. Protected data did not change |
| `UPDATE` | object | `id`, `requestId`, or `batchId` changes | reject, even if the JSON value is unchanged |
| `UPDATE` | object | another column changes, while provenance, `id`, `requestId`, and `batchId` stay | allow. The guard is not a freeze of `requestSnapshot`, `adminUserId`, or `recordedAt` |
| `DELETE` | object | delete the command | reject for ordinary application roles |
| `DELETE` | SQL `NULL` | delete a legacy command | not blocked by this provenance trigger. There is no retained object to protect. The current application has no command delete |

After a provenance object is inserted, ordinary SQL cannot change it, clear it, rebind `commandId` / `batchId` / `id` / `requestId`, or delete that command. `commandId` inside the JSON is protected because the JSON value itself cannot change. `id`, `requestId`, and `batchId` are protected as columns on that same row.

A legacy `NULL` stays `NULL`. An `UPDATE` must not populate it. No synthetic pair list is created.

Privileged database administration can bypass an ordinary trigger. That includes a superuser, a disabled trigger, and replica-role session settings that skip user triggers. This design is not cryptographic immutability and it is not absolute immutability.

Application code still inserts the object only on the original create. Write-off, remaining changes, money edits, replay, and `updateBatch` do not write the column. The trigger is what rejects a direct `UPDATE` or `DELETE` that the application does not currently have.

A migration or script that fills `NULL` from `InventoryMovement`, from `causationSnapshot`, or from a write-off snapshot is a backfill. The trigger rejects that `UPDATE`. It is also forbidden as a design (§7).

## 7. Legacy compatibility

**HEAD DECIDED.** Commands that already exist keep `receiptProvenanceSnapshot = NULL` because the column is added without a default and without a backfill. They do not receive a synthetic pair list. The trigger in §6 rejects a later `UPDATE` that would fill that `NULL`.

Forbidden sources for those rows:

- `InventoryMovement`;
- `batchCreateCausationSnapshotV1` (`raw-purchase-shadow-write.ts` lines 136–156 and 345–349);
- `BatchRemainderWriteOff.effectSnapshot` (`purchase-command-identity.ts` lines 139–157).

Classification does not use `recordedAt` or the creation date (`audit/08.30` §7 Option D).

| Available source | Status under this contract |
| --- | --- |
| column is `NULL` | `NOT_EVALUABLE` for this checker. The document exists and lacks the pair list |
| column is `NULL`, and every original `RailLot` still exists | still `NOT_EVALUABLE` here. Option A would require a separate HEAD authorization. This contract does not give it |
| column is a valid object | Option B coverage for that command only |
| command row itself is absent | `SOURCE_UNAVAILABLE` |

A command inserted as SQL `NULL`, including one inserted by an old application instance after the column exists, stays `NOT_EVALUABLE`. That cannot become `MATCH_OBSERVED`. No new Invariant A status is added for it.

Future verification may list command ids whose provenance column is SQL `NULL`. `recordedAt` after a chosen instant does not prove which writer inserted the row, so that list is not itself a cutover classification. Filling the list is forbidden. An operational alert on that list, and the evidence that would make the alert reliable, stay **DEFERRED** (§13). Deferral does not authorize a writer.

## 8. Invariant A

Future expected effect, for each stored pair with `quantity > 0`, matching `batchCreateReceiptEffects` and `canonicalizeMovementTarget`:

| Field | Value |
| --- | --- |
| `causationKind` | `BATCH` |
| `causationId` | `BatchCreationCommand.id` |
| role | `receipt` |
| movement kind | `RECEIPT` |
| stock domain | `RAIL_LOT` |
| canonical target | `{ stockDomain: "RAIL_LOT", railLotId }` |
| `targetSnapshot` | `{ v: 1, d: "RAIL_LOT", railLotId }` (`inventory-movement-identity.ts` lines 130–136) |
| `quantityDelta` | the stored positive `quantity` |
| `effectKey` | `effectKeyV1("receipt", targetHashV1)` (`raw-purchase-shadow-write.ts` lines 176–179; `inventory-movement-identity.ts` lines 234–240) |

Zero quantities produce no effect. The reconciler is read-only. It does not insert, update, or delete `InventoryMovement`.

| Case | Status |
| --- | --- |
| Valid provenance, expected set equals observed set | `MATCH_OBSERVED` |
| Proven zero effect (`pairs: []` or every quantity `0`) and observed set empty | `MATCH_OBSERVED`. `audit/08.28` §5 item 5 |
| Valid provenance, both sets known, sets differ, including an unexpected extra movement | `MISMATCH` |
| Nonempty expected, empty observed, SHADOW preservation not proven | `GATE_UNKNOWN`. Not `MISMATCH`. `audit/08.28` §3 item 5 and §5 items 2–3 |
| Command row absent | `SOURCE_UNAVAILABLE` |
| Command present, column `NULL` | `NOT_EVALUABLE` |
| Live lots missing and column `NULL` | `NOT_EVALUABLE`. Not an automatic Option A result |
| Malformed JSON, duplicate `railLotId`, negative or non-integer quantity, or id binding mismatch | `INVALID_SOURCE` |
| Replay of `requestId` | not a second effect. Diagnose the retained command id |
| Database read failure, lock failure, or any unfinished read | diagnostic execution error. Not a status (`audit/08.28` §5 item 1) |

Slice 1's checker returns `GATE_UNKNOWN` whenever expected is nonempty and observed is empty (`psr-p3-slice1-invariant-a.ts` lines 502–510). This contract uses that same fail-closed result. An independent proof that SHADOW evidence was preserved, including any reset-generation rule that could upgrade the status to `MISMATCH`, is **DEFERRED**. It is a separate design gate. This rework does not solve it and does not authorize a checker.

`MATCH_OBSERVED` does not prove that a warehouse quantity changed and does not prove Invariant B (`audit/08.28` §2).

Gate inactive plus a positive provenance is `GATE_UNKNOWN` when no movements exist: the expected set is nonempty and preservation is not proven. The provenance column is still written when the gate is inactive. The gate itself is not changed.

## 10. Migration design

Plan only. No `migration.sql` is created here. No `migrate` or `db push`.

| Topic | Plan |
| --- | --- |
| Change | `ALTER TABLE "BatchCreationCommand" ADD COLUMN "receiptProvenanceSnapshot" JSONB` |
| Existing rows | become `NULL`. The table is not empty in the general case; `requestSnapshot` is already `NOT NULL` (migration lines 9–15). A nullable add does not rewrite those identities |
| Default | none. A default of `'[]'` or `'{}'` would erase the difference between legacy `NULL` and a proven empty set |
| JSON shape `CHECK` | **HEAD DECIDED.** The value is SQL `NULL` or `jsonb_typeof(...) = 'object'`. A JSON array, a JSON scalar, and JSON `null` fail the `CHECK`. SQL `NULL` passes it |
| What the `CHECK` does not prove | version, domain, `commandId` / `batchId` binding, unique `railLotId`, integer `quantity >= 0`, or canonical order. Those are writer validation before insert and `INVALID_SOURCE` in the read-only checker. No full JSON Schema is claimed in the database |
| Immutability | the trigger in §6 ships with the same future migration design. It is not optional |
| FK | none |
| Prisma | `receiptProvenanceSnapshot Json?` on `BatchCreationCommand` only |
| Rollback | dropping the column is compatible only before any non-null value is relied on. Dropping it after that discards the new facts and does not restore a historical pair list |
| Deploy order | additive column, then the shape `CHECK` and the trigger, then the writer that fills the column. A checker may exist only after the column exists, and must treat SQL `NULL` as `NOT_EVALUABLE` |
| Rollout gap | between the migration and activation of the new writer, an old application instance can still `INSERT` SQL `NULL`. Those rows stay `NOT_EVALUABLE`. A timestamp is not proof of which writer ran |
| Identities kept | `requestId` unique, `batchId` unique, `requestSnapshot` shape, SHADOW gate, Slice 1 contours |
