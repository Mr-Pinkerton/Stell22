## 1. What this candidate changes

The stacked work in PR #107 through PR #110 stays. This candidate adds the production path those pull requests deliberately refused.

- `stell22` remains the superuser. It is not demoted and it is not the application login.
- `stell22_app` is the only application login. It is `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT`.
- `stell22_migrator` is the only role that may apply pinned P1.
- The application image entrypoint remains `docker-entrypoint-app-only.sh`. Normal startup does not run `prisma migrate deploy`.
- `docker-compose.prod.yml` points the application at `stell22_app` and `${APP_DB_PASSWORD}`. The migrator password is not on the application service. The database volume `db-data` stays. The database port stays unpublished.
- `scripts/deploy.sh` refuses to replace the application until `stell22_app` can log in and is not a superuser, and the pinned P1 row is finished. It does not use `git reset --hard`. A failed health check after that start is forward recovery: stop the application, do not restore the database, do not return to the migrate-on-start image.
- `scripts/release-checkout.sh` detaches HEAD at the exact SHA and keeps local `scripts/backup-db.sh`, `scripts/restore-db.sh`, and untracked `mail.log`. Any other local change stops the checkout.
- `scripts/release-role-split.sh` is locked unless `STELL22_RELEASE_EXECUTE=1` and the Owner phrase match. The phrase is `OWNER_AUTHORIZES_ROLE_SPLIT_RELEASE`. It is an authorization marker, not a database password.
- Workflow `Production role split release` stops before SSH when the phrase or the SHA is missing. Do not dispatch it from this task.
- Workflow `Production Deploy` also stops before SSH without the same phrase. Do not dispatch it for this release. After a completed role split, a later application deploy still refuses to start when the role or pinned P1 is absent.

Database and Caddy memory limits are in the Compose file. This release must not recreate `stell22-db-prod` or `stell22-caddy`, so those running containers keep their current limits and the named volumes stay. Only `stell22-app` is stopped and replaced. The new application container receives 1536 MiB and 0.70 CPU.

## 5. Order

The command, after the Owner workflow has passed the phrase gate, is:

```sh
cd /root/Stell22
git fetch origin
git cat-file -e "${RELEASE_SHA}^{commit}"
sh scripts/release-checkout.sh "$RELEASE_SHA"
STELL22_RELEASE_EXECUTE=1 \
  STELL22_RELEASE_AUTHORIZATION='OWNER_AUTHORIZES_ROLE_SPLIT_RELEASE' \
  STELL22_RELEASE_SHA="$RELEASE_SHA" \
  sh scripts/release-role-split.sh
```

The workflow `Production role split release` performs that sequence over SSH. A manual run of the same commands is the same release. Do not run both.

Inside `scripts/release-role-split.sh`, after the phrase gate:

1. `PROTECTED_FILES`. Detach at the release SHA. Restore the stashed backup and restore scripts. Keep `mail.log`.
2. `WRITE_FREEZE`. `docker stop stell22-app` only.
3. Build the application image while the old container still exists and is stopped. A build failure starts that same old container again. Pinned P1 has not run.
4. `ROLE_TRANSITION`. Read the live catalog as `stell22`. Plan with `databasePolicy=production-candidate`. Apply one `BEGIN` / `COMMIT` as `stell22`: revoke `PUBLIC` on the database and schema, create both roles, transfer each inventoried object with its own `ALTER ... OWNER TO stell22_migrator`, grant application DML, and keep `_prisma_migrations` as `SELECT` only for `stell22_app`. There is no `REASSIGN OWNED`. A SQL failure rolls the transaction back and starts the old application container.
5. `WRITER_EXCLUSION`. Require schema `CREATE` false, migrator membership false, migration `SELECT` true, and migration `INSERT` false for `stell22_app`. Require an insert into `_prisma_migrations` as `stell22_app` to fail with SQLSTATE `42501`. Then run `prisma migrate deploy` as `stell22_app` and require a non-zero exit and an absent pinned P1 row. Any other result stops. If that probe applied P1, do not start the old image and do not restore the database.
6. `PINNED_P1`. From here the old application image stays stopped. `prisma migrate deploy` runs once as `stell22_migrator` from the new image, with a 512 MiB and 0.25 CPU cap. A non-zero exit is `FORWARD_RECOVERY`: no retry, no database restore, no schema rollback, no start of the migrate-on-start image.
7. `APP_START`. `docker compose -f docker-compose.prod.yml up -d --no-deps app`. The database service is not recreated.
8. `HEALTH`. `GET /api/health` from inside `stell22-app`. Failure stops the new application and uses the same forward recovery. It does not start the old image.

Success prints `RESULT=RELEASE_APPLIED`, `P1_APPLY=MIGRATOR`, and `DATABASE_RESTORE=NO`.

- `stell22-db-prod` and `stell22-caddy` were not recreated. Volume `db-data` remains.
- The next backup cron can run after the window. Do not run `scripts/restore-db.sh`.

`scripts/deploy.sh` is the later application update path. It still requires the role and pinned P1, builds the image, and starts only the application. It is not the role-split command.

## 7. Forward recovery

Use this when pinned P1 has been attempted and the new application does not become healthy.

- Leave the schema where the migration stopped.
- Do not restore an older archive.
- Do not run `scripts/restore-db.sh`.
- Do not start the previous image. Its entrypoint runs `prisma migrate deploy` as the superuser.
- Keep `stell22-app` stopped until the Owner chooses the next start.
- Database and Caddy stay as they were.
- Terminal writes remain interrupted until a reviewed application start succeeds.

A failure before step 6 starts the old application container again, because pinned P1 has not been applied. That is not a database restore.
