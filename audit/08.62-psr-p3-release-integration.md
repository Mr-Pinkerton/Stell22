## 1. What this candidate changes

The stacked work in PR #107 through PR #110 stays. This candidate adds the production path those pull requests deliberately refused.

- `stell22` remains the superuser. It is not demoted and it is not the application login.
- `stell22_app` is the only application login. It is `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT`.
- `stell22_migrator` is the only role that may apply pinned P1.
- The application image entrypoint remains `docker-entrypoint-app-only.sh`. Normal startup does not run `prisma migrate deploy`.
- `docker-compose.prod.yml` points the application at `stell22_app` and `${APP_DB_PASSWORD}`. The migrator password is not on the application service. The database volume `db-data` stays. The database port stays unpublished.
- `APP_DB_PASSWORD` and `MIGRATOR_DB_PASSWORD` are 24 to 128 characters from `A-Za-z0-9_-`. That same value is the role password and the database URL userinfo. `+`, `/`, and `=` are refused. `POSTGRES_PASSWORD` is not part of this alphabet and is not changed.
- `scripts/deploy.sh` refuses to replace the application until `stell22_app` can log in and is not a superuser, and the pinned P1 row is finished. It does not use `git reset --hard`. A failed health check after that start is forward recovery: stop the application, do not restore the database, do not return to the migrate-on-start image.
- `scripts/release-checkout.sh` detaches HEAD at the exact SHA and keeps local `scripts/backup-db.sh`, `scripts/restore-db.sh`, and untracked `mail.log`. Any other local change stops the checkout.
- `scripts/release-role-split.sh` is locked unless `STELL22_RELEASE_EXECUTE=1` and the Owner phrase match. The phrase is `OWNER_AUTHORIZES_ROLE_SPLIT_RELEASE`. It is an authorization marker, not a database password.
- Workflow `Production role split release` stops before SSH when the phrase or the SHA is missing. Do not dispatch it from this task.
- Workflow `Production Deploy` also stops before SSH without the same phrase. Do not dispatch it for this release. After a completed role split, a later application deploy still refuses to start when the role or pinned P1 is absent.

Database and Caddy memory limits are in the Compose file. This release must not recreate `stell22-db-prod` or `stell22-caddy`, so those running containers keep their current limits and the named volumes stay. Only `stell22-app` is stopped and replaced. The new application container receives 1536 MiB and 0.70 CPU.

## 2. Terminal interruption

A short interruption of terminal writes is required. The application image is built, and the catalog is planned, while `stell22-app` is still running. `docker stop stell22-app` happens only after that image exists. The stop stays in effect through the role transaction, pinned P1, and the new image start. Terminal writes are not recorded while that container is down. The database and Caddy stay up and are not recreated. Caddy can return errors during the gap. The expected gap is the role change, one migration, and the new application start. `restart: unless-stopped` does not start a stopped container by itself.

The release also requires `STELL22_RELEASE_MAINTENANCE=1`. That flag is the maintenance boundary. Without it the script stops before `docker stop`. Stop before the window if `scripts/backup-db.sh`, `pg_dump`, or the statement-mail fetch is running. The 03:00 backup cron must not overlap the window.

## 5. Order

The command, after the Owner workflow has passed the phrase gate, is:

```sh
cd /root/Stell22
git fetch origin
git cat-file -e "${RELEASE_SHA}^{commit}"
sh scripts/release-checkout.sh "$RELEASE_SHA"
STELL22_RELEASE_EXECUTE=1 \
  STELL22_RELEASE_MAINTENANCE=1 \
  STELL22_RELEASE_AUTHORIZATION='OWNER_AUTHORIZES_ROLE_SPLIT_RELEASE' \
  STELL22_RELEASE_SHA="$RELEASE_SHA" \
  sh scripts/release-role-split.sh
```

The workflow `Production role split release` performs that sequence over SSH. A manual run of the same commands is the same release. Do not run both.

Inside `scripts/release-role-split.sh`, after the phrase gate:

1. `PROTECTED_FILES`. Record HEAD. Copy the on-disk bytes of `scripts/backup-db.sh` and `scripts/restore-db.sh` into a private directory mode `0700`, with SHA-256, mode, and owner. Keep `mail.log`, including a private copy for recovery. Detach at the release SHA. Write the saved bytes back and check the SHA-256. Do not `git stash`, `git reset --hard`, or `git clean`. A checkout failure returns to the recorded HEAD and the saved bytes, then reports `STOP_CHECKOUT`. A failed byte restore reports `STOP_PROTECTED_FILE` and does not continue. `sh scripts/release-checkout.sh --recover` finishes an interrupted checkout.
2. `IMAGE_BUILD` and `NON_MUTATING_VALIDATION`, while the current application is still running. Record the legacy image id. Refuse backup, statement-import, and `prisma migrate` processes. Tag the running image as `stell22-release-legacy:hold` so the build cannot delete it. Build the application image. Resolve the image Compose tagged for `app`. Do not use `docker compose images`, which lists the created container. The new image id must differ from the running container, its entrypoint must be `./docker-entrypoint-app-only.sh`, and the pinned P1 file checksum must match. Any ambiguity stops before `docker stop`. Read the catalog and plan the role SQL. A build, image-identity, or plan failure leaves the running application in place. The migrator later runs that pinned image id.
3. Prove whether the legacy image contains the pinned P1 directory. If that proof fails, the legacy image is treated as able to apply P1.
4. `WRITE_FREEZE`. `docker stop stell22-app` only. Then read client sessions. The inspection session is `application_name=stell22-release-inspect`. Any other client session is `STOP_WRITER`. Do not call `pg_terminate_backend`. An empty `pg_stat_activity` snapshot does not prove that `stell22` or `stell22_migrator` cannot write later. The admission line is `FUTURE_PRIVILEGED_WRITES_PROVEN_IMPOSSIBLE=NO`.
5. `ROLE_TRANSITION`. Apply one `BEGIN` / `COMMIT` as `stell22`. There is no `REASSIGN OWNED` and `stell22` is not demoted. If the transaction fails, re-read the database. Restart the legacy image only when that re-read shows both new roles absent, pinned P1 absent, the migration count unchanged, and the legacy image has no P1 migration file. Otherwise leave the application stopped.
6. After that transaction commits, do not start the legacy image again. `WRITER_EXCLUSION` requires schema `CREATE` false, migrator membership false, migration `SELECT` true, and migration `INSERT` false for `stell22_app`. An insert into `_prisma_migrations` as `stell22_app` must fail with SQLSTATE `42501` and then roll back. Immediately before P1, read client sessions again. Any client session other than the inspection session, or a backup, statement-import, or `prisma migrate` process, is `STOP_WRITER`. `stell22` and `stell22_app` do not run `prisma migrate deploy`.
7. `PINNED_P1`. `prisma migrate deploy` runs once as `stell22_migrator` from the new image, with a 512 MiB and 0.25 CPU cap. A non-zero exit, or a missing finished P1 row, is `FORWARD_RECOVERY`: no retry, no database restore, no schema rollback, no legacy start.
8. `APP_START`. `docker compose -f docker-compose.prod.yml up -d --no-deps app`. The database service is not recreated.
9. `HEALTH`. `GET /api/health` from inside `stell22-app`. Failure stops the new application and uses the same forward recovery. It does not start the old image.

Success prints `RESULT=RELEASE_APPLIED`, `P1_APPLY=MIGRATOR`, and `DATABASE_RESTORE=NO`.

Before the checkout, the release script reads the running application health endpoint and a read-only `SELECT 1` on the database. An unhealthy result is `STOP_HEALTH` and does not change the checkout. The selected SHA must equal `origin/main` after `git fetch`, both in GitHub Actions and again on the host, and that exact commit must already have a successful CI run named `CI`. Image-build, P1, and application-start failures append a root-only log under the repository `.git` directory and redact database URLs and passwords. Those logs are not printed and are not committed. `HUP`, `INT`, and `TERM` stop the script, redact any of those logs, and do not retry P1 or restore a database.

## Enum ownership

The role transaction still inventories relations of kind `r`, `p`, `S`, `v`, and `m`, plus functions. PostgreSQL enum types are outside that inventory. This release does not run `ALTER TYPE ... OWNER TO`. Enum ownership stays with the current owner until a later migration. That later migration is a post-release prerequisite. It is not a P1 blocker, and it does not change the role transaction or the pinned P1 checksum `47ff9c932aea0a692b81ecfaf6c4a931b431e3e332e3e9c5b3fca96694550fe5`.

## 6. After the new application is up

- Health returns ok and the database reports up.
- The application session user is `stell22_app`, and that role is not a superuser.
- Pinned P1 has `finished_at`, no `rolled_back_at`, and `applied_steps_count` greater than 0.
- Restart the application container once. The migration count stays the same and the log does not apply a migration.
- One ordinary terminal write succeeds after the restart.
- `scripts/backup-db.sh`, `scripts/restore-db.sh`, and `mail.log` still match the pre-window bytes.
- `stell22-db-prod` and `stell22-caddy` were not recreated. Volume `db-data` remains.
- The next backup cron can run after the window. Do not run `scripts/restore-db.sh`.

`scripts/deploy.sh` is the later application update path. It still requires the role and pinned P1, builds the image, and starts only the application. It is not the role-split command.

## 7. Forward recovery

Use this when pinned P1 has been attempted and the new application does not become healthy.

- Leave the schema where the migration stopped.
- Do not restore an older archive.
- Do not run `scripts/restore-db.sh`.
- Do not start the previous image. Its entrypoint runs `prisma migrate deploy` as the superuser.
- Keep `stell22-app` stopped until the Owner chooses the next start.
- Database and Caddy stay as they were.
- Terminal writes remain interrupted until a reviewed application start succeeds.

A failure before the role transaction commits may start the legacy image only under the proof in step 5. A committed role change, an uncertain P1, or an unhealthy new application does not start that image. That refusal is not a database restore.
