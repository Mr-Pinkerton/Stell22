## 2. PSR-Q-001 / PSR-DESIGN-001 — causal persistence

**Status:** **CLOSED / ACCEPTED**.

### Decision

**NO** universal `CommandExecution` / generic command bus for Stell22.

Use **narrow domain causal contexts**.

`PSR-REJECT-010` separately forbids copying **Woodveri** `CommandExecution` / door MES as **mandatory Stell22 infrastructure**. This Q1 close is the Stell22 architecture choice: Stell22 does not introduce a universal command bus. It is **not** a restatement that `PSR-REJECT-010` globally forbids any generic `CommandExecution` design in the abstract.

### Production corrections

Already accepted in `audit/08.03`: `ProductionOperationMutation`.

### Normal physical postings

Where a retained domain document/action already exists, that document is the causal source:

- `ProductionOperation`
- `Inventory`
- `SimplePurchase`
- `Batch` / `RailLot`
- `Supply`

`InventoryMovement` persists causal identity **directly** (kind + id of that source, plus effect identity in §3). No extra generic command table.

### Manual physical actions without a retained source document

Persist on the movement (and atomic audit):

- stable `causationId` / request id;
- actor (see §4);
- reason where the action is manual/consequential;
- causal context.

No generic `CommandExecution` table is required for these actions.

### Non-stock contours

- Payroll causal identity remains `Payment` / `PaymentBatchItem`.
- Finance import identity remains `CashFlow` / `importKey`.
- Do **not** create universal command infrastructure for them.

### Direct master-data delete of physical stock

Direct master-data delete that destroys physical stock/projection is **NOT** an accepted authoritative stock writer.

Before authoritative cutover it **must** route through approved movement semantics **or** be disabled under `PSR-MUST-007`.

Current runtime examples (record only; not fixed here): `deleteDetail` drops `DetailStock`; `deleteBatch` can delete `RailLot` rows.

## 3. PSR-Q-002 — movement identity / idempotency

**Status:** **CLOSED / ACCEPTED**.

Two levels:

1. **CAUSATION / POSTING IDENTITY** — stable `causationId` for one business posting/action.
2. **EFFECT IDENTITY** — deterministic `effectKey` unique **inside** that causation.

Conceptual DB invariant:

```text
UNIQUE(causationKind, causationId, effectKey)
```

Exact Prisma names/types are **not** frozen in this documentation task.

`effectKey` **MUST** be deterministic from **stable business semantics**.

It **MUST NOT** depend solely on:

- a newly generated cuid/UUID created during the same posting attempt;
- `OperationDetailLine.id` if that line is recreated during reverse/reapply;
- `OperationNomenclatureLine.id` if recreated;
- array iteration order;
- an arbitrary/random ordinal;
- insertion order.

Reason: current PRISADKA / UPAKOVKA paths may delete/recreate operation lines, so those surrogate ids are **not** retry-stable identities.

If one causation contains several semantically distinct effects that would otherwise produce the same `effectKey`, implementation **MUST** either:

- **A.** aggregate them into one canonical movement at the accepted effect grain; **or**
- **B.** persist/derive a **stable retained source sub-identity BEFORE** movement generation and use that stable identity in `effectKey`.

A transient generated line id is **not** sufficient.

Conceptual semantic components of `effectKey` may include:

- `effectRole`
- `stockDomain`
- canonical physical pool key
- stable source sub-identity where required

Exact encoding / string / hash is a **PSR-P1** implementation detail. Do not freeze Prisma names/types here.

### Physical pool identity (examples)

| Domain | Pool identity |
| --- | --- |
| RAIL_LOT | `railLotId` |
| BLANK | `materialId` + canonical `lengthM` + `detailType` + `sort` |
| DETAIL | `detailId` + `torcevayaDone` + `ploskostDone` |
| NOMENCLATURE | `nomenclatureId` |
| PRODUCT | `productId` |

Blank length identity uses the **existing** exact canonicalization (`canonicalLengthFixed4` / `canonicalLengthDecimal` in `src/server/internal/blank-length.ts`; Prisma `Decimal(12,4)`). Do **not** use JS float formatting as identity.

One causation may produce **many** movements. Retry of the same causation/effect **must not** append another movement.

### `ProductionOperation.clientRequestId`

- remains **terminal-submit** request identity;
- is **NOT** universal;
- is **NOT** reused as a generic admin movement identity.

### Source-document creation in the same retriable request

For actions that **CREATE** their source document **and** the physical effect in one retriable request, source creation itself **must** be idempotent.

Movement uniqueness alone does **not** excuse duplicate source documents.

Hardening needed **before gateway/cutover** (record only; not implemented here):

- `createSimplePurchase` needs stable request dedupe;
- `createBatch` / receipt path needs stable request dedupe;
- other manual posting paths need stable request identity where unknown-commit retry can duplicate the business effect.

### Correction / cancellation

- a new mutation/action = a **new** `causationId`;
- a compensating movement has its **own** effect identity;
- a reversal **references** the original movement/effect;
- do **not** reuse the original movement uniqueness key.

## 4. PSR-Q-005 — actor representation

**Status:** **CLOSED / ACCEPTED**.

Do **not** create a second account/user system. Existing `User` (admin) and `Employee` (terminal) remain the person identities.

### Conceptual actor model

`actorKind`:

- `USER`
- `EMPLOYEE`
- `SYSTEM`

Conceptual fields:

- `userId` nullable
- `employeeId` nullable
- `systemActorKey` nullable
- immutable **actor display snapshot**

Exactly **one** corresponding actor identity is valid. Fail closed on invalid combinations.

| `actorKind` | Required | Absent |
| --- | --- | --- |
| `USER` | `userId` | `employeeId`, `systemActorKey` |
| `EMPLOYEE` | `employeeId` | `userId`, `systemActorKey` |
| `SYSTEM` | `systemActorKey` | `userId`, `employeeId` |

### SYSTEM actor is server-controlled

For `SYSTEM`:

- `systemActorKey` is **stable**;
- **server controlled**;
- **not** arbitrary client input;
- **not** a marketplace `externalId`;
- **not** a free-form “actor name”.

Actor **display snapshot**:

- captured **server-side**;
- immutable historical display;
- **never** trusted directly from a client payload.

Exact DB CHECK / enum implementation belongs to **PSR-P1**.

### Source vs actor

Marketplace / Ozon / WB business identity is **SOURCE / causation context**, not an actor identity.

- If marketplace sync is invoked by an admin: actor = `USER`.
- If an automatic job later invokes it: actor = `SYSTEM`.

Examples of `SYSTEM` keys may include: ledger cutover/opening; scheduled sync; cron/import. Exact enum/string values are an implementation detail later.

### Reason

Mandatory for:

- manual correction;
- manual write-off;
- manual inventory adjustment;
- equivalent consequential manual action.

**Not** mandatory for every ordinary production output/receipt.

Actor + causal identity + required reason + audit are **atomic** with the consequential mutation.

## 5. PSR-Q-007 — shadow / authoritative stream

**Status:** **CLOSED / ACCEPTED**.

Every `InventoryMovement` has an **explicit** authority classification.

Conceptual values:

- `SHADOW`
- `AUTHORITATIVE`

Exact field/enum name is **not** frozen.

Movement **authority** and **epoch binding** are:

- assigned by **trusted server/gateway** logic;
- **not** client-selectable;
- **immutable** after movement insert.

`SHADOW` **MUST NEVER** be promoted in place to `AUTHORITATIVE`.

If shadow rehearsal data later becomes obsolete: it remains `SHADOW` evidence or is handled by the later accepted retention/cleanup policy. It does **not** become authoritative history by `UPDATE`.

`AUTHORITATIVE` rows must belong to the accepted **final epoch stream**.

Do **not** decide `PSR-Q-004` activation mechanism or `PSR-Q-006` barrier implementation here. Those remain at their accepted later timing.

### Before FINAL epoch

**ALL** dual-written movements = `SHADOW`.

`SHADOW` movements:

- diagnostics only;
- excluded from authoritative reconstruction;
- **never** promoted / relabelled **in-place** to `AUTHORITATIVE`.

### FINAL epoch

- write barrier per later `PSR-Q-006` implementation;
- consistent projection snapshot;
- new `OPENING_BALANCE` movements;
- those opening rows belong to the **AUTHORITATIVE** stream;
- bind them to an **immutable final epoch identity**.

Post-final-epoch movements: `AUTHORITATIVE` and associated with that final epoch stream.

### Authority is not inferred

`OPENING_BALANCE` **kind alone does NOT imply authority**. A rehearsal/test opening can remain `SHADOW`.

Authority **MUST NOT** be inferred from:

- `recordedAt`
- `effectiveAt`
- `createdAt`
- `workDate`
- deploy SHA
- `production_cost_flow` Setting
- migration version

Authoritative reconciliation **explicitly selects** `AUTHORITATIVE` rows belonging to the final epoch stream.

`InventoryMovement` schema must support:

- explicit shadow/authoritative distinction;
- future binding to immutable final epoch identity.

Exact epoch/barrier **storage** remains `PSR-Q-006`, timed **BEFORE FINAL EPOCH**, not reopened here.

## 6. PSR-Q-008 / PSR-DESIGN-002 — historical reference retention

**Status:** **CLOSED / ACCEPTED**. Decision = **hybrid** retention by entity role.

### A. Retain authoritative causal source documents

Once used by authoritative movement history, do **not** physically delete causal source facts required for history.

At minimum:

- posted `ProductionOperation`
- `ProductionOperationMutation`
- `CONDUCTED` `Inventory` + relevant lines
- `SimplePurchase`
- authoritative `Batch` / `RailLot` source identities

Use archive / status / correction / compensation instead of hard delete.

**DRAFT** documents that never posted a physical fact may still be deletable.

### B. Immutable identifying snapshot for mutable master references

`InventoryMovement` historical meaning must not depend on current mutable master fields.

For relevant movement types preserve identifying snapshot/context for mutable entities such as:

- `Material`
- `Detail`
- `NomenclatureItem`
- `Product`
- actor display identity

Current IDs may also be stored for navigation, but changing / deleting / renaming a current master row **must not rewrite** the historical meaning of an authoritative movement.

Exact JSON-vs-columns choice belongs to **PSR-P1 schema review**.

### C. RailLot

`RailLot` is physical lot identity.

After authoritative historical use:

- do not allow its physical identity to disappear;
- retain it / restrict destructive deletion.

### D. Marketplace / Supply

Movement source history must preserve immutable **external** source identity:

- `marketplace`
- `externalId`
- `sku`

Do **not** depend solely on continued existence/mutability of a `Supply` row.

### E. No dangling authoritative history

No authoritative movement may depend only on a reference that can disappear with no immutable representation.

Do **not** add `CASCADE` delete from master/source entities into movement history.

## 7. Opening-balance grain

FINAL opening is captured **directly from physical projections** under the final write barrier.

Do **NOT** derive opening from the current Inventory UI/document.

| Domain | Opening grain | Non-zero only |
| --- | --- | --- |
| RailLot | one row per `RailLot.id` with non-zero `remainingQuantity` | yes |
| BlankStock | one row per shared physical pool: `materialId` + canonical `lengthM` + `detailType` + `sort` | yes |
| DetailStock | one row per `detailId` + `torcevayaDone` + `ploskostDone` | yes |
| NomenclatureStock | one per `nomenclatureId` | yes |
| ProductStock | one per `productId` | yes |

Do **NOT** duplicate BlankStock opening per `Detail`.

DetailStock opening includes **ALL relevant WIP flag combinations**, not the ready-only Inventory abstraction.

Opening movement rows are created for **NON-ZERO** balances only.

For quantity reconstruction:

- missing opening row == quantity **0**;
- zero projection row and absent projection row are **equivalent quantity zero**.

Existing zero projection rows may remain as a read-model implementation detail.

If the FINAL snapshot finds an invalid **negative** quantity or an **ambiguous duplicate** physical key: **CUTOVER MUST FAIL CLOSED**. Do not normalize silently.
