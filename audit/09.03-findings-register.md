### BA-P01-001

| | |
| --- | --- |
| Priority | P3 |
| Class | CONFIRMED BUG |
| Proof | CODE and DB. PROD not queried |
| Scenario | E, several batches in one deal |

**Where:** `src/server/internal/finance-operations.ts:311–315`. `totalCost` is `newTotal.toFixed(2)` per batch. `src/lib/deal-cost.ts:44–54` does not keep a residual kopeck for the last batch.

**Condition:** confirmed delivery (or other deal extra) does not divide evenly across batches at 2 decimal places, and the batches are not frozen.

**Expected:** the sum of batch extras equals the deal extra at kopecks. `deal-cost.test.ts` requires that for the pure share (`100 / 3 × 3 = 100`).

**Actual:** each share is rounded alone. Disposable PostgreSQL stored the same figures (`audit/09.06`):

- Extra `100.00`, 3 equal purchases of `10.00`, source cash `130.00` → persisted `43.33 + 43.33 + 43.33 = 129.99` (1 kopeck missing). A second sync stayed on `129.99`.
- Extra `0.01`, 2 equal purchases of `10.00`, source `20.01` → persisted `10.01 + 10.01 = 20.02`.
- Extra `0.01` on two zero-purchase batches → persisted `0.01 + 0.01 = 0.02`. The form rejects purchase `0`; the writer accepts the row.
- Extra `100.01` on purchases `90000` and `30000` persisted `120100.01` exactly. Opposite rounding can conserve.

`Decimal.set({ rounding: ROUND_HALF_UP })` is set in `src/lib/cost.ts:12` and applies to this `toFixed`.

**Impact:** `Batch.totalCost` can disagree with confirmed cash by 0.01 ₽ per split, then the whole (wrong) `C` is spread onto produced metres. One batch is exact. Display in whole rubles can hide it. Not observed on production rows.

### BA-P01-002

| | |
| --- | --- |
| Priority | P3 |
| Class | CONFIRMED BUG |
| Proof | CODE and DB. PROD not queried |
| Scenario | T, frozen batch whose sort costs are not already on a kopeck |

**Where:** `prisma/schema.prisma:1089–1092` (`costSort1`, `costSort2`, both `Decimal(14,2)`). Writer `src/server/internal/cost.ts:322–335` and `384–386` stores the full `Decimal` string. Reader for a frozen batch is `src/lib/cost-report.ts:201–215`, which trusts those columns.

**Condition:** `costSort1` and `costSort2` are exact complements of `C`, and each rounds halfway in the same direction.

**Expected:** stored `costSort1 + costSort2 = C`. The pure function guarantees that (`cost.ts:117–121`, test "без дрейфа").

**Actual:** independent 2 dp rounding. `1.005 + 8.995 = 10` becomes `1.01 + 9.00 = 10.01`. Disposable proof: `'1.005'::numeric(14,2)` is `1.01`; `maybeFreezeBatch` on integer metres `201` and `1799` with `C = 10` wrote FINAL `1.01` and `9.00` (sum `10.01`); a direct insert of those strings stored the same pair. A second freeze returned false and left one FINAL row. The `1/3` of `100` case happens to survive (`33.33 + 66.67 = 100`), so the existing test does not catch the failure.

**Impact:** after freeze, the report and the species blend use a wood total that can be 0.01 ₽ off `Batch.totalCost`. PRELIMINARY rows are not read by the report, so this hits FINAL only. Not observed on production rows.

**Condition:** the gate is active, the batch is not frozen, lots have `initialValue` and `remainingValue`, `cOld > 0`, and the unrounded total is not already on 2 dp.

**Expected:** repeating `syncDealInternal` on unchanged cash is idempotent. Stored `Batch.totalCost`, the lot pool, and `PURCHASE_VARIANCE` events stay on one money figure, and that figure matches the source cash at kopecks.

**Actual:** stored `C` and the pool diverge, and the pool moves on every unchanged sync.
