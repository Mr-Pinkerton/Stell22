## 1. Accepted model

`Supply` remains a **long-lived line**:

`UNIQUE(marketplace, externalId, sku)`

It is **not** replaced by immutable marketplace-event rows.

Durable stock-accounting lifecycle fields:

| Field | Default | Meaning |
| --- | --- | --- |
| `stockAccountingGeneration` | `0` | Monotonic cycle number. Never reset on cancel. |
| `stockAccountingOpen` | `false` | Whether the current generation is an active/processed cycle. |

| generation | open | Meaning |
| --- | --- | --- |
| 0 | false | No post-cutover accounting cycle has started |
| ≥1 | true | Logical stock-accounting cycle is active/processed |
| ≥1 | false | That generation was closed (Ozon cancel). Next SHIPPED opens generation+1 |

Retry of the same **open** cycle keeps generation unchanged.

---

## 2. One-shot shortfall (unchanged)

`delta = targetQty - (deductedQty + shortfallQty)`.

Shortfall is already accounted. A later poll of the **same** SHIPPED cycle with more stock does **not** fill the shortage.

The only same-cycle additional accounting delta is a **quantity increase**.

A full-shortfall result (`toRemove = 0`, `shortfall > 0`) still **opens/keeps** a cycle. Physical delta 0 is not “not processed”.

---

## 3. Deduction

Under the existing Supply `FOR UPDATE` lock:

1. If `targetQty <= deductedQty + shortfallQty` (or no `productId`): no accounting mutation; generation/open unchanged.
2. Else if `stockAccountingOpen = false`: `generation += 1`, `open = true`.
3. Else keep generation.
4. Apply existing `computeSupplyDeduction` and ProductStock decrement.

---

## 4. Ozon cancellation

Select/lock cancelled Supply rows by **identity** (`marketplace = OZON` and cancelled `externalId`), **not** by `deductedQty > 0`.

After the row lock:

| `stockAccountingOpen` | Action |
| --- | --- |
| false | no-op (duplicate / no cycle) |
| true | restore `ProductStock` by **exactly `deductedQty`** (0 if full shortfall); zero watermarks; `status = PENDING`; `open = false`; **generation unchanged** |

Same-sync conflict: if an Ozon id is in both the live SHIPPED/ACCEPTED poll and the cancelled-ID list, **cancellation wins**. That id is excluded from the deduction pass, then cancellation runs. No deduct-then-restore in one snapshot.

Cross-sync / out-of-order polls are a different rule. If a cancellation observation runs while no cycle is open (no-op) and a stale SHIPPED observation later acquires the Supply lock, that SHIPPED mutation is a real stock mutation and belongs to the generation it opens. This is existing marketplace eventual consistency, **not** a cycle-identity failure. The persistent Ozon cancellation poll is responsible for later closing that same generation. R-04 does not add an event-version/sequence field and does not serialize HTTP polling.

ChangeLog: Ozon cancellation-close writes `gp_restore_cancelled` when `closed === true`, including full-shortfall closes (`restored: 0`) plus the closed `generation`. Duplicate/no-cycle cancel remains a no-op and is not logged.
