Question: can `{ railLotId, quantity }[]` for a retained `createBatch` be restored from a source other than `InventoryMovement`?

Answer: **not for a deleted batch.** No retained document stores those pairs independently of the live `RailLot` row and independently of the movement. Full historical Invariant A coverage is not available.

## 1. What a receipt pair must be

Invariant A needs the original receipt set, not the later remainder (`audit/08.28` §2 and §4). `batchCreateReceiptEffects` emits one `RECEIPT +quantity` per created lot with `quantity > 0` (`src/server/internal/raw-purchase-shadow-write.ts` lines 158–173). A zero quantity creates no effect.

`batchCreateCausationSnapshotV1` does store `{ railLotId, quantity }[]`, but it is written onto the movement (`raw-purchase-shadow-write.ts` lines 136–156 and 345–349). `audit/08.28` §4 forbids using that snapshot as `ExpectedEffects`. This discovery does not use it.

## 3. Case A — batch and lots still exist

Current application writers do not update `RailLot.quantity` after insert. The writers found in `src/server` change `remainingQuantity` and, when cost flow is active, monetary columns:

- TORCOVKA decrement: `submit-torcovka-tx.ts` lines 265–268
- R-05 increment: `correct-torcovka-rails-taken-tx.ts` lines 270–272
- active TORCOVKA and its correction: `cost-flow-raw.ts` lines 236–241 and 646–651
- write-off: `purchases.ts` lines 615–618, or `cost-flow-raw.ts` lines 874–878
- purchase variance: `finance-operations.ts` lines 245–247 (`remainingValue` only)
- value initialization: `cost-flow-raw.ts` lines 831–836

`updateBatch` does not edit rails (`purchases.ts` lines 391–394). No application path inserts a later `RailLot` into an existing batch or deletes one lot. The only lot insert in application code is the nested create inside `createBatch`. The only lot delete is `deleteBatch`.

So, while the rows exist, `{ id, quantity }` on those rows is the insert set under the current code. `remainingQuantity` is not that quantity after TORCOVKA or write-off.

This is not a frozen receipt document. Nothing in the schema prevents a later `UPDATE` of `quantity`. `audit/08.28` §4 already calls the live row sufficient for Invariant A and keeps that case out of Slice 1. This discovery does not promote it to a historical proof, and it does not authorize a checker. Eligibility does not depend on whether the command predates a durable pair list. It still requires a separate HEAD decision and proof that every original row is intact. It is not an automatic `MATCH_OBSERVED`.

If any lot row is gone, the live set is not the original set. Do not fill the gap from the snapshot by matching length, type, sort, and quantity: two rails in one command may be identical, and the snapshot has no id (`purchase-command-identity.test.ts` lines 66–97).

## 4. Case B — batch and lots deleted

`deleteBatch` requires every `remainingQuantity = 0`, no `ProductionOperation` for the batch, no deal item, and inactive cost flow (`purchases.ts` lines 670–688). It then deletes costs, lots, and the batch. The command and any write-off remain.

Generic TORCOVKA delete is rejected before stock reversal (`production.ts` lines 350–351; `production-physical-delete-policy.ts` lines 30–31). The reverse body below that call is unreachable for TORCOVKA (`production.ts` lines 331–333). An application consumption therefore leaves an operation, and that operation blocks `deleteBatch`.

Under those guards, a batch that current code managed to delete had not been consumed by TORCOVKA, so a write-off's `quantityBefore` would numerically equal the insert quantity. That equality is an inference from the delete guard. The write-off document does not say the number is the original receipt quantity. A later reducer that changes `remainingQuantity` without leaving an operation would make the same retained write-off describe a different receipt. No such reducer exists in this tree. The inference is still not an independent source.

After deletion, `requestSnapshot` cannot name the generated ids. Two creates with the same snapshot and different generated ids are different receipt sets and leave the same snapshot. The write-off distinguishes the ids only as remainder targets.

Historical commands written before a durable pair list exist cannot be completed later from `InventoryMovement`. The identity migration created the command table empty and did not backfill (`20260920120000` lines 1–2).

## 5. Case C — partial or older data

- Command absent: `SOURCE_UNAVAILABLE`. Pre-identity batches have lots and no `BatchCreationCommand`.
- Command present, snapshot well formed, lots deleted, no durable pair list: `NOT_EVALUABLE`. Missing ids are not `INVALID_SOURCE`. The v1 snapshot is valid without them.
- Command present, some but not all lots present: current code does not produce this. Do not reconstruct the missing ids. `NOT_EVALUABLE`.
- Write-off `quantityBefore` disagreeing with a still-present `RailLot.quantity`: expected after consumption. It is not a receipt mismatch.
- Empty observed movements for a known nonempty receipt set: `GATE_UNKNOWN`, not `MISMATCH`, until SHADOW preservation is proven (`audit/08.28` §5).
- Invariant B: `NOT_EVALUABLE`. No projection witness exists.

Do not report `MATCH_OBSERVED` from the movement snapshot, from the write-off, or from an empty expected set that was not proven.

## 6. Case D — replay

Replay addresses the retained command id. It is not a second physical receipt (`raw-purchase-shadow-write.ts` line 327; `purchases.ts` lines 304–313). A checker must not treat the replay attempt as another effect.

## 7. Options

### Option A — compare only lots that still exist

Covers commands whose batch and every original lot row still exist, and only if HEAD accepts live `RailLot.quantity` as the receipt quantity. Does not cover deleted batches. No schema change. The source is independent of `InventoryMovement`, but it is not durable. A later edit of `quantity` would move the expected set. Historical commands with missing rows stay `NOT_EVALUABLE`.

### Option B — forward-only pairs on the create command

In the same `createBatch` transaction, after the lot ids exist, store `{ railLotId, quantity }[]` on `BatchCreationCommand`. Do not copy it from `InventoryMovement`. Replay must not append a second list. The list survives `deleteBatch` because the command has no FK.

Covers creates after that write ships. Commands already stored are outside this option. An intact live set remains Option A, not this option. A missing original set stays `NOT_EVALUABLE`. Needs a schema change and a writer change. No backfill.

This is the future source already named in `audit/08.28` §4. It is not authorized by this file.

### Option C — another existing source

None found. ChangeLog, package codes, and the write-off remainder do not supply the original pairs after deletion.

### Option D — classify by source availability, not by date

A command that predates a durable pair list is not `NOT_EVALUABLE` merely because of when it was written.

- All original `RailLot` rows are intact. `createBatch` inserts `quantity` and `remainingQuantity` together (`purchases.ts` lines 334–348). The row keeps both (`prisma/schema.prisma` lines 263–278). That command may be eligible for Option A even if it predates a durable pair list. Eligibility needs a separate HEAD authorization and proof that the original set is intact. It is not an automatic `MATCH_OBSERVED`.
- Original rows are missing or incomplete, and no independent durable receipt pair list exists: `NOT_EVALUABLE`.
- A command created before such a list exists is judged by whether its source is still available, not by its creation date.
- A later command that retains its own pair list would be Option B coverage. That write is not implemented and is not authorized here.

Do not report `MATCH_OBSERVED` from `InventoryMovement`, from the write-off, or from an unproven zero.

## 8. Recommendation

Full historical coverage is **not possible** from the documents this tree retains.

Partial coverage of lots that still exist is possible only as Option A, and only after a separate HEAD decision. It does not survive deletion.

A durable source is required for any receipt check that must remain valid after `deleteBatch`. The only source that satisfies the independence rule without reading the movement is Option B, written in the create transaction.

No implementation slice is authorized. A later slice can be considered only if HEAD accepts Option B and all of the following hold:

- the pair list is written in the same transaction as the lot insert, after the ids exist;
- it is not copied from `InventoryMovement` or from `causationSnapshot`;
- replay of `requestId` does not create a second list or a second lot set;
- commands stored before that write are outside Option B; an intact live set may still be eligible for Option A after a separate HEAD decision, and a missing original set stays `NOT_EVALUABLE`;
- there is no historical backfill;
- Invariant B stays `NOT_EVALUABLE`;
- an empty observed movement set stays `GATE_UNKNOWN`.
