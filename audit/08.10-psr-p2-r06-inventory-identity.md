## 1. Reconnaissance evidence (why identity had to change first)

Pre-R-06 `createInventoryDraft` derived DETAIL lines from catalog Details / `getWarehouseStock().details`. No-prisadka Details alias the **full** shared `BlankStock` pool (`buildStockSnapshot`). Two ACTIVE catalog Details A/B with the same physical spec `(materialId, lengthM, detailType, sort)` produced two DETAIL lines, each with `accountedQty = pool quantity`.

Inactive conduct SET the shared pool per line (last write wins). Active `applyBlankInventoryLine` summed deviations through Detail.id. UI showed catalog names. Live validation compared each alias to the same pool (10 vs 10 twice). Inventory boundary expanded a spec to all no-prisadka Detail ids.

That identity cannot be dual-written: one physical pool would mint two InventoryMovement effects or two CostEvents.

R-06 closes identity **before** any INVENTORY InventoryMovement writer.

## 2. Accepted physical target model

Inventory counts **physically countable targets**.

| Line | Identity | Grain |
| --- | --- | --- |
| PRODUCT | `InventoryLine.refType=PRODUCT`, `refId=productId` | `ProductStock(productId)` |
| NOMENCLATURE | `refType=NOMENCLATURE`, `refId=nomenclatureId` | `NomenclatureStock(nomenclatureId)` |
| BLANK | `refType=BLANK`, `refId=BlankStock.id` | one `BlankStock` pool `(materialId, lengthM, detailType, sort)` |
| DETAIL | `refType=DETAIL`, `refId=detail.id` | ready aggregate of one **prisadka** catalog Detail |

A no-prisadka catalog Detail is **not** a physical inventory target.

Database `InventoryLine.refType` remains `String`. Application `InventoryRefType` is `BLANK \| DETAIL \| PRODUCT \| NOMENCLATURE`.

## 5. DETAIL ready aggregate + deterministic bucket effects

Worker counts READY quantity for a prisadka Detail as one aggregate.

Physical projection (accepted):

- Canonical ready bucket `(detailId, torcevayaDone=detail.prisadkaTorcevaya, ploskostDone=detail.prisadkaPloskost)` → `afterQty = InventoryLine.actualQty`
- Every other existing READY bucket for that Detail → `afterQty = 0`
- Non-ready / WIP buckets **unchanged**

Example: torcevaya required; READY `(true,false)=4`, `(true,true)=3`; WIP `(false,false)=2`; accounted=7 actual=5 → `(true,false)=5`, `(true,true)=0`, WIP=2. Effects: canon `+1`, other ready `-3`. Aggregate delta `-2`.

Inactive conduct applies this derived target state. `normalizeReadyBuckets` remains the equivalent write plan; effect-plan tests and projection writes agree.

Active dormant branch (`applyDetailInventoryLine`) **always** consolidates other READY quantity/value into the canon pool first — including when aggregate `deviation === 0` (internal reclassification; no `INVENTORY_GAIN` / `INVENTORY_LOSS`). Net deviation is applied only after that canonicalization. **Physical quantity results match** the effect plan. Gate stays INACTIVE.
