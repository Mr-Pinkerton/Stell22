## 1. Question

Can a future offline maintenance window reliably exclude independent application writers?

This run answers that question for a synthetic harness on disposable PostgreSQL 17 only. The answer is no freeze pass. Some synthetic controls held. Several independent write paths did not.

The model under test:

- new HTTP writes stop being accepted;
- work that already started either finishes or is stopped by an operator;
- a background loop does not keep writing after its own flag closes;
- an old application session cannot COMMIT after the freeze is declared;
- a new application connection does not appear by itself;
- a trusted operator remains a separate access boundary.

Physical isolation of the access terminal stays the Owner's decision. This run did not disconnect a terminal and does not treat any simulation as that proof.

A technical write ban for unrestricted host root or the PostgreSQL bootstrap superuser was not required and was not attempted.

## 3. Harness

Listeners bind `127.0.0.1` and port 0.

- A synthetic application `POST /write` checks an in-memory flag and then inserts as `p1wc_app`. Closed returns 503 and does not insert.
- A synthetic reverse proxy forwards that POST only while its own flag is open. Closed returns 503 and does not forward.
- An in-process interval checks the flag before each insert.
- One delayed writer checks the flag only when it is scheduled. Another checks again at fire time.
- A sibling container, prefix `stell22-p1owa-`, uses the same Postgres image, `restart: unless-stopped`, no published ports, and a test volume mounted at `/admission`. Its loop inserts only when `/admission/state` is `open`.
- A crash is the process exiting (`exit 137`) after the operator writes `/admission/crash`. `docker kill` is measured separately.
- The operator path is the bootstrap superuser and the break-glass superuser inside the test cluster, plus `docker stop`, `docker start`, and `docker kill` of the captured writer id.

The HTTP route is synthetic. It is not a Server Action, not Caddy, and not the production app.

### A. New HTTP writes

Before isolation, both the direct listener and the proxy inserted a row.

Closing only the proxy left the direct listener able to insert. Proxy-only closure is not application admission.

After both flags were closed, all 16 samples across about two seconds were rejected. That is the synthetic interval only.

### B. Existing transactions

Three application sessions were opened with `BEGIN` and `pg_sleep` before the flag and the admission row were closed. Visibility was polled by `application_name`, not by one idle snapshot.

- The session that did not look at the admission row again committed row 1001 after the declaration. **FREEZE PASS is forbidden on this fact alone.**
- The session that raised if `p1owa_admission.state` was not `open` left row 1002 absent.
- `pg_terminate_backend` on the third session, while it was still inside `pg_sleep`, left row 1003 absent. That terminate is an operator action.

Four later races slept one second and were terminated if their backend was visible. All four rows committed. Terminate did not win those windows.

### C. Background writers

The in-process interval inserted while the flag was open. After the flag was closed and `stop` was called, it did not start another insert (`backgroundTicksAfterClose` 0).

A callback that had already passed the in-memory check inserted after the flag closed.

A callback that checked again at fire time did not insert.

The container loop inserted while `/admission/state` was `open` and did not add rows across two 1.5 second samples after the file was set to `closed`.

These are test equivalents. They are not the production schedulers named in section 7.

### D. Restart

On this daemon, `docker kill` is not a process crash that `unless-stopped` restarts. A separate disposable container and the writer container both stayed `exited` with `RestartCount` 0 after `docker kill`.

A process exit (`exit 137`) did increment the restart and changed `StartedAt`.

| Condition | Observed |
| --- | --- |
| Admission file closed, then process exit | Policy restarted the container. No new restart-loop row |
| Admission file open, then process exit | Policy restarted the container. Inserts resumed without a further operator write command |
| `docker stop` | Still `exited` after 3 seconds. No new row |
| `docker start` after that stop | Inserts resumed. This was an operator command |
| `docker kill` after the writer was running again | Stayed `exited`. `RestartCount` 0. The engine did not start it |

Docker daemon restart was **NOT TESTED**. At cleanup, 7 running containers were not this proof, including `woodveri-b2b-wp-migration-wordpress-1`, `woodveri-b2b-wp-migration-db-1`, `woodveri-b2b-wp-migration-mailpit-1`, `woodveri-wordpress-1`, `woodveri-db-1`, `stell22-db`, and `df-cost-db`. Restarting the shared daemon was not safe. No simulation was substituted.

The writer comes back without a separate operator command when the process exits by itself and the admission file is still `open`. An explicit `docker stop` stayed down until `docker start`. `docker kill` on Docker 29.2.1 also stayed down. Those two engine signals are not the same as a process crash on this daemon.

### E. Admission continuity

The synthetic reject held for every sample in the measured interval (8 samples, both ports, 0 breaks). That does not cover a channel the harness never called.

The HTTP flag is not database admission. After HTTP was closed, a new `p1wc_app` session inserted row 9100. The next `pg_stat_activity` sample still showed that query text. One sample, seen or missed, is not proof that every other session is gone.

Five earlier samples saw no `p1wc_app` client backend. The late insert happened after those samples. The zero count is not a proof of an empty server.

### F. Trusted operator

Not banned, and not a production guarantee:

- Bootstrap inserted row 9001.
- Break-glass inserted row 9002. The run throws if either insert fails, and this run completed.
- `pg_terminate_backend`, `docker stop`, `docker start`, `docker kill`, and writes to the admission file are operator actions.
- Host root was not excluded. The test used root inside `docker exec` to write the admission file.
- `p1wc_app` updated `p1owa_admission` from `closed` to `open` because it inherits `p1wc_migrator`, the table owner. SQLSTATE was not `42501`. Bootstrap set the row back to `closed`. Membership in the owner is enough. This does not authorize a production role split.

Other holders not excluded by this run: anyone who has the application password, host root, the bootstrap superuser, and a non-cooperative session that commits before terminate.

## 9. Residual risk

An offline HTTP flag does not stop a session that already passed its check, a session that never checks again, or a new SQL login that still has the application role. A short terminate race can lose. A crash restart restores writes when the admission file stays open. The application role can clear a latch it inherits through the owner. Production Server Actions, Caddy, cron, Prisma pools, and a daemon restart were not exercised. Physical disconnection was not performed.
