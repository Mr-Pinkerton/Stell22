## 12. Edit movement semantics — P1-01 CLOSED BY HEAD

### 12.1 Historical discovery recommendation (superseded)

The discovery HEAD recommended representing PRISADKA/UPAKOVKA SHADOW rows as explicit reverse-old + apply-new ledger events. **HEAD does not accept that as the InventoryMovement representation.** That was P1-01.

### 12.2 Canonical InventoryMovement representation

The runtime transaction may continue internally to reverse and reapply.

SHADOW InventoryMovement for a quantity-edit mutation must represent **the net committed physical change per canonical physical target caused by the edit transaction**.

All A/B/C edit movements are mutation corrections:

```text
causationKind = PRODUCTION_OPERATION_MUTATION
kind          = ADJUSTMENT
semantic role = adjust
```

For each canonical physical target:

```text
quantityDelta =
  post-command physical quantity
  - pre-command physical quantity
```

Aggregate all internal reverse/apply steps for that exact target. Omit the target if resulting delta = 0. One resulting movement per canonical physical target per mutation command.

Do **not** emit the internal algorithm as separate ledger history.

Do **not** model quantity edit as InventoryMovement `REVERSAL`.

Do **not** require `reversalOfMovementId`.

Do **not** make correction correctness depend on historical SHADOW presence. The SHADOW ledger may have been OFF when the original ProductionOperation occurred.

The retained mutation command may store detailed before/after provenance. InventoryMovement effects represent the actual committed projection delta of this correction.

### 12.3 Target aggregation

Aggregation is by exact canonical physical target identity. Do not net different physical target identities together.

### 14.2 Proof matrix

| Condition | Current result |
| --- | --- |
| cost flow ACTIVE | rejected (`COST_FLOW_DELETE_BATCH`) — no lot delete |
| cost flow INACTIVE, ops>0 or deals>0 | rejected — lots kept |

`createBatch` always creates lots with `remainingQuantity = quantity` (`purchases.ts`). A newly created unused batch therefore has **positive** remaining and **is currently deletable**. That is the enabled physical contour.

Write-off then delete: `writeOffBatchRemainder` can zero lots without creating a `ProductionOperation`. Those zeroed lots are then deletable. That destroys the RAIL_LOT target identity that a future SHADOW write-off movement would point at. That is P5 target-lifetime, not a remaining **quantity** mutation if the `== 0` guard is in place.

### 14.3 Is `every remainingQuantity == 0` sufficient?

**Sufficient for physical quantity integrity** of this contour: no RAIL_LOT qty can disappear except at 0.

**Not sufficient** to preserve lot/master identity (P5). Other destroyed values when the guard passes:

- `RailLot` rows (identity, `remainingValue` if ever set — but ACTIVE cost-flow already blocks this delete);
- `BatchCost` rows;
- `Batch` master.

Ops/deal guards must **remain**. They are not implied by remaining==0 (a fully consumed batch that still has TORCOVKA ops has remaining 0 and must stay).

Do **not** reduce the qty guard to `> 0`. `remainingQuantity` is `Int` with **no** CHECK ≥ 0 in `schema.prisma` / init migration. Runtime writers use `gte` decrements, but negatives are structurally possible. The safe P2 guard is `== 0` for **every** lot (vacuous if no lots).

### 14.4 HEAD decision

**FAIL-CLOSED unless every `RailLot.remainingQuantity === 0`.**

Preserve existing conditions:

- `production_cost_flow ACTIVE` → reject;
- any ProductionOperation → reject;
- any DealItem → reject.

Any non-zero quantity, including structurally possible negatives → reject. Not `> 0`.

No SHADOW writer. No retained deletion identity for P2. Zero-quantity RailLot identity destruction is deferred to P5 / history-lifetime work.
