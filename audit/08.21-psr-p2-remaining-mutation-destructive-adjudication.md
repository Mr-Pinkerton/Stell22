## 11. Special question — retained mutation identity (edits)

Investigate only. Schema is **not** frozen.

### 11.1 Required retained information

Minimum fields evidenced by R-05 (`ProductionOperationCorrection`) + raw identity (`08.19`) + the three edit semantics:

| Field | Why |
| --- | --- |
| `requestId` UNIQUE | retry / COMMIT-UNKNOWN replay, same as R-05 and raw commands |
| `operationId` | which ProductionOperation was edited (scalar; **no FK cascade**) |
| `adminUserId` | must capture `requireAdmin().id` (currently discarded) |
| `operationType` | TORCOVKA / PRISADKA / UPAKOVKA — discriminates effect shape |
| old physical effect set | what was reversed or used as CAS baseline |
| new physical effect set | what was applied |
| committed delta / compensating set | actual posted movements (may differ from requested if a branch no-ops) |
| `reason` | **not** required by current quantity-edit UI; R-05 requires it. Do not invent a reason requirement here. Optional / null-ok unless HEAD wants parity with R-05 |
| `recordedAt TIMESTAMPTZ(3)` | movement `effectiveAt` source, same as `08.19` |

CAS: TORCOVKA can use expected-old line qty (like R-05 expected-old railsTaken). PRISADKA/UPAKOVKA need an expected-old **effect/provenance snapshot** (line ids + source flags + qty / `productQty` + provenance rows). A payload-mismatch replay must fail, not silently re-apply.

### 11.2 One row vs child rows vs JSON

**Recommendation: one command row + JSON effect snapshots. No child-effect table.**

Reasons from this repository:

- `08.19` already accepted `effectSnapshot` / `requestSnapshot` JSONB on command rows (`BatchRemainderWriteOff`, `BatchCreationCommand`, `SimplePurchaseCreationCommand`).
- R-05 used **typed scalar columns** because that contour has one RailLot delta. Quantity edits are multi-target for PRISADKA/UPAKOVKA; cloning that into a child-row schema is a generic framework.
- `08.03` `ProductionOperationMutation` with full before/after JSON **and** Correction Center is later P5-ish work; HEAD forbade pulling that into P2.
- Child rows are not required to prove replay: replay returns the retained command and skips stock, same as R-05 / raw writers.

One row per **edit command** is sufficient. One row per operation is **not** sufficient (repeated legal edits).

Do **not** overload `ProductionOperationCorrection` (railsTaken-specific columns).

Working name only (not frozen): `ProductionOperationQuantityMutation` or equivalent narrow table. Not `ProductionOperationMutation`. Not `CommandExecution`.

### 11.3 Causation

```text
causationKind = PRODUCTION_OPERATION_MUTATION
causationId   = retained quantity-mutation command id
               (NOT ProductionOperation.id)
```

This matches `08.11` / R-05 (`causationId = ProductionOperationCorrection.id`). Replay returns the retained mutation without reapplying stock.

### 11.4 Can one model cover all three edits without becoming a framework?

**Yes, if** the table stays “one quantity-edit command for the existing `updateProductionLineQuantity` entry” and effect bodies live in JSON discriminated by `operationType`.

**No, if** the same table is asked to absorb delete/cancellation, R-05 railsTaken, HOURS, or Correction Center. That would be the `08.03` generic mutation. Do not do that in P2.

## 12. Special question — edit effect semantics

| Edit | Recommended movement representation |
| --- | --- |
| TORCOVKA | **Net signed delta** on the single Blank target/role. Old and new are the same spec; increment vs decrement is one semantic correction. |
| PRISADKA | **Explicit reverse of old effects + apply of new effects.** Source target may change (blank vs partial detail bucket; flags). |
| UPAKOVKA | **Explicit reverse of old provenance + apply of new prepared BOM × qty.** Product output and input consumption are different roles even if a refId coincides. |

## 14. Contour G — `deleteBatch`

### 14.1 Exact current behavior (`src/server/purchases.ts`)

```text
requireAdmin()                          // discarded

                                    // "Нельзя удалить партию при включённом денежном учёте."

```

There is **no** dedicated `deleteBatch` integrity test. Only `raw-purchase-shadow-confinement.test.ts` uses the name as a source-slice boundary.

### 14.2 Proof matrix

| Condition | Current result |
| --- | --- |
| cost flow ACTIVE | rejected (`COST_FLOW_DELETE_BATCH`) — no lot delete |
| cost flow INACTIVE, ops>0 or deals>0 | rejected — lots kept |
| cost flow INACTIVE, no ops, no deals, **all** `remainingQuantity == 0` (including no lots) | **allowed**. Lots (if any) hard-deleted. No physical qty destroyed. Lot **identity** destroyed. |
| cost flow INACTIVE, no ops, no deals, **any** `remainingQuantity != 0` | **allowed**. Those RailLots are hard-deleted. **Positive (or nonzero) physical RAIL_LOT balance is destroyed with no movement document.** |

`createBatch` always creates lots with `remainingQuantity = quantity` (`purchases.ts`). A newly created unused batch therefore has **positive** remaining and **is currently deletable**. That is the enabled physical contour.

Write-off then delete: `writeOffBatchRemainder` can zero lots without creating a `ProductionOperation`. Those zeroed lots are then deletable. That destroys the RAIL_LOT target identity that a future SHADOW write-off movement would point at. That is P5 target-lifetime, not a remaining **quantity** mutation if the `== 0` guard is in place.

### 14.3 Is `every remainingQuantity == 0` sufficient?

**Sufficient for physical quantity integrity** of this contour: no RAIL_LOT qty can disappear except at 0.

**Not sufficient** to preserve lot/master identity (P5). Other destroyed values when the guard passes:

- `RailLot` rows (identity, `remainingValue` if ever set — but ACTIVE cost-flow already blocks this delete);
- `BatchCost` rows;
- `Batch` master.

Ops/deal guards must **remain**. They are not implied by remaining==0 (a fully consumed batch that still has TORCOVKA ops has remaining 0 and must stay).

Do **not** reduce the qty guard to `> 0`. `remainingQuantity` is `Int` with **no** CHECK ≥ 0 in `schema.prisma` / init migration. Runtime writers use `gte` decrements, but negatives are structurally possible. The safe P2 guard is `== 0` for **every** lot (vacuous if no lots).

### 14.4 Candidate

**FAIL-CLOSED DISABLE** physical deletion unless every `RailLot.remainingQuantity == 0` (and existing ops/deal + ACTIVE cost-flow guards).

No new SHADOW writer. No identity table. Smallest safe P2.

### 14.5 Concurrency

Current pre-TX counts are **not** a safe guard. Concurrent `submitTorcovka` / `writeOffBatchRemainder` / `createBatch` retry can change lots after the count.

Required future TX (recommendation, not implemented):

1. open TX;
2. lock lots of this batch **then** the batch — **same order as `writeOffBatchRemainder`** (`lockRailLots` then `lockBatches`) to avoid deadlock with write-off / TORCOVKA;
3. re-count `ProductionOperation` and `DealItem` inside the TX;
4. read locked lots; fail if any `remainingQuantity != 0`;
5. then delete costs / lots / batch.

A pre-transaction `count`/`findMany` is insufficient.

### 15.2 Proof matrix

| --- | --- |

| cost flow ACTIVE, any `DetailStock` **row** (qty 0 or not) | rejected (`COST_FLOW_QTY_ONLY_WRITER`) |

### 15.3 Sign of quantity

`DetailStock.quantity` is `Int @default(0)` with **no** CHECK. Do not reduce the P2 guard to `> 0`. Use `!= 0`.

Runtime decrements typically use `quantity: { gte: take }`, so writers try not to go negative; that is not a structural impossibility.

### 15.4 Candidate

**FAIL-CLOSED DISABLE** if any `DetailStock.quantity != 0`.

Allow delete when there is no stock row **or** every row is exactly 0 (HEAD may optionally also fail on any stock row, matching the ACTIVE behavior; that is stricter than physical-qty need). Minimum physical-ledger guard is `!= 0`.

`ProductDetail` guard stays.

ACTIVE path already fails on **row existence**. Do not weaken it.

### 15.5 Concurrency

`ProductDetail` count is outside the TX — TOCTOU vs a concurrent BOM attach (low likelihood; still not serialised).

`lockDetails` locks the **Detail** master, not `DetailStock`. PRISADKA also locks Detail first, so those two serialize. Inventory / other stock writers that lock pools without the Detail row can still race `deleteMany`.

Required future TX:

1. lock Detail (`lockDetails`);
2. lock all `DetailStock` rows for that `detailId` `ORDER BY id FOR UPDATE` (and treat newly created buckets via the Detail lock + unique `(detailId, flags)`);
3. re-count `ProductDetail` inside the TX;
4. fail if any locked stock `quantity != 0`;
5. then `deleteMany` + delete master.

The existing ACTIVE concurrency test (`deleteDetail vs active DetailStock writer`) proves the ACTIVE existence-guard can lose the race one way or the other atomically; INACTIVE positive-stock delete currently **wins** and destroys qty.
