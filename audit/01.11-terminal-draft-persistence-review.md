## 1. CURRENT TERMINAL SESSION BEHAVIOR

### 1.1 Две независимые сессии

Админская cookie `stell22_session` (7 дней) к терминалу **не относится**. `/terminal` — public path в `src/proxy.ts` (`PUBLIC_PATHS`). Терминал не требует admin JWT.

Терминальная cookie:

| Свойство | Факт | Где |
| --- | --- | --- |
| Имя | `stell22_terminal` | `src/lib/session.ts:51` |
| Payload | `{ employeeId, kind: "terminal" }` | `encryptTerminalSession` `:58-66` |
| Алгоритм | HS256, секрет `SESSION_SECRET` | тот же encodedKey |
| JWT `exp` | **12 часов** (`TERMINAL_MAX_AGE_SEC = 60 * 60 * 12`) | `:52`, `:64` |
| Cookie `maxAge` | 12 часов, **fixed** от момента `set` | `terminalCookieOptions` `:81-87` |
| httpOnly | да | `:82` |
| secure | только `NODE_ENV === "production"` | `:83` |
| sameSite | `lax` | `:84` |
| path | `/` | `:85` |
| Sliding refresh | **нет**. Активность не перевыпускает JWT | — |
| Server-side session store | **нет**. Stateless JWT | комментарий `:2-3` |

Создание cookie: `terminalLoginByPin` (`src/server/terminal.ts:322-324`) после успешного PIN.

Снятие cookie: `terminalLogout` (`:328-331`) — `cookies().delete(TERMINAL_COOKIE)`.

Гейт мутаций: `requireTerminalEmployee` (`src/server/session.ts:62-80`) читает cookie, проверяет JWT и `Employee.status === ACTIVE`, сверяет `expectedEmployeeId`. При отсутствии/протухании бросает «Нет активной сессии терминала. Войдите по PIN.» Это **не** редирект и **не** клиентский idle.

### 1.2 Что именно выбрасывает пользователя «примерно через минуту»

**Не JWT.** 12 часов — не минута.

**Не PIN lockout.** `pinLimiter` (`terminal.ts:262-266`): 10 неудачных PIN за 5 минут → блок **60 секунд**. Срабатывает только после перебора PIN, не во время заполнения операции.

**Да: клиентский idle-таймер.**

```19:19:src/components/terminal/terminal-app.tsx
const IDLE_MS = 30_000; // автовыход по бездействию
```

```82:97:src/components/terminal/terminal-app.tsx
  // Автовыход по бездействию: сбрасываем таймер на любую активность.
  const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
  useEffect(() => {
    if (!employee) return;
    const reset = () => {
      if (timerRef.current) clearTimeout(timerRef.current);
      timerRef.current = setTimeout(logout, IDLE_MS);
    };
    const events = ["pointerdown", "keydown", "pointermove"] as const;
    events.forEach((e) => window.addEventListener(e, reset, { passive: true }));
    reset();
    return () => {
      if (timerRef.current) clearTimeout(timerRef.current);
      events.forEach((e) => window.removeEventListener(e, reset));
    };
  }, [employee, logout]);
```

Это **sliding inactivity timeout на клиенте**: любые `pointerdown` / `keydown` / `pointermove` на `window` сбрасывают таймер на новые 30 с. Сервер об idle не знает.

История: константа появилась в `9a546ee` (2026-06-26, «Этап 3: Терминал на моках») вместе с формулировкой «автовыход по бездействию». С тех пор значение не менялось. Комментарий в `session.ts:48-50`: «Живёт короче — одна смена, автовыход по бездействию на клиенте» — JWT = смена (12 ч), lock = клиентский idle.

**Почему владелец ощущает «минуту»:** код = **30 с**. Ощущение «около минуты» согласуется с «отошёл проверить» + 30 с тишины, либо с грубой оценкой. В коде **нет** 60-секундного session timeout. Путать с PIN lockout (60 с после 10 ошибок) нельзя.

Классификация: **INTENTIONAL kiosk lock**, не bug JWT/`exp`. Агрессивность 30 с относительно заполнения торцовки (несколько модалок) — отдельный owner decision, не этот task.

### 1.3 Что делает `logout`

```50:57:src/components/terminal/terminal-app.tsx
  const logout = useCallback(() => {
    sessionGeneration.current += 1;
    setEmployee(null);
    setData(null);
    setLoading(false);
    setScreen("home");
    void terminalLogout(); // A14: снять серверную сессию терминала
  }, []);
```

Порядок:

1. Инкремент `sessionGeneration` — in-flight `getTerminalData` не вернёт сотрудника на экран.
2. `employee = null` → условный рендер показывает `LoginScreen`, **размонтирует** operation screen.
3. Cookie удаляется асинхронно.

Нет промежуточного PIN-lock с сохранённым деревом React. Lock **=** полный unmount.

Явный «Выйти» в шапке вызывает тот же `logout` (`terminal-header.tsx:44`).

### 1.4 Refresh / первый mount

`TerminalApp` стартует с `employee === null`. **Нет** гидрации из cookie. `/terminal` не читает `stell22_terminal` на сервере (`src/app/terminal/page.tsx` рендерит только `<TerminalApp />`).

Следствие: F5 при **живой** 12-часовой cookie всё равно показывает PIN. Повторный PIN перевыпускает JWT (`terminalLoginByPin` всегда `cookies().set`). React-стейт формы уже мёртв — это второй путь потери, независимый от idle.

## 3. clientRequestId LIFECYCLE

Генератор: `src/lib/request-id.ts` — `crypto.randomUUID()` либо fallback `Date.now()-random` (http LAN без secure context).

Паттерн на всех четырёх экранах одинаковый:

```text
const requestId = useRef(newRequestId());  // при mount компонента
// submit: clientRequestId: requestId.current
// catch: id НЕ меняется
// success CREATED: requestId.current = newRequestId(); onDone()
```

| Момент | Новый id? |
| --- | --- |
| Mount экрана | **Да** |
| Открытие QuantityDialog | Нет |
| Перед первым submit | Нет (берётся текущий ref) |
| Failed submit (валидация, сеть, 500) | **Нет** |
| TORCOVKA `ACK_REQUIRED` | **Нет** (тот же id в `pendingAck` и retry) |
| Успешный `CREATED` | **Да**, сразу после toast, до unmount через `onDone` |
| Logout / login | Экран размонтирован → при следующем заходе **новый** id |
| Reset form (смена lot/batch) | **Нет** (ref жив, пока экран смонтирован) |
| Back → home → снова тот же tile | **Да** (новый mount) |
| P2002 retry в том же mount | Тот же id → сервер считает success (A21) |

### 3.1 Может ли один физический незавершённый ввод после logout получить новый clientRequestId?

**YES.**

Это UX + idempotency design risk (не чинить DI-007/008 здесь).

Связь:

- **A21 / текущий UI:** id живёт в `useRef` одной попытки. Повтор в **том же mount** (двойной тап, сеть, ACK retry) — тот же ключ. Это работает.
- **После logout:** работник вводит те же рейки/количества с **новым** UUID. Сервер видит новую операцию. Если остатка хватает — вторая Op, вторая ЗП, второе списание. Это и есть сценарий, которого боится владелец («повторный ввод одной и той же физической работы»), усиленный DI-008 (разные id = разные ops).
- **DI-007:** если первый submit **успел закоммититься**, а клиент получил ошибку и затем logout — старый id потерян. Повтор с новым id не попадёт в P2002-success; для торцовки может упереться в «Недостаточно реек» или создать дубль, если рейки ещё есть.
- **Персистенция id вместе с draft:** повтор после login = тот же ключ = A21 срабатывает (для prisadka/upakovka/hours; для torcovka — насколько позволяет DI-007). Новый id **не** должен появляться «просто из-за повторного входа».

Не закрывает DI-007/008, но убирает главный клиентский источник новых id на том же физическом вводе.

## 4. STORAGE OPTIONS

В `src/` **нет** никакого Web Storage. Выбор с нуля.

| Survives reload | нет | да | да | да | да |
| Survives browser restart | нет | **нет** | **да** | да | да |
| Employee isolation | n/a (стейт умер) | key namespace | key namespace | key namespace | `employeeId` в БД |
| Complexity | 0 | низкая | низкая | высокая (async API, нет в проекте) | миграция + API + уборка |
| Migration | нет | нет | нет | нет | **нужна** |
| Server side effects | нет | нет | нет | нет | строки в БД до submit — прямо против owner intent |
| Serialization | n/a | JSON | JSON | structured clone | JSON/columns |
| Stale draft | n/a | ручная | ручная | ручная | TTL/jobs |
| Quota / private mode | n/a | ~5 MB, может throw | ~5 MB, может throw | больше | n/a |
| Секреты | в RAM | риск, если положить PIN | тот же | тот же | серверный риск |

**Рекомендация: C. localStorage.**

Почему хватает:

- Payload крошечный (ids + целые qty + один UUID + timestamps). ≪ 5 MB.
- Нет файлов, фото, бинарей.
- Owner: «если текущая архитектура позволяет безопасно» — terminal page already `"use client"`, origin = киоск-браузер.
- Restart браузера входит в owner intent (п.9). sessionStorage **не** переживает restart.
- IndexedDB не даёт нужного, чего нет у localStorage, ценой async API и отсутствия инфраструктуры.
- Server draft нарушает «не создавать ProductionOperation Draft rows без явной необходимости» и п.6 (никаких серверных эффектов до submit).

## 5. SECURITY / PRIVACY MODEL

### Нельзя хранить

| Данное | Сейчас | В draft |
| --- | --- | --- |
| PIN | `LoginScreen` `useState`, после submit очищается | **запрещено** |
| `stell22_terminal` JWT | httpOnly cookie, JS не читает | **запрещено** (и технически недоступно) |
| Admin `stell22_session` | другая cookie | не терминал |
| `SESSION_SECRET` / API keys | env / админка | не в терминальном payload |

### Можно хранить

| Поле | Оценка |
| --- | --- |
| `employeeId` | да; ключ изоляции, не секрет (ФИО и так на экране) |
| `operationType` | да |
| entity ids (batch/lot/detail/product) | да; операционные id |
| quantities, `railsTaken`, lengths | да |
| high-waste reason + note | да; цеховая причина, не credential |
| `clientRequestId` | да; нужен для A21 |
| `createdAt` / `updatedAt` | да |

`hourlyRate` **не** класть в draft: preview пересчитывается из `getTerminalData` после login.

### Чувствительное в текущем terminal payload?

`getTerminalData` отдаёт сотруднику каталог (партии, лоты, детали, изделия, остатки) и `currentEmployee` (id, ФИО, ставка). Форма операции **не** содержит PIN, JWT, admin secret, ключи маркетплейса.

**Вывод:** безопасный draft = ids + qty + request id + timestamps + (для TORCOVKA) reason/note. Секретов, которые не должны переживать logout, в форме **нет**.

Остаточный киоск-риск: localStorage origin-wide. Employee B с DevTools **может** прочитать ключ A. Код **не** должен автозагружать чужой draft. Для цехового киоска этого достаточно; не строить server-side confidentiality ради количеств реек.

Private/Safari: `setItem` может бросить — только `try/catch`, терминал не падает, draft просто не сохранится.

## 6. EMPLOYEE ISOLATION

Текущая структура: нет storage. Предлагаемый invariant:

```text
draft employee A никогда автоматически не загружается employee B
```

Рекомендуемый ключ (после проверки: префикса `stell22:` в Storage нет):

```text
stell22:terminal:draft:<employeeId>
```

Один JSON-объект на сотрудника (согласовано с §7: один активный draft). Не `stell22:terminal:drafts` map на всех — меньше шансов случайно прочитать чужое.

`employeeId` для ключа — **только** из сессии после PIN (`employee.id` из `getTerminalData` / `requireTerminalEmployee`), не из черновика «кого угодно». После parse: если `draft.employeeId !== session.employeeId` → игнорировать (защита от ручной порчи JSON).

Сценарий владельца:

1. A начал TORCOVKA → autosave в `stell22:terminal:draft:<idA>`.
2. Timeout → logout. Ключ A остаётся.
3. B вошёл → читается только `...:<idB>` → пусто → нет prompt.
4. B logout.
5. A вошёл → ключ A есть → prompt «Продолжить / Удалить».

B не видит содержимое A в UI.

## 7. ONE ACTIVE DRAFT OR MULTIPLE?

Текущий UX: одно поле `screen`, четыре плитки на home, операция занимает весь main. Параллельно два flow **нельзя** держать смонтированными. Back размонтирует.

**Рекомендация: ONE ACTIVE TERMINAL DRAFT PER EMPLOYEE.**

Не потому что «так правильнее вообще», а потому что UI уже однопоточный. Параллельные TORCOVKA+PRISADKA в localStorage расходятся с тем, как киоск используется, и усложняют resume prompt.

Поведение при живом draft другого типа (та же сессия, home, нажали другую плитку):

- Не стартовать второй draft молча.
- Показать тот же prompt: продолжить незавершённое **или** удалить, затем открыть новый flow.

HOURS входит в ту же модель: форма до submit есть (`HoursScreen.value`).

Owner decision по «один vs несколько» **не** требуется, если принимается рекомендация «как сейчас в UI».

## 8. DRAFT CONTENT

Не сохранять derived: `wastePct` / `takenM` / `producedM` / `canAssemble` / `hourlyRate` / плитки / `lengthTiles`. Пересчёт после `getTerminalData`.

Не сохранять: `submitting`, буфер открытого `QuantityDialog`, PIN, JWT.

### Common (`version: 1`)

```text
version: 1
employeeId: string
operationType: "TORCOVKA" | "PRISADKA" | "UPAKOVKA" | "HOURS"
clientRequestId: string
createdAt: string (ISO)
updatedAt: string (ISO)
payload: <per-type>
```

### TORCOVKA payload

| Поле | Зачем |
| --- | --- |
| `batchId: string \| null` | выбранная партия |
| `lotId: string \| null` | пакет |
| `railsTaken: number` | ввод реек |
| `picks: { lengthM, sort, quantity }[]` | заготовки; не `Record` с `"1.2\|SORT1"` |
| `activeSort: Sort` | какая вкладка была открыта |
| `ackUi.phase: "none" \| "suspicious" \| "extreme"` | был ли открыт ack-диалог |
| `ackUi.highWasteReason` | выбранная причина |
| `ackUi.highWasteNote` | текст «другое» |

Серверные `pendingAck.takenM/producedM/wastePct` не класть: при resume пересчитать `computeTorcovkaWasteMetrics`; если phase ≠ none и band всё ещё требует ack — снова показать диалог. Если band сменился (лот/каталог) — остаться на форме, reason сохранить.

### PRISADKA payload

```text
picks: { detailId: string; kind: "torcev" | "plosk"; quantity: number }[]
```

### UPAKOVKA payload

```text
picks: { productId: string; quantity: number }[]
```

Без packaging/extras как отдельных полей — в текущем UI их нет.

### HOURS payload

```text
hoursInput: string  // сырой keypad, не Number
```

### Когда писать

Пустой экран (ничего не выбрано / qty=0) — **не** создавать draft. Иначе каждый заход на торцовку даст prompt.

Meaningful:

- TORCOVKA: `batchId != null` или `railsTaken > 0` или есть pick
- PRISADKA / UPAKOVKA: есть qty > 0
- HOURS: число часов > 0

## 9. STALE REFERENCES

Между save и resume каталог живой. Draft **не** имеет права слепо submit.

Правило: UI восстанавливает ввод; **сервер** на финальном submit выполняет текущую validation. Ошибка не удаляет draft.

| Flow | Revalidate при resume | Если ссылка мертва |
| --- | --- | --- |
| TORCOVKA | партия `IN_WORK`; лот существует, `batchId` совпадает, `remainingQuantity > 0`; `railsTaken ≤ remaining`; длины есть в ACTIVE details этого `railType`; физика `producedM ≤ takenM` | Показать контролируемую ошибку на confirm bar / баннер. Поля **не** стирать. Confirm disabled, пока не исправит или не удалит draft. |
| PRISADKA | деталь ACTIVE; tile с таким kind ещё в `prisadkaPending`; qty ≤ pending | Orphan pick оставить в draft; если плитки нет — строка «деталь больше не ожидает присадку». Не auto-delete. |
| UPAKOVKA | изделие ACTIVE; `qty ≤ canAssemble` (живой BOM/сток) | Сохранить qty; если max=0 или меньше — ошибка, не submit. |
| HOURS | `hours > 0`; ставка только preview | почти не stale |

Не делать клиентский «умный» submit при resume. Не auto-submit. После Continue — тот же экран, пользователь жмёт «Подтвердить» снова.

ACK_REQUIRED при resume: локальный band; финальный ack всё равно серверный (`decideTorcovkaSubmit`).

## 10. DRAFT VERSIONING

`version: 1`.

Zod в проекте **нет** (`package.json` не содержит `zod` / valibot / arktype). Валидация — ручные type guards, как `src/lib/terminal-auth.ts` / `employee-pin.ts`.

**Нельзя** `JSON.parse` без проверки на critical path терминала.

`parseTerminalDraft(raw: unknown): ParseResult`:

| Вход | Поведение |
| --- | --- |
| не JSON / не object | `{ ok: false, reason: "malformed" }` — UI не падает |
| `version !== 1` | `{ ok: false, reason: "unsupported_version" }` |
| нет обязательных полей / неверный enum / qty не integer ≥ 0 | malformed |
| `employeeId` ≠ сессия | ignore (как будто нет draft) |
| ok | typed draft |

При malformed / unsupported: **не** Continue в слепой форме. Prompt: «Не удалось прочитать черновик» + **[Удалить]**. Автоматически не удалять (нет retention policy). Continue скрыт.

## 11. AUTOSAVE

Один модуль, не копипаста на три экрана.

| Файл | Роль |
| --- | --- |
| `src/lib/terminal-draft-storage.ts` | key, `read`/`write`/`clear`, parser, `isMeaningful`, try/catch Storage |
| `src/lib/terminal-draft-storage.test.ts` | unit, node vitest (как остальные `src/lib/*.test.ts`) |
| `src/components/terminal/use-terminal-draft.ts` | debounce, hydrate, `clientRequestId` ownership |
| `src/components/terminal/terminal-draft-resume-dialog.tsx` | prompt после PIN |

Правила записи:

- Debounce **300 ms** на непрерывный ввод (keypad hours, note, qty уже попавшее в parent).
- Immediate save на дискретные переходы: выбор партии/лота/детали/изделия, смена `ackUi.phase`, confirm QuantityDialog.
- Не писать каждый render.
- Не класть derived.
- `updatedAt = new Date().toISOString()` на каждой записи; `createdAt` и `clientRequestId` фиксируются при **первом** meaningful save.
- Нет сети.

`clientRequestId`: если storage пуст — `newRequestId()` один раз в hook и в первый write. Если hydrate ок — **взять id из draft**, не генерировать.

Clear: только success CREATED (включая P2002-as-success) или явный «Удалить черновик». Не на logout/unmount.

## 12. CLEAR CONDITIONS

| Событие | Clear? |
| --- | --- |
| A. Финальный submit, сервер подтвердил CREATED | **Да** |
| A2. Идемпотентный повтор того же `clientRequestId` → success | **Да** (это successful submit) |
| B. Явный «Удалить черновик» после confirm | **Да** |
| Logout / idle / session expiry | **Нет** |
| Refresh / remount / Back | **Нет** |
| Network error / 500 | **Нет** |
| Валидация / ACK_REQUIRED | **Нет** |
| P2002 handling на клиенте как ошибка (не должно; если toast error — не clear) | **Нет**, пока UI не получил success |
| Смена партии внутри TORCOVKA | **Нет** (тот же draft, payload обновлён; id тот же) |

Клиент clear **после** того, как `submit*` резолвится без throw и (для TORCOVKA) `status === "CREATED"`. Не optimistic clear до ответа.

## 13. RESUME UX

После успешного PIN и `getTerminalData`, если parse(draft) ок и `employeeId` совпал:

Модалка (терминальные кнопки, как QuantityDialog: `h-14 rounded-xl text-lg`):

**Есть незавершённая операция**

`Торцовка · начата 14:32` — тип + время из `createdAt` через `formatDateTime` (`src/lib/format.ts`, зона проекта).

Если возраст ≥ 24 ч — дополнительно возраст («начата вчера» / «N ч назад»). **Порог только для отображения.** Auto-delete нет.

Кнопки:

- **[Продолжить]** — `setScreen(operationType)`, экран гидрирует payload. Не submit.
- **[Удалить черновик]** — confirm (вторая короткая фраза: «Введённые данные будут потеряны») → `clear` → home.

Не подставлять draft B сотруднику A.

Malformed: текст ошибки + только Удалить.

Внутри той же сессии повторный вход в **тот же** flow (Continue или плитка): silent hydrate, без повторного prompt. Prompt — после PIN и при попытке открыть **другой** flow при живом draft.

## 14. SESSION TIMEOUT UX

30 с — **намеренный** kiosk lock, не баг. Менять в этом task **нельзя**.

Рекомендация отдельно:

- Оставить модель: бездействие → PIN. Draft persistence снимает боль потери данных **независимо** от длительности.
- Рассмотреть **5–10 минут** idle как отдельное решение владельца: 30 с мало для торцовки с несколькими модалками и «отойти проверить рейки».
- Не делать sliding JWT; 12 ч смены достаточно.
- Не убирать idle lock: киоск общий.

Если владелец оставит 30 с — draft всё равно обязателен (refresh и Back тоже убивают стейт).
