## 1. Executive summary

Stell22 does **not** store a frozen full SKU cost. `getCostReport` / `getUnitCostSnapshot` **recompute live** from current catalog + all-time wood WAC + period labor averages + period overhead cashflows.

What is factually sourced today:

- **Batch money C** = `Batch.totalCost` = `purchaseCost` + Deal-allocated confirmed delivery extras. Algebra `costSort1 + costSort2 = C` holds exactly on live `Decimal` for every batch that has TORCOVKA output.
- **Physical wood chain** (rails → blanks → details → products) is quantity-tracked. After TORCOVKA, **batch monetary provenance is dropped** on `BlankStock`.
- **Labor rates** on operations are DI-015 snapshots. Payroll unpaid earnings use those snapshots. Product-cost labor does **not** sum those earnings; it applies period-average unit rates to the **live BOM**.
- **HOURS** enter SKU cost only as a same-day surcharge on that employee’s piece units. Hours-only days never reach a product.
- **Fasteners / packaging / extras** use live `NomenclatureItem.unitPrice` × live BOM. Not purchase lots.
- **Overhead** = confirmed EXPENSE CashFlows whose article category has `isOverhead = true`, allocated by share of period direct × packed qty.

What is **not** “true historical SKU cost”:

- Wood ₽/m of a product packed in June moves when a later batch of the same species is cut (all-time WAC). Proven on `stell22_dev`: Липа TORCOVKA 2026-09-07 is inside the wood number of «Полка настенная».
- In-progress batches put **100% of C** onto the metres already cut. Липа 2218: `C = 116 500` on `12.16 m` → `9 580.59 ₽/m` vs ~`740 ₽/m` on Волочек. That spike is inside current SKU wood.
- Payroll production labor (Sept `4 511.00`) vs labor represented on packed SKUs (Sept `1 192.88`) does **not** close.
- `ProductCost` has **zero writers**, **zero rows**, and is not read by the report.

**True production cost today: PARTIALLY.** Batch wood conservation is trustworthy. A SKU number on the cost report is a live model cost, not a frozen fact trail from the unit that was packed.

| | |
| --- | --- |
| SOURCE | `RailLot` (`quantity`, `remainingQuantity`, `lengthM`, `sort`, `railType`) + `Batch.materialId` |

| PROVENANCE PRESERVED | Op has `batchId` + `railLotId`. Blank **stock row** does not. |
| PROVENANCE LOST | Batch/lot identity on the stock pool. |
| COST CARRIED FORWARD | **NO** (quantity only). |

| | |
| --- | --- |
| SOURCE | TORCOVKA lines (length, type, sort, materialId) |
| MUTATION | Upsert `BlankStock` unique `(materialId, lengthM, detailType, sort)` |
| QUANTITY PRESERVED | Blank pieces by spec. |
| PROVENANCE PRESERVED | Material species + geometry + sort. |
| PROVENANCE LOST | Batch, lot, purchase date, `totalCost`. |
| COST CARRIED FORWARD | **NO**. |

### BlankStock → PRISADKA → DetailStock

| | |
| --- | --- |
| SOURCE | `applyPrisadkaPick`: consume matching `BlankStock` (or partial `DetailStock`) for `Detail` of same material/length/type/sort. |
| MUTATION | Blank −qty or partial detail −qty; DetailStock +qty with prisadka flags. Line stores `sourceIsBlank` / `blank*` / `source*Done` for reversal. |

### DetailStock (or BlankStock if no prisadka) → UPAKOVKA → ProductStock

| | |
| --- | --- |
| SOURCE | Live product BOM snapshot at submit (`snapshotUpakovkaApply`). Ready details and/or blanks; fasteners/packaging from `NomenclatureStock`. |

```
Cash / Deal EXPENSE (confirmed)
  └─ syncBatchTotalCostInternal
       C = purchaseCost + Σ deal extra shares
            │
            ▼
     Batch.totalCost  ──────────── live distributeBatchCost ──► costSort1/2, ₽/m³
            │                       (if BatchCost FINAL exists: use FINAL, ignore live C)
            ▼
     TORCOVKA produced metres by sort  (all-time, not period)
            │
            ▼
     blendedCostPerMeterByMaterial  (Σ cost / Σ metres, same materialId + sort)
            │
            ▼
     Product wood = Σ (BOM detail.lengthM × qty × WAC ₽/m of that sort)
```

**Where physical and monetary provenance diverge:** at TORCOVKA → `BlankStock`. Physical pool is species+geometry. Money stays on the batch until the **report** re-reads all TORCOVKA lines and C (or FINAL).

`NomenclatureStock` has **quantity only**. No monetary layer. SimplePurchase.unitPrice is not used by the cost report.

## 5. Batch cost formula

### C

```
C = Batch.totalCost
```

`createBatch`: `totalCost = purchaseCost`.

`syncBatchTotalCostInternal` (`src/server/internal/finance-operations.ts`):

```
extra = Σ over deals containing this batch:
          dealDeliveryExtra(confirmed EXPENSE on deal, Σ purchaseCost of deal batches)
          then batchExtraShare(dealExtra, this.purchaseCost, purchaseTotal, nItems)
newTotal = purchaseCost + extra
updateMany where id AND frozenAt IS NULL
```

Frozen batches: skip (DI-001/P1 + freeze money lock). `updateBatch` forbids changing purchaseCost / sort prices / section / materialId when `frozenAt` is set (`frozenBatchCostInputsChanged`).

Writers that can change C (then `enqueueRecalcBatchCosts`): `createBatch` (init), `updateBatch`, finance Deal/CashFlow/account confirm/import paths, `statement-mail`. Recalc does **not** write `totalCost`; it writes PRELIMINARY `BatchCost` from current C + TORCOVKA.

`purchaseCost` is **not** the distribute input. Schema comment calling `purchaseCost` «истина стоимости партии» is **SPEC / DOC DRIFT**. Runtime C is `totalCost`.

stell22_dev: Волочек 2419 `purchaseCost=150000` + delivery `10500` = `totalCost=160500` (CashFlow «Доставка» 2026-06-03 = 10500).

### Distribute (`src/lib/cost.ts` `distributeBatchCost`)

```
area  = (widthMm/1000) × (heightMm/1000)
V1ф   = producedLengthSort1 × area
V2ф   = producedLengthSort2 × area
weighted1 = P1 × V1ф
weighted2 = P2 × V2ф
denom     = weighted1 + weighted2

if V1ф+V2ф = 0:
  all zeros   // C is not placed on output
else if denom = 0:          // P1=P2=0
  share1 = V1ф / (V1ф+V2ф)  // volume fallback
else:
  share1 = weighted1 / denom
share2    = 1 − share1
costSort1 = C × share1
costSort2 = C − costSort1     // exact: costSort1+costSort2 = C
pricePerM3Sort* = costSort* / V*ф   (0 if V*ф=0)
```

Produced lengths = TORCOVKA `Σ blankLengthM × quantity` by `blankSort` (`producedLinesFromOperations`).

## 6. Waste treatment

Two different objects:

### Physical waste (report «Процент отхода»)

`src/lib/waste.ts` + `getWasteReport`:

```
takenM     = Σ railsTaken × RailLot.lengthM     (TORCOVKA)
producedM  = Σ blankLengthM × qty
wasteTorc  = max(0, takenM − producedM)
writtenOff = max(0, purchasedM − remainingM − allTaken)
totalWaste = wasteTorc + writtenOff
waste%     = totalWaste / (taken+writtenOff)     (all-time)
             or wasteTorc / taken                 (period)
```

Shown on the waste report, **not** as a money line on the cost report.

stell22_dev (all-time):

| Batch | taken m | produced m | physical waste m |
| --- | --- | --- | --- |
| Волочек 2419 | 265.8000 | 233.8400 | 31.9600 |
| Сосна 3020 | 177.6000 | 155.6200 | 21.9800 |
| Липа 2218 | 18.2000 | 12.1600 | 6.0400 |

### Cost of waste

**No separate waste cost line.**

Because **entire C** is allocated onto produced metres, kerf (and, for a depleted/frozen batch, written-off remainder) **raises ₽/m³ and ₽/m** of the usable output.

Statement from JSDoc / cost-integrity, confirmed by formula:

> all `Batch.totalCost` is allocated onto actual produced output, therefore waste increases ₽/m³ / ₽/m of usable output.

**If C = 100 000 and 30% of wood becomes waste:** there is no `30 000` waste account. The `100 000` sits on the remaining 70% of **produced** metres. ₽/m³ ≈ purchase ₽/m³ / 0.70.

**In-progress extra effect (not the same as kerf):** remaining **uncut** rails also do not hold C. Липа: purchased `104 m`, remaining `85.8 m`, produced `12.16 m`, C `116 500` all on `12.16 m` → `pricePerM3 = 11 975 740.13` vs supplier `P1 = 20 500`. Kerf is ~33% of taken; the unit price is inflated far more because uncut stock is not in the denominator. Classification: **EXPECTED for a closed depleted batch**; **INVARIANT WEAKNESS** while `IN_WORK` (COST-001).

## 8. Product material WAC behavior

### Detail / blank (cost report «Детали» tab)

Tied to a **concrete Batch**. `blankMaterialCost(snapshot, length, sort)`. Tests: two batches of one species → `10` vs `20`, not blended `15`. Classification: **EXACT / TRACEABLE** to batch (live or FINAL). Period filter: **which blank rows** (period TORCOVKA). ₽/m³ from **all-time** production of that batch (A11).

### Product / `getUnitCostSnapshot` details

Tied to **material species + sort, all-time WAC** of batches that have TORCOVKA (or FINAL).

```
perM[materialId][sort] = Σ costSort / Σ lengthSort   over snapshots of that material
unit wood(detail) = perM[detail.materialId][detail.sort] × detail.lengthM
product wood = Σ unit wood × BOM qty
```

Not: global WAC across species. Not: period-only WAC. Not: FIFO.

### What is exact / averaged / when it changes

| | |
| --- | --- |
| EXACT | C, TORCOVKA metres, per-batch distribute, Details-tab blank cost |
| AVERAGED BY DESIGN | product wood ₽/m within species+sort |
| WHEN THE AVERAGE CHANGES | any new TORCOVKA (or qty edit) on any unfrozen batch of that species; freeze of a batch (FINAL replaces live); `totalCost`/prices change on unfrozen batches; adding a first cut on a previously idle batch |
| HISTORICAL PRODUCT COST CHANGES RETROACTIVELY | **YES** |

### Proof (not assumption)

`loadCostContext` builds `fullLines` from **all** TORCOVKA, then `snapshots`, then `blendedCostPerMeterByMaterial`. Period is **not** applied to wood.

Example from the brief:

- Batch A cheap, Batch B expensive, same species.
- Product packed when only A existed.
- After B is cut, `getCostReport` for that old month still uses A+B WAC.

stell22_dev numeric analogue: «Полка настенная» packed 90 pcs on 2026-06-29. Липа 2218 (same Хвоя) first TORCOVKA is 2026-09-07, `C=116500` on `12.16 m` (`9580.59 ₽/m`). All-time WAC sort1:

```
costSort1  = 320284.76439973   (Волочек 126441.64456233 + Сосна 77343.11983740 + Липа 116500)
lengthSort1 = 296.66
WAC ₽/m    = 1079.63582687
```

Without Липа: `(126441.64456233+77343.11983740) / 284.50 ≈ 716.29 ₽/m`.

June **and** September product wood for the wall shelf are **the same** `1 295.56` (2 × 0.6 × 1079.63582687). Reopening June after September cutting **does** change June wood. Classification: **EXPECTED / INTENTIONAL DESIGN** (cost-integrity WAC) plus **no period SKU freeze** (`ProductCost` unused). Finding COST-003.

`getUnitCostSnapshot` values **details** with the same blended WAC (not batch-true). Inventory of a catalog Detail is therefore averaged, unlike the Details tab of the cost report.

## 10. Labor / snapshot behavior

DI-015 **CLOSED IN PRODUCTION**. All 46 ops on stell22_dev have `rateSnapshotVersion = 1`. Current TORCOVKA snapshots match live Employee rates (no post-hoc rate edit in this DB).

### What the cost report uses

**B. Weighted-average historical rates from period operations**, then **BOM theoretical application**.

Not A (sum of operation earnings).  
Not C (average live Employee cards) on the production path.  
Not D (BOM × live card rates).

`actualProductionRates` (`src/lib/payroll.ts`):

1. Per employee-day: `HOURS` money = `hours × hourlyRateSnapshot` (JS number, `round2` per op).
2. Per employee-day: production units = TORCOVKA pcs + PRISADKA pcs + UPAKOVKA pcs.
3. `share = dailyHoursPay / dailyUnits` (0 if no units).
4. Each piece unit gets `pieceRateSnapshot + share`.
5. Period unit rate = `Σ (piece+share)×qty / Σ qty` per bucket (sort1/sort2/torcev/plosk/upakovka). Empty bucket → 0.

Then `detailWorkCost` = torcovka(sort) + optional prisadka flags from **live Detail**, plus `rates.upakovka` once per product.

### Sections

| Surface | Method |
| --- | --- |
| Cost report Products | B + live BOM |
| Cost report Details (blank work) | B, torcovka rate by blank sort only (no prisadka) |
| `getUnitCostSnapshot` detailUnit | B + live Detail |
| Payroll unpaid | A: `Σ operationEarning(snapshots)` |

## 13. Overhead treatment

```
periodOverhead = Σ CashFlow.amount
  where flowType=EXPENSE
    and article.category.isOverhead
    and account.confirmed
    and date in period (if period set)

periodTotalDirect = Σ_p (direct_unit(p) × packed_qty(p) in period)

overhead_unit(p) = direct_unit(p) × periodOverhead / periodTotalDirect
                   (0 if periodTotalDirect = 0)

full_unit(p) = direct_unit(p) + overhead_unit(p)
```

**What CashFlows enter:** confirmed EXPENSE, any article whose **current** category has `isOverhead`. Not income. Transfers excluded by being non-EXPENSE or not tagged. Unassigned CF (null article) **out**.

stell22_dev eligible overhead: **one** row, 2026-06-08 «Электроэнергия» `18 200`. September: `0`. Unassigned expenses 12400+3200 are **out**. «Доставка» is «Материалы» / not overhead (already in C). «ЗП производство» not overhead.

**Distribution base:** total **direct unit cost × packed qty in period** (not catalog, not produced blanks). All **ACTIVE** products get a unit overhead even if packed qty = 0; they take **zero mass** of the pool.

**Reconciliation (qty-weighted):**

```
June:  90×152.63 + 30×148.77 = 18199.80   vs  18200.00   Δ = 0.20
all:   94×147.83 + 30×143.46 = 18199.82   vs  18200.00   Δ = 0.18
Sept:  0 vs 0   Δ = 0
```

Δ is `toDecimalPlaces(2)` on the unit row × integer qty. **PARTIAL** (rounding). Unweighted sum of the overhead **column** (two product rows) is ~`301` in June — that is not supposed to equal period overhead.

Edge:

| Situation | Behavior |
| --- | --- |
| Product packed qty 0 in period | Still listed; unit overhead computed; contributes 0 to Σ |
| ProductStock from earlier months | Irrelevant; packed qty is UPAKOVKA in period |
| No production in period | `periodTotalDirect=0` → overhead_unit=0; period OH unallocated |
| Missing material (no WAC) | direct may still be labor+nom; participates if packed |
