## 1. Purpose / non-goals

### Purpose

Define the smallest architecture that lets Stell22 become the **primary operational source of truth** for warehouse and production quantity.

Today Stell22 already runs a real shop-floor chain and is deployed. Paper (and operator memory) still functions as a parallel insurance system because:

- current `*Stock` rows are mutated balances without an append-only physical movement history;
- posted `ProductionOperation` can still be physically deleted (except generic TORCOVKA delete, which is contained);
- consequential manual corrections do not always carry actor + reason + causal identity;
- there is no ledger-vs-projection reconciliation that can prove `OPENING_BALANCE + post-epoch movements = live stock`;
- ledger==projection still would not prove system==factory; physical-count coverage is incomplete (raw rails excluded from current Inventory; WIP keys not equivalent to DETAIL lines).

ARCH-2 is the contract for that foundation. It is a **forward-looking** architecture. Acceptance does not implement anything.

### Non-goals

This architecture contract does **not**:

- reopen AUDIT 1 or change its P0/P1/P2/P3 counts;
- start AUDIT 2 — FINANCE & MONEY INTEGRITY;
- activate `production_cost_flow`;
- apply cost-flow bootstrap;
- invent a second monetary journal;
- copy Woodveri;
- require PeriodClose before the first physical-ledger cutover;
- require arbitrary backdating for the first cutover;
- require a generic persistent `CommandExecution` table;
- rewrite Stell22 into microservices, Kafka, CQRS, or full event sourcing;
- implement any schema/code in this task.

## 6. Physical inventory ledger decision

**ACCEPTED.**

Before Stell22 is the only warehouse/production SoT, introduce an **append-only physical inventory movement register**.

Conceptual flow:

```text
business fact
  → physical movement(s)
  → current stock projection
```

A suitable name: `InventoryMovement`.

It represents **physical quantity history**, not generic business events and not an accounting GL.

Current tables **MUST NOT be deleted**:

- `BlankStock`
- `DetailStock`
- `NomenclatureStock`
- `ProductStock`

Target role of those tables: **current-balance projections / fast read models**.

Do **not** propose ledger-only runtime reads. Do **not** propose full event sourcing.

### 6.1 Movement kinds (illustrative, not a frozen enum dump)

| Kind | Typical cause |
| --- | --- |
| `PURCHASE_RECEIPT` | Batch/RailLot receive; SimplePurchase |
| `PRODUCTION_CONSUME` | TORCOVKA rails; PRISADKA blanks/WIP; UPAKOVKA details/nom |
| `PRODUCTION_OUTPUT` | TORCOVKA blanks; PRISADKA details; UPAKOVKA FG |
| `SHIPMENT` | Marketplace/supply FG deduct |
| `RETURN` | later, if a physical return path exists |
| `SCRAP` | explicit physical loss (not silent reverse) |
| `INVENTORY_ADJUSTMENT` | CONDUCTED inventory SET → signed delta vs accounted |
| `REVERSAL` | compensating movement that references original effects |
| `OPENING_BALANCE` | ledger epoch only; **do not fabricate pre-epoch history** |

Do **not** invent unit-level serial tracking.

### 6.2 Provenance grain (accepted)

- **Raw wood:** `RailLot`-level identity remains. `RailLot.remainingQuantity` / remaining value stay lot-identified, not a mixed WAC pool.
- **Downstream WIP/FG:** operation/movement-level provenance. Pooled `BlankStock` / `DetailStock` / `NomenclatureStock` / `ProductStock` stay fungible. No serial-per-part.

`InventoryMovement` may reference:

- stock kind + pool identity (blank spec / detail flags / nomenclatureId / productId / railLotId);
- causing document (`ProductionOperation.id`, `Inventory.id`, `SimplePurchase.id`, `Supply.id`, …);
- optional reversal pointer to the movement(s) being compensated.

Exact Prisma columns are PSR-P0 / PSR-P1 work. This contract accepts the **role**, not a frozen schema dump. Historical reference retention (`PSR-DESIGN-002`) must be defined before that schema is accepted.

`PSR-MUST-001` — Append-only physical movement register.

### 6.3 Ledger epoch protocol (ARCH2-R1, strengthened by ARCH2-R7)

**MANDATORY.** Dual-write **before** an epoch must not double-count (R1). The **final** epoch that can later become authoritative must not precede destructive-history elimination (R7).

#### A. SHADOW BEFORE EPOCH

`InventoryMovement` may be dual-written for diagnostics before the **final** authoritative-candidate epoch.

Those rows:

- are **pre-epoch shadow evidence only**;
- **MUST NOT** automatically participate in authoritative balance reconstruction;
- must be distinguishable from the post-epoch authoritative stream (`PSR-Q-007`).

A rehearsal / test epoch, if ever created during implementation, is **NON-AUTHORITATIVE and disposable**. It must not become the retained authoritative epoch.

#### B. FINAL EPOCH CUT

`PSR-MUST-003` refers to this **FINAL authoritative-candidate epoch**, not a shadow/test epoch.

**Precondition (ARCH2-R7 / PSR-MUST-005):** posted physical production facts already have history-preserving correction/cancellation, **or** every destructive posted-fact mutation path is disabled. Generic TORCOVKA-delete containment stays throughout.

Then:

1. prevent concurrent physical stock mutations using a bounded write barrier / maintenance gate / equivalent transaction-safe cutover mechanism (`PSR-Q-006` before this cut);
2. capture **one consistent snapshot** of every authoritative physical projection (`RailLot.remainingQuantity`, `BlankStock`, `DetailStock` including WIP keys, `NomenclatureStock`, `ProductStock`);
3. create `OPENING_BALANCE` movements representing **that snapshot only**;
4. persist an **immutable ledger epoch** identity / time / sequence;
5. ensure no mutation can fall ambiguously across the epoch boundary.

Do **not** fabricate movements for pre-epoch shop history. Opening = current qty at the cut, not reconstructed past.

Do **not** allow “block destructive paths only at authoritative cutover” if the **retained** epoch predates that block. No authoritative post-epoch interval may contain destructively erased business facts.

Exact barrier/epoch storage is an implementation design (`PSR-Q-006`). The semantics above are not.

#### C. POST-EPOCH

Authoritative reconstruction is:

```text
OPENING_BALANCE at the FINAL epoch
  + movements belonging to the post-epoch authoritative stream
  = current projection quantity
```

Pre-epoch shadow rows are **excluded** from this equation.

`PSR-MUST-003` — **FINAL** authoritative-candidate ledger epoch: write barrier + consistent snapshot + `OPENING_BALANCE` + immutable epoch identity. Established only after destructive posted-fact paths are gone/blocked. Pre-epoch shadow and any disposable rehearsal epoch are not this opening and are not the post-epoch stream. Do not fabricate historical movements.

## 7. Projection model

**ACCEPTED.**

Target invariant **after epoch**:

```text
OPENING_BALANCE at epoch
  + movements belonging to the post-epoch authoritative stream
  = current projection quantity
```

Pre-epoch shadow dual-writes are **not** in this sum.

Rules:

- Movement append and projection mutation **must be atomic in one DB transaction**.
- Runtime reads continue to use `*Stock` (and `RailLot.remainingQuantity` for lots). **No ledger-only reads.**
- A reconciliation job/query must reconstruct quantities from **epoch opening + post-epoch authoritative movements** and compare them to live projections (`PSR-MUST-004`). That proves ledger == projection. It does **not** prove system == factory (`PSR-MUST-008`).
- Drift is an integrity failure, not a UI inconvenience.
- Never silently edit a projection to match ledger or reality. Adjustments are explicit movements.

`PSR-MUST-002` — Current `*Stock` tables become explicit projections with atomic movement+projection writes.

`PSR-MUST-004` — Automated **ledger-vs-projection** reconciliation (internal consistency only).

`RailLot.remainingQuantity` is an identified-lot balance, not a fungible `*Stock` row. After cutover it obeys the same reconstructability rule (epoch opening remaining + post-epoch lot movements = live remaining). It is in scope for the gateway and both reconciliation kinds.

## 9. Correction / cancellation / reversal semantics

**TARGET SUPERSEDED for posted production hard delete. Runtime unchanged in this documentation pass.**

Do **not** change current delete/correct code in this task.

**Ordering invariant (`ARCH2-R2` + `ARCH2-R7`):**

```text
history-preserving posted facts
  BEFORE final authoritative-candidate epoch
  BEFORE authoritative cutover
```

Destructive posted-operation mutation must be gone or blocked **before the FINAL epoch**, not merely at cutover. Do not retain an epoch that predates that block.

Generic TORCOVKA-delete containment remains intact throughout.

### 9.1 Posted-fact immutability

Target invariant:

A posted physical fact must remain **historically reconstructable** after correction.

It is acceptable for a current normalized representation to exist, but **original posted values/effects must survive in immutable history**.

A correction **must not** rely only on `ChangeLog` JSON after overwriting or deleting the source fact.

| Mode | Target semantics |
| --- | --- |
| Correction | Original posted fact remains reconstructable in immutable history. Current representation may show net result. Effects are explicit deltas, not silent overwrite of the only copy. |
| Cancellation | A **new causal action** with compensating physical movements and a retained reference to the original fact. The original remains identifiable as cancelled. |
| Reversal | Explicitly references original effects (movements and/or stored component snapshots). |

Posted `ProductionOperation` is **not physically destroyed** in the target model.

### 9.2 What stays from current runtime until the target exists

- Generic TORCOVKA-delete containment (`TORCOVKA_GENERIC_DELETE_BLOCKED`). Do not remove it.
- `isPaid` blocks edit/delete.
- Inactive inventory-boundary + gte guards.
- Active `costVersion` exact-or-block (when the gate is on).
- `correctTorcovkaRailsTaken` as the path for over-entered rails that were never taken — distinct from cancelling a physical cut.

Current unpaid PRISADKA / UPAKOVKA / HOURS **hard delete** remains a **FINAL-epoch blocker** until PSR-P5.

### 9.3 INC-001 relationship

INC-001 showed why hard delete of a posted TORCOVKA is not a safe “undo”: rails are not restored, the op row disappears, and reconstruction depends on `ChangeLog`. Containment is deployed. A proper `cancelErroneousTorcovka` is **not** implemented.

ARCH-2 does **not** close INC-001 and does **not** implement Scenario A/B. It records that the **target** cancellation model is the replacement for both generic delete and the missing cancel path.

`PSR-MUST-005` — Before the **final** ledger epoch, posted physical production facts must already have history-preserving correction/cancellation semantics, or all destructive posted-fact mutation paths must be disabled. No authoritative post-epoch interval may contain destructively erased business facts. Cancellation is a new causal action; original posted facts remain reconstructable.

- correlation/causation identity where a retry or compensating action must point at the original;
- release/deploy trace where practical;
- **atomic audit with the mutation** (same DB transaction).

Current gap (readiness, not a new AUDIT 1 P1): `writeChangeLog` supports `userId`, but most production/warehouse/payroll/terminal writers omit it. Settings writes include `admin.id`. That is insufficient for primary-system corrections.

**Implementation choice left open (`PSR-DESIGN-001`):**

- a generic persistent `CommandExecution` table, **or**
- a narrower mutation/audit context attached to existing domain documents + `ChangeLog` / movement rows.

Do **not** prematurely create a universal command bus.

`PSR-MUST-006` — Consequential manual corrections carry actor + reason + causal identity + atomic audit.

### 11.1 Movement idempotency invariant

Every movement-producing business effect must be **idempotently identifiable**.

A retry/replay of the **same** business effect must **not** append a second physical movement or mutate the projection twice.

This applies to terminal submit **and** to correction, cancellation, inventory adjustment, receipt, shipment/restoration, write-off, and any future movement-producing path.

`ProductionOperation.clientRequestId` remains a useful domain identity for terminal submit. It is **not** a universal solution.

Exact uniqueness / source-effect identity = `PSR-Q-002`, closed in PSR-P0. Do **not** introduce a universal command bus solely for this.

### 11.2 Historical reference retention (`PSR-DESIGN-002`, ARCH2-R5)

Before `InventoryMovement` schema is accepted, define how movement history stays interpretable when referenced domain entities would otherwise be deleted.

For identities referenced by authoritative movements / causality, default target is **one of**:

- **A.** archive + FK/restrict physical deletion after first historical use; or
- **B.** immutable identifying snapshot stored on the movement where reference deletion must remain possible.

Do **not** silently allow an append-only movement to point at an identity that can disappear with no historical representation.

Applies conceptually to relevant: `ProductionOperation`, `Product`, `Detail`, `Material`, `NomenclatureItem`, `RailLot` / source documents.

Do **not** freeze a Prisma schema in this architecture contract.

`PSR-DESIGN-002` — Historical reference retention (A or B). Implementation choice open (`PSR-Q-008`). Closed in PSR-P0 **before** PSR-P1.

## 16. Migration strategy

**No big bang. Do not implement in this task.**

Mandatory ordering:

```text
history-preserving posted facts
  BEFORE final authoritative-candidate epoch
  BEFORE authoritative cutover
```

**NO FINAL epoch before:**

- destructive posted-operation mutation is gone or blocked;
- every writer is covered or disabled (or will dual-write through the gateway in shadow until then);
- physical reconciliation capability exists.

**NO authoritative cutover before:**

- the **final** epoch is safe (no shadow double-count; epoch after destructive-path elimination);
- ledger↔projection reconciliation is green on the post-epoch stream;
- soak with zero unexplained drift.

Preferred sequence:

```text
SHADOW schema
  → dual-write / diagnostic validation
  → physical reconciliation capability
  → history-preserving correction/cancellation
  → disable every destructive posted-operation mutation
  → FINAL epoch/barrier + OPENING_BALANCE
  → reconciliation/soak
  → authoritative cutover
```

Any earlier test/rehearsal epoch is **NON-AUTHORITATIVE and disposable**.

Do **not** dual-write into an equation that later adds `OPENING_BALANCE` on top of those same shadow rows.

`PSR-MUST-003` — §6.3 **FINAL** epoch only. Shadow before that epoch is diagnostics only.

Shadow/dual-write is compatible with current inactive runtime. Cost-flow stays inactive.
