# Устав аудита Stell22

Владелец: **2026-09-04**. Действует для всех последующих этапов аудита и для remediation, которая из аудита следует.

Проект развивался итеративно. Часть решений намеренно изменилась по ходу разработки и **может отличаться** от первоначального ТЗ (`Описание проекта v2.txt`), `roadmap.md`, старых планов и ранних файлов в `audit/`.

## Цель аудита

Проверить, что **текущая фактически выбранная модель** работает непротиворечиво и не портит деньги, склад, производство, зарплату и себестоимость.

Не цель: вернуть Stell22 к первоначальному ТЗ.

## Приоритет источников истины

1. Текущие явные решения владельца (сообщение в чате, этот устав, поздние пометки в `audit/`).
2. Подтверждённое намеренное текущее поведение (JSDoc, комментарий в коде рядом с веткой, smoke/тест, который **утверждает** поведение, согласованный audit-документ после этой даты).
3. Фактические инварианты текущего кода и БД (`src/**`, `prisma/schema.prisma`, migrations).
4. Старые ТЗ / планы / ранние audit docs / `roadmap.md`.
5. Generic best practices.

При конфликте документа и работающего кода **не исправлять код только потому, что документ говорит иначе**. Сначала обновить понимание правила или пометить документ как drift.

## Запрещено

- Считать расхождение с первоначальным заданием багом само по себе.
- Автоматически возвращать код к старому ТЗ / старому plan / v2.
- Использовать старый spec как абсолютный source of truth.
- «Чинить» работающую логику ради соответствия устаревшей документации.

## Классификация расхождения с ТЗ / старым аудитом

Сначала:

```text
SPEC DRIFT — POSSIBLY INTENTIONAL
```

Проверить:

- есть ли комментарий / JSDoc / commit / audit evidence, что так задумано;
- согласовано ли это с другими частями **текущей** системы;
- приводит ли различие к неправильным данным;
- нарушает ли оно **текущий** бизнес-инвариант (код+БД+решение владельца), а не формулировку v2;
- требуется ли решение владельца.

Только если доказано нарушение **текущего** инварианта:

```text
CONFIRMED BUG
```

Если намерение неясно:

```text
NEEDS BUSINESS DECISION
```

Ничего не исправлять, пока владелец не выбрал правило.

## Как ссылаться на v2 и roadmap

Их можно цитировать как **исторический контекст** или как гипотезу инварианта. Нельзя закрывать finding статусом BUG только цитатой из v2.

Пример уже разобранный: удаление TORCOVKA не возвращает рейки — не баг из-за «в ТЗ иначе», а **текущее** правило (JSDoc + v2 в этом месте совпали + smoke). Если бы v2 требовал возврат, а код и JSDoc нет — это был бы SPEC DRIFT / NEEDS BUSINESS DECISION, не автофикс.
