## 1. Retained models

Three narrow tables. No `CommandExecution`. No Prisma relations. No FK. Must survive later Batch / SimplePurchase deletion.

### BatchCreationCommand

`requestId` UNIQUE. `batchId` UNIQUE. `adminUserId`. `requestSnapshot` JSON. `recordedAt TIMESTAMPTZ(3)`.

### BatchRemainderWriteOff

`requestId` UNIQUE. `batchId` **not** unique — one Batch may have multiple legitimate write-off lifecycles. `totalQuantity > 0`. `effectSnapshot` JSON. `@@index([batchId, recordedAt])`.

### SimplePurchaseCreationCommand

`requestId` UNIQUE. `simplePurchaseId` UNIQUE. `adminUserId`. `requestSnapshot` JSON. `recordedAt TIMESTAMPTZ(3)`.

Tables start empty. No backfill from Batch names, ChangeLog, historical SimplePurchase, timestamps, or RailLot state.

## 2. Advisory lock

`PURCHASE_COMMAND_REQUEST_LOCK_NAMESPACE = 8326`.

Distinct from SHADOW `(8322, 1)` and R-05 `8325`.

Keys:

```text
batch-create:<requestId>
batch-writeoff:<requestId>
simple-purchase:<requestId>
```

`pg_advisory_xact_lock(8326, hashtext(key))`. Never recover a P2002 by querying inside an already-aborted transaction.

Stable mismatch: `PURCHASE_REQUEST_ID_REUSE`.

Missing retained target on replay: `PURCHASE_REPLAY_TARGET_MISSING`. Do not recreate the old row.

## 3. Authenticated admin

All three Server Actions capture `requireAdmin()` outside the physical transaction and retain `admin.id`. No inferred User. No SYSTEM actor. This package emits no InventoryMovement actor.

## 4. Snapshots

Batch create v1: `{ v:1, d:"BATCH_CREATE", name, materialId, purchaseDateInput, purchaseCost, priceSort1, priceSort2, note, rails[{mode,lengthM,railType,sort,quantity,rows,layers}] }`.

Name trimmed. Client `sectionWidthMm/sectionHeightMm` excluded. Submitted date including null retained. Money = exact 2-decimal string. `lengthM` = 4-decimal string. Note trimmed or null. rows/layers null when absent. Rail order command-significant. Generated package code and Material display name excluded.

Simple purchase v1: `{ v:1, d:"SIMPLE_PURCHASE_CREATE", nomenclatureId, quantity, unitPrice, purchaseDateInput }`. Positive integer quantity. unitPrice exact 2-decimal string. No Nomenclature name.

Write-off v1 from locked positive RailLots, sorted by `railLotId`: `{ v:1, d:"BATCH_REMAINDER_WRITEOFF", batchId, effects[{railLotId,quantityBefore,quantityDelta}] }` where `quantityDelta = -quantityBefore` and `totalQuantity = Σ quantityBefore`. This is retained physical evidence, not InventoryMovement.

## 5. Replay

`createBatch` / `createSimplePurchase`: lookup after request lock and before mutable DB validation. Same admin + same canonical snapshot → replay success, no physical mutation, no second ChangeLog. Mismatch → `PURCHASE_REQUEST_ID_REUSE` before mutation.

`writeOffBatchRemainder`: lookup after request lock. Same `batchId` + admin → replay success without inspecting current stock and without mutation. New requestId while remainder is already zero → existing already-zero error, no command row. After a later legitimate reopen, retry A is still silent; request B may write a second lifecycle.

## 6. ChangeLog atomicity

Primary creation ChangeLog for `createBatch` and `createSimplePurchase` is inside the same transaction as the physical projection and retained command. `writeOffBatchRemainder` continues to log in TX and now includes command/request identity. ChangeLog is never retry identity.

## 7. UI requestId

Purchases UI owns pending requestIds in synchronous refs / identity owners, not React state.

`createPurchaseRequestIdentityOwner` / `createKeyedPurchaseRequestIdentityOwner` assign the minted id to the owner **before** `startTransition` / async Server Action. Same-render duplicate submit of the same logical command reuses that id.

Cleared after definitive success, dialog abandon/`openCreate` new lifecycle, and `PURCHASE_REQUEST_ID_REUSE` rotation. Transient/network errors retain the id if payload is unchanged. Payload change rebinds via `commandKey`. Batch editing is out of scope.
