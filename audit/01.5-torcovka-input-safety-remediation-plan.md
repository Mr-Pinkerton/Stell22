# TORCOVKA Input Safety Remediation Plan (DI-020)

> **For agentic workers:** do not implement until the owner says implement. When implementing: `superpowers:subagent-driven-development` or `executing-plans`. Evidence: `audit/01.4-torcovka-input-safety-review.md`, `audit/01-data-integrity-findings.md` (DI-020). This file is the spec.

**Goal:** Terminal TORCOVKA cannot silently accept implausible aggregate waste; admin can decrease `railsTaken` and return rails to `RailLot` without touching blanks, payroll, or FINAL.

**Architecture:** Aggregate waste only (`railsTaken × lengthM` vs Σ blank lengths). Server is authority for `wastePct` and bands. `submitTorcovka` returns `CREATED | ACK_REQUIRED` (no thrown ack). Retry echoes canonical Decimal strings; server recomputes and compares canonically. Submit-time ack fields are history, not live classification. Correction is a new admin action (not delete). Lock order matches today’s RailLot-before-Batch writers so correction cannot deadlock with submit/write-off.

**Tech Stack:** Prisma 6.19.3, PostgreSQL 17, Next.js server actions, Vitest + integrity harness (`INTEGRITY_TEST_DATABASE_URL`, two `PrismaClient`s). Isolation stays READ COMMITTED.

**HEAD this plan assumes:** `cc571f5075b873b3f0ded733eedc438792562b40`

## Global Constraints

- Do not implement until the owner says implement.
- **Waste model:** aggregate per TORCOVKA operation. **No** per-rail bin-packing / cutting optimizer. **DI-021 не открывать.**
- Minimum physics (already INV-008, keep): each pick `lengthM ≤ RailLot.lengthM`; `producedM ≤ railsTaken × lengthM`.
- Ordinary `deleteProductionOperation` TORCOVKA **does not change**: rails are not returned (INV-047).
- BlankStock / OperationDetailLine / Payment / `isPaid` are **not** mutated by rails correction.
- Frozen batch: correction **rejected**; no implicit unfreeze / FINAL rewrite (01.2 BD-2).
- Thresholds are **temporary business policy**, not a statistically proven shop norm (prod N_healthy=2).
- `enqueueRecalcBatchCosts` / `revalidatePath` stay **after commit**. `src/server/internal/*` must not import `next/cache`.
- Money/length: `Decimal` (`src/lib/cost.ts` `D()`, precision 40, ROUND_HALF_UP). Length columns are `Decimal(12, 4)`. Ack metrics are **canonical strings**, not JS floats.
- Do not rotate secrets. Do not migrate deploy without owner.

### Locked business decisions (owner, 2026-09-04)

| ID | Decision |
| --- | --- |
| Waste | Aggregate: `takenM = railsTaken × lot.lengthM`, `producedM = Σ blankLengthM×qty` |
| NORMAL | `wastePct < 20` → ordinary confirm |
| SUSPICIOUS | `20 ≤ wastePct < 50` → strong warning + second explicit confirm |
| EXTREME | `wastePct ≥ 50` → ordinary submit forbidden; only «Высокий отход / брак» + required reason |
| High-waste reasons | кривизна, трещины, сучки, дефект материала, подбор цвета/текстуры, неверный размер, другое |
| Correction | Admin, decrease only; return `remainingQuantity`; no BlankStock/lines/payroll |
| Paid | Rails-only correction **allowed** if batch not frozen; Payment unchanged |
| Frozen | Correction forbidden |
| Reopen | If `frozenAt == null` and after correction batch remaining > 0: `IN_WORK`, `closedAt = null` (depletion **and** write-off). Rails correction asserts physical rails exist. Do not read ChangeLog for close reason. |
| Delete | Unchanged: TORCOVKA delete does not return rails |

## 3. SERVER GUARD (`submitTorcovka`)

Server recomputes:

```text
takenM     = railsTaken × lot.lengthM
producedM  = sumDetailLengthM(picks)
wasteM     = wasteLengthM(takenM, producedM)
wastePct   = wastePercent(wasteM, takenM)   // Decimal, 0 if takenM=0
band       = bandFromWastePct(wastePct)
```

Keep existing checks (`railsTaken > 0`, picks, lot belongs to batch, INV-008, remaining gte). Add `every pick.lengthM ≤ lot.lengthM` (uniform rail length; **not** packing).

Return type (not `void`):

```ts
type SubmitTorcovkaResult =
  | { status: "CREATED" }
  | {
      status: "ACK_REQUIRED";
      band: "SUSPICIOUS" | "EXTREME";
      railsTaken: number; // int
      takenM: string;     // canonical 4dp
      producedM: string;  // canonical 4dp
      wastePct: string;   // canonical 2dp
    };
```

`ACK_REQUIRED` is returned **before any mutation** (no remaining decrement, no Op, no BlankStock, no ChangeLog). Locks/reads for the check are allowed; TX must roll back / not write.

Real validation/business failures stay **exceptions** (no employee, bad lot, INV-008, insufficient rails, empty picks, malformed ack on a retry, ack kind/band mismatch, HIGH-WASTE without reason).

Then (only after metrics computed, still pre-mutation):

| Band | Required input | Result |
| --- | --- | --- |
| NORMAL | `plausibilityAck` **absent** | mutate → `{ status: "CREATED" }`. If ack present → **throw** (stale/wrong) |
| SUSPICIOUS, no ack | — | `{ status: "ACK_REQUIRED", band: "SUSPICIOUS", …canonical strings }` |
| SUSPICIOUS + ack | `kind === "SUSPICIOUS"` and canonical echo matches recomputed strings | mutate → `CREATED` |
| EXTREME, no ack | — | `{ status: "ACK_REQUIRED", band: "EXTREME", … }` |
| EXTREME + ack | `kind === "HIGH_WASTE"` + reason in enum + echo matches; OTHER → nonempty note | mutate → `CREATED` |
| EXTREME + SUSPICIOUS ack | — | **throw** (wrong kind; not a second ACK_REQUIRED) |

Persist **only on successful CREATED**, submit-time only (§6):

- NORMAL: submit fields null
- SUSPICIOUS: `torcovkaSubmitAckBand = SUSPICIOUS`, reason/note null
- HIGH-WASTE: `torcovkaSubmitAckBand = HIGH_WASTE`, `torcovkaSubmitWasteReason`, `torcovkaSubmitWasteNote`

Auth still `requireTerminalEmployee`. Recalc/revalidate after commit unchanged (`CREATED` only).

## 4. Second-confirm token / server contract

**No cryptography, no nonce table, no session secret. No thrown typed error as the happy-path second step.**

Boolean `confirmed=true` is **not** a field. Direct action callers cannot “just confirm” without echoing **canonical strings** from `ACK_REQUIRED`.

### 4.1 Precision (actual schema)

| Quantity | Source | DB / engine | Canonical ack string |
| --- | --- | --- | --- |
| `railsTaken` | input int | `Int` | integer (JSON number is fine; compare `===` as int) |
| `RailLot.lengthM` | DB | `Decimal(12, 4)` | — |
| `blankLengthM` | lines | `Decimal(12, 4)` | — |
| `takenM` | `railsTaken × lengthM` via `D()` | Decimal.js precision 40, ROUND_HALF_UP | **`D(takenM).toFixed(4)`** |
| `producedM` | `Σ blankLengthM × qty` via `D()` | same | **`D(producedM).toFixed(4)`** |
| `wastePct` | `wastePercent(wasteM, takenM)` | same; tests already use `toFixed(2)` | **`D(wastePct).toFixed(2)`** |

Do **not** put `takenM` / `producedM` / `wastePct` on the wire as JS `number`. No epsilon. Equality is canonical string `===` after the server recomputes `toFixed` from Decimal (or `D(ack.takenM).eq(D(canonTakenM))` **after** parsing the canonical string — never `Math.abs(float - float)`).

### 4.2 Types

```ts
type PlausibilityAckKind = "SUSPICIOUS" | "HIGH_WASTE";

type TorcovkaWasteReason =
  | "CURVATURE"      // кривизна
  | "CRACKS"         // трещины
  | "KNOTS"          // сучки
  | "MATERIAL_DEFECT"
  | "COLOR_TEXTURE"
  | "WRONG_SIZE"
  | "OTHER";

interface TorcovkaPlausibilityAck {
  kind: PlausibilityAckKind;
  railsTaken: number;       // int, same as input
  takenM: string;           // echo ACK_REQUIRED.takenM
  producedM: string;        // echo ACK_REQUIRED.producedM
  wastePct: string;         // echo ACK_REQUIRED.wastePct
  reason?: TorcovkaWasteReason;     // required if HIGH_WASTE
  reasonNote?: string;              // required if OTHER
}
```

### 4.3 Protocol

1. First `submitTorcovka` without ack.
2. NORMAL → mutate → `{ status: "CREATED" }`.
3. SUSPICIOUS/EXTREME → **return** `{ status: "ACK_REQUIRED", band, railsTaken, takenM, producedM, wastePct }` with **no writes**.
4. UI dialog copies those strings (and integer `railsTaken`) verbatim.
5. Retry **same** picks/`railsTaken` with `plausibilityAck` echoing them + `kind`.
6. Server **recomputes** Decimal metrics from current input+lot, formats canonical strings again, accepts only if:

```text
ack.railsTaken === input.railsTaken
ack.takenM === canonTakenM          // both toFixed(4)
ack.producedM === canonProducedM    // both toFixed(4)
ack.wastePct === canonWastePct      // both toFixed(2)
ack.kind matches band
  (EXTREME requires HIGH_WASTE, not SUSPICIOUS)
```

If picks/`railsTaken` changed since `ACK_REQUIRED`, strings mismatch → **throw** (must start over). Wrong `kind` on retry → **throw**.

A script that copies `ACK_REQUIRED` into a retry can still create the Op — that **is** an explicit confirm of those metrics. Accidental `confirmed: true` does not exist.

Client: branch on `result.status === "ACK_REQUIRED"`; do not treat exceptions as ack.

## 6. HIGH-WASTE / SUBMIT-TIME STORAGE

These columns are **submit-time acknowledgement/history**, not the live waste classification after admin correction.

```text
submit fields   = исторический факт подтверждения работником (write-once at submitTorcovka)
current waste   = derived: current railsTaken × lot.lengthM vs current OperationDetailLine[]
correction history = ChangeLog (oldRailsTaken / newRailsTaken / deltaReturned / reason)
```

`correctTorcovkaRailsTaken` **must not** update these columns. A stored `KNOTS` after rails correction is **not** “current cause of waste”; it is what the worker acknowledged at original submit. Live `%` is always recomputed from current fact.

ChangeLog is **not** SoT for the original high-waste reason.

Prisma:

```prisma
enum TorcovkaAckBand {

  HIGH_WASTE
}

enum TorcovkaWasteReason {
  CURVATURE
  CRACKS
  KNOTS
  MATERIAL_DEFECT
  COLOR_TEXTURE
  WRONG_SIZE
  OTHER
}

  // existing fields…
  torcovkaSubmitAckBand      TorcovkaAckBand?
  torcovkaSubmitWasteReason  TorcovkaWasteReason?

```

All nullable. Old rows stay null. CHECK in app: HIGH_WASTE ⇒ reason set; OTHER ⇒ note trim nonempty; SUSPICIOUS ⇒ reason null.

Correction reason is **not** this enum. It lives in ChangeLog `newValues.reason` (mandatory string). Optional: do not add a second column unless UI must show last correction on the row (not required for v1).

## 7. CORRECTION RULES

New `correctTorcovkaRailsTaken` in `src/server/production.ts`, `requireAdmin()`.

Input: `{ operationId, newRailsTaken: int, reason: string }` (`reason.trim()` nonempty).

Preconditions after locks + reread:

- Op exists, `type === TORCOVKA`, `railLotId` and `batchId` set, `railsTaken` set
- `newRailsTaken < oldRailsTaken` (decrease only)
- `newRailsTaken > 0`
- `producedM ≤ newRailsTaken × lot.lengthM` (INV-008 on the **new** taken length)
- `batch.frozenAt == null` → else throw, no writes
- `isPaid` **does not** block

TX writes:

```text
delta = oldRailsTaken - newRailsTaken
RailLot.remainingQuantity += delta
ProductionOperation.railsTaken = newRailsTaken
torcovkaSubmitAckBand / Reason / Note: **no**
BlankStock: no
lines: no
isPaid / Payment / PaymentBatchItem: no
```

ChangeLog on the Op:

```json
{
  "field": "railsTaken",
  "oldRailsTaken": 1280,
  "newRailsTaken": 4,
  "deltaReturned": 1276,
  "reason": "<admin text>"
}
```

After commit: `enqueueRecalcBatchCosts(batchId)`; `revalidatePath` `/production`, `/reports`, `/purchases`, `/` layout.

Do **not** call `archiveBatchIfDepleted` (remaining increases). Reopen §10.

## 8. PAID RULE

If `isPaid === true` and `frozenAt === null`: **allow** rails-only correction.

Payment amount stays. Earning is blank qty × rates, not `railsTaken`.

Do not add Payment ChangeLog. Do not flip `isPaid`.

## 9. FROZEN RULE

If `batch.frozenAt != null`: throw «Нельзя исправить — себестоимость партии заморожена». Zero writes (no remaining increment, no `railsTaken` update).

No unfreeze, no FINAL delete/create, no recalc of that batch’s FINAL (existing recalc already skips frozen).

---

## 10. REOPEN RULE

**Closed.** Admin rails correction is explicit confirmation that the returned rails **physically exist**. If they were already discarded, do not run correction.

After remaining increment, still in the same TX, with Batch locked:

```text
if frozenAt != null → already rejected
if frozenAt == null
   AND sum(RailLot.remainingQuantity where batchId) > 0:
     status = IN_WORK
     closedAt = null
     ChangeLog Batch: { reopened: true, viaOperationId }
```

Applies whether the batch was closed by **depletion** (`archiveBatchIfDepleted` after TORCOVKA) **or** **write-off**. Do **not** inspect ChangeLog to recover the old close reason.

If remaining is already > 0 and status is IN_WORK, leave as-is. Do not clear `frozenAt` (impossible here). Do not create PRELIMINARY inside this TX (queue after commit).

## 11. LOCK ORDER

### 11.1 What the code does today (HEAD `cc571f5`)

| Path | Locks today | Order |
| --- | --- | --- |
| `submitTorcovka` | `RailLot.updateMany` remaining (row X lock). **No** `FOR UPDATE` helper. Creates **new** Op. `archiveBatchIfDepleted` → `UPDATE Batch` then `maybeFreezeBatch({ batchAlreadyLocked: true })` — Batch lock only if remaining hits 0 | **RailLot → (optional) Batch**. Never locks a pre-existing Op |
| `writeOffBatchRemainder` | `railLot.updateMany` all lots remaining=0 (**no ORDER BY**). Then archive `UPDATE Batch` | **RailLot(s) → Batch**. No Op |
| `archiveBatchIfDepleted` | `findUnique` Batch (no FOR UPDATE), then `UPDATE Batch` (row lock), `maybeFreeze` assumes locked | Batch after caller already mutated lots |
| `maybeFreezeBatch` / freeze | `lockBatches` unless `batchAlreadyLocked`. Counts unpaid TORCOVKA **without** Op FOR UPDATE. Does not lock RailLot | **Batch only** (payroll already holds Ops) |
| `markEmployeePaid` | `lockProductionOperations` sorted → claim → `lockBatches` sorted → freeze | **Op → Batch** |
| `recalcBatchCosts` | `lockBatches` per batch. Reads TORCOVKA ops without Op lock | **Batch only** |
| `updateProductionLineQuantity` | `lockProductionOperations` then BlankStock. **No** Batch, **no** RailLot | **Op → BlankStock** |
| `deleteProductionOperation` TORCOVKA | `lockProductionOperations` → `lockBatches` → BlankStock decrement → delete Op → `maybeFreeze` | **Op → Batch → BlankStock**. RailLot **not** locked (INV-047) |

01.3 canonical **Op → Batch → stock** is for freeze/payroll/edit of **existing** Ops. Submit/write-off already take **RailLot before Batch**. Correction mutates **both** an existing Op **and** RailLot remaining, so it must not take Batch **before** RailLot: that deadlocks with submit/write-off.

### 11.2 Canonical order for DI-020 (and compatible callers)

```text
1. ProductionOperation   existing ops only, ids ASC FOR UPDATE
2. RailLot               ids ASC FOR UPDATE
3. Batch                 ids ASC FOR UPDATE
4. BlankStock / lines    only on paths that already touch stock
```

**Forbidden:** Batch then RailLot. **Forbidden:** Batch then ProductionOperation (still vs payroll).

Add `lockRailLots` next to `lockBatches` (`TABLE_IDENT.RailLot`, `ORDER BY id FOR UPDATE`).

### 11.3 Path after this plan

| Path | Order |
| --- | --- |
| `correctTorcovkaRailsTaken` | **Op → RailLot → Batch** → increment remaining, update `railsTaken`, maybe reopen. No BlankStock |
| `submitTorcovka` | **RailLot FOR UPDATE** → reread → INV-008 + waste band → remaining decrement → create Op → `archiveBatchIfDepleted` (Batch UPDATE after lots, as today). Do **not** lock other Ops. Do **not** lock Batch before the lot |
| `writeOffBatchRemainder` | **lockRailLots(all lots of batch)** → **lockBatches** → `updateMany` remaining=0 → archive `{ batchAlreadyLocked: true }`. Same Lot→Batch as today; sorted lots avoid lot-vs-lot deadlock |
| `deleteProductionOperation` TORCOVKA | **unchanged** Op → Batch → BlankStock. No RailLot |
| payroll / freeze / recalc | **unchanged** |

### 11.4 Deadlock proof (correction vs the three named races)

**correction ∥ submit same RailLot**

- C: waits/holds Op, then Lot, then Batch
- S: holds Lot, then maybe Batch; never waits on C’s Op

S cannot wait for C’s Op. C waiting Lot while S holds Lot+Batch: S commits or S waits Batch. C does not hold Batch before Lot → **no cycle**. Remaining: one TX wins the lot row; submit `gte` still prevents negative.

**correction ∥ write-off same Batch**

- W: Lots ASC then Batch
- C: Op then Lot then Batch

Both Lot before Batch. Same lot: row lock serializes. C never takes Batch before Lot → **no cycle** with W.

**correction ∥ archive/freeze**

- Archive/freeze hold Batch (and freeze does not lock RailLot). Payroll: Op then Batch.
- C: Op then Lot then Batch

Vs payroll same Op: both lock that Op first → serialize. Vs payroll other Ops then Batch: C holds Lot waiting Batch; payroll holds Ops waiting Batch — **no cycle** (both wait Batch, neither holds Batch yet). Vs freeze already holding Batch: C waits Batch after Lot; freeze does not need Lot → **no cycle**.

**correction ∥ delete same Op:** both `lockProductionOperations` first → serialize. Delete does not return rails.

**correction ∥ recalc:** recalc Batch-only. C takes Lot before Batch. Recalc never takes Lot → **no cycle**.

Do **not** lock Batch in correction before RailLot. Do **not** change delete to lock RailLot.

## Итоговая сводка

UX:
Диалог реек с новым копирайтом; confirm всегда показывает R / X м / N заготовок / Y м / Z м и P%. Первый submit без ack: NORMAL → `CREATED`, иначе `ACK_REQUIRED` (без мутации). Retry эхоит server strings. EXTREME — «Высокий отход / брак» + причина. Нет `confirmed: true`.

SERVER GUARD:
`submitTorcovka` returns `CREATED | ACK_REQUIRED`. Ack is not a thrown happy path. Canonical strings `takenM`/`producedM` 4dp, `wastePct` 2dp; server recomputes and compares strings. Validation errors still throw. INV-008 и `pick.lengthM ≤ lot.lengthM` остаются.

THRESHOLDS:
NORMAL `< 20`; SUSPICIOUS `20–50`; EXTREME `≥ 50`. Policy, не статистика. Dashboard 30% не подключать.

HIGH-WASTE STORAGE:
`torcovkaSubmitAckBand` + `torcovkaSubmitWasteReason` + `torcovkaSubmitWasteNote` — write-once at original submit. Current waste is derived. Correction history is ChangeLog.

CORRECTION RULES:
Admin decrease-only; remaining += delta; blanks/lines/payroll **and submit-time fields** не трогать; INV-008 на новом takenM; ChangeLog с reason.

PAID RULE:
Разрешено, если не frozen. Payment не менять.

FROZEN RULE:
Запрет, ноль записей, без unfreeze/FINAL.

REOPEN RULE:
`frozenAt == null` и remaining партии > 0 после возврата → `IN_WORK`, `closedAt=null`. Depletion и write-off одинаково. ChangeLog close reason не читать. Correction = физические рейки на месте.

LOCK ORDER:
Существующие submit/write-off: **RailLot → Batch**. Correction: **Op → RailLot → Batch**. Payroll: **Op → Batch**. Delete TORCOVKA: без изменений, RailLot не лочить. Нельзя Batch перед RailLot.

SCHEMA:
Два enum + три nullable колонки (`torcovkaSubmit*`). Additive migration.

TEST MATRIX:
13 кейсов §13 (`CREATED`/`ACK_REQUIRED` + canonical strings; correction; paid; frozen; reopen including write-off; delete; concurrency).

MIGRATION:
Только ADD COLUMN/TYPE. Удалённый инцидент не восстанавливать.
