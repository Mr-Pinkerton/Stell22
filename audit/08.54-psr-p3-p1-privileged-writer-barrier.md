## Authority model

Six actors are distinct. A PostgreSQL privilege does not bind an unconstrained superuser, and a Docker or host administrator is outside the PostgreSQL permission model.

| Actor | Who it is here | Can write during the held file? | Can a PostgreSQL privilege stop it? |
| --- | --- | --- | --- |
| A. Application | `p1wc_app`, non-superuser, member of the owning migrator until that membership is revoked | Yes, while it inherits the owner, holds an existing session, or is allow-listed after `ALTER ROLE SUPERUSER` | A new login can be rejected by `pg_hba`. Table `REVOKE` alone did not stop a plain insert |
| B. Owning migrator | `p1wc_migrator`, `NOSUPERUSER`, owns the business objects | Yes when its login is allow-listed, and yes when the admitted superuser uses `SET ROLE` | A new login can be rejected. Ownership is not removed |
| C. Bootstrap superuser | `stell22`, the role `initdb` created | Yes in an existing session. A new TCP login and a new Unix-socket login were rejected after the file was loaded | No. `REVOKE` does not apply. The role cannot be demoted (`08.49`) |
| D. Break-glass | `p1wc_breakglass`, login superuser | Yes before the file change. A new TCP login was rejected after it | No, once authenticated. A new connection can be rejected by `pg_hba` |
| E. Other logins | `p1pb_unexpected`, created as `LOGIN SUPERUSER` after the file was loaded; `p1pb_dump`, non-superuser | The unexpected superuser could not connect. | F. Host root / Docker | `docker exec -u root` and any holder of this daemon socket | Yes. Root rewrote `pg_hba` to trust and a new bootstrap insert then committed | No |

## Architectures

All four were executed or bounded by the same run. None is sufficient. `judgeArchitectures` returns `ARCHITECTURE_BLOCKED` and `sufficient: false` for each.

### A. Permissions and session draining

`REVOKE ALL` on tables and sequences from the application and from `PUBLIC` left a plain application insert committed, because `p1wc_app` inherits `p1wc_migrator` and the migrator owns the table. Bootstrap, break-glass, and migrator inserts also committed. `pg_terminate_backend` removed an uncommitted insert (id 51 absent). It did not stop an insert that committed from a session that was already authenticated when `pg_hba` was reloaded.

### B. Authentication barrier

The loaded file allow-lists one role with `scram-sha-256` and rejects every other `local` and `host` user, including loopback. New bootstrap TCP, new bootstrap socket, break-glass, migrator, application, unexpected superuser, and a sibling container were rejected. `pg_reload_conf` does not re-authenticate an existing backend. An allow-listed superuser still inserts. `ALTER ROLE` of the application to `SUPERUSER` did not connect until an allow line existed; with that line the insert committed.

### C. Host-level exclusive maintenance

Not proven. A second container on the cluster network connected before the file change. The test process is a Docker socket holder. No second OS user and no daemon authorization plugin were created. An unpublished port does not stop `docker exec` or a sibling. Host exclusivity would also not revoke a session that is already open.

### D. Supervised admission

This is the strongest incomplete shape. One admitted superuser session, default-reject for every other login, migrator DDL only through `SET ROLE` inside that session, backup only with an explicit non-superuser allow line and current `SELECT` grants, an unexpected client backend as a reason to abort, and a journal that does not authorize widening without `RELEASE`. It still admits that superuser, and host root can replace the file. The gate stays blocked. Design D in `audit/08.48` is not accepted by this result.

## Trusted operator boundary

No boundary in this package is sufficient, so none is installed. The incomplete shape, if an owner later accepts a host-trust assumption, would have to be specified as follows. This paragraph is a requirement list, not an implementation.

- The barrier owner is the operator who holds the Docker socket and the single admitted credential. The application does not hold either.
- Acquire by writing the default-reject file, reloading, and terminating every other client backend. Release only by an explicit journal `RELEASE` for the same binding, then a deliberate file change. `HELD` without `RELEASE` reopens as `AMBIGUOUS` and `mayWiden` is false.
- The only admitted database login is that one superuser. Everyone else, including a newly created superuser, has no allow line.
- The migrator is not a second login during the interval. P1 DDL would run as `SET ROLE` inside the admitted session. Adding a migrator allow line was shown to restore a direct migrator insert, so that line is not part of the held file.
- Backup is a non-superuser with `SELECT` on the relations that exist at dump time, and an allow line that is removed afterward. Production `backup-db.sh` does not match that shape.
- An unexpected client backend aborts progress. A point-in-time empty `pg_stat_activity` does not.
- The file survived client exit and `docker stop` / `docker start`. `system_identifier` stayed `7698635978520289314`. `StartedAt` changed, and Package E `reconfirm` then failed with `container StartedAt changed`. A restart is not a silent continuation.
- Ambiguous release stays closed in the test journal. The journal is a file on the test runner. It does not itself reject a TCP connection. A lost journal does not authorize widening (`mayWiden` is false for an empty file) and also does not put a replaced `pg_hba` back.
- The binding used in the journal is container id, image id, daemon id, `system_identifier`, and `StartedAt`. A mismatch becomes `AMBIGUOUS`.

The admitted superuser and the host-root path remain writers. They are accounted for by refusing `PRIVILEGED_WRITER_BARRIER_VERIFIED`.

## PostgreSQL 17 observations

Image baseline, active lines, first match wins:

```text
local   all             all                                     trust
host    all             all             127.0.0.1/32            trust
host    all             all             ::1/128                 trust
local   replication     all                                     trust
host    replication     all             127.0.0.1/32            trust
host    replication     all             ::1/128                 trust
host all all all scram-sha-256
```

Loopback and the Unix socket are trust. Non-loopback scram is the later rule. The restrictive file's sha256 was `9a1c77b853e07ac2d7c8c9e01e0c74f4b90d792f11c856d223792bcc49624664`. It has no replication allow line. Replication was not probed as its own session.

`COPY (SELECT 1) TO PROGRAM` with `sh -c printf` rewrote the file from the admitted superuser. A multiline `COPY` text format is not a rewrite: it escapes newlines and the old rules stay loaded. Root `docker exec` wrote the same trust file, `chown postgres`, mode `600`, and reloaded. Both reopened bootstrap.

`SET log_statement = none` hid `p1pb-hidden-marker`. The earlier `p1pb-logged-marker` was present. The log is not a complete record of an admitted superuser.

## Transient writes

A role `p1pb_flash` was created, used for `INSERT` id 4242, then the row was deleted and the role dropped inside one admitted session. The role count was 0 before and after. The inventory digest was unchanged. Other client backend pids were unchanged, so `pg_stat_activity` missed the writer. `pg_waldump` from the sampled LSN contained `INSERT` and the inventory filenode. Equal digests are not proof of zero transient writes.

`pg_stat_activity` shows a backend that still exists at the sample. It does not show one that exited between samples. A role created and dropped between catalog reads is absent from both reads. The server log can be suppressed by the admitted superuser. WAL showed this one reverted insert on this image; a log setting or a missing `pg_waldump` would not. Logical snapshots were not used and are not claimed.

## Crash and lock recovery

- Client disconnect left the restrictive file bytes in place.
- `docker stop` then `docker start` kept those bytes and the system identifier, changed `StartedAt`, and still rejected a new bootstrap login.
- Package E `reconfirm` refused the new `StartedAt`. This package does not treat the restarted container as the same admission epoch.
- The test journal is fsynced. `ACQUIRE` without `RELEASE` does not permit widening. Binding mismatch is `AMBIGUOUS`. There is no automatic unfreeze.
- An open transaction terminated with `pg_terminate_backend` left insert id 51 absent. A transaction that commits before terminate is durable.

## Migrator and backup admission

Migrator login stayed closed (`28000`) except during the explicit extra line, when insert id 81 committed. The admitted superuser created `p1pb_migrator_canary` with `SET ROLE p1wc_migrator` without opening that login. That statement is a stand-in. Pinned P1 was not applied.

`p1pb_dump` is `LOGIN NOSUPERUSER NOINHERIT` with no createdb, createrole, replication, or bypassrls. The first `GRANT SELECT ON ALL TABLES` did not cover the canary created later; `pg_dump` then failed with `permission denied for table p1pb_migrator_canary`. After a second grant, `pg_dump` exited 0 and the dump role's insert was `42501`. A non-superuser can dump only what it is granted at that moment. It is not a writer of `p1wc_inventory`. Production backup was not changed and still uses `stell22`.

## Coverage and GO / NO-GO

`PRIVILEGED_WRITER_BARRIER_VERIFIED` is defined as every precondition below being true. This run does not claim it. `FROZEN_VERIFIED` is not reused. `FREEZE_COVERAGE` stays `APPLICATION_ROLE_ONLY`.

Failed on the recorded run:

- `uncontrolledExistingSessionBlocked` — the pre-existing bootstrap insert committed after reload.
- `admittedSuperuserWritesBlocked` — the admitted role inserted.
- `hostRootRewriteBlocked` — root reopened trust.
- `admittedSuperuserHbaRewriteBlocked` — `COPY TO PROGRAM` reopened trust.
- `startedAtStableAcrossRestart` — `StartedAt` changed.
- `hostSocketExclusivityProven` — left false. No second principal was locked out.

Held on the recorded run, and still not a full barrier: new bootstrap TCP and socket rejected, new break-glass rejected, new unexpected login rejected, migrator login closed, ambiguous journal does not widen, the file survived client exit and restart, bootstrap stayed rejected after restart, transient insert was visible in WAL while the digest and `pg_stat_activity` missed it, and the dump role completed `pg_dump` without being able to insert.

The label `AUTHENTICATION_ADMISSION_EXCEPT_ADMITTED_SUPERUSER_AND_HOST_CONTROL` names that incomplete admission shape. It is not a passed coverage classification. Reaching it would still require, as independently testable preconditions, a loaded default-reject file, no other client backend, a proven sole holder of the daemon socket, a binding that includes container id, image id, daemon id, system identifier, and `StartedAt`, and an explicit owner acceptance that the admitted superuser and that socket holder remain writers. This package does not have those, and it does not ask for Design D or P1-3 to be approved.

`PRIVILEGED_WRITER_BARRIER_BLOCKED` is the result.

## Production prerequisites not met

An owner-approved role split, an application that no longer logs in as `stell22`, break-glass custody outside the app, and an external control on the Docker socket. This package does not perform that cutover. Rejecting `stell22` in production would take the current application offline, because that login is the bootstrap superuser. Allow-listing it would admit a superuser.
