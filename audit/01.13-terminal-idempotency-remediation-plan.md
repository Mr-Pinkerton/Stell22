## 1. Review correction — почему одного `findUnique` до lock недостаточно

Контрпример (остаток лота = `railsTaken`):

```
T1 findUnique → none
T2 findUnique → none
T1 lockRailLots
T2 ждёт лок
T1 decrement remaining → 0
T1 create + commit
T2 получает лок
T2 stock guard → «Недостаточно реек»
T2 никогда не доходит до UNIQUE
```

Это ровно S1a / критический concurrent-кейс. Fast precheck закрывает только
**уже закоммиченный** sequential retry. Под конкуренцией сериализация идёт
через `RailLot FOR UPDATE`; поэтому **после** получения лока обязателен
повторный `findUnique`. T2 увидит строку T1 и вернёт idempotent success,
не доходя до stock guard и `decideTorcovkaSubmit`.

UNIQUE (`P2002`) остаётся страховкой, если два TX всё же дойдут до INSERT
(разные лоты, один ключ: лок RailLot их не сериализует). Тогда проигравший
откатывает всю TX, включая decrement.

## 2. DI-007 — точный алгоритм TORCOVKA

Файл: `src/server/terminal.ts` `submitTorcovka`.
Пороги / `decideTorcovkaSubmit` / `computeTorcovkaWasteMetrics` **не менять**.
`lockRailLots(tx, [railLotId])` остаётся первым локом RailLot (канон).
`archiveBatchIfDepleted` по-прежнему может взять `lockBatches` **после**
RailLot — порядок не переставлять и не добавлять `lockProductionOperations`.

### 2.1 Снаружи TX

1. `requireTerminalEmployee(input?.employeeId)` — **первый** statement, без изменений.
2. `const clientRequestId = requireClientRequestId(input.clientRequestId)` — до любой
   мутации и до TX.
3. Существующие проверки работника / `railsTaken` / непустых picks — как сейчас.

### 2.2 Внутри TX

```
1. fast findUnique({ where: { clientRequestId } })
   если есть → return { status: "IDEMPOTENT_REPLAY" }
   (без lockRailLots, без физики, без ACK, без склада, без ChangeLog)

2. lockRailLots(tx, [railLotId])     // канонический порядок, без изменений

3. findUnique({ where: { clientRequestId } })  // ПОВТОРНО, уже под локом лота
   если есть → return { status: "IDEMPOTENT_REPLAY" }

4. текущие чтения lot/batch
5. физика длины заготовки
6. INV-008 producedM ≤ takenM
7. decideTorcovkaSubmit (DI-020) → ACK_REQUIRED = return из TX без writes
8. stock guard updateMany gte → «Недостаточно реек в пакете»
9. decrement
10. productionOperation.create (UNIQUE — страховка)
11. blankStock.upsert (тот же sort key, что сейчас)
12. writeChangeLog
13. archiveBatchIfDepleted
14. return { status: "CREATED_NEW" }
```

`.catch` на TX: `isDuplicateClientRequest` → `{ status: "IDEMPOTENT_REPLAY" }`
(не `CREATED_NEW`).

### 2.3 После TX

```
если ACK_REQUIRED → вернуть как есть (без enqueue)
если IDEMPOTENT_REPLAY → revalidatePath, без enqueueRecalcBatchCosts
если CREATED_NEW → enqueueRecalcBatchCosts(batchId) + revalidatePath
публичный return: { status: "CREATED" }  // и для NEW, и для REPLAY
```

`revalidatePath` на replay оставляем (дёшево, UI не ломается).
Enqueue на replay **не** делаем: это не новое событие партии.

### 2.4 Публичный контракт UI

`SubmitTorcovkaResult` **не ломать**:

```ts
| { status: "CREATED" }
| { status: "ACK_REQUIRED"; band; railsTaken; takenM; producedM; wastePct }
```

Экраны проверяют только `status === "ACK_REQUIRED"`, иначе success
(`torcovka-screen.tsx:157`, `:206`). Внутренние статусы `CREATED_NEW` /
`IDEMPOTENT_REPLAY` **не** экспортировать из server action.

Сервер **не** генерирует и **не** подменяет `clientRequestId`. Тот же id,
что пришёл, пишется в строку. Это сохраняет будущий инвариант draft:
одна попытка черновика владеет одним id через logout/reload/resume.

### 2.5 ACK

Идентичность уже созданной операции **важнее** текущей ACK-валидации.

| Ситуация | Результат |
| --- | --- |
| Новый id, NORMAL, без ack | `CREATED` / `CREATED_NEW` |
| Новый id, SUSPICIOUS/EXTREME, без ack | `ACK_REQUIRED`, zero writes |
| Новый id, SUSPICIOUS/EXTREME, неверный ack | ошибка DI-020 как сейчас |
| Новый id, корректный ack | `CREATED` / `CREATED_NEW` |
| Тот же id после успеха, **с** ack | `CREATED` / `IDEMPOTENT_REPLAY` |
| Тот же id после успеха, **без** ack | `CREATED` / `IDEMPOTENT_REPLAY` — **не** `ACK_REQUIRED` |

Повторный lookup обязан стоять **до** `decideTorcovkaSubmit`. Для нового id
требования ACK не ослаблять.

### 3.2 Общий runtime-helper

Файл: `src/lib/request-id.ts` (рядом с `newRequestId`, без PIN/session).

Конвенции длины в проекте нет (`String` = TEXT). Граница приложения:

- UUID = 36 символов;
- http-фолбэк `newRequestId` ≈ 40;
- UPAKOVKA хранит `${clientRequestId}:${productId}` (cuid ≈ 25) — это **уже
  после** валидации входа; лимит применяется к **входному** ключу попытки.

```ts
export const CLIENT_REQUEST_ID_MAX_LENGTH = 128;
export const CLIENT_REQUEST_ID_REQUIRED = "Не указан ключ попытки операции";
export const CLIENT_REQUEST_ID_TOO_LONG = "Слишком длинный ключ попытки операции";

export function requireClientRequestId(value: unknown): string {
  if (typeof value !== "string") throw new Error(CLIENT_REQUEST_ID_REQUIRED);
  const id = value.trim();
  if (!id) throw new Error(CLIENT_REQUEST_ID_REQUIRED);
  if (id.length > CLIENT_REQUEST_ID_MAX_LENGTH) {
    throw new Error(CLIENT_REQUEST_ID_TOO_LONG);
  }
  return id;
}
```

Формат UUID **не** требовать (`seed:...` / `test:...` валидны).

Вызов: **после** `requireTerminalEmployee`, **до** TX / `productionOperation.create`.
В CREATE писать **trimmed** значение.

UPAKOVKA: после helper всегда

```ts
clientRequestId: `${clientRequestId}:${pick.productId}`
```

Ветку `undefined` удалить.

PRISADKA / UPAKOVKA / HOURS: порядок склада **не** перепроектировать.
Create-first + `P2002` → void success остаётся. Только обязательный ключ.

## 4. DI-008 — инвариант БД

### 4.1 Prisma

`prisma/schema.prisma` ProductionOperation:

```prisma
  // Идемпотентность терминала (A21): уникальный ключ попытки с клиента.
  // Дубль одной попытки (двойной тап / сетевой retry / replay того же id)
  // ловится unique-констрейнтом. Две вкладки обычно дают два разных id —
  // это две попытки, не дедуп физического действия.
  // NOT NULL: приложение требует ключ на каждом submit (DI-008 C).
  clientRequestId String @unique
```

Индекс Prisma `@unique` уже существует как
`ProductionOperation_clientRequestId_key`. Миграция **не** дропает и **не**
пересоздаёт его: только `SET NOT NULL`.

### 4.2 Миграция SQL

Каталог (имя фиксировать при реализации; timestamp > `20260905160000`):

`prisma/migrations/<ts>_production_operation_client_request_id_not_null/migration.sql`

Образец дисциплины: `20260904170000_batchcost_final_unique`,
`20260905160000_di016_inventory_single_draft`.

Prisma 6 classic PostgreSQL `migration.sql` **не** оборачивается в транзакцию
автоматически → явные `BEGIN`/`COMMIT`. Без `CONCURRENTLY`.

```sql
-- DI-008 C: ProductionOperation.clientRequestId NOT NULL, UNIQUE сохраняется.
-- LOCK + recheck + RAISE при NULL. Без UPDATE / backfill / DELETE.
-- Существующий UNIQUE INDEX ProductionOperation_clientRequestId_key не трогать.

BEGIN;

LOCK TABLE "ProductionOperation" IN ACCESS EXCLUSIVE MODE;

DO $$
DECLARE
  n_null integer;
  detail text;
BEGIN
  SELECT count(*) INTO n_null
  FROM "ProductionOperation"
  WHERE "clientRequestId" IS NULL;

  IF n_null > 0 THEN
    SELECT string_agg(
             format(
               'id=%s type=%s employeeId=%s workDate=%s createdAt=%s',
               id,
               type,
               "employeeId",
               "workDate",
               "createdAt"
             ),
             '; ' ORDER BY "createdAt", id
           )
    INTO detail
    FROM "ProductionOperation"
    WHERE "clientRequestId" IS NULL;

    RAISE EXCEPTION
      'DI-008: % ProductionOperation row(s) have NULL clientRequestId: %; resolve before migrate (no backfill/delete)',
      n_null, detail;
  END IF;
END $$;

ALTER TABLE "ProductionOperation"
  ALTER COLUMN "clientRequestId" SET NOT NULL;

COMMIT;
```

Запрещено в этой миграции: `UPDATE ... SET "clientRequestId"`, `DELETE FROM
"ProductionOperation"`, `DROP INDEX`, `CREATE UNIQUE INDEX` (индекс уже есть).

Откат (только документировать, не класть в migrate): `ALTER COLUMN DROP NOT NULL`.
UNIQUE при откате остаётся.

### 10.1 Тест 7 — детерминированный RailLot-барьер

Цель расписания (без этого post-lock lookup можно не исполнить):

```
blocker: lockRailLots(lot) FOR UPDATE, держит
T1 fast findUnique → none
T2 fast findUnique → none
T1 lockRailLots → WAIT
T2 lockRailLots → WAIT
           [наблюдаемо: 2 ungranted waiters]
blocker RELEASE
T1 получает лок, create, commit
T2 получает лок, POST-LOCK findUnique видит T1 → IDEMPOTENT_REPLAY
```

Если post-lock `findUnique` отсутствует: T2 после release идёт в stock
guard (`remaining === 0`) → «Недостаточно реек» → тест красный.

**Механизм** (узкий, на существующем harness: `prismaA`/`prismaB` + app
`prisma` из `@/server/db`, как `di-020.integrity.test.ts`):

1. Фикстура: один лот, `remainingQuantity === railsTaken`, NORMAL waste
   (без ACK), один `clientRequestId`.
2. **Blocker** на `prismaB.$transaction` (свой backend, не app-pool):
   `lockRailLots(tx, [lotId])` — тот же helper, что production
   (`SELECT … ORDER BY id FOR UPDATE`). Сразу после лока
   `SELECT pg_backend_pid()` в этой же TX. Дальше TX **не** мутирует
   склад; ждёт явного `release` (Promise), timeout/maxWait ≥ 20s.
3. Дождаться, что blocker **уже держит** лок (resolve после
   `lockRailLots`, до запуска submit).
4. Запустить **оба** `submitTorcovka` (app `prisma`). Они проходят fast
   precheck (строки ещё нет) и встают в очередь на RailLot.
5. **Наблюдаемый барьер** — poll (не sleep-as-proof) через `prismaA`
   до обоих условий или timeout → fail `barrier: expected 2 RailLot lock waiters`.

`pg_stat_activity`: ≥ 2 сессии с `wait_event_type = 'Lock'`, исключая
pid blocker.

плюс `pg_locks`: ≥ 2 соответствующих ungranted lock, у которых либо
`relation = '"RailLot"'::regclass`, либо `locktype = 'transactionid'`
(pid этих lock — те же Lock-waiters, не blocker).

Не требовать `'"RailLot"'::regclass AND NOT granted` ≥ 2: PostgreSQL
row-lock convoy при `FOR UPDATE` показывает одного waiter как ungranted
tuple/relation на `"RailLot"`, а второго — на `transactionid` первого
waiter (`relation` NULL). Два relation-wait на RailLot — неверная модель.

Интервал poll — деталь ожидания; корректность = счётчик waiters, не
«прошло N мс». Production-код **без** sleep.

6. Только после `waiting >= 2`: `release()` blocker TX (commit без
   складских writes).
7. `Promise.allSettled` двух submit + blocker. Оба submit
   `{status:"CREATED"}`; remaining=0; ops=1; BlankStock один раз;
   ProductionOperation ChangeLog = 1; enqueue на replay не второй раз;
   ни один reject с «Недостаточно реек».

Не использовать `delay(50|80|250|300)` как в `di-020` / cost-freeze
как доказательство, что оба дошли до лока.

### 10.3 Тест 21(b) — crash-safe NULL-guard

Не оставлять колонку nullable, если тест упал между `DROP NOT NULL` и
`SET NOT NULL`. PostgreSQL DDL транзакционен — предпочтительный каркас:

`prismaB.$transaction` (interactive, timeout достаточный):

1. `ALTER TABLE "ProductionOperation" ALTER COLUMN "clientRequestId" DROP NOT NULL`
2. `INSERT` одной валидной NULL-строки (те же NOT NULL/FK, что §10.2,
   плюс живой `employeeId`)
3. Тот же recheck, что миграция: `count(*) WHERE "clientRequestId" IS NULL`
   → если >0 `RAISE EXCEPTION` с `id/type/employeeId/workDate/createdAt`
   (без `UPDATE`/`DELETE`/`SET` ключа)
4. Ожидаемый throw. Callback **не** коммитит.

ROLLBACK интерактивной TX откатывает DROP NOT NULL и INSERT.
Это нормальный ожидаемый путь.

`try/finally` **обязателен** (если Prisma/драйвер не откатили DDL).
Emergency cleanup в `finally` — только harness, не migrate/preflight.
Порядок (сначала delete: leftover NULL блокирует `SET NOT NULL`):

1. удалить ТОЛЬКО тестовую фикстуру по точному `fixtureId`
   (после ROLLBACK delete = 0 строк)
2. inspect `attnotnull`
3. если `attnotnull = false`:
   `ALTER TABLE "ProductionOperation" ALTER COLUMN "clientRequestId" SET NOT NULL`
4. assert `attnotnull = true`
5. assert `count(*) WHERE "clientRequestId" IS NULL` = 0

```sql
SELECT a.attnotnull
FROM pg_attribute a
WHERE a.attrelid = '"ProductionOperation"'::regclass
  AND a.attname = 'clientRequestId';
-- must be true
SELECT count(*) FROM "ProductionOperation" WHERE "clientRequestId" IS NULL;
-- must be 0
```

Миграция и preflight по-прежнему без DELETE/backfill. Следующий тест
**не** должен чинить схему.

Не вызывать `SET NOT NULL` из миграции внутри этой TX как «успешный путь».
