## 2. BUSINESS MODEL FROM CODE

Вопрос: может ли одна `ProductionOperation` быть выплачена как A / B / C / D?

**Ответ: A — exactly once, in full, atomically.**

Доказательства (порядок `00-audit-principles.md`):

| Приоритет | Свидетельство |
| --- | --- |
| 2. Намеренный код | JSDoc `markEmployeePaid`: «все его невыплаченные операции переводятся в `Payment` + `PaymentBatchItem`, помечаются isPaid/paidAt. После выплаты операции нельзя редактировать/удалять». |
| 2. UI | `report-salaries-tab.tsx`: кнопка только на unpaid-строке работника; **нет** выбора операций, сумм, частичной выплаты. Paid-строки рендерятся без `onPaid`. |
| 2. Writer | Единственный production-writer создаёт **один** `Payment` на все текущие unpaid ops работника и по одному item на op (`sortedUniqueIds` → `createMany`). |
| 3. Schema | У item нет `amount` — частичная сумма на item невозможна. Prisma relation 1:N, но приложение всегда пишет 1 item / op. |
| 3. Нет reversal writer | Нет `payment.delete` / cancel / unpay / `isPaid: false` в `src/`. |

Отвергнуто:

- **B (partial across several items):** нет поля суммы на item, нет UI/API частичной выплаты.
- **C (adjusted/reopened/repaid):** нет reversal; `isPaid` в production-коде переходит только `false → true`.
- **D:** не требуется.

`PaymentBatchItem` — **membership snapshot** (какие ops вошли в выплату), не independently editable amount. Авторитетная сумма выплаты — `Payment.amount`, посчитанная в той же TX после lock.

Candidate invariant «one ProductionOperation belongs to at most one PaymentBatchItem and is paid atomically in full» — **доказан как текущий бизнес-инвариант приложения**. DB его не кодирует.

### 3.3 Main payroll flow — exact order (`markEmployeePaid`)

Файл: `src/server/payroll.ts`. Helper locks: `src/server/internal/finance-operations.ts`.

1. **Auth:** `requireAdmin()` (`payroll.ts:191`).
2. **Input:** `employeeId: string`. Операции клиент не передаёт.
3. **Pre-TX selection:** `prisma.productionOperation.findMany({ where: { employeeId, isPaid: false }, select: { id } })` (`:192-195`). Сортировка `sortedUniqueIds` (`:196`). Пусто → throw `"Нет невыплаченных операций"` **до** TX.
4. **TX start:** `prisma.$transaction` (`:201`). Isolation **не** задан → PostgreSQL default **READ COMMITTED**. `retryOnLockSetChange` **не** используется.
5. **Lock ops:** `lockProductionOperations(tx, opIds)` → `SELECT id FROM "ProductionOperation" WHERE id IN (...) ORDER BY id FOR UPDATE` (`finance-operations.ts:106-115`, `:125-129`).
6. **Re-read after lock:** `tx.productionOperation.findMany({ id in opIds, include lines })` (`payroll.ts:203-206`). Если length mismatch (op удалена) или `ops.some(isPaid)` → throw `"Операции уже выплачены — обновите отчёт"` (`:207-209`).
7. **Authoritative amount after lock:** `buildRefMaps(tx)` (live `Employee` rates + `Detail.sort`) + `computeOp` / `operationEarning` (`:211-212`). Employee row **не** `FOR UPDATE`.
8. **Claim `isPaid`:** `updateMany({ id in opIds, isPaid: false }, { isPaid: true, paidAt })`; `claimed.count !== opIds.length` → throw, rollback (`:214-220`).
9. **`Payment.create`:** `{ employeeId, amount: amount.toFixed(2), paidAt }` (`:222-224`).
10. **`PaymentBatchItem.createMany`:** один row на каждый `opIds` (`:225-227`).
11. **ChangeLog:** `writeChangeLog({ entity: "Payment", ... }, tx)` (`:228-235`).
12. **Freeze:** `lockBatches(tx, torcovkaBatchIds)` затем `maybeFreezeBatch(tx, batchId, { batchAlreadyLocked: true })` (`:237-243`).
13. **Notification:** `notifyEvent({ key: event:salary-paid:${payment.id} }, tx)` — `Notification` upsert **в той же TX** (`:245-254`, `notification-event.ts:18-31`).
14. **Commit.**
15. **After commit (не DB):** `revalidatePath("/reports")`, `"/production"`, `"/" layout` (`:257-260`). Cost-queue **не** вызывается из payroll.
16. Return `getSalaryReport()`.

Все DB-writes выплаты (claim, Payment, items, ChangeLog, freeze FINAL, Notification) — **одна** `$transaction`.

## 4. CURRENT LOCKING

### 4.1 Payroll / freeze order (verified, not assumed)

```
ProductionOperation  ORDER BY id FOR UPDATE   // выбранные unpaid ids
→ re-read ops + isPaid check
→ live amount
→ UPDATE isPaid (claim)
→ INSERT Payment
→ INSERT PaymentBatchItem
→ INSERT ChangeLog
→ Batch              ORDER BY id FOR UPDATE   // TORCOVKA batch ids only
→ maybeFreezeBatch (batchAlreadyLocked)
→ UPSERT Notification
```

Канонический порядок из `audit/01.2-cost-freeze-review.md` (Op → Batch) **соблюдён**. Добавлен в `cc571f5`, не в исходном A19-claim (`b9e7821`).

### 4.2 Details

| Question | Answer |
| --- | --- |
| Ops sorted before lock? | **YES** — `sortedUniqueIds` + SQL `ORDER BY id` |
| All selected ops locked before calculation? | **YES** |
| `isPaid` re-read after lock? | **YES** (`findMany` + `ops.some(isPaid)`), затем ещё claim `WHERE isPaid:false` |
| Payment amount recomputed after lock? | **YES** для qty/hours/lines операции. Ставки Employee — live read после Op lock, **без** lock Employee (это DI-015, не double-pay) |
| TX all-or-nothing? | **YES** |
| Empty lock set skipped? | **YES** (`lockTableIds` returns if no ids) |

Соседние writers, которые тоже берут Op lock: `updateProductionLineQuantity`, `deleteProductionOperation`, `correctTorcovkaRailsTaken` — Op (затем Batch/RailLot). Порядок Op → Batch совместим с payroll.

`markEmployeePaid` **не** вызывает `retryOnLockSetChange`. Если между pre-TX `findMany` и lock op исчезла — throw. Если появилась новая unpaid — в эту выплату не попадёт (следующий клик). Это не double-pay.

## 5. SEQUENTIAL DOUBLE PAY

Операция OP-1, `isPaid=false`.

**Request A** проходит flow §3.3, коммитит `isPaid=true` + Payment + item.

**Request B** (тот же работник, позже):

1. Pre-TX `findMany isPaid:false` → пусто.
2. Throw `"Нет невыплаченных операций"` **до** TX.
3. Новых `Payment` / `PaymentBatchItem` нет.

Если B как-то передаст уже выплаченные ids (app так не делает): внутри TX lock → re-read `isPaid=true` → throw → rollback.

**Sequential double pay: NO.**

## 6. CONCURRENT DOUBLE PAY

T1 и T2: два `markEmployeePaid(sameEmployee)` на одни и те же unpaid ops. Isolation: READ COMMITTED. Lock SQL фильтрует **по id**, не по `isPaid`, поэтому после commit T1 строка всё ещё находится и лочится T2.

```
T1 findMany unpaid → [OP-1]
T2 findMany unpaid → [OP-1]
T1 BEGIN
T1 SELECT ... WHERE id IN (OP-1) ORDER BY id FOR UPDATE     -- lock held
T2 BEGIN
T2 SELECT ... FOR UPDATE                                     -- WAITS
T1 findMany: isPaid=false
T1 compute amount from locked rows + live rates
T1 updateMany isPaid=true (count=1)
T1 INSERT Payment + PaymentBatchItem(OP-1)
T1 ChangeLog / Batch lock / freeze / notify
T1 COMMIT                                                    -- lock released
T2 FOR UPDATE returns
T2 findMany: isPaid=true
T2 throw "Операции уже выплачены — обновите отчёт"
T2 ROLLBACK
```

Второй insert `PaymentBatchItem(operationId=OP-1)` **не выполняется**.

Почему `isPaid` flag **сам по себе** недостаточен, а здесь достаточен:

- Без `FOR UPDATE` два READ COMMITTED TX могли бы оба прочитать `isPaid=false` и оба вставить item (классический TOCTOU).
- Сейчас проверка `isPaid` идёт **после** row lock; проигравший видит committed `true`.
- Второй рубеж: `updateMany WHERE isPaid:false` + `count` match (A19, `b9e7821`) — даже если re-read check убрать, claim второго TX даст `count=0` и rollback **до** `payment.create`.
- Третий рубеж в БД (**отсутствует**): UNIQUE(`operationId`).

`isPaid` exists ≠ serialization. **Evidence of post-lock check: YES.**

Перекрытие lock-set (T1 платит [OP-1], T2 успел выбрать [OP-1, OP-2]): T2 после wait видит OP-1 paid → throw **всей** TX → OP-2 остаётся unpaid → повторный клик выплатит OP-2 один раз. Не double-pay; UX retry.

**Concurrent double pay on this path: NO.**

Обход app-path (Prisma Studio, будущий writer, test harness) UNIQUE не остановит сегодня. Это и есть weakness.

| Action | Exists? |

Связанное (не reversal выплаты):

## 9. PAYMENT AMOUNT SOURCE OF TRUTH (только для 1:1 mapping)

Не DI-015 redesign.

- Начисление в отчёте unpaid: live `Employee.*Rate` × факты операции (`lib/payroll.ts` `operationEarning`).
- В момент выплаты: та же формула **после** Op lock, snapshot в `Payment.amount`.
- `PaymentBatchItem` суммы не хранит.
- Paid-строка отчёта: `total` = `Payment.amount`; day breakdown заново через live `computeOp` по `items.operationId` (`getSalaryReport` `:162-178`). Дубль item в одном Payment **удвоил бы** produced/days, не `Payment.amount`.

Вывод для DI-014: один op → один item. Сумма не сплитуется по items.

## 12. FAILURE / RETRY

Все writes §3.3 шаги 5–13 в одной TX. Throw на freeze / changelog / notify → rollback claim+Payment+items.

После commit: только `revalidatePath` (не DB). Retry успешной выплаты: sequential §5.

Notification key содержит `payment.id` (новый cuid) — upsert не создаёт ложный «уже отправлено» на retry после rollback.

**Retry cannot create duplicate PaymentBatchItem on the production path.**

## 15. UNIQUE RECOMMENDATION (DO NOT IMPLEMENT IN THIS PASS)

Инвариант: одна `ProductionOperation` **никогда** не должна иметь несколько `PaymentBatchItem` за жизнь. При текущем коде это верно. UNIQUE семантически безопасен.

Рекомендация (high-level):

```text
UNIQUE ("operationId") ON "PaymentBatchItem"
```

Prisma: `operationId String @unique` (это также даст недостающий lookup-индекс).

Preflight (ожидание: 0 rows) — уже выполнено на local+prod:

```sql
SELECT "operationId", COUNT(*)
FROM "PaymentBatchItem"
GROUP BY "operationId"
HAVING COUNT(*) > 1;
```

Migration strategy:

- fail if duplicates exist
- no DELETE
- no UPDATE
- no auto-dedup
- add UNIQUE only

План/тесты (не этот pass): sequential replay, concurrent same-employee `markEmployeePaid`, прямой insert второго item → P2002. App catch для P2002 необязателен, если writer остаётся единственным и уже бросает на `isPaid`; UNIQUE — backstop.

Future reversal: если появится и historical item сохранят — UNIQUE нужно будет менять **до** включения reversal, не наоборот.

## 16. IF UNIQUE WERE NOT SAFE

Не применяется. Причины, которые сделали бы UNIQUE небезопасным, в текущем коде **отсутствуют**:

- reversal retaining historical item — нет
- partial payment — нет
- intentional re-payment new item — нет

Фактический инвариант, который UNIQUE должен кодировать:

> Каждая ProductionOperation присутствует не более чем в одной строке PaymentBatchItem; выплата — all unpaid ops работника, целиком, один Payment.
