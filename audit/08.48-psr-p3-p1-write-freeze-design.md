## Verdict

No mechanism that exists in the running architecture meets the freeze gate.

The application and the P1 one-shot use one login, `stell22`. The repository's production Compose file asks the official `postgres:17-alpine` image to create that login as `POSTGRES_USER` and to create the database `stell22`. The published entrypoint of that image line creates a non-default `POSTGRES_USER` as a superuser and makes it the database owner. This repository does not vendor that entrypoint, and this task did not read `pg_roles` or `pg_database`. Superuser and ownership are therefore **EXPECTED FROM THE IMAGE CONTRACT / UNPROVEN IN PRODUCTION**.

That expectation is enough to reject the current controls. A superuser bypasses `REVOKE`. A table owner who is not a superuser can still grant the revoked privilege back in the same session. `default_transaction_read_only` applies to new sessions only, and any session can turn it off. The running image has no write-admission flag. Adding one replaces the application image and changes `StartedAt`, which the dossier treats as a different runtime.

The safe design is a later, separate package: a non-superuser application role that can only read, a different owner role used only by the migrator, a drain of existing sessions, and an operator recheck of those privileges immediately before spawn. That package is not the P1 migration, not an application deploy, and not authorized by this record.

Until that package is implemented and proven on disposable PostgreSQL 17, the write-freeze is **DESIGN BLOCKED**.

## What the freeze would have to guarantee

All of the following, together:

- No restart of `stell22-app` or `stell22-db-prod`.
- No replacement of the application image.
- No change of Docker daemon identity.
- No change of either container's `StartedAt`.
- No loss of committed business data.
- No business write committed during the protected interval.
- Read-only verification still possible after the cutover.
- The approved P1 migration still able to run as a different database identity.
- No SHADOW gate change and no ledger activation.

`docker-compose.prod.yml` gives the app `DATABASE_URL` with username `stell22` at process start. Changing that URL recreates the container. The freeze therefore has to constrain the existing login, not replace it.

## Database privilege assessment

### What the repository actually configures

`docker-compose.prod.yml` sets `POSTGRES_USER=stell22`, `POSTGRES_DB=stell22`, image `postgres:17-alpine`, and no published database port. The app URL uses the same user. The adapter constant `PRODUCTION_ROLE_NAME` is `stell22`. `identity.ts` rejects any other observed role. There is no migrator role, no `NOSUPERUSER` statement, and no grant script in the repository.

Prisma migrations run as that same user, from the entrypoint on the historical image and from the one-shot on a future P1 apply. P1 DDL is `ALTER TABLE`, `CREATE FUNCTION`, and `CREATE TRIGGER` on `BatchCreationCommand`. The one-shot has `connect_timeout=5` and no `lock_timeout`.

### PostgreSQL 17 behavior that blocks a privilege-only freeze

These are engine rules. They are not production measurements. A disposable PostgreSQL 17 test must reproduce them before any later package is trusted.

- A superuser passes table privilege checks. `REVOKE INSERT, UPDATE, DELETE` does not stop it.
- The owner of a table can revoke their own ordinary privileges and can grant them back. `REVOKE` against the owner is reversible by that owner.
- `ALTER ROLE ... SET default_transaction_read_only = on` and the same setting at database level are copied into a session at login. Existing pooled sessions keep their current value.
- `default_transaction_read_only` is user-settable. The application role can execute `SET default_transaction_read_only TO off`.
- A transaction that has already started read-write is not changed by a later default. A prepared `INSERT` executed inside that transaction still writes. `COMMIT` does not re-check the privilege of a statement that already succeeded.
- `nextval` and `setval` are writes. Table `REVOKE` does not cover them. A read-only transaction does reject `nextval`. Sequence values survive rollback, so a drained transaction can still move a sequence without changing a row count.
- A `SECURITY DEFINER` function owned by a writing role would run with that role's rights. The only function in migrations is not security-definer and is not deployed. Any other function in the live catalog is **UNKNOWN** and must fail closed if found.
- The database owner can create objects in `public`. A new table created during a freeze would be writable by its owner. `REVOKE` on existing tables does not prevent that.
- `CREATE ROLE` and `ALTER ROLE` cannot run inside a transaction block. A crash between those statements leaves a partial catalog. That state is **UNCERTAIN**, not a completed freeze and not an automatic rollback.
- `pg_terminate_backend` aborts the target transaction. It rolls back uncommitted work. It does not commit it, and it does not restart the postmaster. Container `StartedAt` does not change because of that call. The pool then reconnects. Without a privilege change, the new session writes again.
- `ALTER TABLE ... OWNER TO` and the P1 `ADD COLUMN` each need `ACCESS EXCLUSIVE` on the affected table. `pg_dump` needs `ACCESS SHARE`. A freeze that holds `ACCESS EXCLUSIVE` for the whole window blocks the backup and can deadlock the migration. Long-lived `ACCESS EXCLUSIVE` locks are not the freeze.
- PostgreSQL 17 login event triggers run at connect. They do not stop a superuser, or the table owner, from turning a GUC off afterwards.

`catalog.ts` compares `count(*)` for every public table except `_prisma_migrations`. An `UPDATE` that preserves the count, including a stock-quantity change or a notification text update, does not change `aggregateFingerprint`. Row-count equality is required and is not proof that no business write committed.

The signed dossier binds container identity, `StartedAt`, and the one-shot image id. It does not bind `rolsuper`, grants, or owners. A privilege change is invisible to `dossierSha256`. A privilege reversal that preserves row counts is invisible to `recoverySha256`. The current `apply` path does not re-read grants before `authorize`.

### Migrator identity

`planProductionOneShot` puts `roleName` into the one-shot URL. Production requires that name to be `stell22`. Freezing `stell22` with a control that actually works also freezes the only role the merged operator can use for P1 DDL.

A distinct migrator is a new role plus an operator change that accepts it. That change edits the host-run operator. It does not by itself replace the application image. It is still a prerequisite, and it is not authorized here. Putting the role change inside `migration.sql` would change the pinned P1 checksum and would hide the security change inside the migration. That is rejected.

### Backup and the entrypoint

`pg_dump --no-owner --no-acl` can run with `SELECT` if the later test proves it. Ownership is not part of the dump or of the row-count fingerprint.

If the application container exits, `docker-entrypoint.sh` runs `prisma migrate deploy` before the server. On the historical image that command replays the migrations baked into that image. It does not contain the P1 file. Whether a demoted `stell22` can complete a no-op `migrate deploy` is **UNPROVEN**. A failed entrypoint exits the process, Compose restarts it, and `StartedAt` changes. The attempt must then stop. The restart is not an unfreeze.

## Design comparison

### A. Application maintenance mode

The running source has no maintenance flag, no write gate, and no mounted file that the server reads before a mutation. `Caddyfile` proxies every request to `app:3000`.

Shipping a gate means a new application image and a new container start. That changes `StartedAt` and the image id, so it cannot happen inside the protected interval. It is a separate deploy, which remains **NOT AUTHORIZED**, and it still does not stop `psql`, `docker exec`, or a connection that reaches `app:3000` on the Docker network.

Caddy can be reloaded without recreating the app or database containers. A proxy rule is not admission control inside the database. In-flight requests already inside Node continue. The notification poll and every other Server Action are POST, so a blunt POST block also blocks ordinary reads through the UI. Direct database sessions do not pass Caddy.

**Result:** does not meet the gate. Not sufficient even after a future deploy.

### B. Database restriction with the current role

`REVOKE`, `NOLOGIN` alone, and `default_transaction_read_only` do not bind a superuser owner, do not stop an already-open writing transaction, and do not leave a second identity for P1 DDL.

`NOLOGIN` plus `pg_terminate_backend` would also stop read-only verification until login is restored, and the restored login would still be the writer.

**Result:** does not meet the gate. Rejected as a complete freeze.

### C. Hybrid of A and B on the current system

There is no application control to coordinate with, and the database control does not hold. A hybrid of two insufficient controls is not a third control.

**Result:** does not meet the gate.

### D. Recommended later architecture

This is the only design that can meet the gate, and only after a prerequisite that does not exist yet.

1. Create `stell22_migrator` as a login that is not a superuser, not the application URL user, and not a role the application can `SET ROLE` into.
2. Transfer ownership of the database, schema `public`, tables, sequences, views, and functions to `stell22_migrator`.
3. Remove superuser, createdb, createrole, and role membership from `stell22`.
4. Grant `stell22` connect, schema usage, and `SELECT`. Revoke `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`, sequence `USAGE` and `UPDATE`, and `CREATE` on `public`.
5. Do this while `stell22` is `NOLOGIN` and after its backends have been terminated, so a pooled superuser session cannot grant the privileges back during the transfer.
6. Restore `LOGIN` only after a canary `INSERT`, `UPDATE`, `DELETE`, `nextval`, and `CREATE TABLE` from `stell22` have failed and a canary `SELECT` has succeeded.
7. Change the operator so the one-shot connects as `stell22_migrator`, and so `apply` re-reads the privilege postcondition immediately before `authorize`. The application URL stays `stell22`.
8. Keep the P1 SQL file unchanged.

The cutover is SQL against the running cluster. It must not be a Prisma migration in the application image. `CREATE ROLE` is not transactional, so any missed postcondition stops the procedure in **UNCERTAIN** and does not grant `LOGIN` back by itself.

Host root and an in-container superuser session can still type SQL. The design does not pretend otherwise. Any such session observed in `pg_stat_activity` during the protected interval makes the state **UNCERTAIN** and forbids spawn. Detection is not the same as prevention. The Owner has to accept that residual before the package can be authorized.

**Result:** this is the recommended design. It is **not implementable on current permissions**. The freeze remains **DESIGN BLOCKED** until the package is separately authorized, implemented, and proven.

## Freeze lifecycle

The states below are the procedure for that later package. Nothing in this task may enter them on production.

An uncertain or failed state stays frozen or stays unreadably logged-in-off. It never returns to `NORMAL` by timeout, crash, expired signature, or a failed migration.

| State | Who may enter | Durable evidence | Writes |
| --- | --- | --- | --- |
| `NORMAL` | Ordinary operation. Not a freeze action. | Current catalog. | Admitted. |
| `FREEZE_REQUESTED` | Owner, in a record outside the database. Operator may not start from a chat message. | Owner decision naming the attempt id and the container ids. | Still admitted. This state is not protection. |
| `DRAINING` | Operator, only after that decision, using the migrator or the image superuser for the cutover statements. | `NOLOGIN` on `stell22`, `pg_stat_activity` showing its backends terminated, lock waiters empty or explicitly aborted. | New logins fail. An open transaction that already wrote can still `COMMIT` until its backend is terminated. Termination rolls that transaction back. |
| `FROZEN_VERIFIED` | Operator only if every postcondition below holds. Otherwise `UNCERTAIN`. | Role attributes, owners, grants, failed canaries, successful `SELECT`, zero non-migrator superuser sessions, container `StartedAt` unchanged. | `stell22` cannot commit a business write. Reads work. |
| `BACKUP_IN_PROGRESS` | Operator `verify-recovery` only from `FROZEN_VERIFIED`. | New attempt backup triple. `pg_dump` must not be the privilege proof. | Same freeze. |
| `RESTORE_VERIFICATION` | Operator, disposable database only. | `RECOVERY_VERIFIED` and the printed digests. | Source freeze unchanged. Disposable writes are not production writes. |
| `AWAITING_OWNER_AUTHORIZATION` | Owner, offline, from the printed digests. | Signed file not yet installed, or installed and not yet accepted. | Freeze unchanged. Absence of a signature does not unfreeze. |
| `P1_APPLY` | Operator `apply`, and only if the pre-spawn privilege recheck still matches `FROZEN_VERIFIED`. | Spawn intent, then the one-shot as `stell22_migrator`. | The migrator may run the pinned P1 DDL. `stell22` still cannot write business data. |
| `P1_POSTCHECK` | Operator after a zero exit. | 46 successful migration rows, P1 objects present, app and db identity unchanged. | Freeze still on. Success does not grant the application its writes back. |
| `UNFREEZE_AUTHORIZED` | Owner, as a separate decision. The apply signature is not that decision. | Owner record plus the reverse grants executed by the migrator. | Writes admitted only after the reverse grants commit and a canary write from `stell22` succeeds. |
| `ERROR` | Any failed check whose catalog postcondition is still the freeze. | The failing command and the re-read catalog. | Stay frozen. |
| `UNCERTAIN` | Partial role change, unexpected superuser session, process death during cutover, or evidence that cannot be re-read. | Whatever catalog rows can still be read. | Fail closed. No spawn. No automatic `LOGIN` or `GRANT`. |

### Admitted writes and draining

There is no application-wide "last write" column. Before `NOLOGIN`, the operator records `pg_stat_activity.xact_start` and `query` for sessions that are `active` or `idle in transaction`, and the `n_tup_ins`, `n_tup_upd`, and `n_tup_del` counters in `pg_stat_user_tables`. After termination, those transactions are aborted, not committed. The last committed business write is the last commit that happened before the terminate calls. The counters after that point are the baseline.

New `stell22` work waits until `LOGIN` returns. It then fails the canaries. Cron and the mail route fail at the database even if HTTP still reaches the process. The in-process cost queue fails when its connection is terminated or its next statement is rejected. A rejection is not SHADOW activation.

Read-only requests from `stell22` are `SELECT` and the health check. Notification sync, mark-read, and cost recalculation are not read-only and must fail.

The only session allowed to run P1 DDL is the one-shot connected as `stell22_migrator`. An application session must not be a member of that role.

The freeze stays in the catalog from `FROZEN_VERIFIED` through restore verification, signing, apply, and postcheck. `verify-recovery` and the second restore inside `apply` do not grant privileges. The interval between them is protected by the catalog, not by the 15-minute signature.

### Owner does not sign, or the signature expires

The signature window is 15 minutes (`SIGNING_WINDOW_MS` in `owner-sign.ts`). The verifier allows at most 24 hours and rejects `now > notAfter` with `AUTHORIZATION_REPLAY` before `replay.consume`. An expired file is not consumed and is not extended.

`apply` calls `executeTrustedRestore` before `authorize` (`execute.ts`). The second disposable restore happens inside the window. This task does not measure that restore on production and does not treat any earlier dump size as a duration. If the restore consumes the window, `authorize` fails, the spawn intent is removed, and Prisma is not started. The freeze stays. The Owner may sign a new payload with a new nonce and a new 15-minute window for the same digests, if a new `apply` still computes those digests. That is a new authorization. It is not an extension of the expired one. The refusal path returns null dossier and recovery hashes, so the Owner must keep the `verify-recovery` transcript.

The backup files are created with `wx` under the attempt directory. The same attempt cannot replace them. A new attempt can take a new backup only while the freeze still holds. A new backup is not an unfreeze.

If the Owner never signs, the state remains `FROZEN_VERIFIED` or `AWAITING_OWNER_AUTHORIZATION`. Return to `NORMAL` requires `UNFREEZE_AUTHORIZED`.

### Process death and failed migration

Killing the operator does not change role attributes. Re-read them. If they still match, remain `FROZEN_VERIFIED`. If they cannot be read, `UNCERTAIN`.

Killing a database backend aborts that transaction. Killing the PostgreSQL container changes `StartedAt` and forbids apply. Privileges stored in the data directory survive that restart. They are not an unfreeze. The new `StartedAt` makes the existing dossier false.

P1 SQL is one explicit transaction. A failed statement rolls the DDL back. Business rows are not restored from the backup, because they were not modified by that statement. If the one-shot is killed after commit and before the postcheck record, the schema may already contain the column, function, and trigger. The unfinished migration row is the ambiguous case already defined by the operator. Do not drop the column. Do not load the pre-migration backup over production. Leave the freeze on, and leave the attempt blocked. A later forward fix is a separate Owner decision.

`scripts/restore-db.sh` remains a hard refusal. This design does not create an automatic production restore.

## Business data the freeze must not roll backwards

Committed rows stay where they are. The cutover grants and the P1 DDL do not `DELETE`, `UPDATE`, or `TRUNCATE` business tables. The P1 column is nullable and has no default and no backfill.

| Area | Invariant during a failed or skipped P1 |
| --- | --- |
| Inventory movements | No new `InventoryMovement` from the application role. Existing SHADOW rows stay. The gate setting stays as it was. |
| Warehouse stock | `BlankStock`, `DetailStock`, `ProductStock`, `NomenclatureStock`, `RailLot`, and `MpStock` quantities are not rewritten by the freeze or by a rolled-back P1. |
| Production operations | No new or corrected `ProductionOperation` and no line edit from the application role. |
| Cost and accounting | `BatchCost`, `ProductCost`, `CostPeriod`, `CostEvent`, and `ChangeLog` are not recalculated by a rejected queue job. A job killed mid-statement rolls back with its transaction. |
| Finance | Accounts, cashflow, statements, payments, and deals are not deleted or imported. |
| Purchases | Batches, commands, and receipts already committed stay. The main-only provenance writer is not in the running image. |
| SHADOW | No activation, deactivation, epoch, or opening balance. |
| Provenance | Absent before P1. Present only if the P1 transaction committed. A later unfreeze does not backfill it. |
| Migration history | `_prisma_migrations` changes only if the migrator commits P1. A rollback leaves the previous successful history. |

An `UPDATE` that the privilege check failed to stop would change these rows without changing `count(*)`. That is why the canary and the grant recheck are mandatory, and why the row-count fingerprint cannot replace them.

## Signing window

The Owner signs after `verify-recovery`, for 15 minutes. `apply` spends part of that window on another disposable restore and on identity checks, and only then verifies the signature.

The freeze has to be in `FROZEN_VERIFIED` before the backup that the signature binds. Otherwise a committed write between dump and apply changes the live aggregate and `apply` stops with `RESTORE_MISMATCH`. The backup of that attempt cannot be replaced.

The signature does not measure, extend, or replace the freeze. This design does not change `SIGNING_WINDOW_MS` or the verifier. It does not move `authorize` earlier, because that would consume a signature before a restore that might fail. That tradeoff can be reconsidered only in a later reviewed operator change.

No production restore duration is claimed here. An overrun is a failed authorization with the freeze left on.

## Failure and recovery

| Event | Required result |
| --- | --- |
| Canary write succeeds | `UNCERTAIN`. Do not back up. Do not sign. |
| `pg_dump` blocks on a lock | Abort the dump. Do not take `ACCESS EXCLUSIVE` to force it. Remain frozen only if the privilege postcondition still holds. |
| Owner silent | Stay frozen. |
| Signature expired | No spawn. Stay frozen. New signature allowed only for digests that still match. |
| Second restore mismatches | No spawn. Stay frozen. Do not repair production from the disposable. |
| `prisma migrate deploy` nonzero | P1 transaction rolled back if PostgreSQL aborted it. Ambiguous if the process was killed. Stay frozen. No second spawn of the same attempt. |
| App process exits | `StartedAt` changes. Stop. Do not treat the entrypoint as the migrator. Do not unfreeze to make the entrypoint succeed. |
| Operator wants the old database back | Not available. No automatic restore. Committed business data is not rolled back. |

## Future test matrix

These tests are not authorized by this task. They belong to a later disposable PostgreSQL 17 package. No production database is a fixture.

Each case needs the historical application image, or a harness that uses its Prisma client, against a database initialized by `postgres:17-alpine` with `POSTGRES_USER=stell22`. The test must record container id, image id, and `StartedAt` before and after, and must show they are unchanged for the app and database containers.

| Case | Pass condition |
| --- | --- |
| Active HTTP write | A `createBatch` or terminal submit that starts before `FROZEN_VERIFIED` either commits before the baseline or rolls back on terminate. A request that starts after the canary gets a database error and commits nothing. |
| Background cron write | POST `/api/cron/fetch-statements` during the freeze commits no statement, cashflow, or cost row. |
| Open transaction | `BEGIN` plus a successful `INSERT` before the cutover, then terminate. The row is absent. `COMMIT` of a statement that already finished, issued before terminate, is the case the drain must not leave behind. |
| Transaction started during the freeze | `BEGIN` and `INSERT` from `stell22` fail. |
| Direct SQL | `psql` as `stell22` cannot `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `nextval`, or `CREATE TABLE`. |
| App role DML | Prisma `create`, `update`, and `delete` from the historical client fail. `findMany` succeeds. |
| Sequence | `nextval` and `setval` fail. A rolled-back earlier `nextval` is recorded as a sequence movement, not as a business insert. |
| DDL as the app | `ALTER TABLE` and `CREATE FUNCTION` as `stell22` fail. |
| Privileged bypass | A session as the image superuser can write. The procedure's evidence marks that session `UNCERTAIN` and does not spawn. |
| Migrator exception | `stell22_migrator` can apply the pinned P1 SQL once. `stell22` cannot. |
| Backup | `pg_dump --no-owner --no-acl` as the role the operator will use completes while only `SELECT` is granted, without an `ACCESS EXCLUSIVE` freeze lock. |
| Restore verification | Disposable restore matches live row counts. An `UPDATE` that preserves counts is detected by the canary evidence even though the fingerprint matches. |
| SIGKILL | Kill the cutover client after `NOLOGIN` and before `LOGIN`. A new client re-reads `UNCERTAIN` and does not grant `LOGIN`. Kill the operator during apply. The catalog stays frozen. |
| Evidence corruption | A missing or edited freeze record prevents spawn even if the dossier matches. |
| Expired authorization | `authorize` at one millisecond after `notAfter` does not consume replay and does not spawn. The frozen grants remain. |
| Failed migration | Abort the P1 transaction. Business counts match the backup. The column is absent. |
| Safe manual recovery | From `UNCERTAIN`, a human re-reads `pg_roles` and `relowner` and stops. No script grants writes. |
| Controlled unfreeze | Only the Owner record plus the migrator reverse grants. A canary write then succeeds. Container identity is still unchanged. |

Zero unauthorized commits means all of the following, not any one of them:

- The canaries failed for the whole interval.
- `pg_stat_activity` shows no `stell22` session whose transaction is not read-only, and no superuser session other than the recorded migrator.
- `n_tup_ins`, `n_tup_upd`, and `n_tup_del` for public business tables do not move, except for the migrator's P1 DDL if a test shows that DDL itself changes a counter. That exception has to be named from the test output, not assumed.
- `count(*)` matches the backup.
- A table checksum or equivalent tuple hash, taken as a read after the freeze and again before spawn, matches. The current operator does not compute this hash. The later package has to add it. Row counts alone are not the proof.

Container identity is `docker inspect` of the app and database containers: id, image id, `State.StartedAt`, and the daemon id, equal before `DRAINING` and after `P1_POSTCHECK`.

## Implementation boundary

| Question | Answer |
| --- | --- |
| Recommended mechanism | Design D, after a role split. Blocked today. |
| New database roles | Yes. `stell22_migrator` owner. `stell22` reader. Required before any production freeze. |
| Prisma schema migration | No. Do not edit the P1 `migration.sql`. Do not add a migration the historical entrypoint would run. |
| Application maintenance deploy | Not required for enforcement and not sufficient. Forbidden inside the protected interval. |
| Operator change | Required so the one-shot uses the migrator and rechecks grants before `authorize`. Host checkout only. Still not authorized. |
| Order | Disposable proof. Reviewed operator change. Separately authorized catalog cutover. Rehearsed freeze. Only then a production `verify-recovery`. P1 `apply` stays behind the existing gates as well. |
| Production identity | App image, both container ids, both `StartedAt` values, and the daemon id stay constant. The catalog of roles changes. The dossier does not record that change, so the freeze record has to. |
| Unproven | Live `rolsuper` and ownership. Host cron. Mail environment. Open production transactions. That a terminated pool does not exit Node. That a demoted no-op `migrate deploy` exits 0. Production restore duration. Any `SECURITY DEFINER` function outside migrations. |

## Owner decisions required

1. Accept or reject design D as the direction. Rejection leaves P1-3 blocked with no alternative in the current architecture.
2. Authorize, later and separately, creation of `stell22_migrator` and demotion of `stell22` on production. This record does not authorize it.
3. Accept the residual that host root and the image superuser can write, with spawn forbidden if such a session appears.
4. Accept that an application crash during the freeze can leave the historical entrypoint unable to start until an Owner unfreeze, and that this changes `StartedAt` and aborts the attempt.
5. Confirm that a successful P1 postcheck does not itself unfreeze writes.
6. Confirm that an expired or missing signature leaves the database frozen.
7. Confirm that a failed P1 is forward-fix only. No production restore and no drop of a committed column.
8. Decide later whether the signed payload should grow a freeze digest. This design does not add one and does not lengthen the 15-minute window.
