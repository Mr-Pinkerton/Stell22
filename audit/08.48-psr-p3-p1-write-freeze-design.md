## Verdict

No mechanism that exists in the running architecture meets the freeze gate.

The application and the P1 one-shot use one login, `stell22`. `docker-compose.prod.yml` sets `POSTGRES_USER=stell22` on `postgres:17-alpine`. The current published Docker entrypoint initializes an empty data directory with `initdb --username="$POSTGRES_USER"`. PostgreSQL 17 `initdb` documents `--username` as the name of the bootstrap superuser, and it always creates databases named `postgres`, `template1`, and `template0`. Those are database names. They are not a role named `postgres`. This repository does not vendor that entrypoint, and this task did not read `pg_authid`. Whether the running cluster has any superuser besides `stell22` is **UNKNOWN**.

Design D in this file is a **candidate**. HEAD has not accepted it as the production architecture. The Owner has not approved a role split.

A superuser bypasses `REVOKE`. The bootstrap superuser cannot be altered to `NOSUPERUSER`. A table owner who is not a superuser can grant a revoked privilege back. `default_transaction_read_only` applies to new sessions only, and any session can turn it off. The running image has no write-admission flag. Adding one replaces the application image and changes `StartedAt`.

Until a later disposable proof exists, and until the Owner separately accepts a permanent split, the write-freeze is **DESIGN BLOCKED**.

## R1 — transaction semantics

The first draft said `CREATE ROLE` and `ALTER ROLE` cannot run inside a transaction block. That is false for PostgreSQL 17.

Primary references:

- PostgreSQL 17 `CREATE ROLE` does not say the command is prohibited in a transaction block: [sql-createrole](https://www.postgresql.org/docs/17/sql-createrole.html).
- PostgreSQL 17 `ALTER ROLE` likewise has no such prohibition: [sql-alterrole](https://www.postgresql.org/docs/17/sql-alterrole.html). It does say that a role-specific configuration value is applied only when a session logs in, not on `SET ROLE`.
- Commands that are prohibited say so. `CREATE DATABASE` "cannot be executed inside a transaction block": [sql-createdatabase](https://www.postgresql.org/docs/17/sql-createdatabase.html). `VACUUM` has the same sentence: [sql-vacuum](https://www.postgresql.org/docs/17/sql-vacuum.html). `ALTER DATABASE ... SET TABLESPACE` has it: [sql-alterdatabase](https://www.postgresql.org/docs/17/sql-alterdatabase.html). `ALTER DATABASE ... OWNER TO` does not.
- PostgreSQL 17.0 `src/backend/tcop/utility.c` on `REL_17_STABLE` calls `PreventInTransactionBlock` for `COMMIT PREPARED`, `ROLLBACK PREPARED`, `CREATE TABLESPACE`, `DROP TABLESPACE`, `CREATE DATABASE`, `DROP DATABASE`, `ALTER SYSTEM`, `ALTER TABLE ... DETACH CONCURRENTLY`, `CREATE INDEX CONCURRENTLY`, and `DROP INDEX CONCURRENTLY`. `T_CreateRoleStmt`, `T_AlterRoleStmt`, `T_AlterRoleSetStmt`, `T_DropRoleStmt`, `T_GrantStmt`, `T_GrantRoleStmt`, `T_AlterOwnerStmt`, and `T_ReassignOwnedStmt` are not in that set.
- `src/backend/commands/user.c` on the same tag refuses `NOSUPERUSER` when `roleid == BOOTSTRAP_SUPERUSERID`, with the detail "The bootstrap superuser must have the SUPERUSER attribute." The `ALTER ROLE` manual states the same limit.

`GRANT`, `REVOKE`, `ALTER ... OWNER TO`, `REASSIGN OWNED`, and `ALTER DEFAULT PRIVILEGES` are ordinary catalog updates. In one transaction they commit together or roll back together. Another session does not see them before `COMMIT`. After `COMMIT`, another backend sees them at its next command boundary, when it processes catalog invalidation. A statement already running is not restarted. A transaction that already executed a successful `INSERT` can still `COMMIT` that work after the revoke becomes visible.

`pg_terminate_backend` is a function. PostgreSQL 17 [functions-admin](https://www.postgresql.org/docs/17/functions-admin.html) says it sends `SIGTERM`. The signal is sent when the function executes. `ROLLBACK` of the calling transaction does not recreate the session. Only a superuser can terminate a superuser backend. A role with `pg_signal_backend`, or a member of the target role, can terminate a non-superuser backend of that role. Call it only after the privilege transaction has committed.

`nextval` consumes a sequence value even if the surrounding transaction rolls back. That is a sequence movement, not a committed business row.

Unavoidable windows:

1. After the privilege `COMMIT` and before every old backend has been terminated, a transaction that already wrote can commit, and a statement that started before invalidation can finish under the old rights.
2. `pg_terminate_backend` is a separate step. A crash between `COMMIT` and the termination leaves the new privileges in place and the old sessions alive. That state is **UNCERTAIN** until the sessions are gone and the privileges are re-read.
3. Switching the application from the bootstrap login to a non-superuser login changes the app container environment and therefore `StartedAt`. That switch is not inside the protected interval. It is an earlier package.
4. The signed dossier does not include role attributes. A grant change that preserves row counts does not change `recoverySha256`.

## Administrator model

Three identities, and they are not interchangeable.

| Identity | Attributes | What it is for |
| --- | --- | --- |
| Break-glass administrator | `LOGIN`, `SUPERUSER`, not the application URL, not the migrator | Create roles, terminate backends, recover from a failed cutover. Provisioned and proven before any other role change. |
| `stell22_migrator` | `LOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOBYPASSRLS`, `NOREPLICATION`, `NOINHERIT` | Own the database objects and run the pinned P1 DDL. Not a member of the administrator. |
| Application role | `LOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOBYPASSRLS`, `NOREPLICATION`, `NOINHERIT` | The only login in the application `DATABASE_URL` after a future cutover. During a freeze it has `SELECT` and no write path. |

No role membership joins the application to the migrator or to the administrator. No `ADMIN` option and no `SET` option point that way. A superuser can still `SET ROLE` to either of them. The application must not be a superuser, so it cannot.

The published entrypoint does not create this administrator. If `POSTGRES_USER` is `stell22`, `initdb --username=stell22` makes `stell22` the bootstrap superuser, and PostgreSQL will reject `ALTER ROLE stell22 NOSUPERUSER`. The candidate therefore does not demote `stell22`. It stops using `stell22` as the application login. Whether the live cluster matches that initialization is **UNKNOWN**. A disposable test has to show the error, or show that this cluster is not that case. Production SQL is not that test.

Provisioning order, later, on a disposable cluster first:

1. Connect as the existing superuser. Create the break-glass role in its own committed transaction. Store its secret outside the repository, outside the application container, and outside the operator credential directory. This document contains no secret.
2. Open a second connection that authenticates as the break-glass role and can `CREATE ROLE`. If that connection fails, stop. Do not create the migrator, do not transfer ownership, and do not change `stell22`.
3. From the break-glass session, create the migrator and the application role and transfer ownership in one transaction. `ROLLBACK` on any error.
4. Only a later, separately authorized application change may put the application role into `DATABASE_URL`. That change recreates `stell22-app` and changes `StartedAt`. It is not part of P1 apply.

Who terminates backends: the break-glass superuser. The migrator cannot terminate a remaining superuser session.

Who may restore rights: the break-glass superuser. The migrator owns the objects, so it can also `GRANT` them. Its secret is therefore an unfreeze secret and stays out of the application environment. Restoring rights is an Owner decision. It is not a timeout and not a successful postcheck.

If the break-glass secret or its `SUPERUSER` attribute is missing, the procedure does not start. If it is lost after a split, the state is **UNCERTAIN / NO-GO**. There is no automatic grant, no production restore, and no schema rollback.

## NOLOGIN and canaries

The first draft told tests to `SELECT` and write as `stell22` while that role was `NOLOGIN`. A connection attempt in that state fails authentication. It never reaches a privilege check. That is not a canary.

`LOGIN` / `NOLOGIN` controls only the initial session authorization name. [CREATE ROLE](https://www.postgresql.org/docs/17/sql-createrole.html) says a role without `LOGIN` cannot be used as the initial role of a connection. [SET ROLE](https://www.postgresql.org/docs/17/sql-set-role.html) is different: a superuser may `SET ROLE` to a `NOLOGIN` role, and privilege checks then use that role. `SET ROLE` does not apply `ALTER ROLE ... SET` configuration values. Those apply at login.

The candidate does not use `NOLOGIN` as the freeze. `LOGIN` stays set on the application role.

Sequence after the application is already using the non-superuser role, and after a single transaction has revoked its write privileges and committed:

1. Terminate application-role backends. Confirm `pg_stat_activity` has no remaining session of that role in a transaction, and no unexpected superuser session.
2. From the break-glass session, `SET ROLE` to the application role. `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `nextval`, and `CREATE TABLE` must fail with insufficient privilege. `SELECT` must succeed. `RESET ROLE` afterwards. This is an effective-privilege check, not a login check.
3. Open a new network connection as the application role. Authentication must succeed. The same write statements must fail with insufficient privilege, and `SELECT` must succeed. An authentication error is a failed test, not a passed canary.
4. Re-read grants, owners, memberships, `rolsuper`, `rolbypassrls`, and `rolcanlogin` in the same administrator session. If they still match, record `FROZEN_VERIFIED`. If a grant reappeared, the state is **UNCERTAIN**.

New application sessions between the revoke commit and this re-read have the revoked privileges. They do not reopen writes unless something grants the privileges back. The application role must not be able to grant them. The re-read is what makes the freeze verified.

## Permanent split and application restart

This is not a temporary maintenance mode. After the split, ordinary business writes return only by `GRANT` to the non-superuser application role. Ownership stays with the migrator. `SUPERUSER` stays with the bootstrap role and the break-glass role. Putting `SUPERUSER` back on the application role would recreate the hole this design exists to close.

`docker-entrypoint.sh` in the historical application and on this `main` is unchanged: `npx prisma migrate deploy`, then the server, with `set -e`. Prisma's current `migrate deploy` description says it applies pending migrations and does not look for drift ([Prisma CLI reference](https://www.prisma.io/docs/orm/reference/prisma-cli-reference)). `migrate status` is a different command and does report history that is not in the local directory. This task did not run either command as a restricted role.

Consequences the disposable packages have to measure, not assume:

| Situation | What must be recorded |
| --- | --- |
| Application role is not superuser and does not own tables, no pending migration in the image | Exit code of `prisma migrate deploy`. If it is non-zero, the entrypoint exits, Compose restarts the container, `StartedAt` changes, and the site stays down while the command keeps failing. |
| Restart before P1 | Same measurement on a database whose migration history matches the historical image. |
| Restart after P1 | The historical image does not contain the P1 migration directory. `migrate deploy` says it does not look for drift. The package still records the exit code. A failure here means the application cannot return until a later image or entrypoint change, which is another deploy. |
| Pool terminated | In-flight transactions roll back. The process staying up is unproven. A process exit changes `StartedAt`. |
| Business write | Must fail for the application role during the freeze and succeed only after the Owner's unfreeze grant. |
| Notification poll | `getNotifications` and `pollNotifications` upsert and delete `Notification`. They are writes. During the freeze they fail even though the operator may think of them as reads. The screen errors until unfreeze. That is an operational consequence, not a reason to leave those writes allowed. |

Return to ordinary operation requires all of the following: the entrypoint's `migrate deploy` exits 0 as the application role; the application can `SELECT` and, after unfreeze, perform its real writes including sequences and the notification sync; `pg_dump` with the operator's `--no-owner --no-acl` succeeds as the role that will run it; the migrator can apply P1; the application cannot `SET ROLE` to the migrator. None of that is proven.

## Completeness of the candidate split

Before `FROZEN_VERIFIED`, a re-read has to show every line below. A missing line is **UNCERTAIN**, not a freeze.

- Database owner is the migrator. Schema `public` owner is the migrator.
- Every table, sequence, view, materialized view, function, and type in `public` that the application used to own is owned by the migrator. Extensions are listed. A non-superuser migrator cannot `CREATE EXTENSION`. P1 does not create one. A later migration that does needs the break-glass role, not the migrator.

Whether `pg_dump --no-owner --no-acl` still dumps sequence state with only `SELECT` is a disposable proof. If it does not, the dump role for the backup has to be the migrator, and that choice is recorded. It is not assumed.
- `ALTER DEFAULT PRIVILEGES` for the migrator grants the application role `SELECT` on future tables and does not grant write privileges. Defaults left behind for the old owner that would grant write to `PUBLIC` or to the application role are revoked.
- No `SECURITY DEFINER` function executable by the application role can write. The P1 function is not `SECURITY DEFINER`. It is not in production yet. Any other function in the live catalog is **UNKNOWN** until listed.
- The application role is not a member of the migrator or the administrator, with or without `INHERIT`, `SET`, or `ADMIN`.
- `rolsuper`, `rolcreatedb`, `rolcreaterole`, `rolreplication`, and `rolbypassrls` are false for the application role and the migrator.
- The migrator can `INSERT` and `UPDATE` `_prisma_migrations`, and can `ALTER TABLE`, `CREATE FUNCTION`, and `CREATE TRIGGER` on `BatchCreationCommand`. That is the P1 requirement. The application role cannot.
- `pg_dump` as chosen above completes, and a restore of that dump matches the source row counts on a disposable server.

`count(*)`, `pg_stat_user_tables` counters, and a handful of canaries do not prove that no business write committed. Counters can be reset by a superuser. Canaries prove only the statements that were tried. The later proof package has to compare a full logical data snapshot taken at `FROZEN_VERIFIED` with the same snapshot taken immediately before spawn. This operator does not compute that snapshot today.

## Database privilege assessment

### What the repository actually configures

`docker-compose.prod.yml` sets `POSTGRES_USER=stell22`, `POSTGRES_DB=stell22`, image `postgres:17-alpine`, and no published database port. The app URL uses the same user. The adapter constant `PRODUCTION_ROLE_NAME` is `stell22`. `identity.ts` rejects any other observed role. There is no migrator role, no `NOSUPERUSER` statement, and no grant script in the repository.

Prisma migrations run as that same user, from the entrypoint on the historical image and from the one-shot on a future P1 apply. P1 DDL is `ALTER TABLE`, `CREATE FUNCTION`, and `CREATE TRIGGER` on `BatchCreationCommand`. The one-shot has `connect_timeout=5` and no `lock_timeout`.

### PostgreSQL 17 behavior that blocks a privilege-only freeze

These are engine rules. They are not production measurements. A disposable PostgreSQL 17 test must reproduce them before any later package is trusted.

- A superuser passes table privilege checks. `REVOKE INSERT, UPDATE, DELETE` does not stop it.
- The owner of a table can revoke their own ordinary privileges and can grant them back. `REVOKE` against the owner is reversible by that owner.
- `ALTER ROLE ... SET default_transaction_read_only = on` and the same setting at database level are copied into a session at login. Existing pooled sessions keep their current value.
- `default_transaction_read_only` is user-settable. The application role can execute `SET default_transaction_read_only TO off`.
- A transaction that has already started read-write is not changed by a later default. A prepared `INSERT` executed inside that transaction still writes. `COMMIT` does not re-check the privilege of a statement that already succeeded.
- `nextval` and `setval` are writes. Table `REVOKE` does not cover them. A read-only transaction does reject `nextval`. Sequence values survive rollback, so a drained transaction can still move a sequence without changing a row count.
- A `SECURITY DEFINER` function owned by a writing role would run with that role's rights. The only function in migrations is not security-definer and is not deployed. Any other function in the live catalog is **UNKNOWN** and must fail closed if found.
- The database owner can create objects in `public`. A new table created during a freeze would be writable by its owner. `REVOKE` on existing tables does not prevent that.
- `CREATE ROLE`, `ALTER ROLE`, `GRANT`, `REVOKE`, and `ALTER ... OWNER TO` can run in one transaction and commit or roll back together. See the R1 section. A crash before `COMMIT` rolls that transaction back. A crash after `COMMIT` and before backend termination leaves the new privileges and the old sessions. That is **UNCERTAIN**.
- `ALTER ROLE stell22 NOSUPERUSER` is rejected when `stell22` is the bootstrap superuser. The candidate does not demote it.
- `pg_terminate_backend` sends `SIGTERM` when the function runs. It aborts the target transaction. It does not restart the postmaster, so container `StartedAt` does not change because of that call. `ROLLBACK` of the caller does not bring the session back. Call it after the privilege `COMMIT`. The pool then reconnects. Without a privilege change, the new session writes again.
- `ALTER TABLE ... OWNER TO` and the P1 `ADD COLUMN` each need `ACCESS EXCLUSIVE` on the affected table. `pg_dump` needs `ACCESS SHARE`. A freeze that holds `ACCESS EXCLUSIVE` for the whole window blocks the backup and can deadlock the migration. Long-lived `ACCESS EXCLUSIVE` locks are not the freeze.
- PostgreSQL 17 login event triggers run at connect. They do not stop a superuser, or the table owner, from turning a GUC off afterwards.

`catalog.ts` compares `count(*)` for every public table except `_prisma_migrations`. An `UPDATE` that preserves the count, including a stock-quantity change or a notification text update, does not change `aggregateFingerprint`. Row-count equality is required and is not proof that no business write committed.

The signed dossier binds container identity, `StartedAt`, and the one-shot image id. It does not bind `rolsuper`, grants, or owners. A privilege change is invisible to `dossierSha256`. A privilege reversal that preserves row counts is invisible to `recoverySha256`. The current `apply` path does not re-read grants before `authorize`.

### Migrator identity

`planProductionOneShot` puts `roleName` into the one-shot URL. Production requires that name to be `stell22`. Freezing `stell22` with a control that actually works also freezes the only role the merged operator can use for P1 DDL.

A distinct migrator is a new role plus an operator change that accepts it. That change edits the host-run operator. It does not by itself replace the application image. It is still a prerequisite, and it is not authorized here. Putting the role change inside `migration.sql` would change the pinned P1 checksum and would hide the security change inside the migration. That is rejected.

### Backup and the entrypoint

`pg_dump --no-owner --no-acl` can run with `SELECT` if the later test proves it. Ownership is not part of the dump or of the row-count fingerprint.

If the application container exits, `docker-entrypoint.sh` runs `prisma migrate deploy` before the server. On the historical image that command uses the migrations baked into that image. It does not contain the P1 file. The exit code as the non-superuser application role is **UNPROVEN**. A failed entrypoint exits the process, Compose restarts it, and `StartedAt` changes. The attempt must then stop. The restart is not an unfreeze.

## Design comparison

### A. Application maintenance mode

The running source has no maintenance flag, no write gate, and no mounted file that the server reads before a mutation. `Caddyfile` proxies every request to `app:3000`.

Shipping a gate means a new application image and a new container start. That changes `StartedAt` and the image id, so it cannot happen inside the protected interval. It is a separate deploy, which remains **NOT AUTHORIZED**, and it still does not stop `psql`, `docker exec`, or a connection that reaches `app:3000` on the Docker network.

Caddy can be reloaded without recreating the app or database containers. A proxy rule is not admission control inside the database. In-flight requests already inside Node continue. The notification poll and every other Server Action are POST, so a blunt POST block also blocks ordinary reads through the UI. Direct database sessions do not pass Caddy.

**Result:** does not meet the gate. Not sufficient even after a future deploy.

### B. Database restriction with the current role

`REVOKE` and `default_transaction_read_only` do not bind a superuser, do not stop an already-open writing transaction, and do not leave a second identity for P1 DDL. `NOLOGIN` blocks authentication. It does not test privileges, and it does not remove rights from a session that is already connected.

**Result:** does not meet the gate. Rejected as a complete freeze.

### C. Hybrid of A and B on the current system

There is no application control to coordinate with, and the database control does not hold. A hybrid of two insufficient controls is not a third control.

**Result:** does not meet the gate.

### D. Candidate later architecture

This is a candidate, not an accepted architecture. It is the only shape found so far that could meet the gate, and only after packages that do not exist and are not authorized.

1. Prove a break-glass superuser that is not the application login. If that proof fails, stop.
2. In one transaction, create `stell22_migrator` and a non-superuser application role, transfer ownership, and set grants. Do not `ALTER ROLE` the bootstrap superuser to `NOSUPERUSER`.
3. A later application package points `DATABASE_URL` at the application role. That recreates the app container. It is not inside the freeze window. `stell22` remains the bootstrap superuser and is no longer the application login.
4. A freeze, on that new identity, is one transaction that revokes the application role's write privileges, then a commit, then termination of that role's backends, then the canary sequence in the R1 section. `LOGIN` stays on.
5. The operator one-shot connects as `stell22_migrator` and re-reads the privilege postcondition immediately before `authorize`.
6. The P1 SQL file stays unchanged.

Host root and any remaining superuser session can still type SQL. Such a session during the protected interval is **UNCERTAIN** and forbids spawn.

**Result:** candidate only. **DESIGN BLOCKED** on the current login. Not Owner-approved.

## Freeze lifecycle

The states below are the procedure for that later package. Nothing in this task may enter them on production.

An uncertain or failed state stays frozen. It never returns to `NORMAL` by timeout, crash, expired signature, or a failed migration. It does not clear `LOGIN` and it does not grant rights back.

| State | Who may enter | Durable evidence | Writes |
| --- | --- | --- | --- |
| `NORMAL` | Ordinary operation after a permanent split, or today's single login. Not a freeze action. | Current catalog. | Admitted for the application role. |
| `FREEZE_REQUESTED` | Owner, in a record outside the database. The operator may not start from a chat message. | Owner decision naming the attempt id, the container ids, and that the application login is already the non-superuser role. | Still admitted. This state is not protection. |
| `REVOKE_COMMITTED` | Break-glass administrator, one transaction, then `COMMIT`. | The transaction committed. Grants re-read as the freeze postcondition. | New statements see the revoke at their next command boundary. An already-executed write can still commit. |
| `DRAINING` | Break-glass administrator, only after that commit. | `pg_terminate_backend` for application-role sessions, then no such session left in a transaction. | Termination rolls back uncommitted work. `LOGIN` stays on. A new login has the revoked rights. |
| `FROZEN_VERIFIED` | Operator only if the canary sequence and the full postcondition hold. Otherwise `UNCERTAIN`. | `SET ROLE` denial, a real login denial of writes, successful `SELECT`, logical snapshot, no unexpected superuser session, `StartedAt` unchanged. | The application role cannot commit a business write. Reads work. |
| `BACKUP_IN_PROGRESS` | Operator `verify-recovery` only from `FROZEN_VERIFIED`. | New attempt backup triple. `pg_dump` is not the privilege proof. | Same freeze. |
| `RESTORE_VERIFICATION` | Operator, disposable database only. | `RECOVERY_VERIFIED` and the printed digests. | Source freeze unchanged. |
| `AWAITING_OWNER_AUTHORIZATION` | Owner, offline, from the printed digests. | Signed file not yet accepted. | Freeze unchanged. Silence does not unfreeze. |
| `P1_APPLY` | Operator `apply`, only if the pre-spawn recheck still matches `FROZEN_VERIFIED`. | Spawn intent, then the one-shot as `stell22_migrator`. | The migrator may run the pinned P1 DDL. The application role still cannot write business data. |
| `P1_POSTCHECK` | Operator after a zero exit. | 46 successful migration rows, P1 objects present, app and db identity unchanged. | Freeze still on. Success does not grant writes back. |
| `UNFREEZE_AUTHORIZED` | Owner, as a separate decision. The apply signature is not that decision. | Owner record plus grants from the break-glass role. | Writes return only after those grants commit and a real login can write. The role split remains. |
| `ERROR` | A failed check whose catalog is still the freeze. | The failing command and the re-read catalog. | Stay frozen. |
| `UNCERTAIN` | Missing break-glass proof, crash after commit and before drain, unexpected superuser session, or evidence that cannot be re-read. | Whatever catalog rows can still be read. | Fail closed. No spawn. No automatic `GRANT`. |

### Admitted writes and draining

There is no application-wide "last write" column. The last committed business write is the last commit that completed before the application backends were terminated. Counters in `pg_stat_user_tables` are recorded, and they are not the proof. The proof is the logical snapshot plus the privilege re-read.

Cron, mail intake, the cost queue, and notification sync fail at the database when their next statement is rejected. A rejection is not SHADOW activation. `SELECT` and the health check stay reads. Notification sync is not a read.

The only session allowed to run P1 DDL is the one-shot connected as `stell22_migrator`. An application session must not be a member of that role.

The freeze stays in the catalog from `FROZEN_VERIFIED` through restore verification, signing, apply, and postcheck. `verify-recovery` and the second restore inside `apply` do not grant privileges. The interval between them is protected by the catalog, not by the 15-minute signature.

### Owner does not sign, or the signature expires

The signature window is 15 minutes (`SIGNING_WINDOW_MS` in `owner-sign.ts`). The verifier allows at most 24 hours and rejects `now > notAfter` with `AUTHORIZATION_REPLAY` before `replay.consume`. An expired file is not consumed and is not extended.

`apply` calls `executeTrustedRestore` before `authorize` (`execute.ts`). The second disposable restore happens inside the window. This task does not measure that restore on production and does not treat any earlier dump size as a duration. If the restore consumes the window, `authorize` fails, the spawn intent is removed, and Prisma is not started. The freeze stays. The Owner may sign a new payload with a new nonce and a new 15-minute window for the same digests, if a new `apply` still computes those digests. That is a new authorization. It is not an extension of the expired one. The refusal path returns null dossier and recovery hashes, so the Owner must keep the `verify-recovery` transcript.

The backup files are created with `wx` under the attempt directory. The same attempt cannot replace them. A new attempt can take a new backup only while the freeze still holds. A new backup is not an unfreeze.

If the Owner never signs, the state remains `FROZEN_VERIFIED` or `AWAITING_OWNER_AUTHORIZATION`. Return to `NORMAL` requires `UNFREEZE_AUTHORIZED`.

### Process death and failed migration

Killing the operator does not change role attributes. Re-read them. If they still match, remain `FROZEN_VERIFIED`. If they cannot be read, `UNCERTAIN`.

Killing a database backend aborts that transaction. Killing the PostgreSQL container changes `StartedAt` and forbids apply. Privileges stored in the data directory survive that restart. They are not an unfreeze. The new `StartedAt` makes the existing dossier false.

P1 SQL is one explicit transaction. A failed statement rolls the DDL back. Business rows are not restored from the backup, because they were not modified by that statement. If the one-shot is killed after commit and before the postcheck record, the schema may already contain the column, function, and trigger. The unfinished migration row is the ambiguous case already defined by the operator. Do not drop the column. Do not load the pre-migration backup over production. Leave the freeze on, and leave the attempt blocked. A later forward fix is a separate Owner decision.

`scripts/restore-db.sh` remains a hard refusal. This design does not create an automatic production restore.

## Business data the freeze must not roll backwards

Committed rows stay where they are. The cutover grants and the P1 DDL do not `DELETE`, `UPDATE`, or `TRUNCATE` business tables. The P1 column is nullable and has no default and no backfill.

| Area | Invariant during a failed or skipped P1 |
| --- | --- |
| Inventory movements | No new `InventoryMovement` from the application role. Existing SHADOW rows stay. The gate setting stays as it was. |
| Warehouse stock | `BlankStock`, `DetailStock`, `ProductStock`, `NomenclatureStock`, `RailLot`, and `MpStock` quantities are not rewritten by the freeze or by a rolled-back P1. |
| Production operations | No new or corrected `ProductionOperation` and no line edit from the application role. |
| Cost and accounting | `BatchCost`, `ProductCost`, `CostPeriod`, `CostEvent`, and `ChangeLog` are not recalculated by a rejected queue job. A job killed mid-statement rolls back with its transaction. |
| Finance | Accounts, cashflow, statements, payments, and deals are not deleted or imported. |
| Purchases | Batches, commands, and receipts already committed stay. The main-only provenance writer is not in the running image. |
| SHADOW | No activation, deactivation, epoch, or opening balance. |
| Provenance | Absent before P1. Present only if the P1 transaction committed. A later unfreeze does not backfill it. |
| Migration history | `_prisma_migrations` changes only if the migrator commits P1. A rollback leaves the previous successful history. |

An `UPDATE` that the privilege check failed to stop would change these rows without changing `count(*)`. That is why the canary and the grant recheck are mandatory, and why the row-count fingerprint cannot replace them.

## Signing window

The Owner signs after `verify-recovery`, for 15 minutes. `apply` spends part of that window on another disposable restore and on identity checks, and only then verifies the signature.

The freeze has to be in `FROZEN_VERIFIED` before the backup that the signature binds. Otherwise a committed write between dump and apply changes the live aggregate and `apply` stops with `RESTORE_MISMATCH`. The backup of that attempt cannot be replaced.

The signature does not measure, extend, or replace the freeze. This design does not change `SIGNING_WINDOW_MS` or the verifier. It does not move `authorize` earlier, because that would consume a signature before a restore that might fail. That tradeoff can be reconsidered only in a later reviewed operator change.

No production restore duration is claimed here. An overrun is a failed authorization with the freeze left on.

## Failure and recovery

| Event | Required result |
| --- | --- |
| Break-glass connection cannot be proved | Do not start. No roles are created. |
| Privilege transaction errors or the client dies before `COMMIT` | PostgreSQL rolls the transaction back. Re-read. If the catalog is unchanged, remain at the previous state. |
| Crash after `COMMIT` and before drain | `UNCERTAIN`. Do not grant. Do not spawn. Terminate leftover application sessions only after the re-read shows the freeze grants. |
| Ownership transfer fails inside the transaction | The whole transaction rolls back. No partial owner list from that attempt. |
| A grant to the application role reappears | `UNCERTAIN`. No backup. No signature. |
| Break-glass secret missing after the split | `UNCERTAIN / NO-GO`. No automatic recovery. |
| Canary write succeeds, or the login fails authentication | `UNCERTAIN`. An authentication failure is not a passed `SELECT` canary. |
| `pg_dump` blocks on a lock | Abort the dump. Do not take `ACCESS EXCLUSIVE` to force it. |
| Owner silent, or the signature expires | No spawn. Stay frozen. A new signature is a new payload, and only if the digests still match. |
| Second restore mismatches | No spawn. Stay frozen. Do not repair production from the disposable. |
| App process exits | `StartedAt` changes. Stop. Do not treat the entrypoint as the migrator. Do not grant rights so the entrypoint can succeed. |
| P1 statement fails inside its transaction | DDL rolls back. Business rows are not restored from backup, because that statement did not change them. Stay frozen. |
| P1 commits and the postcheck record is lost | Schema may already contain the column, function, and trigger. Do not drop them. Do not load the pre-migration backup. Leave the attempt blocked and the freeze on. |
| Freeze lasts longer than expected | It stays. Duration is not an unfreeze. |
| Controlled return of business writes | Owner decision, then break-glass `GRANT` of the ordinary DML and sequence rights. Not superuser. Not a return of ownership. |
| Operator wants the old database back | Not available. No automatic restore. No schema rollback. |

## Future test matrix

These tests are not authorized by this task. They belong to a later disposable PostgreSQL 17 package. No production database is a fixture.

Each case needs the historical application image, or a harness that uses its Prisma client, against a database initialized by `postgres:17-alpine` with `POSTGRES_USER=stell22`. The test must record container id, image id, and `StartedAt` before and after, and must show they are unchanged for the app and database containers.

| Case | Pass condition |
| --- | --- |
| Active HTTP write | A `createBatch` or terminal submit that starts before `FROZEN_VERIFIED` either commits before the baseline or rolls back on terminate. A request that starts after the canary gets a database error and commits nothing. |
| Background cron write | POST `/api/cron/fetch-statements` during the freeze commits no statement, cashflow, or cost row. |
| Open transaction | `BEGIN` plus a successful `INSERT` before the cutover, then terminate. The row is absent. `COMMIT` of a statement that already finished, issued before terminate, is the case the drain must not leave behind. |
| Role transaction | `BEGIN; CREATE ROLE ...; ALTER ROLE ...; GRANT ...; REVOKE ...; ALTER ... OWNER TO ...; ROLLBACK` leaves no role and no owner change. The same statements in one `COMMIT` appear together. `CREATE DATABASE` inside the block fails and is not used. `ALTER ROLE` of the bootstrap superuser to `NOSUPERUSER` fails, and that failure rolls the test transaction back. |
| Transaction started during the freeze | A new login as the application role authenticates. `BEGIN` and `INSERT` then fail with insufficient privilege. |
| Direct SQL | `psql` as the application role cannot `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `nextval`, or `CREATE TABLE`. The same session's `SELECT` succeeds. |
| App role DML | Prisma `create`, `update`, and `delete` from the historical client, pointed at the application role, fail. `findMany` succeeds. Notification sync fails. |
| Sequence | `nextval` and `setval` fail. A rolled-back earlier `nextval` is recorded as a sequence movement, not as a business insert. |
| DDL as the app | `ALTER TABLE` and `CREATE FUNCTION` as the application role fail. |
| Privileged bypass | A session as the bootstrap superuser or the break-glass role can write. The procedure marks that session `UNCERTAIN` and does not spawn. |
| Migrator exception | `stell22_migrator` can apply the pinned P1 SQL once. The application role cannot. The application role cannot `SET ROLE` to the migrator. |
| Backup | `pg_dump --no-owner --no-acl` as the role the operator will use completes while only `SELECT` is granted, without an `ACCESS EXCLUSIVE` freeze lock. |
| Restore verification | Disposable restore matches live row counts. An `UPDATE` that preserves counts is caught by the logical snapshot, not by `count(*)` alone. |
| SIGKILL | Kill the cutover client after `COMMIT` and before drain. A new client re-reads `UNCERTAIN` and does not `GRANT`. Kill the operator during apply. The catalog stays frozen. |
| Evidence corruption | A missing or edited freeze record prevents spawn even if the dossier matches. |
| Expired authorization | `authorize` at one millisecond after `notAfter` does not consume replay and does not spawn. The frozen grants remain. |
| Failed migration | Abort the P1 transaction. Business counts match the backup. The column is absent. |
| Safe manual recovery | From `UNCERTAIN`, a human re-reads `pg_roles` and `relowner` and stops. No script grants writes. |
| Controlled unfreeze | Only the Owner record plus the migrator reverse grants. A canary write then succeeds. Container identity is still unchanged. |

Zero unauthorized commits is not established by counters, `count(*)`, or a sparse canary. The proof package has to show, together:

- The write canaries failed, and the login canary authenticated and then failed the write.
- `pg_stat_activity` shows no application-role session in a writing transaction and no superuser session except the recorded break-glass or migrator session.
- A logical snapshot of every public business table, taken at `FROZEN_VERIFIED` and again immediately before spawn, matches. The current operator does not compute it.
- `count(*)` matches the backup. That match is necessary and not sufficient.

Container identity is `docker inspect` of the app and database containers: id, image id, `State.StartedAt`, and the daemon id, equal before `DRAINING` and after `P1_POSTCHECK`.

## Owner decisions required

Design D is not approved. This correction does not record an approval.

1. The decision, if it is made later, is a permanent role split. It is not a temporary maintenance mode and it is not "demote `stell22` for the window and restore superuser afterwards."
2. The operational consequence is that a failed application switch or a failed entrypoint leaves the site down, on the new `StartedAt`, until the break-glass role repairs the grants. Business data is not restored from backup to undo that.
3. Host root and the bootstrap superuser can still write. A visible session of either during the freeze forbids spawn.
4. A successful P1 postcheck does not unfreeze writes. An expired or missing signature does not unfreeze them. A long freeze does not expire.
5. A failed P1 is forward-fix only. No production restore and no drop of a committed column.
6. A later decision may add a freeze digest to the signed payload. This correction does not add one and does not lengthen the 15-minute window.
