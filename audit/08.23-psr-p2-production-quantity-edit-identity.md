## 2. Schema

```prisma
model ProductionOperationQuantityEdit {
  id                       String        @id @default(cuid())
  requestId                String        @unique
  operationId              String
  adminUserId              String
  actorDisplaySnapshot     String
  operationType            OperationType
  targetLineId             String?
  expectedOldQuantity      Int
  newQuantity              Int
  expectedStateFingerprint String
  requestSnapshot          Json
  effectSnapshot           Json
  recordedAt               DateTime      @default(now()) @db.Timestamptz(3)

  @@index([operationId, recordedAt])
}
```

No Prisma relation to `ProductionOperation` or `User`. No FK. No CASCADE.

`targetLineId`:

- TORCOVKA / PRISADKA: required original `OperationDetailLine.id`
- UPAKOVKA: null; target is the ProductionOperation / `productQty`

`operationType` on rows created by this package is only TORCOVKA / PRISADKA / UPAKOVKA.

Migration: `prisma/migrations/20260920180000_psr_p2_production_quantity_edit_identity/migration.sql`.

No historical backfill. Table empty at cutover. No InventoryMovement schema change. Existing correction tables unchanged.

## 3. Public API

Dedicated physical action:

`editProductionOperationQuantity(input: ProductionQuantityEditInput)`

```ts
type ProductionQuantityEditInput = {
  operationId: string;
  requestId: string;
  targetLineId?: string | null;
  expectedOldQuantity: number;
  newQuantity: number;
  expectedStateFingerprint: string;
};
```

`operationType` is not accepted from the client. The locked server row is authoritative.

`lineIndex` is not accepted as the A/B/C identity.

HOURS stays on `updateProductionLineQuantity` and does not require a physical-edit requestId.

Existing integrity callers that still pass a current id-ordered index through `updateProductionLineQuantity` for physical types are adapted internally to a new retained command (fresh requestId + current stable line id + current fingerprint). That adapter is not the retained identity.

## 4. Stable UI target

`ProductionDetailLine` exposes `id`, current quantity, and opaque `editStateFingerprint` for TORCOVKA / PRISADKA.

UPAKOVKA exposes current `productQty` and operation-level `editStateFingerprint` on `ProductionEntryRow`.

Array indexes remain render-only.

UI helper: `src/lib/production-quantity-edit-request.ts`. Same requestId is retained for retry of the exact command and rotates after `STALE_QUANTITY_EDIT` / `REQUEST_ID_REUSE`. No mandatory reason UI.

## 5. Fingerprint v1

```text
version = qedit-state-v1
digest = SHA-256
encoding = lowercase hex
```

Canonical material is an explicit field-order builder. Arrays are sorted by stable row id. The fingerprint is the OLD COMMITTED operation state. It does not bind the future UPAKOVKA BOM used for the new apply.

TORCOVKA binds: operationId, operationType, lineId, quantity, blankMaterialId, blankLengthM (4-decimal), blankType, blankSort.

PRISADKA binds: operationId, operationType, lineId, quantity, detailId, blank*, prisadka flags, sourceIsBlank, source*Done.

UPAKOVKA binds: operationId, operationType, productId, productQty, committed `OperationDetailLine[]` + `OperationNomenclatureLine[]`.

## 6. Expected-old CAS

After lock/load:

- TORCOVKA / PRISADKA: exact `targetLineId` belonging to the operation; `line.quantity === expectedOldQuantity`; recomputed fingerprint must match.
- UPAKOVKA: `targetLineId == null`; `op.productQty === expectedOldQuantity`; recomputed provenance fingerprint must match.

Mismatch: `STALE_QUANTITY_EDIT`. No physical mutation. No retained command. No ChangeLog. No silent retarget.

## 7. Request / replay

Namespace `8326`: `pg_advisory_xact_lock(8326, hashtext(requestId))` inside the TX.

Same `requestId` + exact command-defining payload (operationId, adminUserId, targetLineId/null, expectedOldQuantity, newQuantity, expectedStateFingerprint): replay success. No second stock mutation, retained row, or ChangeLog.

Same `requestId` + different payload or different authenticated admin: `REQUEST_ID_REUSE`.

Replay is resolved before interpreting the post-edit line collection. This is required for PRISADKA because the original line may have been deleted by the first command.

## 8. Actor / ChangeLog

`requireAdmin()` and `userMovementActorFromAdmin` run outside the TX.

Retained: `adminUserId`, immutable `actorDisplaySnapshot`.

Successful non-replay ChangeLog: entity `ProductionOperation`, `userId = actor.userId`, old/new quantity, `quantityEditId`, `requestId`.

Replay and no-op do not create ChangeLog.

## 9. TX order

`Prisma.TransactionIsolationLevel.ReadCommitted`.

```text
requireAdmin outside TX
→ build retained USER actor
→ pure input validation
→ BEGIN READ COMMITTED
→ read SHADOW write gate first
→ if SHADOW ACTIVE: QUANTITY_EDIT_SHADOW_WRITER_NOT_READY
→ acquire qedit request advisory lock
→ lookup retained command by requestId
→ exact replay return OR REQUEST_ID_REUSE
→ lock ProductionOperation
→ optional retained-row recheck
→ load authoritative operation/provenance
→ unpaid guard
→ type/target validation
→ expected-old quantity CAS
→ expected-state fingerprint CAS
→ cost-flow/type safety guards
→ capture exact pre-mutation physical state
→ execute existing physical edit algorithm
→ capture exact post-mutation physical state
→ derive canonical physical adjustments
→ persist ProductionOperationQuantityEdit
→ ChangeLog with admin userId + editId/requestId
→ COMMIT
```

No physical mutation before replay/CAS validation.

## 11. Cost-flow

UPAKOVKA + `production_cost_flow = ACTIVE`: fail closed before physical mutation with `QUANTITY_EDIT_UPAKOVKA_COST_FLOW_NOT_READY`. `ARCH-P1-001` remains OPEN / CONFIRMED. Package 2 does not close it.

UPAKOVKA + INACTIVE remains supported.

## 12. No-op

If authoritative current quantity equals `newQuantity`: success/current row; no stock mutation; no retained command; no ChangeLog.

## 14. Effect snapshot v1

```json
{
  "v": 1,
  "before": { "... canonical committed old provenance ..." },
  "after": { "... canonical committed new provenance ..." },
  "physicalAdjustments": [
    { "... canonical physical target ...", "quantityDelta": 1 }
  ]
}
```

`physicalAdjustments` are NET COMMITTED PHYSICAL CHANGE per exact target (BLANK / DETAIL / NOMENCLATURE / PRODUCT). Zero deltas omitted. Sorted by targetType then canonical target-key. No monetary fields. No InventoryMovement `REVERSAL`. No `effectKey` grammar — Package 3 owns that.

PRISADKA after-provenance is the replacement line set (old line id is gone). Replacement rows are the before/after line-id set difference under the ProductionOperation lock.
