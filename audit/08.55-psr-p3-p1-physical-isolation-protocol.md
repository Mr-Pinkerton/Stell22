## 1. Scope / assumptions

In scope: a documentation protocol for a future critical window. The Owner has decided the trust model. This package does not choose another architecture.

Out of scope, and not done here:

- source edits, scripts, SQL, Prisma migrations, Dockerfile, Compose, entrypoints, GitHub Actions, production configuration, credentials;
- a new superuser barrier or a second Opus audit;
- production APPLY, UNFREEZE, deploy, restore, or workflow dispatch;
- any claim that a process is running on the production host.

Assumptions that are fixed:

- Physical isolation of the access terminal is the accepted operational boundary.
- A trusted maintenance operator may perform controlled work. That path is retained on purpose.
- An unconstrained superuser or host root cannot be given an impossible technical write ban. Their presence is a trust fact, not a proof that every other channel is closed.
- Independent write channels stay in scope until each one has evidence.
- `APPROVAL TO PREPARE` is not `APPROVAL TO APPLY`. `APPROVAL TO APPLY` is not `APPROVAL TO UNFREEZE`. Neither decision replaces a technical gate.
- Design D in `audit/08.48` stays a candidate. `audit/08.54` left `PRIVILEGED_WRITER_BARRIER_BLOCKED`. Neither result is upgraded here.
- Current `main` functions are not production functions. The last documented production application SHA remains `678cbc1d308ddfe568b901ebf53f7e05f9a8c014`.

No production command in this file was executed. A command labeled STATE-CHANGING is a design for a later Owner authorization. A command with an ambiguous side effect is not labeled READ-ONLY.

`docker-entrypoint.sh` always runs `npx prisma migrate deploy` and then `exec npm run start`. The comment in that file says migrate deploy updates schema and does not touch data. That comment is not a proof that a pending migration is safe, and it is not a proof that production has no pending migration.

`docker-compose.prod.yml` sets `restart: unless-stopped` on `db`, `app`, and `caddy`. The database service uses `postgres:17-alpine`, `POSTGRES_USER=stell22`, `POSTGRES_DB=stell22`, and does not publish `5432`. The app `DATABASE_URL` uses username `stell22`. Caddy publishes host ports `80` and `443` and mounts `./Caddyfile` read-only.

`Caddyfile` reverse-proxies `{$DOMAIN}` to `app:3000` and redirects `www.{$DOMAIN}` to that host. It has no path filter and no maintenance rule.

`docker-entrypoint-app-only.sh` and `docker/app-only-startup/Dockerfile` exist. The app-only script checks schema readiness and starts Next.js. It does not run `prisma migrate deploy`. Compose and the production Dockerfile do not use it. `audit/08.52` records that candidate. It is not the production startup path.

### Deploy, backup, restore

`scripts/deploy.sh` runs `scripts/p1-writer-preflight.sh`, then `scripts/backup-db.sh`, then checks out a SHA and runs `docker compose -f docker-compose.prod.yml up -d --build`. The entrypoint applies migrations during that start. Rollback in the same script resets the app git checkout and rebuilds the app. It does not roll database schema or data back.

`scripts/ci-prod-remote.sh` is what `.github/workflows/deploy-production.yml` runs over SSH. It runs the preflight script and then `scripts/deploy.sh`. The workflow trigger is `workflow_dispatch` only. A push to `main` does not start it. The workflow resolves `origin/main` at dispatch time and deploys that SHA. Dispatching it would deploy current `main`, including the P1 migration file, through the entrypoint. That dispatch is not authorized.

`scripts/p1-writer-preflight.sh` opens `psql` as `stell22` on database `stell22` and runs `scripts/p1-writer-preflight.sql`. The SQL text is a `SELECT` against `_prisma_migrations`. The shell comment says the wrapper does not mutate. The session it opens is still the bootstrap superuser. This protocol does not classify that command READ-ONLY.

`scripts/backup-db.sh` runs `pg_dump -U stell22` through `docker compose exec` and publishes `backups/stell22_<timestamp>.sql.gz` plus a SHA-256 file. It prints `BACKUP SUCCESS` only after its checks. That line does not mean `RESTORE-VERIFIED`. Retention deletion is suspended in the script.

`scripts/restore-db.sh` prints a refusal and exits 1. It does not connect and does not read a dump.

### Write admission standard

`UNAUTHORIZED_WRITERS_EXCLUDED` is **NOT PROVEN**.

These observations are not that gate:

- browsers someone already knows about were closed;
- cookies someone already knows about were listed;
- no new business row appeared;
- a session list was empty at one instant;
- the access terminal was physically disconnected.

A positive gate needs a control that can be checked for the whole interval. This tree does not contain that control. `Caddyfile` proxies every path. There is no `src/middleware.ts`. `audit/08.48` records that the running source has no maintenance flag. This protocol does not add a control, does not build a superuser barrier, and does not name a production command for a host whose topology was not inspected.

| --- | --- | --- |
| Public HTTP POST | New POST requests that can write are rejected for the whole interval, and a repeatable check shows the rejection still holds | A quiet access log. A closed laptop. The name staying on port 443 |
| Server Actions | The same control covers every `"use server"` mutation in this section. A request that does not reach the action commits nothing new | A cookie inventory. Logout. "Nobody was at the terminal" |

## 5. Physical isolation contract

Three predicates are separate. The first does not prove the second or the third. This draft does not invent the device, its ports, its radio, or the site layout. Any path the observer cannot identify stays `UNKNOWN` and is a STOP.

| Predicate | Meaning | What a later check has to cover | What does not count |
| --- | --- | --- | --- |
| `PHYSICAL_TERMINAL_DISCONNECTED` | The physical device the Owner named is the device that was inspected, and that device has no remaining path into the system | Identity matches the Owner record. Power is removed, not only the screen. Wired links that are present are disconnected. Wi-Fi and every other radio or network path the device can use are off. No alternate path remains: a dock, a second adapter, a phone tether, or a remote-desktop session from that device. Observer and time are recorded outside the application | A Stell22 screenshot. Logout. A closed lid that still has power. A cable pulled while Wi-Fi is unexamined. A guess about which radios exist |
| `TERMINAL_ACCESS_BLOCKED` | That named device can no longer send a request | The disconnect record still holds, and a separate check shows the device itself has no path. This predicate is about that device | A list of other browsers. A cookie inventory. Missing new rows. The disconnect record used as proof about the rest of the network |
| `UNAUTHORIZED_WRITERS_EXCLUDED` | Every writer in section 4 except the one controlled operator action is covered by the admission standard | The positive gate in section 4, shown for the whole interval | Closed browsers, known cookies, quiet tables, one empty session list, and the unplugged terminal. Current result: **NOT PROVEN** |

Confirmation procedure:

1. The Owner names the device outside the database and outside this file. If it cannot be named, stop.
2. Inspect that same device. Record power, each wired connection the observer can see, and each wireless path the observer can establish. If a path might exist and was not checked, the predicate is `UNKNOWN`. Stop. Do not fill the gap with a topology this repository does not contain.
3. That record can establish only `PHYSICAL_TERMINAL_DISCONNECTED`. It does not establish `TERMINAL_ACCESS_BLOCKED` until the same device is shown to have no remaining path, and it does not establish writer exclusion.
4. `TERMINAL_ACCESS_BLOCKED` still leaves every other client, the public proxy, cron, open database sessions, and in-flight work untouched. Those belong to the admission standard.
5. Keep one controlled path: the trusted operator's recorded SSH or console session. Do not describe that path as write-incapable.
6. `UNAUTHORIZED_WRITERS_EXCLUDED` stays **NOT PROVEN** until the admission standard is shown. Unknown channels stay `UNKNOWN IN PRODUCTION`.
7. Restore ordinary access only in stage 7, after a separate Owner decision. Reconnecting the device is an unfreeze action.

If writer exclusion is **NOT PROVEN**, or any independent writer remains `UNKNOWN IN PRODUCTION`, APPLY is NO-GO.

## 6. Trusted operator boundary

The Owner accepted an operational trust boundary:

- one trusted maintenance operator;
- physical isolation of the named access terminal;
- controlled execution of later work;
- explicit checks of the other write channels;
- a separate Owner decision for APPLY;
- a separate Owner decision for UNFREEZE.

The operator may hold SSH and the Docker socket. PostgreSQL privileges do not bind that person, and this protocol does not ask them to. Work they perform is admitted only when it is the single recorded action for that stage.

The boundary does not extend to:

- a second person with the SSH key, the sudo password, or the Docker socket;
- a browser that still has a cookie;
- host cron or GitHub Actions;
- an app restart;
- a superuser session the operator did not open for the current stage.

No stage transition widens this boundary. Prepare does not grant apply. Apply does not grant unfreeze. A successful postcheck does not grant unfreeze.

Design D and the privileged-writer barrier are not this boundary. They stay unaccepted. This protocol does not install them.

`scripts/deploy.sh` is a full application deploy. It is the wrong tool for a P1-only migration. Using it would check out current `main`, rebuild, and let the entrypoint apply every pending migration in that image, including P1 and any later file.

The uncontrolled path is structural. Compose will restart a dead app, and the entrypoint will run `prisma migrate deploy`, without a new Owner command. This package does not change that behavior. Inability to exclude that start is a **HARD STOP** for APPLY. A written Owner acceptance of the residual does not replace the technical gate. A wish that the process will not crash does not exclude it.

A later proof of safe startup is not built here. It would have to show all of the following before stage 5 can even be considered:

1. The startup files that production Compose and `Dockerfile` actually run.
2. A pending migration present in that image before the trial.
3. An ordinary start does not run `prisma migrate deploy` and does not add a migration row.
4. A process exit followed by `restart: unless-stopped` does not run it either.
5. A daemon restart that brings the same service back does not run it either.
6. The trial database is not production.
7. The captured result is the command behavior and the migration table, not an Owner sentence.

`docker-entrypoint-app-only.sh` does not run `prisma migrate deploy`. The production `Dockerfile` does not select it. Citing that candidate is not items 1–5. Until those items are shown for the path production runs, stage 5 stays closed.

## 8. Stage gates

Nothing in this section is permission to run the stage. Owner execution approval is absent. Commands are designs. They were not run.

Command classes:

- READ-ONLY — no database session, no container create/start/stop/build, no file publish, no git checkout, no crontab edit, no HTTP POST.
- STATE-CHANGING — everything else, including a superuser `psql` session, `pg_dump`, `docker exec`, `docker compose up`, image build, crontab edit, and HTTP POST.

`docker inspect`, `docker ps`, `crontab -l`, `git rev-parse`, and `git status` on the server are READ-ONLY only when they do not exec into a container and do not check out files. `docker compose exec db psql` is not READ-ONLY. `GET /api/health` uses the application pool and is not a freeze proof. Notification page loads are STATE-CHANGING.

### Stage 1 — READ-ONLY PREFLIGHT

A. Preconditions. This document is still a draft. No production socket is open for this task. The operator has not been told to APPLY.

B. Required evidence. Repository identity (`main` SHA and tree), the historical application SHA citation, and a written list of channels that are still `UNKNOWN IN PRODUCTION`. Fresh host evidence is not collected until a later execution approval exists.

C. Trusted operator actions. None on production during this documentation task. A later execution of this stage, after its own approval, may run only READ-ONLY host commands: inspect of `stell22-app`, `stell22-db-prod`, and `stell22-caddy` (id, image, `StartedAt`), `crontab -l`, process list, and `git rev-parse HEAD` in the deployed checkout. No `psql`.

D. STOP. Remote `main` is not the SHA the Owner named for the window. The deployed checkout cannot be read. Any command would open a database session. The named access terminal cannot be identified.

E. Recovery. Stop. Do not "just look" with `psql`. There is nothing to roll back if no session was opened.

F. Owner authorization. A later decision to collect host evidence is not `APPROVAL TO PREPARE` and is not `APPROVAL TO APPLY`. This task does not hold that decision.

G. Next stage. Only if the Owner separately authorizes stage 2. An unknown writer list does not become known by moving on.

### Stage 4 — FREEZE

A. Preconditions. Predicate 1 is recorded. Predicates 2 and 3 are still open. No new role, no `pg_hba` edit, and no Design D step is part of this stage. The preliminary backup from stage 2 is not reused as the pre-APPLY copy.

### Stage 5 — APPLY

A. Preconditions. All of them, together. Stage 4 admission standard shown. Section 7 startup proof shown for the path production runs. B. Required evidence. Immediately before the shot: `StartedAt` still matches, the admission standard still holds, and an ordinary app start cannot run `prisma migrate deploy`. The second of those is a hard stop today.

C. Trusted operator actions. None. The action, if a future package ever meets the preconditions, is one controlled P1 execution by the trusted operator.
