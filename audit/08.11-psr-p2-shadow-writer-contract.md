## 3. Common InventoryMovement writer/gateway API

Introduce one narrow internal gateway, not a generic CommandExecution bus. Conceptual API:

```ts
appendShadowInventoryMovements(
  tx: Prisma.TransactionClient,
  input: {
    effectiveAt: Date;
    actor: MovementActorSnapshot;
    causation: MovementCausationSnapshot;
    effects: readonly MovementEffect[];
  }
): Promise<{ gateActive: boolean; inserted: number }>
```

Contract:

- accepts an **open** `Prisma.TransactionClient` only; root Prisma client fails closed;
- the approved writer entry must call `isInventoryMovementShadowWriteActiveForWriter(tx)`; no caller performs a direct gate read;
- helper obtains SHARED advisory TX lock on `(8322,1)` before reading the gate;
- malformed gate fails closed before physical mutation;
- inactive gate means legacy projection behavior and zero InventoryMovement rows;
- active gate writes authority = SHADOW and epochId = NULL;
- writer never supplies `recordedAt`; DB generates TIMESTAMPTZ(3);
- no monetary fields or monetary lookups;
- `quantityDelta=0` is omitted;
- insertion order is deterministic by canonical semantic effect key, never `recordedAt` or input-array order;
- projection mutation + movement insertion are in the same DB transaction;
- no post-commit/background insert and no root Prisma client;
- no runtime module may create an InventoryMovement row except through this approved gateway;
- future static policy must reject `inventoryMovement.create` / `createMany` and raw `INSERT INTO "InventoryMovement"` (plus aliases/unquoted equivalents where detectable) outside the allowlist: gateway implementation, gateway-specific tests, `src/server/integrity/**`, schema/migrations, and any explicitly approved non-runtime maintenance path that genuinely needs INSERT;
- duplicate InventoryMovement uniqueness is the final barrier only; caller contour must independently prove physical idempotency.

## 4. Mandatory transaction / gate / lock order

For every SHADOW-capable physical transaction:

1. open DB transaction;
2. obtain SHARED InventoryMovement advisory TX lock via `isInventoryMovementShadowWriteActiveForWriter(tx)`;
3. read/validate `inventory_movement_shadow_write` inside that helper;
4. if contour is Inventory and gate is active, evaluate `production_cost_flow`; if it is also active, fail closed **before business/stock mutation** until the ACTIVE projection is unified with `InventoryPhysicalEffect[]`;
5. acquire business/document/stock locks in the contour's globally deterministic order;
6. validate current state;
7. derive exact physical effects;
8. mutate projection;
9. insert corresponding SHADOW InventoryMovement rows;
10. perform status/audit updates;
11. commit.

Gate OFF/reset continues to take EXCLUSIVE advisory TX lock on the same `(8322,1)` pair. Do not reuse `production_cost_flow`.

## 5. Canonical target key and effectKey v1

All effect keys are <=200 chars. To make collisions impossible without relying on separators inside ids, define a canonical target serialization and hash.

`targetKeyV1` is canonical UTF-8 JSON with keys in the exact order below and Decimal values encoded as exact strings:

- RAIL_LOT: `{"v":1,"d":"RAIL_LOT","railLotId":"..."}`
- BLANK: `{"v":1,"d":"BLANK","materialId":"...","lengthM":"0.0000","detailType":"...","sort":"..."}`
- DETAIL: `{"v":1,"d":"DETAIL","detailId":"...","torcevayaDone":true|false,"ploskostDone":true|false}`
- NOMENCLATURE: `{"v":1,"d":"NOMENCLATURE","nomenclatureId":"..."}`
- PRODUCT: `{"v":1,"d":"PRODUCT","productId":"..."}`

BLANK `lengthM` in `targetKeyV1`, the `targetSnapshot` physical tuple, and effect derivation identity MUST always be the canonical fixed-4 decimal string, using the same semantics as `canonicalLengthFixed4(...)` in `src/server/internal/blank-length.ts`. Example: `"1.8000"`, never `"1.8"`. `Decimal.prototype.toString()` variable-scale representation and JS-number stringification are forbidden for this identity. `"1.8"` and `"1.8000"` must not hash as different BLANK targets. If an upstream current structure contains a JS number, the future writer must canonicalize it through the fixed-4 formatter before hashing or snapshot identity. This contract does not change runtime types.

`targetHashV1 = lowerHex(SHA-256(UTF8(targetKeyV1)))`.

Exact `effectKey` grammar:

`imfx1:<semantic-role>:<targetHashV1>[:<qualifier>]`

where semantic-role is one of `receipt`, `consume`, `output`, `adjust`, `writeoff`, `restore`. Qualifiers below are part of the exact identity where specified. Hashing is deterministic, semantic (derived only from the physical target), retry-stable, independent of array order, and bounded well below 200 characters. The unhashed canonical target remains in `targetSnapshot`/target columns for interpretation.

## 7. Supply contract

- causationKind = `SUPPLY`
- causationId = `Supply.id`
- target = PRODUCT
- stockAccountingGeneration is part of effect identity
- accounting watermark is explicitly **processedQtyAfter = newDeducted + newShortfall** after the step
- shortfall contributes to retry/accounting watermark but **never** to movement quantity
- consume `quantityDelta = -toRemove` only; if `toRemove=0`, emit no row

Exact consume key:

`imfx1:consume:<productTargetHash>:g=<generation>:w=<processedQtyAfter>`

A later step in the same generation has a higher processed watermark. Retry of an already processed target emits no physical effect and no second movement.

Ozon cancellation uses a **positive ADJUSTMENT**, not `REVERSAL`. Reason: a SHADOW reset may have deleted the corresponding consume row, the cycle may have begun before SHADOW was enabled, and one generation may contain multiple consume steps. Requiring `reversalOfMovementId` would therefore make cancellation correctness depend on SHADOW history that is not guaranteed to exist.

Exact cancellation key:

`imfx1:restore:<productTargetHash>:g=<generation>:w=<deductedQtyBeforeClose>`

`quantityDelta = +deductedQtyBeforeClose` only when that physical restore actually commits. Zero restore emits no row.

Before Supply writer work, run the required **read-only** production query for `Supply.productId IS NULL AND (deductedQty>0 OR shortfallQty>0)`. No mutation. Regardless of the result, future cancellation must fail closed if an open deducted cycle has restoreQty > 0 but no bound productId.

Before writer implementation, compute the full Supply + ProductStock target set, then acquire one deterministic lock order. Do not rely on API/findMany/per-loop order.

## 8. Production-operation contract

Normal terminal operations use:

- causationKind = `PRODUCTION_OPERATION`
- causationId = retained `ProductionOperation.id`
- actorKind = EMPLOYEE; employeeId and immutable employee display snapshot captured at causal action
- `clientRequestId` is the retained retry identity and must remain unique/atomic with the projection mutation

Effects are derived from retained operation inputs/provenance, grouped by **semantic role + physical target**. Multiple retained lines with the same role/target are summed. Consume and output are not netted against each other merely because they happen to share a target.

Exact keys:

- consume: `imfx1:consume:<targetHashV1>`
- output: `imfx1:output:<targetHashV1>`

TORCOVKA: RailLot CONSUMPTION `-railsTaken`; Blank PRODUCTION_OUTPUT `+sum(outputs by spec)`.

## 11. Time contract

`recordedAt`:
- DB generated; writer never supplies it;
- TIMESTAMPTZ(3);
- transaction record time, not an intra-transaction cursor/sequence.

`effectiveAt`:
- writer supplied but server controlled;
- one timestamp per causal physical action unless an explicitly documented exception exists;
- never arbitrary client backdating;
- employee `workDate` does not authorize stock backdating.

Current schema (do **not** convert in this contract package): `effectiveAt` is PostgreSQL `TIMESTAMP(3)` without timezone. Contract decision for the current schema:

- application derives it from server-side occurrence time;
- normalize to UTC before persistence;
- stored TIMESTAMP value is interpreted as UTC by Stell22 (UTC-naive storage);
- never interpret it in database/session/local timezone;
- never derive it from arbitrary client-local time;
- comparisons with `recordedAt` must normalize both to UTC instants.

Converting the column to TIMESTAMPTZ requires a separate explicit schema/migration decision.

Before the first SHADOW writer, mandatory PostgreSQL-backed CI must include an `effectiveAt` round-trip test under a non-UTC DB/session timezone so the UTC interpretation cannot silently depend on environment timezone.

Freeze current semantics:
- Inventory: server occurrence timestamp of successful conduct;
- Supply deduction/restore: server occurrence timestamp of the accounting mutation, not external marketplace `createdAt`;
- R-05 correction: server occurrence timestamp of accepted correction;
- terminal operation: server occurrence timestamp of the submitted physical operation.

Arbitrary backdating remains P10.

## 12. Snapshot contract

`targetSnapshot` and `causationSnapshot` are versioned JSON objects (`v:1`) sufficient to interpret history after mutable masters/sources change or disappear.

Rules:
- exact Decimal values are strings; never JS float serialization when an exact Decimal exists;
- BLANK `lengthM` is always the canonical fixed-4 string (`canonicalLengthFixed4`); never `Decimal.prototype.toString()` or JS-number stringification;
- no monetary cost/value fields;
- BLANK authoritative identity remains physical tuple, not a catalog Detail alias;
- mutable display labels may be snapshot metadata only;
- row ids may be provenance metadata but not the sole BLANK identity;
- Supply causationSnapshot records at least Supply identity, marketplace, externalId, sku, generation, accounting watermark, and action direction;
- production causationSnapshot records operation type, retained clientRequestId, and immutable causal source identifiers needed to explain the effect.

## 13. Zero delta and duplicate/retry rules

Global invariant: `InventoryMovement.quantityDelta` is never zero.

State transitions such as full Supply shortfall, zero cancellation restore, or zero Inventory effect may still update retained business state but write zero InventoryMovement rows.

`UNIQUE(causationKind, causationId, effectKey)` is a final duplicate barrier only. It does not make projection writes idempotent.

Required retry proof by contour:
- Inventory: DRAFT -> CONDUCTED state gate.
- Supply: locked generation + cumulative accounting watermark.
- R-05: requestId serialization + retained correction row + expected-old state.
- terminal production: unique `clientRequestId` atomic with operation/projection.
- `writeOffBatchRemainder`: projection SET-to-zero is not sufficient; remain BLOCKED until a retained write-off command/lifecycle identity exists.
- every other contour: prove independently or remain BLOCKED.

## 14. Reconciliation diagnostic contract (design only; P3 NOT STARTED)

Every connected P2 writer must expose enough deterministic information to diagnose:

- expected signed movement delta;
- exact physical target;
- causal action;
- projection result after action;
- missing/duplicate movement;
- wrong sign;
- wrong target;
- wrong quantity.

Per-writer diagnostics may be implemented during P2. Projection remains the operational stock source during SHADOW. No authoritative reads. Formal ledger<->projection reconciliation remains PSR-P3.

P2 is incremental. Until every enabled physical contour is dual-writing or disabled:

- the SHADOW ledger is knowingly incomplete globally;
- diagnostics are authoritative only for already-connected writer contours;
- a missing movement caused by a not-yet-connected BLOCKED contour is not by itself a P3 reconciliation anomaly;
- P3 does not start early.

In particular, current admin production edit/delete contours (`updateProductionLineQuantity` and relevant delete paths) remain BLOCKED and may alter projection and replace/delete retained operation provenance. Movements already written by an earlier causal operation remain immutable historical facts; their interpretation must rely on their stored immutable snapshots, not on assuming current operation provenance still exists unchanged. P2 diagnostics must be contour-aware until P2 COMPLETE.

This does not weaken the P2 completion requirement: every enabled physical mutation must still eventually dual-write correctly or be disabled.
