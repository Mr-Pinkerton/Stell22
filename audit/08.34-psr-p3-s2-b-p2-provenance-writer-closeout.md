## 2. What P2 implemented

`createBatch` (`purchases.ts` lines 290–389) stays one transaction.

1. Outside the transaction: admin, actor, `requestId`, `validateBatch`, and `canonicalBatchCreateSnapshot` (lines 294–298).
2. Inside the transaction, the existing SHADOW gate is read first (line 301).
3. The existing request lock, namespace `8326` (`purchase-command-identity.ts` lines 15 and 35–42), and the `requestId` lookup follow (lines 302–305).
4. A matching replay returns the existing batch at lines 306–315. It does not insert another command, another lot set, or another provenance object, and it does not update the stored object. Comparison is still `requestSnapshot` only.
5. `requestSnapshot` is still `canonicalBatchCreateSnapshot`. It has no `railLotId`.
6. The batch and its `RailLot` rows are inserted before provenance is built (lines 323–354). `remainingQuantity` is still set from the inserted quantity.
7. `commandId` is `randomUUID()` at line 358, before `batchCreationCommand.create`. The column default remains `@default(cuid())` (`schema.prisma` line 307) for an insert that omits `id`. New commands supply the UUID. Older rows are unchanged.
8. The snapshot is built from `batch.railLots` (lines 359–367), not from `InventoryMovement`, `causationSnapshot`, or a write-off record.
9. `id` and `receiptProvenanceSnapshot` are columns of that same insert (lines 368–377). There is no later provenance `UPDATE`.
10. The object is `{ v: 1, d: "BATCH_RECEIPT_PROVENANCE", commandId, batchId, pairs: [{ railLotId, quantity }] }` (`batch-receipt-provenance.ts` lines 22–28 and 63–69).
11. Pairs are sorted by `railLotId.localeCompare`, the same comparison as `sortByRailLotId` (`raw-purchase-shadow-write.ts` lines 92–94).
12. Every supplied lot becomes one pair. A duplicate id, a blank id, or a lot from another batch throws `BATCH_RECEIPT_PROVENANCE_INVALID`.
13. Two lots with the same specification and different ids stay two pairs.
14. Quantity `0` stays in `pairs`.
15. A negative, fractional, non-finite, or non-integer quantity throws before commit. It is not coerced.
16. After the insert, the existing `appendBatchCreateShadowMovements` still runs (lines 378–383). When the gate is active, `batchCreateReceiptEffects` still skips quantity `0` (lines 158–173) and appends one `RECEIPT` per positive lot.
17. When the gate is inactive, the object is still stored and no `InventoryMovement` row is appended. The inactive return remains inside the existing append helper. This closeout does not classify that case as `GATE_UNKNOWN`.
18. A builder failure or a SHADOW append failure aborts the same transaction. The tests observe zero batches, lots, commands, and movements after either failure.
19. `writeOffBatchRemainder` (line 572) and `deleteBatch` (lines 664–703) do not load or update `BatchCreationCommand`. After a legal write-off and delete, the command and its pairs remain. `deleteBatch` removes `BatchCost`, `RailLot`, and `Batch` only.
20. A command whose `receiptProvenanceSnapshot` is already SQL `NULL` is not updated. There is no backfill.
21. The builder comment and its inputs are the inserted lot id, batch id, and original quantity. `remainingQuantity` is not read.
22. No schema change and no migration were added.

`validateBatch` (lines 236–241) still does not require `quantity > 0`.
