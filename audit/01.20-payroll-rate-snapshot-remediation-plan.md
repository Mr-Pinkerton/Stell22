# Payroll rate snapshot — remediation plan (DI-015)

> **For agentic workers:** do not implement until this document is reviewed. When implementing: `superpowers:subagent-driven-development` or `executing-plans`. Evidence: `audit/01.19-payroll-rate-snapshot-review.md`. This file is the spec. **Do not** edit `audit/01-data-integrity-findings.md` until implementation is shipped and the owner closes DI-015.

**Goal:** Every `ProductionOperation` is valued with the Employee rates copied at successful submit; later card changes affect only future operations; fact edits before pay keep the snapshotted rates.

**Architecture:** Six nullable `Decimal(14,2)` snapshot columns plus required `rateSnapshotVersion Int` (NOT NULL, no default) on `ProductionOperation`. Writers copy the live Employee vector inside the same TX as the Op insert, after existing stock locks, under `Employee … FOR UPDATE`, and stamp `rateSnapshotVersion: RATE_SNAPSHOT_VERSION` (1). Readers (`operationEarning` via a single helper) use the six rate columns only — never live Employee rates. `rateSnapshotVersion` is not a rate: it proves the server captured the vector. `Payment.amount` stays the pay-time aggregate. No rate-history table, no line-level prices, no PaymentBatchItem amount, no DI-014 change.

**Tech Stack:** Prisma 6 / PostgreSQL 17 / existing `operationEarning` JS `round2` / Vitest unit + integrity harness (`INTEGRITY_TEST_DATABASE_URL`). Isolation stays READ COMMITTED.

No new model. No columns on `OperationDetailLine`. No `ratesCapturedAt`. Rate columns stay nullable forever (Employee rates are nullable; do not fake 0). The capture marker is NOT NULL without default so a forgotten/old writer fails at the DB boundary.

A legitimate employee may have all six rates NULL. Those six columns alone cannot distinguish “legitimately NULL at submit” from “old writer never captured rates.” `rateSnapshotVersion` provides that distinction.

Relation `ProductionOperation.payment` / UNIQUE `PaymentBatchItem.operationId` unchanged.

## 2. MIGRATION AND ROLLOUT

### Why rate columns stay nullable (capture marker is NOT NULL)

Employee rates are nullable. Owner forbade a fake SQL default of 0 on the six rate columns. Do not tighten those to NOT NULL.

`rateSnapshotVersion integer NOT NULL` (no DEFAULT) is valid because migrate runs only when the table is empty (ACCESS EXCLUSIVE + count recheck).

### Preflight (read-only, before checkout) — schema-state aware

`scripts/preflight-prod.sh` queries production catalog (`pg_attribute` / `ProductionOperation`) for the seven expected DI-015 columns. Do **not** depend only on migration filenames.

Print: snapshot_column_count; ProductionOperation total / paid / unpaid / by type; Payment; PaymentBatchItem. No sensitive values. No reconstruction, no UPDATE/DELETE.

| Catalog | Ops | Verdict |
| --- | --- | --- |
| 0 of 7 columns | 0 | OK (pre-migration, empty table) |
| 0 of 7 columns | >0 | PRECHECK FAILED / STOP (cannot reconstruct) |
| 7 of 7 columns | any | OK (migration landed; ops are expected) |
| 1–6 of 7 | any | INCONSISTENT DI-015 SCHEMA / PRECHECK FAILED / STOP |

After DI-015 ships, ProductionOperation **will** contain rows. Preflight must **not** fail merely because count > 0 once all 7 columns exist.

Preflight alone is **not** enough for first migrate: an op can be created after preflight and before migrate. Migration still rechecks under ACCESS EXCLUSIVE.

### Migration (mandatory fail-closed TOCTOU guard)

Prisma 6 classic PostgreSQL `migration.sql` is **not** auto-wrapped. Use one explicit transaction, same pattern as DI-014.

```sql
BEGIN;
LOCK TABLE "ProductionOperation" IN ACCESS EXCLUSIVE MODE;
-- DO $$ count; IF op_count > 0 THEN RAISE EXCEPTION 'DI-015: ...' $$
ALTER TABLE "ProductionOperation" ADD COLUMN … numeric(14,2)  -- six, nullable, no DEFAULT
ALTER TABLE … ADD COLUMN "rateSnapshotVersion" integer NOT NULL  -- no DEFAULT
COMMIT;
```

No UPDATE / DELETE / backfill / default 0 / current-rate copy. ACCESS EXCLUSIVE serializes against INSERT until COMMIT. If any row exists at migrate time, deploy **fails closed**.

### SAFE FOR CURRENT DEPLOY MODEL — not generally rolling-deploy compatible

Verified scripts:

- `docker-compose.prod.yml`: **one** `app` container (`stell22-app`).
- `scripts/deploy.sh`: `docker compose up -d --build` recreates that container (build may run while old app still serves; recreate **stops** the old writer, then starts the new one).
- `docker-entrypoint.sh`: `prisma migrate deploy` **then** `npm start`.

Order that is safe for **migrate apply**:

```
single app container → old app stopped → migration → new app starts
```

**Do not** claim this design is generally rolling-deploy compatible.

Application rollback **does not** roll back DB migrations. After DI-015 migrate lands, a pre-DI-015 app is **not** write-compatible: `ProductionOperation` INSERT fails closed because `rateSnapshotVersion` has no default. That is intentional and safer than silently inserting ops with unknown historical rates (NULL snapshots → earning 0).

Do **not** redesign deploy/rollback in this workstream. Do **not** add DB triggers. Do **not** add fake defaults.

A failed DI-015 deploy after migration requires an immediate **forward-fix** before production terminal writes resume.

Future multi-replica / rolling deploy remains **OUT OF SCOPE** (would still need expand/contract). The capture marker makes old-writer INSERTs fail closed; it does not make rolling two app versions safe.

No live-Employee fallback if rate snapshots are NULL (NULL = earning 0, same as a worker with no rate). `rateSnapshotVersion` is not a rate.

## 3. SHARED HELPERS

Add small functions next to existing payroll code (prefer `src/lib/payroll.ts` for pure mapping, `src/server/internal/finance-operations.ts` for lock):

**`employeeRateSnapshots(emp)`** — map Prisma Employee Decimal|null → the six snapshot field values (pass through null; do not coerce to 0).

**`RATE_SNAPSHOT_VERSION = 1`** — single shared constant. Not terminal input.

**`operationRateSnapshotWrite(emp)`** — six snapshots plus `rateSnapshotVersion: RATE_SNAPSHOT_VERSION`. All four writers use this after `lockEmployees`.

**`operationRatesFromSnapshots(op)`** → `OperationRates` using existing `num()` (null → 0). Used by all earning readers. Does not read `rateSnapshotVersion`.

**`evaluateDi015Preflight(columnCount, opCount)`** — catalog-state verdict (`ok` / `stop-ops-before-migrate` / `stop-inconsistent-schema`). Bash preflight implements the same rules against `pg_attribute`.

**`lockEmployees(db, ids)`** — `SELECT id FROM "Employee" WHERE id IN (…) ORDER BY id FOR UPDATE`. Same pattern as `lockTableIds`. Add `"Employee"` to `TABLE_IDENT`.

**Do not** add Employee to payroll/freeze lock order. Submit paths only.

### Current replay / lock order (traced 2026-09-06, before DI-015)

**`submitTorcovka`:** findUnique `clientRequestId` (fast replay) → `lockRailLots` → findUnique again (post-lock replay) → physics / approval / `railLot.updateMany` → `productionOperation.create` → BlankStock → ChangeLog. `P2002` → `IDEMPOTENT_REPLAY` / public `CREATED`. Employee is **not** read. DI-015 inserts Employee lock **after** replay+RailLot+approval, **before** create. Replay returns without touching snapshots.

**`submitPrisadka`:** `lockDetails(pick detailIds)` → `create` (`clientRequestId`) → `applyPrisadkaPick` (stock) → ChangeLog. Replay today: Details lock then create `P2002` (apply never runs). Stock emptiness does not fail the lock. DI-015 adds findUnique replay **before** Details so a retry never depends on post-success stock. Then Details → Employee → create. Keep `P2002` catch.

**`submitUpakovka`:** per pick: `create` (`${clientRequestId}:${productId}`) → `applyUpakovkaPick` (`snapshotUpakovkaApply` + `lockDetails` + stock). Outer `P2002` → success. **One TX = all picks or none.** Replay today hits `P2002` on the first existing id and never reaches stock. If we prepare/lock Details **before** create, a retry after stock consume would fail unless fast replay runs first. Expected ids = existing convention. Partial set → throw. Concurrent overlap → existing `P2002` catch.

**`submitHours`:** `create` then ChangeLog **outside** TX. `P2002` → return. DI-015 wraps Employee + create + ChangeLog in one TX; optional fast replay; keep `P2002`.

Lock order after this plan (submit):

```
existing stock / RailLot / Details / (optional TorcovkaApproval)
→ Employee (sorted ids, FOR UPDATE)
→ INSERT ProductionOperation including snapshots
→ remaining stock writes / ChangeLog
```

**UPAKOVKA special case:** today `create` runs *before* `lockDetails` inside `applyUpakovkaPick`. Do **not** lock Employee at TX start (Employee→Details vs PRISADKA Details→Employee → deadlock).

**Replay-safe reorder (mandatory):** `snapshotUpakovkaApply` / `lockDetails` can fail after stock was consumed. A committed retry with the same logical `clientRequestId` must not reach that validation. Fast-replay **before** prepare/locks:

1. Expected ids = current convention `${clientRequestId}:${productId}` per pick (do not invent new semantics).
2. `findMany` those ids.
3. **All exist** → return success; do not lock Employee; do not touch stock; do not rewrite snapshots.
4. **None exist** → prepare + `lockDetails`(union, sorted) + `lockEmployees` + create+apply.
5. **Partial set** → invariant anomaly (throw). Current TX is all-or-none; do not silently create the remainder. Keep outer `P2002` catch for concurrent same-id.

**Forbidden:** Employee before RailLot/Details; Employee lock inside `markEmployeePaid` / `maybeFreezeBatch` / recalc; Batch then ProductionOperation (unchanged freeze rule).
