## Existing startup

`docker-entrypoint.sh` runs `npx prisma migrate deploy` and then `exec npm run start`. The production `Dockerfile` sets that script as `ENTRYPOINT`. `docker-compose.prod.yml` builds that image as `stell22-app`. `scripts/deploy.sh` step `[3/5]` assumes the entrypoint applies migrations. Those four files are unchanged in this package.

`GET /api/health` remains `SELECT 1`, returning 200 or 503. The candidate starts the same `npm run start`.

## Read-only gate

`prisma migrate status` was run on disposable PostgreSQL 17 before the gate was chosen.

- Empty database: exit 1. The command listed migrations as not applied. It did not create `_prisma_migrations`. Public relation count stayed 0.
- A history row with `finished_at` NULL was still present after `migrate status`. The captured stdout did not name that row as failed. Exit 1 is a refusal, but it is not a reliable classification of an unfinished row.
- `prisma migrate diff` was not used. A shadow database is DDL.

The selected gate is read-only SQL plus the image's `prisma/migrations/*/migration.sql` inventory. Checksums are SHA-256 after stripping carriage returns, so a CRLF working tree matches the LF git pin. A database migrated from raw CRLF bytes does not match that pin. The live test applies migrations from `git show HEAD:` bytes.

The schema probe sets `search_path` to `pg_catalog` inside the statement. That is the same deparse setting as the accepted P1 catalog probe. Without it, `pg_get_triggerdef` omitted `public.` and the canonical trigger contract returned mismatch.

Startup is refused for:

- empty image inventory or a non-boolean privilege flag (`MIGRATION_HISTORY_UNVERIFIABLE`)
- a database name that is not the URL database, or a forbidden name (`WRONG_DATABASE`)
- `current_user` or `session_user` different from the URL user (`ROLE_MISMATCH`)
- a superuser (`BOOTSTRAP_SUPERUSER`)
- missing `LOGIN`, `CREATEDB`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS`, any membership, schema `CREATE`, owned public tables, or missing schema `USAGE` (`APP_ROLE_REFUSED`)
- no `_prisma_migrations` (`MIGRATION_HISTORY_MISSING`)
- duplicate names, a null `finished_at`, rollback, null `started_at`, or `applied_steps_count` other than 1
- an image migration absent from history (`PENDING_MIGRATION`) or a checksum mismatch (`UNEXPECTED_CHECKSUM`)
- history the image does not contain, except one case (`EXTRA_HISTORY`)
- P1 present in the image or in history when the schema shape is not `match`, or P1 absent from both when the shape is not `absent` (`SCHEMA_NOT_READY`)

The only extra history row allowed is `20261010210000_psr_p3_s2_b_batch_receipt_provenance` with checksum `47ff9c932aea0a692b81ecfaf6c4a931b431e3e332e3e9c5b3fca96694550fe5`, and only when that directory is not in the image. The schema shape must then be `match`. A historical image with 45 applied migrations and no P1 objects passes. The same image does not pass when the current tree's P1 directory is still pending. An arbitrary extra name does not pass.

There is no environment flag that skips the gate.

## Candidate entrypoint

`docker-entrypoint-app-only.sh` checks that `DATABASE_URL` and `SESSION_SECRET` are set, runs `src/server/internal/p1-app-only-startup/run.ts` through `tsx`, and on success `exec npm run start`. It does not call Prisma migrate, reset, DDL, or privilege changes. The script is LF. `.gitattributes` pins that file and `docker/app-only-startup/Dockerfile` to LF so a Windows checkout does not write a CR shebang.

`docker/app-only-startup/Dockerfile` is a separate image. It copies `src` and `tsconfig.json` so the gate can run. The production `Dockerfile` does not reference it.

A role with no `USAGE` on `public` makes Prisma's `search_path` setting fail with SQLSTATE `42501`. The gate then refuses `MIGRATION_HISTORY_UNVERIFIABLE`. That is fail-closed. It is not a classified `APP_ROLE_REFUSED`, because the role catalog was not read.

## Later deploy sequence

This package does not perform these steps and is not permission to perform them.

1. A separate administrator is available.
2. A dedicated migrator is available.
3. Migrations are applied before the restricted application starts.
4. Schema state is verified independently of application startup.
5. A new application identity is provisioned.
6. An image that uses `docker-entrypoint-app-only.sh` is prepared.
7. Application and database role separation is verified.
8. Write-freeze is exercised separately.
9. Production cutover is approved separately.

`scripts/deploy.sh` would later have to stop treating entrypoint `migrate deploy` as the migration step. The health wait can stay. Rollback of the application container must still not roll the schema back. A failed app-only gate must leave the new container down instead of migrating. That change is not in this package.

## Not proven

Production role split, production startup, Owner approval, and P1-3 are not done. Two catalog reads are not an atomic freeze. A role that cannot set `search_path` is refused as unverifiable rather than by privilege class. The local full unit run was not green. Windows CRLF of the writer preflight remains NOT PASS.
