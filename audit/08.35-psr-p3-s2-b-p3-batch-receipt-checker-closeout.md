## 2. Retained source

The checker addresses one `BatchCreationCommand` by its `id`.

| Field | Value |
| --- | --- |
| Input | `BatchCreationCommand.id` |
| `causationKind` | `BATCH` |
| `causationId` | `BatchCreationCommand.id` |
| Expected source | `BatchCreationCommand.receiptProvenanceSnapshot` |

`command.id`, `requestId`, and `batchId` are not the same identity. A lookup by `requestId` does not diagnose the command. Replay is not a second physical action (`audit/08.28` §6).

Expected effects are not built from `InventoryMovement`, from `InventoryMovement.causationSnapshot`, from `BatchRemainderWriteOff.effectSnapshot`, or from live `RailLot.remainingQuantity`. Option A is not implemented. A missing live lot does not become a synthetic pair list.

Version 1 shape, as stored by P2 and read here:

```text
{
  v: 1,
  d: "BATCH_RECEIPT_PROVENANCE",
  commandId,
  batchId,
  pairs: [{ railLotId, quantity }]
}
```

## 4. Invariant A

For each stored pair with `quantity > 0`, `receiptEffect` (lines 131–140) builds one effect with the existing helpers `canonicalizeMovementTarget` and `effectKeyV1`:

| Field | Value |
| --- | --- |
| `kind` | `RECEIPT` |
| `stockDomain` | `RAIL_LOT` |
| `quantityDelta` | the stored positive quantity |
| target | `{ stockDomain: "RAIL_LOT", railLotId }` |
| `targetSnapshot` | `{ v: 1, d: "RAIL_LOT", railLotId }` (`inventory-movement-identity.ts` lines 130–136) |
| `effectKey` | `effectKeyV1("receipt", targetHashV1)` (lines 234–240) |

Quantity `0` stays in the retained pairs and creates no movement. An all-zero set and a valid `pairs: []` are independently empty expected sets. They are not SQL `NULL`.

Observed rows are only `authority = SHADOW`, `causationKind = BATCH`, and `causationId = command.id` (lines 384–389). The reader orders them by id (lines 418–421). The pure comparison also sorts by id before matching (line 337).

Comparison is by effect key, kind, sign, `quantityDelta`, stock domain, canonical target, and `targetSnapshot` (lines 230–329). A difference is not removed by summing two quantities or by dropping an extra row. Reported differences are ordered by code, effect key, expected value, then observed value (lines 322–329).

A wrong stock domain is a different canonical target, so the status is `MISMATCH` through a missing expected effect and an unexpected observed row.

| Case | Status |
| --- | --- |
| Command absent | `SOURCE_UNAVAILABLE` |
| Command present, SQL `NULL` | `NOT_EVALUABLE` |
| Malformed retained object | `INVALID_SOURCE` |
| Proven expected set equals the observed set | `MATCH_OBSERVED` |
| Independently proven empty set and no observed movements | `MATCH_OBSERVED` |
| Nonempty expected set, zero observed movements, preservation not proven | `GATE_UNKNOWN` (lines 353–361). Not `MISMATCH` |
| Extra movement, or a wrong target, kind, effect key, sign, quantity, or snapshot | `MISMATCH` |
| Duplicate observed effects for one target | `MISMATCH`. They are not combined |
| Database read does not finish | `BatchReceiptDiagnosticExecutionError`. Not a status (lines 437–442) |

An ACTIVE gate setting at the time of the read is not preservation proof. The checker does not read the gate. `GATE_UNKNOWN` is not upgraded because the current setting is ACTIVE.

`finished` sets `invariantB` to `NOT_EVALUABLE` on every completed result (line 104). `MATCH_OBSERVED` does not mean a warehouse quantity changed and does not mean Invariant B passed (`audit/08.28` §2).

## 5. Read-only execution

`readBatchReceiptInvariantA` (lines 406–443) opens one `RepeatableRead` transaction, sets `transaction_read_only = on`, then selects the command and the matching movements. Both reads see that snapshot. The function does not insert, update, or delete `InventoryMovement`. It does not write `ChangeLog`, mutate the SHADOW gate, or store the diagnostic status.

There is no Server Action, route, endpoint, UI, cron, or background job in this package. The checker source being on `main` does not mean an operator has run it, and it does not mean a production receipt was diagnosed.
