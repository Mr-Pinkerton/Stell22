## 2. What P1 implemented

`BatchCreationCommand.receiptProvenanceSnapshot` is `Json?` (`prisma/schema.prisma` lines 311–314). There is no `@default` and no relation.

The migration is one explicit `BEGIN` / `COMMIT` (`migration.sql` lines 6–53):

- `ADD COLUMN "receiptProvenanceSnapshot" JSONB` with no default and no `NOT NULL` (lines 8–9).
- CHECK `BatchCreationCommand_receiptProvenanceSnapshot_shape`: the column is SQL `NULL` or `jsonb_typeof(...) = 'object'` (lines 11–16). JSON `null`, a JSON array, and JSON scalars fail that check. SQL `NULL` passes it.
- Function `batch_creation_command_provenance_guard()` is `LANGUAGE plpgsql` and has no `SECURITY DEFINER` (lines 18–46).
- Trigger of the same name is `BEFORE UPDATE OR DELETE` for each row (lines 48–51). It does not fire on `INSERT`.

Trigger behavior, from that function:

| Old value | Attempt | Result |
| --- | --- | --- |
| SQL `NULL` | column stays SQL `NULL`, including an unrelated column change | allowed |
| SQL `NULL` | replaced by an object | rejected: `legacy batch creation command provenance cannot be filled` |
| object | different object, or SQL `NULL` | rejected: `batch creation command provenance is immutable` |
| object | `id`, `requestId`, or `batchId` changes | rejected, same message |
| object | same JSON value, identities unchanged | allowed. Comparison is `IS DISTINCT FROM` |
| object | `adminUserId` or `requestSnapshot` changes, provenance and the three identities unchanged | allowed |
| object | `DELETE` | rejected: `batch creation command provenance is retained` |
| SQL `NULL` | `DELETE` | not blocked by this trigger |

There is no `INSERT`, no `UPDATE` of existing rows, no `REFERENCES`, and no `CREATE TABLE`. The migration source test (`psr-p3-s2-b-provenance-migration.test.ts` lines 13–38) locks those absences, including the absence of `"InventoryMovement"`.

## 5. Risks

1. Production schema is not confirmed migrated. This closeout did not query production.
2. Deploying a P2 writer before the P1 migration is applied would fail because the column is absent.
3. After a P1 schema deployment and before a P2 writer, the old application inserts SQL `NULL`.
4. Mixed writer versions can keep inserting SQL `NULL`. `recordedAt` does not identify the writer.
5. Database triggers can be bypassed by privileged operations.
6. `src/server/integrity/psr-p2-production-quantity-edit-shadow-writers.integrity.test.ts` line 492 matches `causationSnapshot` text against `/amount|money|cost|price|value/i`. A generated id that contains one of those substrings can fail that assertion. This closeout does not mark that flake fixed.
