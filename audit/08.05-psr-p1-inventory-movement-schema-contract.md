Prisma `@@unique([causationKind, causationId, effectKey])` is the conceptual uniqueness already accepted in `audit/08.04` (`PSR-Q-002`). Default index name expected from Prisma: `InventoryMovement_causationKind_causationId_effectKey_key`.

## 4. No FK relations (PSR-P1)

`InventoryMovement` **MUST NOT** declare Prisma relations / SQL foreign keys to:

- `User`
- `Employee`
- `Material`
- `Detail`
- `NomenclatureItem`
- `Product`
- `Batch`
- `RailLot`
- `ProductionOperation`
- `Inventory`
- `SimplePurchase`
- `Supply`

`reversalOfMovementId` is a **bare** `String?`. **NO self-FK** in PSR-P1.

### Why

1. **Immutable historical IDs/snapshots survive mutable/deletable masters.** Current runtime hard-deletes exist for Employee (if unused), Material/Detail/Product/NomenclatureItem (if unused), Batch (with `RailLot.deleteMany`), DetailStock (with Detail), DRAFT Inventory, unpaid PRISADKA/UPAKOVKA/HOURS operations, CashFlow, and others. `ChangeLog.userId` is SET NULL; `ProductionOperation.employeeId` is RESTRICT; `Payment.employeeId` and several line/master ids have **no FK**. Historical movement meaning must not depend on current master rows remaining. Identifying context lives in `targetSnapshot` / `actorDisplaySnapshot` / `causationSnapshot` (`PSR-Q-008` hybrid).

2. **SHADOW must not alter current delete behavior.** PSR-P1 table is unused diagnostics capacity. Adding RESTRICT FKs would change which masters can be deleted **before** any writer exists. That is out of scope.

3. **Causal source is polymorphic.** `causationKind` + `causationId` address several document types. A single SQL FK cannot point at all of them. Existing polymorphic pairs: `ChangeLog.entity`/`entityId`, `InventoryLine.refType`/`refId`, `CostEvent.stockKind`/`stockId`.

4. **Source-retention hardening is later.** `PSR-Q-008` retain-document rules and Correction Center / PSR-P5 are **not** implemented here. Gateway/P5 work may later restrict deletes of authoritative sources. PSR-P1 schema must not pretend that hardening already exists.

Actor identities (`userId`, `employeeId`, `systemActorKey`) and physical target ids are **stored strings**, CHECK-shaped, not FKs.

### 6.4 authority / epoch (R-01)

**REMOVED:** `SHADOW ⇒ epochId MUST be NULL`.

**Canonical:**

- `AUTHORITATIVE`: `epochId` MUST be NOT NULL and `btrim(epochId) <> ''`.
- `SHADOW`: `epochId` MAY be NULL. If non-null it MUST be nonblank. A non-null SHADOW `epochId` identifies a **rehearsal/test stream only**. It does **not** make the rows authoritative.
- SHADOW is **never** promoted in place to AUTHORITATIVE.
- Authority remains **explicit** and **immutable**.
- `OPENING_BALANCE` kind alone does **not** imply authority (`audit/08.04` `PSR-Q-007`).
- `PSR-Q-006` still owns FINAL epoch/barrier implementation. Not decided here.

```sql
ALTER TABLE "InventoryMovement"
  ADD CONSTRAINT "InventoryMovement_authority_epoch"
  CHECK (
    ("epochId" IS NULL OR btrim("epochId") <> '')
    AND (
      "authority" <> 'AUTHORITATIVE'
      OR "epochId" IS NOT NULL
    )
  );
```

Together: any non-null `epochId` is nonblank; AUTHORITATIVE additionally requires `epochId IS NOT NULL` (hence also nonblank). SHADOW may omit `epochId` or carry a nonblank rehearsal identity.

Default `authority = SHADOW`.

Authority and epoch binding are assigned by trusted server/gateway logic, **not client-selectable**, **immutable after INSERT**. **No in-place `SHADOW` → `AUTHORITATIVE` UPDATE path.** Obsolete shadow rows remain SHADOW evidence or later retention/cleanup.

`PSR-Q-004` activation and `PSR-Q-006` barrier storage remain later-timing. Not decided here.

### 6.8 reversal (R-03)

`REVERSAL` is a history-preserving compensating physical movement.

Each REVERSAL row:

- references exactly one prior movement through `reversalOfMovementId`;
- has its **own** causation identity and `effectKey`;
- has a signed non-zero `quantityDelta`.

A reversal **MAY be partial**. Multiple later reversal/compensation rows **MAY** reference the same original movement. A later correction **MAY** compensate a prior compensation; the schema does **not** prohibit reversal chains.

**NOT accepted** as PSR-P1 DB constraints (independent review proposed these; rejected):

- `UNIQUE(reversalOfMovementId)`
- `UNIQUE(id, authority, epochId)`
- composite self-FK / `InventoryMovement_id_authority_epoch`
- mandatory 1:1 full reversal

**No self-FK in PSR-P1.** `reversalOfMovementId` remains a bare `String?`.

```sql
ALTER TABLE "InventoryMovement"
  ADD CONSTRAINT "InventoryMovement_reversal_shape"
  CHECK (
    (
      "kind" = 'REVERSAL'
      AND "reversalOfMovementId" IS NOT NULL
      AND btrim("reversalOfMovementId") <> ''
      AND "reversalOfMovementId" <> "id"
    )
    OR (
      "kind" <> 'REVERSAL'
      AND "reversalOfMovementId" IS NULL
    )
  );
```

REVERSAL ⇒ `reversalOfMovementId` IS NOT NULL AND `reversalOfMovementId <> id`. Non-REVERSAL ⇒ `reversalOfMovementId` IS NULL.

Before authoritative writers exist, **gateway/cutover rules MUST** ensure (writer/authoritative invariants, **not** PSR-P1 DB constraints):

- referenced movement exists;
- reference is to an earlier retained movement;
- same authority stream;
- same epoch for AUTHORITATIVE;
- same `stockDomain`;
- same exact physical pool;
- no causal cycle.

## 7. Snapshot contract

`targetSnapshot` is immutable JSONB context, versioned:

`v = 1`

`targetSnapshot` itself remains: **NOT NULL**, JSON **object**, `v = 1`.

**“Minimum fields” means keys are present.** It does **not** mean every value is non-null (R-08). Where the canonical source allows null, the snapshot **may preserve null**. Do **not** invent replacement values.

Explicit examples:

- RAIL_LOT: `code` may be null (`RailLot.code` is nullable for non-package lots).
- BLANK material snapshot: `sectionWidthMm` / `sectionHeightMm` may be null (`Material.section*` nullable migration debt).

## 8. Effect identity

Accepted invariant (`audit/08.04` `PSR-Q-002`):

```text
UNIQUE(causationKind, causationId, effectKey)
```

`effectKey` = `String`.

Exact builder / encoding / hash is **NOT implemented** in the PSR-P1 schema package.

Contract remains:

- retry-stable;
- deterministic from stable business semantics;
- **MUST NOT** depend solely on a newly generated cuid/UUID in the same posting attempt;
- **MUST NOT** use `OperationDetailLine.id` / `OperationNomenclatureLine.id` if those lines are recreated during reverse/reapply;
- **MUST NOT** use array iteration order, insertion order, or an arbitrary/random ordinal as the only identity;
- uses canonical physical pool identity;
- Blank length uses existing `canonicalLengthFixed4` semantics.

If one causation contains several semantically distinct effects that would otherwise collide on `effectKey`, implementation MUST either aggregate to one canonical movement at the accepted effect grain, **or** persist/derive a stable retained source sub-identity **BEFORE** movement generation and use it in `effectKey`. A transient generated line id is not sufficient.

Correction / cancellation: a new mutation = a new `causationId`. A compensating movement has its own effect identity. A reversal **references** the original via `reversalOfMovementId`. Do **not** reuse the original uniqueness key.

`ProductionOperation.clientRequestId` remains terminal-submit only. It is not a generic admin movement identity.
