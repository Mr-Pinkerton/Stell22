## 2. Implementation

### Gateway

`src/server/internal/inventory-movement-shadow-gateway.ts` → `appendShadowInventoryMovements(tx, input)`.

- requires `Prisma.TransactionClient`; root Prisma fails closed via existing `assertInventoryMovementShadowTransactionClient`
- calls approved `isInventoryMovementShadowWriteActiveForWriter(tx)` (SHARED lock `(8322,1)` then gate read)
- missing / explicit inactive → `{ gateActive: false, inserted: 0 }` and zero inserts
- malformed gate → existing `InventoryMovementShadowWriteConfigError` (fail closed)
- active → authority `SHADOW`, `epochId = NULL`
- writer does not supply `recordedAt` (DB `TIMESTAMPTZ(3) DEFAULT CURRENT_TIMESTAMP`)
- `quantityDelta = 0` omitted
- insert order is sorted by canonical `effectKey`, not input-array order or `recordedAt`
- `effectiveAt` persisted as UTC-naive `timestamp` text (`YYYY-MM-DDTHH:mm:ss.sss`) cast to `timestamp`, so PostgreSQL session TimeZone cannot shift the stored UTC calendar fields
- **not wired** to any physical mutation path

`effectiveAt` is written with an explicit `::timestamp` literal rather than a JS `Date` through Prisma `create`, because a timestamptz-parameterized write would be converted using the session TimeZone. Schema remains `TIMESTAMP(3)` without time zone. No TIMESTAMPTZ migration.

### Gate-read confinement

`scripts/security/check-inventory-movement-shadow-write-control.mjs` now forbids ordinary application `setting.findUnique` / `findFirst` / `findMany` and raw `SELECT ... Setting` when the file references `inventory_movement_shadow_write`.

Allowed special paths:

- gate implementation + its tests
- reset continues to use the accepted unlocked `readInventoryMovementShadowWriteGate` after exclusive lock
- integrity fixtures may set/read the Setting for isolated gateway tests
- Q4 control-plane remains: only the coordinated setter mutates the gate; CLI calls the setter; unlocked read is reset-only

Ordinary future writer-facing code uses only `isInventoryMovementShadowWriteActiveForWriter(tx)`.

### INSERT confinement

`scripts/security/check-inventory-movement-insert-confinement.mjs`

Detects, outside the allowlist:

- `inventoryMovement.create` / `createMany`
- `inventoryMovement["create"]` / `["createMany"]`
- raw `INSERT INTO "InventoryMovement"` and unquoted `INSERT INTO InventoryMovement`

Allowed only:

- approved gateway implementation
- gateway-specific tests
- `src/server/integrity/**`
- `prisma/migrations/**`
- `scripts/security/**` (checker fixtures only)

No blanket `src/**` exclusion.

### TRUNCATE / append-only

Existing `check-inventory-movement-append-only.mjs` still forbids update / updateMany / delete / deleteMany / upsert / raw UPDATE / raw DELETE.

Added obvious `TRUNCATE "InventoryMovement"` and unquoted `TRUNCATE InventoryMovement`.

R-10 reset keeps its controlled SHADOW-only `DELETE`. No unrestricted TRUNCATE reset path.

### TransactionClient

Canonical helper remains `assertInventoryMovementShadowTransactionClient`. No second mechanism.

Unit + DB-backed tests: TransactionClient accepted; root Prisma rejected; fail closed.

### Canonical target / effect infrastructure

`src/server/internal/inventory-movement-identity.ts`

- `targetKeyV1` exact JSON key order from `08.11`
- BLANK `lengthM` always `canonicalLengthFixed4` (`"1.8000"`, never `"1.8"`)
- `targetHashV1 = sha256(utf8(targetKeyV1))` lowercase hex
- `effectKey = imfx1:<role>:<hash>[:qualifier]`
- roles: receipt / consume / output / adjust / writeoff / restore

### Actor pattern

`src/server/internal/inventory-movement-actor.ts`

- USER requires authenticated `User.id`
- helper `userMovementActorFromAdmin({ id, name })` for future admin actions
- EMPLOYEE / SYSTEM constructors exist
- marketplace/provider is not an actor

Physical mutation actions were **not** rewritten to propagate `requireAdmin()` results. That wiring remains a writer-specific prerequisite.

## 4. PostgreSQL CI design

GitHub Actions `verify` job now starts a disposable `postgres:17-alpine` **service container**.

- database name `stell22_integrity`
- reachable as `127.0.0.1:5432` from the job (not a containerized job)
- no production database, no production secrets, no remote/shared DB
- `npx prisma migrate deploy` against that URL
- `npm run test:integrity:ci` → `scripts/run-integrity-ci.mjs` → `vitest.integrity.config.ts` (`src/server/integrity/**/*.integrity.test.ts`)

Local `npm run test:integrity` still uses Docker Compose + `setup-integrity-db.mjs`. If local Docker is unavailable, that is **not** a reason to drop the suite; GitHub CI is the mandatory gate.
