## 1. ACTUAL COST MODEL (код, не v2)

### 1.1 Что считается себестоимостью материала партии

`distributeBatchCost` (`src/lib/cost.ts`):

```
C = Batch.totalCost
доля сортов = P1·V1 / (P1·V1+P2·V2)   (P = priceSort1/2, V = длина сорта × сечение)
costSort* + pricePerM3*  — результат
```

Входы снапшота: `totalCost`, `priceSort1`, `priceSort2`, сечение, факт TORCOVKA lines.

`purchaseCost` в снапшот не входит напрямую (только через формулу `totalCost` у sync).

### 1.2 PRELIMINARY vs FINAL — фактический смысл

| | PRELIMINARY | FINAL |
| --- | --- | --- |
| Кто пишет | `recalcBatchCosts` | только `freezeBatch` |
| Когда | после commit ops / finance / updateBatch, через очередь | внутри TX выплаты или archive, если `canFreezeBatch` |
| SoT для UI отчёта с/с | **нет**. `loadCostContext` читает **только** `status: FINAL` | да, если строка есть: `buildBatchSnapshots` берёт frozen map вместо live `distribute` |
| Бейдж «Предварительно / Итог» | `batch.frozenAt ? FINAL : PRELIMINARY` (`cost-report.ts:385`) — **не** статус строки BatchCost | тот же флаг `frozenAt` |
| Live отчёт без frozen map | считает `distribute` от текущего `Batch.totalCost` + текущих TORCOVKA lines | если `frozenAt` есть, а FINAL-строки нет — live distribute (бейдж всё равно «Итог») |

PRELIMINARY — **disposable cache** (owner BD-1, 2026-09-04). Ни один production-reader не делает `findMany/findFirst` по `status: PRELIMINARY`. Несколько PRELIMINARY у открытой партии **сами по себе не баг**. UNIQUE PRELIMINARY не нужен. Механизм recalc в этом pass не удалять.

FINAL — единственный persisted snapshot, который отчёт использует вместо live. После `frozenAt` recalc партию на стартовом `findMany` пропускает и FINAL не переписывает.

### 1.3 Жизненный цикл

```
createBatch: totalCost = purchaseCost; BatchCost нет
→ TORCOVKA / update qty / delete TORCOVKA / finance sync / updateBatch
  → after commit enqueueRecalc → deleteMany PRELIMINARY + create PRELIMINARY
→ remaining=0 → archive (closedAt, ARCHIVED); freeze только если unpaid TORCOVKA=0
→ markEmployeePaid последних TORCOVKA → maybeFreeze → frozenAt + FINAL
```

Архив без выплаты: `frozenAt=null`, бейдж PRELIMINARY, recalc ещё пишет. Это намеренно (`cost-report.ts:383-385`, `canFreezeBatch`).

Нет функции `closeBatch`. Roadmap «кнопка закрытия» = archive + поздний freeze через ЗП / write-off без ops.

## 3. Может ли существовать…

| Состояние | DB constraint | App | Вердикт |
| --- | --- | --- | --- |
| Несколько PRELIMINARY одного Batch | нет unique | два recalc не в одной TX; очередь коалесцирует **один** ключ в **одном** процессе | возможно. Не баг для текущего UI |
| PRELIMINARY после FINAL | нет | freeze `deleteMany` все, затем FINAL; recalc `create PRELIMINARY` **без** повторной проверки `frozenAt` на write | **да, гонка DI-006** |
| Несколько FINAL | нет unique | два `freezeBatch` сериализуются на `UPDATE frozenAt` → второй `deleteMany`+create. Практически один FINAL | маловероятно с текущего freeze path |
| Orphan/stale PRELIMINARY после freeze | нет | late recalc create; freeze не подбирает чужой committed PRELIMINARY после своего deleteMany | **да, DI-006** |
| `frozenAt` без FINAL | нет | `computeBatchSnapshot` = null (нет TORCOVKA lines) → `frozenAt` ставится, FINAL не создаётся | возможно (write-off без производства) |
| FINAL без `frozenAt` | нет | freeze всегда пишет `frozenAt` **до** create FINAL в той же TX | нет на intended path |

Schema (`BatchCost`): PK `id`; `@@index([batchId])` only; FK `batchId → Batch.id` **ON DELETE RESTRICT** (`init` SQL). Partial unique на `(batchId, status)` / `FINAL` / `PRELIMINARY` **нет**. CHECK нет.

`ProductCost`: `@@index([productId, periodStart, periodEnd])` не unique; writers нет — в remediation **не включать**.

## 4. Карты ENTRY → TX → reads → locks → writes → after-commit

Isolation везде: PG **READ COMMITTED**. `SELECT FOR UPDATE` на Batch есть у finance sync / `updateBatch`, **нет** у freeze/recalc. Recalc **не** в `$transaction`.

### 4.1 `enqueueRecalcBatchCosts`

```
ENTRY enqueueRecalcBatchCosts(batchId?)
→ lock: in-memory Map `running` / Set `dirty`  (один Node-процесс)
→ если ключ уже running: dirty.add; return тот же Promise
→ иначе job:
     do {
       dirty.delete
       recalcBatchCosts({ batchId } | {})     // БЕЗ db/tx
     } while dirty
→ after: нет queue/revalidate внутри
```

Ключ = `batchId` или `"__all__"`. Два разных batchId = **два параллельных** recalc (разные строки BatchCost — ок). Второй инстанс / CLI, обошедший очередь, коалесцинг не видит (DI-012, не пересматривался).

### 4.2 `recalcBatchCosts`  (нет Internal-близнеца)

```
ENTRY recalcBatchCosts({ batchId?, db? })
→ transaction boundary: НЕТ (каждый await — свой auto-commit)
→ READ batch.findMany { frozenAt: null, id? }
   если пусто → return
→ READ productionOperation TORCOVKA + lines  (по id найденных партий)
→ per batch (без lock):
     WRITE deleteMany { batchId, status: PRELIMINARY }
     computeBatchSnapshot(in-memory batch row, lines)
     если snapshot null → continue  (PRELIMINARY уже стёрт)
     WRITE create { status: PRELIMINARY, ...snapshot }
→ after-commit: нет
```

| Условие | Поведение |
| --- | --- |
| `frozenAt = null` на стартовом findMany | переписывает PRELIMINARY |
| `frozenAt != null` на стартовом findMany | партия не в списке; FINAL не трогает; **хвост PRELIMINARY не чистит** |
| параллельный `maybeFreezeBatch` | см. Race F-vs-R ниже |
| два recalc одной партии | очередь 1 процесса: последовательно + dirty follow-up. Без очереди / 2 процесса: два PRELIMINARY |
| queue vs CLI/direct | CLI recalc нет. Direct = та же функция без коалесцинга. Prod callers — только queue |

Стартовый `findMany frozenAt: null` **не** защищает write: freeze может закоммититься между findMany и create.

### 4.3 `maybeFreezeBatch` / `freezeBatch`

```
ENTRY maybeFreezeBatch(tx, batchId)     // только внутри уже открытого caller I
→ transaction: inherit caller
→ READ batch.findUnique                 // БЕЗ FOR UPDATE
→ if !batch || frozenAt || !closedAt → false
→ READ count ProductionOperation { batchId, TORCOVKA, isPaid:false }
   // не лочит остальные ops; видит isPaid этой же TX (уже claimed)
→ canFreezeBatch(in-memory flags + count)
→ freezeBatch(tx, batch)                // batch = снимок findUnique
     READ TORCOVKA ops+lines
     computeBatchSnapshot(STALE in-memory batch, ops)
     WRITE batch.update { frozenAt: now }          // первая блокировка строки Batch
     WRITE batchCost.deleteMany { batchId }        // все статусы
     WRITE batchCost.create FINAL  (если snapshot)
     WRITE changelog + notifyEvent
→ return true
```

Порядок относительно вопроса 6:

| Событие | В той же TX, что FINAL? | До или после compute |
| --- | --- | --- |
| `frozenAt` | да | **после** compute, **до** deleteMany/create FINAL |
| unpaid TORCOVKA count | да | **до** compute; без lock всех TORCOVKA партии |
| чтение `Batch.totalCost` / prices / section | да, но из объекта `findUnique`, **не** повторный read после lock | **до** `UPDATE frozenAt` |
| чтение TORCOVKA lines | да, после count, до frozenAt | да |
| payroll rates / Payment | да (caller) | Payment уже создан; в FINAL не входит (FINAL = только материал партии) |

### 4.4 `archiveBatchIfDepleted`

```
ENTRY archiveBatchIfDepleted(tx, batchId)

→ READ batch; if closedAt → false  (maybeFreeze НЕ вызывается)
→ READ rail lots remaining

### 4.7 TORCOVKA edit/delete (blocker 01.2b)

#### `updateProductionLineQuantity` — ветка TORCOVKA (`production.ts:202-369`)

```
ENTRY updateProductionLineQuantity(id, lineIndex, newQty)
→ requireAdmin
→ pre-TX READ: productionOperation.findUnique + lines
→ pre-TX CHECK: op.isPaid → throw   // ЕДИНСТВЕННАЯ проверка isPaid
→ (HOURS/UPAKOVKA/PRISADKA — другие ветки; не входы FINAL)
→ TORCOVKA: line fields from pre-TX snapshot; delta = newQty - oldQty
→ $transaction I
     locks: НЕТ ProductionOperation, НЕТ Batch, НЕТ FOR UPDATE
     повторной проверки isPaid: НЕТ
     UPDATE/DELETE WHERE isPaid=false: НЕТ
     если delta<0:
       WRITE blankStock.updateMany decrement WHERE qty gte
     если delta>0:
       READ railLot.findUnique (plain SELECT)
       CHECK over-length по pre-TX op.lines
       WRITE blankStock.upsert increment
     WRITE operationDetailLine.update { id: lineId, quantity: newQty }
     WRITE changelog
→ AFTER COMMIT: enqueueRecalcBatchCosts(batchId); revalidate
```

Claim payroll может закоммититься между pre-TX check и U TX: **да**. Line update не конфликтует с `PaymentBatchItem` (FK на Op, не на line). Parent `UPDATE isPaid` не блокирует child quantity update.

#### `deleteProductionOperation` — ветка TORCOVKA (`production.ts:388-448`)

```
ENTRY deleteProductionOperation(id)
→ requireAdmin
→ pre-TX READ: op + lines + nomenclatureLines
→ pre-TX CHECK: op.isPaid → throw   // ЕДИНСТВЕННАЯ проверка isPaid
→ $transaction I
     locks: BlankStock (updateMany); затем delete lines; затем delete Op
     повторной проверки isPaid: НЕТ
     DELETE WHERE isPaid=false: НЕТ  (delete({ where: { id } }))

## 5. Гонки (конкретный interleaving)

PostgreSQL READ COMMITTED: plain `SELECT` не ждёт чужой `FOR UPDATE`; `UPDATE`/`FOR UPDATE` ждут row lock, затем перечитывают WHERE.

### Race F1 — DI-005 (осталась после P1)

**Инвариант:** после freeze FINAL и «Общая» должны отражать один C (P1: frozen money не менять; cost-integrity: frozen не трогаем).

P1 **закрыл** write `totalCost` **после committed** `frozenAt` (`updateMany count=0`).

P1 **не закрыл** compute FINAL из in-memory Batch **до** захвата строки.

```
Исходное: closedAt set, frozenAt=null, unpaid TORCOVKA=0 после claim в TX-F,
          totalCost = A (например 100 000)

TX F  markEmployeePaid / maybeFreeze
  F1  claim last TORCOVKA isPaid
  F2  batch.findUnique  → frozenAt=null, totalCost=A     // нет FOR UPDATE
  F3  count unpaid TORCOVKA = 0
  F4  READ ops; compute FINAL from in-memory A
  F5  UPDATE frozenAt                                 // здесь впервые лочится Batch

TX S  createCashFlow / updateDeal / updateBatch / setAccountConfirmed / IMAP import
  S1  FOR UPDATE Batch (если F5 ещё не было — берёт lock сразу)
  S2  frozenAt всё ещё null
  S3  compute C = B (например 130 000)
  S4  updateMany WHERE frozenAt=null → пишет totalCost=B
  S5  COMMIT

Дальше:
  F5  ждёт lock, если S ещё не commit; после S5 ставит frozenAt
  F6  deleteMany BatchCost; create FINAL(from A)
  F COMMIT

Enqueue recalc после S: findMany frozenAt!=null → skip
```

**Конечное состояние БД (неправильное):**

- `Batch.frozenAt` set
- `Batch.totalCost = B`
- `BatchCost` FINAL посчитан из **A** (`costSort1+costSort2 ≈ A`)
- PRELIMINARY может отсутствовать или быть orphan (DI-006)
- Закупки «Общая» = B; отчёт с/с изделия по FINAL = A
- B **больше никогда** не попадёт в cost (recalc skip; sync skip)

Ответ на вопрос 7: **да**, этот interleaving ровно «A → FINAL(A) → writer commits B → frozenAt стоит → B не в cost».

Симметрично: F5 раньше S1 → S ждёт, видит frozenAt, не пишет. SAFE.

Тест P1 «freeze \|\| updateBatch» лочит Batch **до** delay — это **не** production `freezeBatch`. Поэтому тест зелёный, гонка F1 жива.

Confidence: HIGH на механизм; окно = от `findUnique` до `UPDATE frozenAt` (чтение ops + compute, обычно короткое). Нужны параллельные выплата (последние TORCOVKA закрытой партии) и мутация C/цен.

### Race F2 — DI-006 recalc vs freeze

```
TX R  recalcBatchCosts (auto-commit statements)
  R1  findMany frozenAt=null  → партия в списке
  R2  deleteMany PRELIMINARY  COMMIT
  … freeze TX F: UPDATE frozenAt; deleteMany ALL; create FINAL; COMMIT …
  R3  create PRELIMINARY      COMMIT   // нет where frozenAt; нет unique
```

**Конечное состояние:** `frozenAt` set + FINAL + **лишний PRELIMINARY**.

Вариант: F.deleteMany уже выполнен в открытой TX F, R3 коммитит PRELIMINARY, F.create FINAL. После commit F: PRELIMINARY (R) + FINAL. Freeze не видит committed-после-deleteMany строку.

**Два recalc без freeze:**

```
R1 deleteMany PRELIMINARY
R2 deleteMany PRELIMINARY
R1 create PRELIMINARY
R2 create PRELIMINARY
→ две PRELIMINARY
```

На 1 app + queue same key почти не происходит. 2 процесса / прямой вызов — да.

**Влияние на текущий UI:** `loadCostContext` читает только FINAL; бейдж от `frozenAt`. Цифры отчёта **не** берутся из лишнего PRELIMINARY. Мусорные строки; риск если будущий reader возьмёт PRELIMINARY как SoT или `findMany FINAL` без unique (два FINAL — last-wins без `orderBy`).

Не считать несколько PRELIMINARY у **открытой** партии багом автоматически: это cache.

### Race F3 — два markEmployeePaid последних TORCOVKA (новый DI-018)

```
Партия: closedAt set, frozenAt=null
T1 unpaid TORCOVKA emp1, T2 unpaid TORCOVKA emp2  — вместе это все remaining

TX P1  claim T1 isPaid
TX P2  claim T2 isPaid
P1 count unpaid TORCOVKA → видит T2 (P2 не committed) → 1 → no freeze
P2 count → видит T1 → no freeze
оба COMMIT
```

**Конечное состояние:** все TORCOVKA `isPaid=true`, `frozenAt=null`, FINAL нет.

`archiveBatchIfDepleted` при уже `closedAt` **не** вызывает `maybeFreeze`. Других callers нет. Freeze **не произойдёт никогда**, пока кто-то не добавит повторный проход.

Деньги C и цены остаются редактируемыми (`updateBatch` смотрит `frozenAt`). Recalc продолжает PRELIMINARY. Бейдж «Предварительно».

Нужны две параллельные выплаты разных сотрудников по последним TORCOVKA одной закрытой партии. Sequential безопасен.

Confidence: HIGH на RC-семантику count; сценарий редкий.

### Race F4 — DI-019 update TORCOVKA vs payroll freeze

`isPaid` для `updateProductionLineQuantity` / `deleteProductionOperation` проверяется **вне** TX (`production.ts:210-215`, `:390-395`). Внутри TX повторного `isPaid=false` нет. TORCOVKA update **не** трогает строку `ProductionOperation` (только `OperationDetailLine` + `BlankStock`) — не ждёт claim lock и не видит `WHERE isPaid=false`.

`PaymentBatchItem.operationId → ProductionOperation` **ON DELETE RESTRICT** (`init` SQL). После committed Payment **delete op** падает (P2003), TX rollback вместе со складом. **UPDATE line FK не касается.**

```
UPDATE (подтверждён):

TX U  updateProductionLineQuantity TORCOVKA
  U0  findUnique op  isPaid=false          // вне TX
  U1  $transaction:
        blankStock ±qty                    // lock BlankStock, не Op
        operationDetailLine.update qty     // lock LINE, не Op
        changelog
  (нет lock ProductionOperation, нет where isPaid=false)

TX P  markEmployeePaid
  P1  updateMany ops isPaid=false → true   // row lock Op
  P2  Payment + PaymentBatchItem
  P3  freezeBatch: READ lines → FINAL; UPDATE frozenAt
  P COMMIT

Interleaving:
  U0 → P1..P COMMIT (FINAL от старых lines) → U1 COMMIT новые qty
  или U0 → P1 (lock Op) → U1 всё равно проходит (line не ждёт parent UPDATE)
     → P3 FINAL из lines на момент findMany freeze → U1 может уже закоммитить другое qty

Конец БД:
  frozenAt set, FINAL от qty A, OperationDetailLine qty B, BlankStock под B.
  Recalc skip frozen. Отчёт с/с = A. Факт производства = B.
```

```
DELETE (опровергнут для committed freeze):

TX D  deleteProductionOperation TORCOVKA
  D0  findUnique  isPaid=false             // вне TX
  D1  $transaction:
        blankStock decrement
        deleteMany lines
        productionOperation.delete({ id }) // нет where isPaid=false
        // ждёт row lock Op, если P1 держит UPDATE

После P COMMIT: PaymentBatchItem существует → D delete Op = RESTRICT → throw
→ rollback D включая stock. FINAL и lines не расходятся.

Если D commit ДО P: op нет → P claim count mismatch → Payment/freeze rollback.
Не «после freeze».
```

## 6. SAFE PATHS

- Последовательная выплата последних TORCOVKA одной партии → один freeze, один FINAL.
- Payment и freeze в одной I TX: throw freeze откатывает выплату.
- После committed `frozenAt`: `syncBatchTotalCostInternal` не пишет C; `updateBatch` money throw.
- Recalc после committed freeze: стартовый findMany пуст.
- Два `freezeBatch` на одной строке: сериализация на `UPDATE frozenAt`; второй перезаписывает единственный FINAL.
- Очередь 1 процесса: один recalc ключа + один follow-up.
- `gte` склад / claim isPaid — вне этого этапа, фаза 1.

## 7. BUSINESS DECISIONS

Зафиксировано владельцем 2026-09-04 (blocker-check перед remediation):

**BD-1.** PRELIMINARY = disposable cache, не source of truth. UNIQUE PRELIMINARY не нужен. Механизм recalc в этом pass **не** удалять без отдельного доказательства, что нет полезных callers/readers.

**BD-2.** Существующие расхождения FINAL vs `Batch.totalCost` **не** auto-fix. После remediation — read-only production report; владелец решает каждую строку.

**BD-3.** Сечение — cost input. После `frozenAt` менять `sectionWidthMm` / `sectionHeightMm` (и материал, если он меняет сечение) **запрещено**. `name` / `note` и реально descriptive поля остаются editable.

**BD-4.** `closedAt != null` и unpaid TORCOVKA = 0 **должно** приводить к freeze. Партия не должна оставаться PRELIMINARY навсегда из-за concurrent payments (закрывает F3 / DI-018).

## 9. RECOMMENDED REMEDIATION SCOPE (не делать в этом pass)

Минимум: F1+F2+F3+F4. ProductCost нет. UNIQUE PRELIMINARY нет (BD-1). Существующие FINAL/C mismatch не чинить в коде (BD-2).

1. **`maybeFreezeBatch` / `freezeBatch`:** в начале `SELECT Batch WHERE id FOR UPDATE`; перечитать totalCost/prices/**section**; count unpaid держа lock; compute → `frozenAt` → FINAL.
2. **`recalcBatchCosts`:** TX (или Batch FOR UPDATE); не create PRELIMINARY если `frozenAt` уже set. Не удалять recalc. Unique FINAL ок; unique PRELIMINARY нет.
3. **DI-018 / BD-4:** тот же Batch FOR UPDATE в payroll **после** claim ops, **до** count unpaid.
4. **DI-019:** в `updateProductionLineQuantity` TORCOVKA (и для дисциплины тот же каркас на `deleteProductionOperation` TORCOVKA): **сначала** lock/recheck `ProductionOperation` `WHERE id AND isPaid=false` (FOR UPDATE или условный update), **потом** BlankStock / line. Нет in-TX isPaid check сегодня.
5. **`updateBatch`:** после `frozenAt` запретить сечение (BD-3), не только money.
6. Тест P1 freeze — реальный `maybeFreezeBatch`. Тест F4: pay+freeze || update TORCOVKA qty.
7. Не трогать ProductCost. Не auto-fix старых FINAL vs C.

### Lock order (исследовать; не реализовывать в audit pass)

Текущее:

| Path | Порядок блокировок сегодня |
| --- | --- |
| `markEmployeePaid` | ProductionOperation (`updateMany isPaid`) → Payment/PBI → Batch (`UPDATE frozenAt`) |
| `maybeFreezeBatch` | нет lock до `UPDATE frozenAt` (Batch) |
| `archiveBatchIfDepleted` | Batch (`UPDATE closedAt`) → maybeFreeze (тот же Batch) |
| update TORCOVKA | BlankStock → OperationDetailLine (**не** Op, **не** Batch) |

Совместимый порядок (не реверсить payroll):

```
ProductionOperation  (claim / isPaid=false FOR UPDATE)
→ Batch              (FOR UPDATE / frozenAt / closedAt)
→ stock / lines
```

- Edit/delete TORCOVKA: **Op first**, затем stock/line. Batch в edit **не обязателен** для DI-019 (после freeze все TORCOVKA paid → recheck isPaid достаточно). Если когда-нибудь добавить Batch — только **после** Op.

- **Запрещено:** archive/finance Batch lock + edit Op-after-Batch.

Не commit/push.
