## 2. Gate-first transaction order

Ordinary code does not read `inventory_movement_shadow_write`. Each physical submit TX starts with `isInventoryMovementShadowWriteActiveForWriter(tx)` (SHARED advisory + gate). The gateway later re-reads SHADOW in the same TX. That second read is not bypassed.

### TORCOVKA

```text
requireTerminalEmployee + employeeMovementActor outside TX
BEGIN
→ SHARED SHADOW lock + gate read
→ replay lookup (before and after RailLot lock) → IDEMPOTENT_REPLAY, zero movements
→ lockRailLots
→ waste/approval decision
→ ACK_REQUIRED / APPROVAL_NEEDED / WRONG_CODE / EXPIRED / METRICS_CHANGED:
     zero InventoryMovement rows (no new ProductionOperation)
→ lockAndReadRateSnapshots + isCostFlowActive
→ occurredAt = new Date()
→ create ProductionOperation + physical projection (inactive or applyActiveTorcovkaInTx(occurredAt))
→ load retained ProductionOperation + OperationDetailLine
→ plan + appendProductionShadowMovements if outer gate ACTIVE
→ ChangeLog + batch archive
COMMIT
```

`submitTorcovka` remains the `"use server"` action. The physical TX body lives in `src/server/internal/submit-torcovka-tx.ts` so it is **not** a Server Action. Integrity timezone proof calls that internal helper after `SET LOCAL TIME ZONE`.

### PRISADKA

```text
requireTerminalEmployee + employeeMovementActor outside TX
BEGIN
→ SHARED SHADOW lock + gate read
→ replay by clientRequestId → return, zero new movements
→ lockDetails (existing sorted Detail serialization)
→ occurredAt = new Date()
→ create ProductionOperation
→ applyPrisadkaPicks (inactive or existing ACTIVE cost-flow path)
→ load retained ProductionOperation + OperationDetailLine
→ plan + appendProductionShadowMovements if outer gate ACTIVE
→ ChangeLog
COMMIT
```

No new AB-BA lock order. Effects come from retained post-apply provenance, not from the request pick list.

### UPAKOVKA

```text
requireTerminalEmployee + employeeMovementActor outside TX
BEGIN
→ SHARED SHADOW lock + gate read
→ whole-request replay (`base:productId` set) or `Несогласованный повтор упаковки`
→ snapshotUpakovkaApply for every product (BOM freeze; no physical mutation)
→ isCostFlowActive (mode-specific lock helpers only)
→ lockUpakovkaPhysicalWriteSet (one global request-level write-set)
→ lockAndReadRateSnapshots
→ per product:
     occurredAt = new Date()
     create ProductionOperation (clientRequestId = `${base}:${productId}`)
     applyUpakovkaPrepared
     load retained op + OperationDetailLine + OperationNomenclatureLine
     plan + appendProductionShadowMovements (own causation / own insert invariant)
     ChangeLog
COMMIT
```

Failure for any product rolls back the entire multi-product request.

## 5. Effect derivation and grouping

Plans are derived from the **retained ProductionOperation + retained provenance rows created in the same TX**, not from the UI payload after mutation.

Narrow helpers: `planProductionShadowMovements` / `aggregateProductionMovementEffects` in `src/server/internal/production-movement-plan.ts`. No event bus.

Grouping: **semantic role + canonical physical target**. Same-role same-target quantities are summed. CONSUMPTION and PRODUCTION_OUTPUT are **never netted** against each other. Zero-quantity effects are dropped. Result is input-order independent. Gateway remains final INSERT-order owner via semantic `effectKey`.

```text
imfx1:consume:<targetHashV1>
imfx1:output:<targetHashV1>
```

No qualifier. No MANUAL causation. No reason.

```text
causationKind = PRODUCTION_OPERATION
causationId = retained ProductionOperation.id
```

Canonical target identity uses the accepted P2 helpers (`canonicalizeMovementTarget` / `targetHashV1`). BLANK lengths are fixed-4 strings.

## 8. UPAKOVKA effect plan

Each retained UPAKOVKA operation is its own causation.

From retained `OperationDetailLine`:

- blank source → CONSUMPTION BLANK
- detail source → CONSUMPTION DETAIL `{ detailId, sourceTorcevayaDone, sourcePloskostDone }`

From retained `OperationNomenclatureLine`:

- CONSUMPTION NOMENCLATURE `{ nomenclatureId }` `quantityDelta = -quantity`

Do not net source and output roles. Do not combine several operations under one causation.

## 10. Gateway result invariant

`appendProductionShadowMovements` calls `appendShadowInventoryMovements` only when the outer SHADOW read was ACTIVE, then `assertProductionShadowGatewayResult`.

When outer SHADOW was ACTIVE:

- `result.gateActive === true`
- `result.inserted === expected nonzero semantic effect count`

Otherwise throw `PRODUCTION_SHADOW_GATE_INVARIANT_VIOLATION` and rollback.

Legal zero-effect operations may accept `0 → 0`. The assertion does not require at least one row by itself.

## 11. Retry / no backfill

Unique `clientRequestId` (UPAKOVKA: `${base}:${productId}`) is the retained retry identity.

If the retained `ProductionOperation` already exists:

- existing replay semantics
- no second projection
- no second operation
- no movement backfill, including when the original commit was SHADOW OFF and the gate is later ON
- SHADOW-ON original + retry also adds no second movement

UPAKOVKA partial replay (some expected operation IDs present but not all) still throws `Несогласованный повтор упаковки` and performs no new physical mutation.

Concurrent same request: one durable physical result.

## 12. UPAKOVKA global lock

Request-level union, independent of incoming pick order and `findMany` natural order. Not incremental product-by-product.

```text
SHADOW advisory
→ replay validation
→ Detail master anchors (sorted)
→ BlankStock targets (canonical sorted; no-prisadka BOM details)
→ DetailStock source targets (canonical sorted)
→ NomenclatureStock targets (sorted; fasteners ∪ packaging ∪ extras)
→ ProductStock output targets (sorted)
→ physical mutation
```

INACTIVE: existing `lockBlankSpecs` / `lockNomenclatureIds` / `lockProductIds` (may create quantity-0 projection rows) plus `SELECT ... FOR UPDATE` of all existing `DetailStock` buckets for the Detail set (superset).

ACTIVE: `lockExistingActiveBlankPools` / `lockExistingActiveDetailPools` (qty>0 superset) / `lockExistingActiveNomPools` / `ensureAndLockActiveProductPools`. These are existing initialized-pool helpers. They do **not** mint quantity-only uninitialized monetary rows. `ensureAndLockActiveProductPools` creates missing product pools with monetary zeros (existing ACTIVE semantics).

Normal terminal `submitUpakovka` resolves `production_cost_flow` **exactly once** for the transaction's apply decision. The captured boolean is passed into both `lockUpakovkaPhysicalWriteSet(..., { costFlowActive })` and `applyUpakovkaPrepared(..., { costFlowActive })`. `applyUpakovkaPrepared` still live-reads the Setting when the optional argument is omitted (`applyUpakovkaPick`, admin qty edit, `di-009`). There is no process-global cache and no production activation lock.

```text
one normal UPAKOVKA transaction
→ one captured costFlowActive decision
→ same decision controls global lock mode
→ same decision controls apply mode
```

`production_cost_flow` remains INACTIVE and is not activated. Monetary semantics are unchanged. `ARCH-P1-001` is not fixed here.
