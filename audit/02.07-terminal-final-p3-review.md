## F-09 — NOT REPRODUCED

**Cause (02.03):** SORT2 tab made SORT1 tiles look empty. This pass also asked whether **picked qty reorders** tiles/pages.

**Diagnosis:**

- TORCOVKA `lengthTiles` = catalog lengths sorted by metres ascending. Quantity does not enter the comparator. After 0,44 м = 3 then 0,46 м = 2, order stayed 0,44 → 0,46 → 0,48 …
- PRISADKA / UPAKOVKA map live catalog order; extras (orphan picks) append at the end. Changing qty does not resort live tiles.
- No pageable tile grid; horizontal lot/batch pager is unrelated.

SORT1/SORT2 tabs still show only the active sort’s catalog. Other-sort picks remain in state and on the sort badge (e.g. «1 сорт 2»). That is tab filtering, not qty-driven jump. No code change.

**Live evidence:** Selected 0,44 м and 0,46 м stayed in place while quantities changed.

## F-13 — CLOSED

**Cause:** `setSubmitting(true)` ran before `await`, but React state is not a same-tick lock. Two clicks before paint could both enter the handler (duplicate toast / flicker). Server `clientRequestId` already idempotent.

**Change:** Client-only `beginExclusiveSubmit` / `endExclusiveSubmit` ref lock on TORCOVKA (confirm + ack + approval), PRISADKA, UPAKOVKA, HOURS. Quantity dialog confirm also locks once. No new `clientRequestId`, no server change.

Not classified «NO CODE CHANGE»: same-tick double tap was not fully guarded by `submitting` state alone.

**Files:** `src/lib/terminal-submit-guard.ts`, `src/lib/terminal-submit-guard.test.ts`, the four operation screens, `quantity-dialog.tsx`.

**Live evidence:** Two `click()` on «Сохранить операцию» in one script tick → one EXTREME approval dialog («Высокий процент брака»). Dismissed without writing. No second toast.
