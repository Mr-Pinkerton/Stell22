**Зафиксированная модель отхода (владелец, 2026-09-04):** Stell22 **не** считает раскрой каждой рейки. Bin-packing / cutting optimizer не нужен. Отход TORCOVKA — агрегат операции: `railsTaken × lengthM` vs сумма длин заготовок. Минимальная физика: каждая заготовка не длиннее рейки лота; суммарный выход ≤ суммарной длины взятых реек (INV-008). Основная задача guard — ловить класс «ввели весь пакет → аномальный общий отход».

Уже существующие правила, которые **не** отменяются этим отчётом:

- INV-008 / A7: длина заготовок ≤ длина взятых реек (односторонняя защита «не создать заготовки из воздуха»).
- INV-047: обычный `deleteProductionOperation` TORCOVKA **не** возвращает рейки (физически распилены). Это правило для обычного delete сохраняется. Ошибочный ввод требует **отдельного** сценария.

### 1.2 Что означает `railsTaken` — по коду, не по имени

Это **«рейки, которые эта операция списывает с лота сейчас»**.

Evidence:

- schema: `railsTaken Int? // взято реек (длина = railsTaken * railLot.lengthM)` (`prisma/schema.prisma`).
- списание: `RailLot.remainingQuantity.decrement(railsTaken)` (`src/server/terminal.ts`).
- отход и отчёты: `takenM = railsTaken × lot.lengthM` (`src/server/reports.ts`, `src/lib/waste.ts`).
- v2 (исторический контекст, совпадает с кодом): «После подтверждения торцовки выбранные рейки считаются полностью израсходованными. Остаток рейки на склад не возвращается.»

Это **не** «количество реек в пакете». Исходное `RailLot.quantity` на терминал **не сериализуется** (`serLot` / `TerminalRailLot` отдают только `remainingQuantity`).

### 1.5 Можно ли взять весь лот одним действием?

**Да.** Отдельной кнопки «весь пакет» нет, но:

- `max` диалога = `remainingQuantity`;
- hint прямо показывает это число;
- одно подтверждение клавиатуры списывает весь доступный остаток.

Повторный клик по выбранному лоту снова открывает диалог реек (можно исправить до submit). После submit пути уменьшить `railsTaken` **нет** (см. §6).

### 1.6 Что UI подставляет автоматически

- `railsTaken := 0` при смене лота/партии. **Не** подставляется `remainingQuantity`.
- Длины плиток — уникальные `Detail.lengthM` того же `railType`, что у лота.
- Отход в метрах считается на клиенте до submit: `wasteM = railsTaken × lengthM − Σ(lengthM×qty)`.

## 2. CURRENT WASTE FORMULA

Единица: **погонные метры**. Не штуки и не м³.

```text
takenM     = railsTaken × RailLot.lengthM
producedM  = Σ (blankLengthM × quantity)   по строкам этой операции (все сорта вместе)
wasteM     = max(0, takenM − producedM)
wastePct   = wasteM / takenM × 100         (0 если takenM = 0)
```

Движок: `src/lib/waste.ts` (`wasteLengthM`, `wastePercent`, `employeeWaste`).

Отчёт партии без фильтра периода (`getWasteReport`):

```text
consumedM   = takenM_alltime + writtenOffM
writtenOffM = max(0, purchasedM − remainingM − takenM_alltime)
totalWaste  = wasteTorcovkaM + writtenOffM
wastePct    = totalWaste / consumedM × 100
```

`writtenOffM` — остаток, исчезнувший со склада **без** операции TORCOVKA (write-off партии **или** delete TORCOVKA, который оставляет decrement реек). С периодом база % = только торцовочный отход / взято за период.

Себестоимость материала — **не** эта формула. `distributeBatchCost` кладёт всю `C = Batch.totalCost` на **произведённый** объём (`Vф = ΣL × сечение`). `railsTaken` в снапшот не входит напрямую. Следствие: лишние списанные рейки не создают строк выхода → `Vф` меньше → **₽/м³ с отходом растёт** (отход «зашит» в цену).

### 2.1 Сорта, разная длина, штуки vs м vs м³

| Вопрос | Факт |
| --- | --- |
| Штуки? | `railsTaken` и qty заготовок — штуки. Отход % — **только метры**. |
| м³? | В отходе нет. В с/с: м³ = длина × сечение партии. Внутри одного лота % в м и в м³ совпадает. |
| Сорта? | Сорт **не** участвует в % отхода. SORT1 и SORT2 едят одну и ту же `takenLengthM`. Сорт влияет на ЗП и на долю C в `distributeBatchCost`. |
| Разная длина реек? | Один `RailLot` = одна `lengthM`. Смешать длины в одной операции нельзя. Разные лоты = разные операции. |
| Отрицательный отход? | Нет. UI `overLength` блокирует confirm; сервер `isOverRailLength` бросает. `wasteLengthM` дополнительно clamp к 0. |
| > 100%? | Нет на формуле `waste/taken`: produced ≥ 0, waste ≤ taken. Сервер отвергает `picks.length === 0`, поэтому produced > 0 и % строго < 100, но может быть 97%+. |
| min/max validation %? | **Нет.** Есть только односторонний max выхода (INV-008) и max `railsTaken ≤ remaining`. Порог настроек `wasteThresholdPct` (дефолт **30**) красит дашборд/отчёт, **submit не трогает**. |

### 2.2 Почему ошибочный ввод всего пакета даёт ~97%

Пример, согласованный с инцидентом (числа иллюстративные, формула — код).

Пакет: 100 реек × 6,00 м. Работник физически взял 4 рейки, в `railsTaken` ввёл **100**. Нарезал 38 заготовок суммарной длиной 19,6 м.

| | Правильный ввод | Ошибочный ввод |
| --- | --- | --- |
| `railsTaken` | 4 | 100 |
| `takenM` | 24,0 м | 600,0 м |
| `producedM` | 19,6 м | 19,6 м |
| `wasteM` | 4,4 м | 580,4 м |
| `wastePct` | **18,3%** | **96,7% ≈ 97%** |

Система считает оба варианта валидными: выход 19,6 м < взятой длины (24 или 600). INV-008 срабатывает только если выход **больше** взятого.

На confirm bar сейчас было бы: `38 заг.  Отход: 580,4 м` цветом `text-muted-foreground`. Красный (`text-destructive`) — только при отрицательном отходе. Процент не показывается.

Побочные эффекты ошибочного 100:

1. Со склада пакета исчезают 100 реек, физически ушли 4. Остаток лота занижен на 96. **Инкремента `remainingQuantity` в production-коде нет** (только create = quantity, decrement на submit, обнуление write-off).
2. Если это был последний остаток партии → `ARCHIVED` + `closedAt` («выработана»).
3. Recalc кладёт C на маленький `Vф` → завышенная ₽/м³.
4. ЗП не раздувается (`railsTaken` не в формуле earning).
5. Следующая торцовка этого лота невозможна, пока remaining = 0 (плитка скрыта фильтром `remainingQuantity > 0`).

## 3. CURRENT GUARDS

Проверено по фактическому коду.

### 3.1 `submitTorcovka` (`src/server/terminal.ts`)

| Проверка | Защищает от | Не защищает от |
| --- | --- | --- |
| `requireTerminalEmployee` | чужой employeeId | — |
| `railsTaken > 0` | ноль/отрицательные рейки | слишком много реек |
| `picks.length > 0` | операция без выхода | крошечный выход |
| `lot.batchId === batchId` | чужой лот | — |
| `isOverRailLength(taken, used)` | заготовки длиннее взятых реек | взято ≫ выхода |
| `remainingQuantity.gte railsTaken` | минус на лоте / больше остатка | взять весь остаток при крошечном выходе |
| unique `clientRequestId` | двойной тап | повтор с новым id |
| нет проверки `wastePct` | — | 97% проходит |

### 3.2 UI терминала (`torcovka-screen.tsx` + `QuantityDialog`)

- Confirm disabled при `railsTaken ≤ 0`, `pickedCount === 0`, `overLength`.
- Max реек = remaining. Max заготовок данной длины = `maxDetailQuantity` (floor остатка метров).
- Высокий положительный отход **не** красится и **не** требует второго подтверждения.

### 3.3 `updateProductionLineQuantity` (`src/server/production.ts`)

Только qty строк выхода, **не** `railsTaken`.

- Увеличение выхода: снова INV-008 относительно **текущего** (возможно завышенного) `railsTaken`. Можно «наполнить» фантомные 96 реек фальшивыми заготовками.
- Уменьшение выхода: BlankStock gte; если заготовки ушли в присадку — блок. Отход от этого **растёт**.
- `isPaid` → нельзя.
- Пути исправить инцидент (снизить `railsTaken`, вернуть remaining) **нет**.

### 3.4 `deleteProductionOperation` TORCOVKA

- Снимает заготовки с `BlankStock` (gte; иначе «уже прошли присадку/упаковку»).
- **Не** делает `remainingQuantity += railsTaken` (INV-047, smoke `scripts/smoke-production-reversal.ts`).
- `isPaid` → нельзя.
- После delete: операция исчезает из `takenM`, remaining остаётся заниженным → разница уходит в `writtenOffM` отчёта отхода. Для ошибочного ввода это **ухудшает** склад, не чинит его.
- Затем `maybeFreezeBatch` (если партия уже closed и unpaid TORCOVKA = 0).

**Обычный delete не менять.** Он правилен для «рейки реально распилены».

### 3.5 `lib/waste.ts`

Clamp отрицательного отхода. Нет верхней границы %. `isWasteOverThreshold` — дашборд, не мутация.

### 3.6 Инвариант «выход не длиннее взятых реек»

INV-008 / A7 **существует и работает** (UI + сервер + правка qty вверх).

Он **не** защищает от обратной ошибки инцидента:

```text
взято слишком много реек  →  произведено слишком мало  →  принято
```

Односторонняя защита: нельзя создать материал из воздуха; можно «уничтожить» учётный материал вводом.

### 3.7 Прочие связанные, не guards ввода

- `writeOffBatchRemainder` — админ сознательно обнуляет remaining в отход. Это не per-operation брак.
- Дашборд-алерт «Высокий процент отхода» после факта, по партии, порог из настроек. Терминал не останавливает.

1) plausibility guard на терминале + сервере до commit;
2) отдельный admin/terminal сценарий «исправить ошибочный ввод»

Почему не только DESIGN RISK: односторонний INV-008 — слабый инвариант расхода материала; P1, потому что склад и с/с уже искажаются на штатном пути.

## 5. PLAUSIBILITY METRICS AVAILABLE BEFORE SUBMIT

Всё ниже уже есть на клиенте **до** `submitTorcovka` (кроме помеченного):

| Метрика | Откуда | Есть сейчас |
| --- | --- | --- |
| `railsTaken` | диалог | да |
| `lot.lengthM` | `TerminalRailLot` | да |
| `takenLengthM` | произведение | да, локально |
| `pickedCount` | picks | да |
| `usedLengthM` / полезный выход | `sumDetailLengthM` | да |
| `wasteM` | taken − used | да, в confirm bar |
| `wastePct` | wasteM / takenLengthM | **не считается / не показывается** |
| `remainingQuantity` | лот | да |
| «взяли весь доступный остаток» (`railsTaken === remaining`) | сравнение | легко, не используется |
| исходное `RailLot.quantity` (весь пакет с закупки) | schema есть | **нет на терминале** |
| исторический median/P90 работника или партии | БД | нет на терминале |
| `wasteThresholdPct` из настроек | Setting | терминал **не** читает |
| сорт/тип/код пакета | лот | да (для текста, не для %) |

Сервер перед commit видит то же: `railsTaken`, `lot.lengthM`, `picks`, `remainingQuantity`. Может посчитать `wastePct` тем же `wastePercent`. Для hard-block нельзя полагаться только на UI.

### Предлагаемые три подхода (не реализация)

**A (рекомендуемый).** Три зоны по `wastePct` операции, плюс UX-сводка метров:

- normal → обычный confirm;
- suspicious → крупное предупреждение + повторное подтверждение;

## 8. CORRECTION: «Исправить ошибочный ввод»

Не реализовывать. Обычный delete TORCOVKA не менять.

Семантика обычного delete (рейки распилены → remaining не трогать) **верна**. Для ошибки «ввёл 100, взял 4» нужна другая операция: **учётный расход реек был ложным, физические рейки на месте**.

Сегодня `railsTaken` после create неизменяем. `remainingQuantity` нигде не инкрементируется. Штатного recovery нет.

Минимальный корректный патч учёта при **верном выходе заготовок** (типичный инцидент):

```text
deltaRails = oldRailsTaken − newRailsTaken     (new < old, new ≥ ceil(producedM / lengthM))
RailLot.remainingQuantity += deltaRails
ProductionOperation.railsTaken = newRailsTaken
BlankStock / OperationDetailLine — без изменений
enqueueRecalcBatchCosts
ChangeLog: { field: "railsTaken", old, new, reason: "input-correction" }
если remaining партии снова > 0 и closedAt был от depletion — reopen batch
  (status IN_WORK, closedAt = null), иначе партия останется ложно «выработанной»
```

Не трогать, если правили только рейки: ЗП (считается по заготовкам), строки picks.

### Что пришлось бы трогать по сущностям

| Сущность | Correction только railsTaken | Полный undo операции (как delete + возврат реек) |
| --- | --- | --- |
| `RailLot.remainingQuantity` | **да, increment** (новый write path) | да |
| `ProductionOperation.railsTaken` | да | delete строки |
| `BlankStock` | нет | decrement по spec (пул без партии) |
| `OperationDetailLine` | нет | delete |
| `BatchCost` PRELIMINARY | recalc | recalc |
| `BatchCost` FINAL / `frozenAt` | нельзя silently | нельзя silently |
| `ChangeLog` | обязателен | обязателен |
| payroll / `isPaid` | обычно нет | выплату реверсить нельзя текущим кодом |
| `closedAt` / ARCHIVED | возможно reopen | возможно reopen |
| downstream PRISADKA/UPAKOVKA | нет, если выход верный | блок или reverse цепочки |

## 9. HIGH-WASTE / DEFECT FLOW

Не смешивать с ошибочным вводом.

| | Ошибочный ввод | Реально высокий отход |

Предлагаемые причины (справочник, schema пока не добавлять):

- кривизна
- трещины
- сучки
- дефект материала
- подбор цвета/текстуры
- неверный размер
- другое

| Кандидат | Почему не подходит |

## 10. DEPENDENCY ON DI-009

DI-009 (`audit/01-data-integrity-findings.md`): `conductInventory` ставит `qty = actual` абсолютом, без движения и без связи с ops. Reverse PRISADKA/UPAKOVKA и decrement `BlankStock` после инвентаризации могут украсть/раздуть пул.

`BlankStock` ключ — `materialId + lengthM + detailType + sort`, **без `batchId`**. Комментарий schema: «привязки к партии здесь нет». Это тот же класс «пул без provenance», что ломает reverse после inventory.

Пересечение с коррекцией TORCOVKA:

| Действие | Нужен ли DI-009 сначала? |
| --- | --- |
| Снизить `railsTaken`, вернуть `RailLot.remainingQuantity`, не трогая BlankStock | **Нет. Можно отдельно.** Рейки не в инвентаризации. Increment remaining — новый путь, не reverse BlankStock. |
| Удалить/уменьшить выход TORCOVKA, пока blanks на месте и inventory не проводилась | Текущий gte-пул, как сейчас. Слабость та же, что у delete сегодня; не новый блокер. |
| То же после `conductInventory` по DETAIL без присадок (она пишет BlankStock абсолютом) | **Да, DI-009.** Reverse может не сойтись с пулом. |
| Reverse TORCOVKA после PRISADKA/UPAKOVKA | Нужен reverse downstream (уже есть, со своими gte). После inventory — снова DI-009. |
| Provenance заготовок по партии (FIFO-слои) | Это расширение DI-009 / модели склада. Для rails-only correction **не обязательно**. |

Вывод: **узкий corrective workflow инцидента (railsTaken + remaining) можно проектировать и делать до решения DI-009.** Не объединять задачи. Полный undo TORCOVKA «как будто операции не было» после движения заготовок/инвентаризации — не делать в том же скоупе; либо ждать provenance, либо явно блокировать, как сейчас.

Не решать DI-009 здесь.

## Итоговая сводка

CURRENT TORCOVKA FLOW:
Терминал выбирает партию → лот → `railsTaken` (списание целых реек лота сейчас) → picks заготовок по длине/сорту → `submitTorcovka` в TX списывает `RailLot.remainingQuantity`, пишет Op+lines, приходует `BlankStock` без партии, возможно архивирует партию, затем recalc PRELIMINARY.

CURRENT WASTE FORMULA:
`wastePct = max(0, railsTaken×lengthM − Σ blankLengthM×qty) / (railsTaken×lengthM) × 100`. Метры, сорта в % не входят, м³ только в с/с. Отрицательный и >100% отсечены формулой+INV-008; верхней границы % нет.

WHY 97% WAS ACCEPTED:
INV-008 проверяет только `produced ≤ taken`. Hypothetical 19,6 м из 600 м → 97% ок. Prod инцидент: 1383 м из 5120 м → **72,98%**, тоже ок. UI: отход в метрах серым, без %. Hint «Доступно N шт».

CURRENT GUARDS:
