## 2. Privilege topology on that database

`PUBLIC` lost database privileges and `CREATE` / `USAGE` on schema `public`. Future functions created by `stell22_migrator` do not keep `PUBLIC` execute.

`stell22_app`: `LOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS`, `NOINHERIT`. `CONNECT` on the disposable database. `USAGE` on `public`. No schema `CREATE`. No membership. Default privileges from the migrator grant table DML, sequence `USAGE`/`SELECT`, and function `EXECUTE`. `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, and `TRIGGER` on `_prisma_migrations` were revoked. `SELECT` on that table remains, so the startup gate can read history.

`stell22_migrator`: same login limits, plus schema `USAGE` and `CREATE`. It owns `BatchCreationCommand` and the migration history it created. The application is not a member.

`p1as_admin`: the container bootstrap superuser. It was not demoted and was not the application `DATABASE_URL`.

## 3. What this does not prove

`UNAUTHORIZED_WRITERS_EXCLUDED` is **NOT VERIFIED**. The administrator and the migrator can still write. `FREEZE_PASS_FORBIDDEN` is unchanged. Design D is not accepted for production. The production login is still `stell22`. `scripts/deploy.sh` still assumes migrate-on-start. A successful disposable combination is not a production sequence.

No production SSH, SQL, credential, workflow dispatch, merge, or deploy was performed. The Docker daemon was not restarted. Cleanup removed only the labeled resources of this run.
