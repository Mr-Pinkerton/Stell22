## 2. Two distinct invariants

### 2.1 Invariant A — retained business fact ↔ InventoryMovement

```text
ExpectedEffects(command) = ObservedMovementSet(command)
```

`ExpectedEffects` is built only from a retained business source that is not the `InventoryMovement` row under test. `ObservedMovementSet` is the set of SHADOW rows with that command's `causationKind` and `causationId`.

Equality is by semantic effect:

- `effectKey`;
- `kind`;
- sign and `quantityDelta`;
- canonical physical target.

A proven zero effect has an empty expected set. An empty expected set and an empty observed set satisfy Invariant A only when that zero was derived from the retained source. Absence of a source is not a zero.

Invariant A is the first implementable read-only slice. It checks that the ledger recorded the declared business effect. It does not prove that the projection changed by that delta.

### 2.2 Invariant B — committed projection delta ↔ InventoryMovement

```text
projection_after(target) - projection_before(target)
  = sum(movement.quantityDelta for the same action and the same target)
```

`projection_before` and `projection_after` are quantities of one physical target read inside the transaction that committed the mutation. Invariant B requires a projection witness independent of the movement row. Recomputing the delta from that movement, or from its `causationSnapshot`, is not a projection witness.

No such historical witness exists for actions already committed. For those actions Invariant B is `NOT_EVALUABLE`. This contract does not reconstruct history and does not invent an opening balance to manufacture `projection_before`.

A `MATCH_OBSERVED` result for Invariant A does not mean Invariant B was checked or passed.

## 3. Prohibited substitutions

This contract forbids:

1. An arbitrary sum of pre-epoch SHADOW `InventoryMovement` rows as a substitute for either invariant.
2. Substitution of the current `*Stock.quantity` or `RailLot.remainingQuantity` for a historical `projection_after`.
3. Deriving `ExpectedEffects` from the same `InventoryMovement` row, or from that row's `causationSnapshot`, that the check is comparing.
4. Treating a passed Invariant A as proof of Invariant B.
5. A diagnostic `MATCH_OBSERVED` when `ExpectedEffects` is nonempty and the observed set is empty. If the duty to write and the preservation of that SHADOW evidence are both proven, the status is `MISMATCH`. Without the preservation proof the status is `GATE_UNKNOWN`.

## 4. Batch receipt limitation

The runtime sequence `createBatch` → `writeOffBatchRemainder` → `deleteBatch` is reachable.

- `createBatch` inserts `RailLot` rows with `remainingQuantity = quantity` and retains `BatchCreationCommand` (`src/server/purchases.ts`, `createBatch`).
- `canonicalBatchCreateSnapshot` stores rail specification fields and `quantity`. It does not store generated `railLotId` (`src/server/internal/purchase-command-identity.ts`, `canonicalBatchCreateSnapshot`).
- `writeOffBatchRemainder` stores `railLotId`, `quantityBefore`, and `quantityDelta` on `BatchRemainderWriteOff.effectSnapshot` (`canonicalWriteOffEffectSnapshot`). That snapshot is the remainder at write-off, not a labeled receipt identity.
- `deleteBatch` deletes `RailLot` rows when every `remainingQuantity` is 0, no production operation and no deal item exist, and `production_cost_flow` is inactive (`deleteBatch`). `BatchCreationCommand` and `BatchRemainderWriteOff` have no foreign key to `Batch` (`prisma/schema.prisma`) and survive that delete.

After `RailLot` deletion, `BatchCreationCommand.requestSnapshot` cannot supply the exact `(railLotId, quantity)` pairs of the original receipt. A full independent historical receipt `ExpectedEffects` set is therefore not guaranteed.

While a `RailLot` row still exists, its `id` and `quantity` are a sufficient receipt source for Invariant A. That case is not part of the first slice.

Batch receipt is excluded from the first implementation slice.

A possible future source, not implemented here, is a durable `{ railLotId, quantity }[]` written on `BatchCreationCommand` in the same transaction as the lot insert, after the ids exist, and not copied from `InventoryMovement`.

The receipt `causationSnapshot` written onto `InventoryMovement` by `batchCreateCausationSnapshotV1` (`src/server/internal/raw-purchase-shadow-write.ts`) is observed ledger data. It is not an allowed `ExpectedEffects` source.

## 5. Diagnostic statuses

A completed read of one causal action returns exactly one of these statuses for the invariant being checked. A failed database read is not one of them.

| Status | Meaning |
| --- | --- |
| `MATCH_OBSERVED` | `ExpectedEffects` was derived from the retained source, the observed movement set was read, and the two sets are equal. The empty/empty case qualifies only when the retained source independently proves a zero effect. |
| `MISMATCH` | Both sets are known and they differ. An empty observed set is `MISMATCH` only when the retained source proves a duty to write a nonempty effect and preservation of the corresponding SHADOW evidence is also proven. |
| `GATE_UNKNOWN` | `ExpectedEffects` is known and nonempty, the observed set is empty, and preservation of SHADOW evidence for that action is not proven. An unknown gate is this status. |
| `SOURCE_UNAVAILABLE` | The retained document required to build `ExpectedEffects` is absent. |
| `NOT_EVALUABLE` | The retained document exists but does not contain the historical facts the invariant needs, or the document no longer describes the original action. Invariant B without an independent projection witness is this status. |
| `INVALID_SOURCE` | The retained document exists and fails its own shape: malformed JSON, a non-integer quantity, a duplicate canonical target, or an illegal sign. |

HEAD refinements, normative for every future checker:

1. A database read error, a lock failure, or any other failure to finish the read is a fail-closed diagnostic execution error. It is not `INVALID_SOURCE` and it is not a successful status.
2. A retained document that exists but lacks the required historical facts yields `NOT_EVALUABLE`, not `SOURCE_UNAVAILABLE`.
3. Nonempty `ExpectedEffects`, zero movement rows, and an unknown gate yield `GATE_UNKNOWN`.
4. `MATCH_OBSERVED` for Invariant A does not assert that Invariant B passed.
5. Empty `ExpectedEffects` and an empty observed set yield `MATCH_OBSERVED` for Invariant A only when the zero effect is independently proven from the retained source.
6. `MISMATCH` for a missing movement requires both a proven duty to write and proven preservation of the corresponding SHADOW evidence.

Movements whose causation document is absent do not satisfy `MATCH_OBSERVED` for that causation. The reverse lookup returns `SOURCE_UNAVAILABLE`. Those rows are not folded into another command's equality.

The first slice evaluates Invariant A only. It reports Invariant B as `NOT_EVALUABLE` on every result, including `MATCH_OBSERVED` for A.

## 6. First implementation slice

Not started. Read-only. Invariant A only. Three contours:

1. R-05 correction.
2. Batch remainder write-off.
3. SimplePurchase receipt.

Batch receipt is not in this slice. No reconciler is implemented by this file. Completion of this slice does not make PSR-P3 complete.

For each contour below, a replay of the same `requestId` returns the retained command and must not be diagnosed as a second physical effect. The checker addresses the retained causation id, not the replay attempt.

Absence of movement rows for a nonempty expected set is `GATE_UNKNOWN` in this slice. The duty to write can be read from the retained source. Preservation of the SHADOW stream cannot. `MISMATCH` on mere absence is therefore not available until the open preservation decision in §8 is closed.

## 7. Forward-only projection witness

This section is future architecture. It is not an accepted implementation and it does not exist in runtime. It does not by itself complete PSR-P3.

A future witness, for actions committed after it exists, records for every physical target the action changes:

- `projection_before`;
- `projection_after`;
- canonical target identity (`audit/08.11` §5, including BLANK fixed-4 `lengthM` and DETAIL `torcevayaDone` / `ploskostDone`);
- the causation identity of the action.

Requirements:

- The witness is written in the same database transaction as the projection mutation and the movement append.
- The target row is locked before `projection_before` is read and remains locked through `projection_after`.
- A missing projection row has `projection_before = 0`. Creating that row is not itself a nonzero effect when the committed quantity stays 0.
- Rollback removes the projection change, the witness, and the movement together.
- The witness quantities are read from the projection row. They are not copied from `InventoryMovement.quantityDelta` and not derived by adding a ledger delta to a later balance.
- The movement continues to be built from the retained business effect. The diagnostic compares the two. A shared copy would not be Invariant B.

Under the existing writer coordination lock, the same transaction also records the SHADOW gate state it observed. The writer lock is the SHARED advisory lock `(8322, 1)` taken by `isInventoryMovementShadowWriteActiveForWriter` before the gate read (`src/server/internal/inventory-movement-shadow-write.ts`, `src/server/internal/inventory-movement-shadow-coordination.ts`). The witness stores that observed gate value with the action. A later claim that the gate was ACTIVE is then a retained fact of the transaction, not a reconstruction from soak snapshots.

Actions committed before such a witness exist stay `NOT_EVALUABLE` for Invariant B.

## 8. SHADOW evidence preservation

Gate ACTIVE at the time of an action is not proof that the movement rows are still present.

`scripts/reset-inventory-movement-shadow.ts` deletes `InventoryMovement` rows with `authority = SHADOW` under the EXCLUSIVE advisory lock on `(8322, 1)`. A reset after a successful dual-write removes the observed set without removing the retained business command. An empty observed set after that reset is not, by itself, a missed write.

Therefore:

- `MISMATCH` for a missing movement requires a proven duty to write and proven preservation of the SHADOW evidence that should still contain that movement.
- Until preservation is proven, nonempty `ExpectedEffects` and zero rows stay `GATE_UNKNOWN`.
- Two soak snapshots do not prove that preservation.

A reset-generation, or an equivalent evidence-continuity mechanism that lets a checker know whether the observed stream still contains a given action, is an **OPEN DESIGN DECISION**. This contract does not choose or implement that mechanism.

The forward witness in §7 does not close this decision. A witness can show that a movement was appended in the original transaction. It cannot show that a later reset left that movement in place, unless the preservation mechanism says so.

## 9. Remaining coverage path

Future packages, each separately authorized. None of them is started here.

1. Batch receipt provenance, only after a durable `{ railLotId, quantity }[]` source exists or HEAD explicitly accepts a narrower rule for lots that still exist.
2. Production submit for an operation whose retained lines are still the submit-time lines.
3. Production quantity edit, using `ProductionOperationQuantityEdit.effectSnapshot`, with the same-writer measurement labeled as such.
4. Inventory, including DETAIL side buckets. A side bucket whose historical `before` quantity was not retained is `NOT_EVALUABLE`, not a reconstructed zero.
5. Supply step provenance outside the movement row. The current `Supply` watermark is the latest cumulative state, not a per-step expected effect.
6. Forward-only projection witness from §7.
7. Coverage verification that all 12 enabled physical writers have an applicable Invariant A rule, and that Invariant B is either witnessed or explicitly `NOT_EVALUABLE`.
8. Final PSR-P3 HEAD acceptance.

This path does not include physical factory or count reconciliation (P4), a formal stability soak (P7), or authoritative cutover (P8). It does not close `INC-001` or `ARCH-P1-001`.
