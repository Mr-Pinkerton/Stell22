## What this package does

`src/server/internal/p1-production-adapter/` is a separate executor. It does not change `executeP1OnlyRelease`, `authenticateTopology`, `productionReleaseAuthorized()`, or `EXECUTION_POLICY.allowProduction`. Those stay closed. The disposable runner still refuses production container names, the production database name, and the production compose network by its own checks. This adapter does not replace those checks with a general name check.

The adapter phases are read-only preflight, recovery verification, explicit authorization, P1-only apply, and postcheck. Preflight and recovery do not spawn Prisma. Apply is refused when the caller supplies `DATABASE_URL`. Production scope is refused when `GITHUB_ACTIONS=true`.

At execution the adapter requires the live Docker daemon id, both container ids, both image ids, `StartedAt`, running state, the named network, DNS alias `db`, unpublished database port, PostgreSQL 17, database name, and role. An image id must be `sha256:` plus 64 hex digits. A 40-hex Git SHA in that field is refused. `imageGitSha` is always `UNVERIFIED`.

A production declaration must also match the installed daemon pin at `/var/lib/stell22/p1-production-daemon-pin.json`. The path is fixed. The file is not in this repository. A missing pin stops with `PRODUCTION_DAEMON_UNPINNED`. The pin records a daemon id. Its text is not owner authorization.

Docker commands resolve the active CLI context when `DOCKER_HOST` is unset. Remote TCP and SSH endpoints, an unrecognized socket, and contradictory `DOCKER_HOST` plus `DOCKER_CONTEXT` stop the attempt. Inspect, catalog, and the one-shot share one restricted environment that does not inherit unrelated parent credentials. A change of endpoint or daemon id before the one-shot stops the attempt.

Recovery evidence comes from `executeTrustedRestore`. The controller hashes the archive, inspects the restore container, runs the restore, and reads the restored catalog. A caller snapshot, a boolean, or an object with the right field names is not evidence. The restore container must be attempt-owned, on a different network from the source, and must not bind a production volume or a volume mounted by the source. Migration fingerprints, logical structure, and business-table aggregates must match. Invalid indexes and not-valid constraints are `CORRUPTED_DATA`. The string `RESTORE_VERIFIED` is rejected. The archive SHA-256 is checked again immediately before the one-shot.

Apply then takes the host lock, re-reads the lock owner, re-inspects the target, reclassifies the catalog, rechecks the archive, materializes the pinned historical migrations plus P1, and spawns one container. The one-shot uses image `stell22-p1-oneshot:node22`, entrypoint `node`, DNS alias `db`, and a mode `0600` credential file. Docker arguments do not contain the password, a PostgreSQL URL, `docker-entrypoint.sh`, the application container id, or the application container name. The one-shot does not rebuild or replace the application container.

After a zero exit, postcheck requires `ALREADY_APPLIED`, 46 successful migration rows, and unchanged application id, image id, `StartedAt`, running state, and name, plus the same database container id. Any other completion, a thrown spawn, a null status, or a signal writes a marker outside the sealed migration directory and returns `BLOCKED` / `AMBIGUOUS_COMPLETION`. `retryAttempted` is false. A later call that sees the marker does not spawn. If P1 is already applied, the adapter rechecks application identity and returns read-only. It does not spawn.

Catalog reads set `search_path=pg_catalog`, matching the accepted probe, so pretty `pg_get_triggerdef` qualifies `public`. The P1 object matchers in `audit/08.42` are unchanged.

Production apply accepts an Ed25519 signature over a canonical payload binding the attempt, dossier digest, recovery digest, daemon id, operation `P1_ONLY_APPLY`, nonce, and a window of at most 24 hours. The public key is read only from `/var/lib/stell22/p1-owner-authorization.pub`. The signed document is read only from `/var/lib/stell22/p1-owner-authorization.json`. A caller-supplied JSON object is not authority. The executor does not sign and does not read a private key. A missing trust key stops with `PRODUCTION_TRUST_UNPROVISIONED` before the disposable restore. Consumption is an exclusive-create marker under `/var/lib/stell22/p1-owner-authorization-replay`. It happens only after the host lock is held and the pre-spawn checks have passed. A second use, a symlink, or an unsafe directory stops the attempt. Production apply does not use an in-memory replay store. Test-owned apply can verify a signature made with a key that exists only in the test process. That key is not a production trust key.

Recovery reads the checksum, archive, and witness written for this attempt. A missing, null, or caller-built witness is not provenance, and verification does not mint a replacement. An existing release backup is not overwritten. Docker inspect must contain a real `Mounts` array. A missing, null, or malformed mount list stops the attempt. An empty array is an observed empty list.

The public CLI rejects shortcut flags. It stops at `PRODUCTION_APPLY_NOT_WIRED_TO_THIS_CLI` and does not parse an authorization file into an apply call.

CI adds the test-owned live test to the existing pull-request disposable step. That step does not run on push or on Production Deploy. It does not receive production credentials.

`scripts/deploy.sh`, `.github/workflows/deploy-production.yml`, and `scripts/p1-writer-preflight.sh` are unchanged. The production release does not gain an automatic P1 step. The writer prerequisite remains.

## Test-owned proof

One local Docker run used PostgreSQL 17, no published database port, a test-owned network, and DNS alias `db`. Names were `p1pa-*`, not `stell22-app`, `stell22-db-prod`, or `stell22`. The result class was `TEST_OWNED_NOT_PRODUCTION`. The run covered a wrong application id, a restarted database container (`StartedAt` mismatch), an incomplete backup, a real `pg_dump` with checksum-before-archive, restore into a second disposable PostgreSQL, an aggregate mismatch, then a clean restore and verification. The one-shot applied only `20261010210000_psr_p3_s2_b_batch_receipt_provenance`. Postcheck recorded `ALREADY_APPLIED` / `P1_APPLIED`, 46 successful rows, the pinned checksum, and the P1 column, CHECK, function, and trigger. The application container id, image id, and `StartedAt` were unchanged. Its entrypoint remained `node /app/health.js`. A repeat call did not spawn.

That application container is a health probe. It is not the production Next.js image and it is not production. The Docker daemon used for the proof is the local test daemon. It is not the production daemon.

The R1 live run again used a test-owned PostgreSQL 17 pair. The adapter itself restored the archive, refused an aggregate mismatch, restored a clean disposable database, applied only the pinned P1 migration, and did not spawn on the repeat call. Result class: `TEST_OWNED_NOT_PRODUCTION`.

Unit tests cover unsigned authorization, a forged restore object, a restore volume named `stell22_pgdata`, signature replay, a remote SSH context, a remote default context, a TCP `DOCKER_HOST`, contradictory Docker settings, an unrecognized socket, an endpoint change, and a daemon-id change. A self-authored production authorization object does not apply.
